# 开发管线 · Dev Pipeline

> 合抱之木，生于毫末；九层之台，起于累土；千里之行，始于足下。
> 图难于其易，为大于其细。天下难事，必作于易；天下大事，必作于细。

## 触发条件

- 用户给出需求（一句话或一段描述），期望完整交付
- 新项目从零开始，或现有项目的完整功能模块
- 用户显式调用 `/dao-dev`

## 总览 · 道生万物

一句话需求 → **一·谋**（道生一：析→设）→ 🔒用户确认方向 → **二·造**（一生二：编→筑→部）→ 🔒用户预览 → **三·成**（二生三：试→验→书）→ 🔒用户验收 → 万物·涅槃。

**三个关卡（🔒）是止（艮）的时刻**——确认后才继续，避免南辕北辙。

**静默模式**（深度工作模式激活时）：

> 大音希声。善行无辙迹。

关卡降级规则：

- 方向明确（需求具体+技术选型无争议）→ 🔒自动通过，不中断执行
- 方向有歧义（多种合理路径）→ 🔒仍止，路歧则问（用 AskUserQuestion 工具，只在方向不明/需用户拍板/不可逆决策时问）
- 静默≠跳过思考。每个关卡仍内部评估，只是不输出中间文字
- 最终报告包含所有阶段产出的压缩总结
- 若处于 `delegated-continuous`（用户已授权持续推进 / autopilot 隔离模式）下，所有非阻断关卡自动通过并记录；只有凭证、权限、不可逆、安全/隐私/费用风险、目标互斥歧义时才用 AskUserQuestion 询问

## Subagent 调度（按需而动，不强制）

> 动善时。治大国若烹小鲜。

主会话在每个阶段**自评**是否派 subagent。

**核心判据**：满足 ≥3 项才派（模板化? 需不同模型? context 臃肿? rate limit 有预算? 值 15× token? 可并行?），否则主会话直接做。见 `ccswitch/agents/` profiles。

---

## 一 · 谋（道生一 · 从混沌到清晰）

> 为之于未有，治之于未乱。

谋定而后动。这一阶段不写代码，只让需求从一句话变成可执行的图纸。

### 1.1 析 · 需求分析（☲离 · 视 · 照见本质）

从一句话中提取完整信息。

1. **解构需求**
   - 用户要什么？（功能目标）
   - 给谁用？（用户画像）
   - 有什么约束？（技术栈、平台、性能、截止时间）

2. **知彼**（集成/逆向/对接外部系统时）
   - 目标系统的隔离边界在哪？（权限、作用域、沙箱）
   - 哪些路径看起来通但实际不通？（读代码≠验证可行，关键假设须实调确认）
   - 最小验证：在写任何代码前，用最短路径验证核心假设能跑通

3. **补全缺失**
   - 用户没说但必须决定的事项
   - 小缺失：AI自行决定，在设计中注明
   - 大缺失（影响方向）：路歧则问，用 AskUserQuestion 工具，最多问一轮
   - **原则**：认知卸载——替用户想到他没想到的，不制造新的认知负担

4. **拆解范围**
   - MVP（最小可行）包含什么？
   - Nice-to-have 是什么？
   - 明确不做什么？（划边界）

**产出**：需求清单（功能列表 + 约束 + 范围边界）

### 1.2 设 · 架构设计（☶艮 · 味 · 止而品）

在动手前把方案想清楚。

1. **技术选型**
   - 框架、语言、工具链
   - 优先用户已有的技术栈
   - 无偏好时选主流+轻量方案

2. **结构设计**
   - 目录结构
   - 核心组件/模块划分
   - 数据流/状态管理
   - 关键接口定义

3. **实施计划**
   - 编码顺序：依赖 → 核心 → UI → 集成
   - 预估复杂度：哪些部分可能需要深度迭代（§2.5）
   - 风险点：哪些部分可能需要深度调试（debug 镜头）

**产出**：设计方案（技术栈 + 结构 + 计划）

### 🔒 关卡一：方向确认

向用户呈现：需求理解 + 技术选型 + 核心结构 + 实施计划。确认→进入造，调整→修订后重新确认。

## 二 · 造（一生二 · 从图纸到实体）

> 天下大事，必作于细。

按计划逐步构建。每个步骤都是一个完整的小交付。

### 2.1 编 · 编码实现（☳震 · 触 · 一触推到底）

按设计方案的顺序，逐模块实现。

1. **基础设施审计**（编码第一步，不写代码先扫描）
   - 读取架构文档（ARCHITECTURE.md / 设计方案），提取需要的基建清单
   - 扫描项目目录，逐项判定基建是否就绪：

   | 基建需求 | 检测方式 | 缺失时的动作 |
   |---------|---------|-------------|
   Web 前端（前端目录+配置 → `stacks/frontend-nextjs.md` 处方）/ 后端（`server/` 入口 → 骨架）/ 数据库（migration+ORM → 框架）/ CI/CD（`.github/workflows/` → 按部署方案）。已有的不动，缺失的补全，子管线自带探测逻辑。

2. **依赖安装**（安全命令按 settings.json 的 permissions 配置自动执行，无需逐条确认的命令已在 allow 列表）
   - 基础设施审计中触发的技术栈处方（如 `stacks/frontend-nextjs.md`）会自行处理依赖
   - 其余依赖在此安装
   - 配置基础设施（linter、tsconfig 等）

3. **核心模块**
   - 按设计的组件顺序，逐个实现
   - 每个组件：接口 → 实现 → 基本验证
   - **原则**：一触推到底——开始一个组件就做完，不留半成品

4. **UI/交互层**（如适用）
   - 前端处方已在基建审计阶段完成脚手架 + 设计系统。此处聚焦业务页面
   - 具体标准由 `ui-ux-pro-max` skill 的规范文件提供（dao 不重复）
   - 美观现代的界面（不是毛坯）
   - 响应式、无障碍
   - 最佳UX实践

5. **集成**
   - 连接各模块
   - 端到端基本流程能跑通

**何时启动深度迭代（§2.5）**（满足任一即升级）：
- 改动跨 ≥3 个文件且有相互依赖
- 首次尝试失败，需要回溯推理
- 模块涉及并发/状态机/复杂算法
- 你感到不确定——不确定本身就是信号

**如编码中发现设计缺陷** → 记录，完成当前模块后评估是否需要回到「设」

### 2.2 筑 · 构建（☵坎 · 听 · 听回响）

让系统编译/构建，听它的反馈。

1. **构建配置**：涉及凭证管理、商业分发或用户明确表达时，加入代码混淆（`wg:obfuscate: true`）；其余场景保持简洁。

2. **构建**（安全命令按 settings.json 的 permissions 配置自动执行，无需逐条确认的命令已在 allow 列表）
   - 运行 build / compile
   - 如有错误 → 先读完所有错误再修（不一个一个改）

3. **构建失败** → 深度迭代（§2.5）+ debug 镜头

### 2.3 部 · 部署/启动（☵坎 · 听 · 水就下）

让系统跑起来。

1. **本地启动**
   - 启动 dev server（用 Bash 工具 `run_in_background: true` 非阻塞）
   - 等待就绪信号

2. **预览**
   - 让用户看到实际效果
   - 或提供可访问的URL

**启动失败** → 深度迭代（§2.5）+ debug 镜头

### 2.5 深度迭代（转法轮 · 五相循环）

> 万物并作，吾以观复。复杂模块用五相螺旋深入，简单任务直行不转。

**触发条件**（满足任一即启动）：跨 ≥3 文件且有相互依赖 / 首次尝试失败需回溯 / 涉及并发/状态机/复杂算法 / 感到不确定。

**五相**：**观**（读懂现状+差距，搜 `dao-evolution` 历史教训）→ **行**（最小有效变更，一触推到底）→ **验**（跑测试/构建，听系统反馈）→ **省**（与目标对比达成度，过审视清单：边界？更简？影响？可用？隐患？）→ **改升**（损掉上轮局限，升维重新理解问题）。

**涅槃判定**（五门全通 = 止）：苦灭（核心痛点已解）+ 无新苦（无新问题）+ 熵减（更整洁）+ 无为（体验自然）+ 智增（洞见已记录）。任一未通 → 继续转。

**转数控制**：简单 1 转，常规 1.5 转（自动半转审视），复杂 2-3 转，**超 5 转 = 方向错，止**。第一转就涅槃是最好的。

**涅槃后**：① 教训提炼（有洞见→写 `dao-evolution` CSV，纯机械→跳过）② 虚·归位（知识归文件）③ 总结交付。顺序铁律：① ② 在写报告前完成。

### 🔒 关卡二：用户预览

展示已实现功能列表 + 预览地址。满意→进入成，调整→回到编修改。

## 三 · 成（二生三 · 从实体到交付）

> 慎终如始，则无败事。

最后阶段不是收尾，是让交付物从"能用"变成"可信赖"。

### 3.1 试 · 测试（☱兑 · 说 · 让系统开口）

1. **功能测试**
   - 对照需求清单，逐项验证
   - 正常路径 + 边界情况 + 异常输入

2. **自动化测试**（如适用）
   - 核心逻辑的单元测试
   - 关键流程的集成测试
   - 运行测试套件（安全命令按 settings.json 的 permissions 配置自动执行，无需逐条确认的命令已在 allow 列表）

3. **视觉/交互测试**（如有UI）
   - 不同视口 / 设备
   - 无障碍检查
   - 性能基本检查

**测试发现bug** → 深度迭代（§2.5）+ debug 镜头

### 3.2 验 · 验证（☲离 · 视 · 回到本源）

回到最初的一句话需求，对照验证。

1. **需求对照**
   - 逐条检查：每个需求是否已实现？
   - 遗漏 → 补。偏离 → 修

2. **质量检查**
   - 代码简洁无冗余（为道日损）
   - 无硬编码/临时代码遗留
   - 错误处理完备

3. **涅槃判定**
   - [ ] 功能完备：需求清单全部✓
   - [ ] 构建通过：无错误无警告
   - [ ] 测试通过：自动化测试全绿
   - [ ] 体验自然：用户流程顺畅（无为而无不为）
   - [ ] 代码清净：无多余（为道日损）

### 3.3 书 · 文档（☴巽 · 风 · 传灯）

加载 `/dao-doc` 工作流处理文档生成（README / 架构说明 / 交付总结）。
够用即止，不写废话。

### 🔒 关卡三：用户验收

展示：原始需求 + 实现功能 + 文档位置 + 验证结果。

---

## 工作流协作

内置 §2.5 深度迭代（五相循环）；文档生成调 `/dao-doc`；前端初始化由基建审计自动触发 `stacks/frontend-nextjs.md`。

## 反模式

不析就编（谋定而后动）| 盲建（外部系统约束是析的一部分）| 读当验（读懂≠验证可行，关键假设须实调）| 熵遗（中间物用完即清）| 过度设计（MVP 先行）| 毛坯交付（UI/UX 不可选）| 跳过测试（验是必经之路）| 文档堆砌（够用即止）| 不等确认就继续（三关卡必止）

## 执行格式

启动时报：需求原话 + 预估复杂度 + 重点阶段。

结束时：① 演化记录（`dao-evolution` skill → `search.py ensure` → CSV 写入）② 虚·归位（知识归文件 + memory 清理）③ 涅槃报告（需求→成果→阶段回顾→归位摘要）。
