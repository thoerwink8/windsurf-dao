
# 设计标准 · Design Standards

> 少则得，多则惑。读而后行，最小变更。

本 skill 是 UI 设计的**标准与判据库**——定义"什么是好设计"（§4 通用判据），提供分诊、形态探索、自适应布局（§L）、组件审计、资产管理的完整方法论。`open.md` 和 `fidelity.md` 引用本 skill 判据做翻译和验证。

**适用范围**：product UI（桌面/Web 应用、工具、仪表盘、多步骤流程、数据密集界面）为主。营销落地页专属规则见 §A 附录，默认不启用。

## §0-pre · 组件系统健康扫描（Component Health Scan）★ 无条件首步

> 不知常妄作凶。动手前先看清全貌——用户无法感知项目的组件把控情况，AI 必须主动发现。

**每次 skill 被触发时无条件执行本步骤**，不管后续分诊结果是 FULL/SCOPED/DIRECT。扫描结果作为分诊和实施的上下文注入后续所有步骤。

### 扫描三步法（Grep/Glob，30 秒内完成）

1. **组件盘点** — Glob 扫 `components/ui/`，统计组件数/variant 数/测试数
2. **重复模式检测** — Grep 五类高频重复（focus ring / hover overlay / transition 串 / inset shadow / Surface variant map）。3+ 组件同模式才标"需提取"，提取走组件常量或 CVA variant，**不用 `@apply`**
3. **健康度结论** — 注入后续流程：健康（≤2 重复）→ 正常分诊；需整理（3-5 重复）→ 先提取公用常量再做功能改动；各自为战（>5 重复）→ 强烈建议先合并组件再做样式改动

**扫描静默完成**——健康时一句带过，有问题时主动报告。

### 跨页组件整合扫描（3+ 页面时追加）

任务涉及 3+ 页面时，清点全部设计页面 → 识别跨页共享模式（≥2 次出现）→ 按 native/extend/wrap/custom 四策略决策（native: 原生够用 / extend: 组件库加 variant / wrap: 组合封装 / custom: 从零建）→ Top-Down 排序（共享优先）。详见 `open.md` §1.5.0。

## §0 · 分诊门 + 形态探索（Triage Gate）★ 入口

> 治之于未乱。流程的重量由「未知量」决定，不由「改动大小」决定。

### 三档分诊

| 档位 | 信号 | 流程 |
|------|------|------|
| **FULL** | 重定产品形态/风格（启动/换肤/大重构） | 形态探索→风格定调（产 tokens）→ §1-§8 全流程 |
| **SCOPED** | 加形态未知的东西（新交互/信息架构不清） | tokens 不动→局部探索→实现→补进 gallery |
| **DIRECT** | 在已知形态里做事（改样式/调间距/复用组件） | 跳过探索→查 gallery→写代码→过 §8 验收 |

**默认 DIRECT，升档要有明确信号。** gallery 兼任分诊裁判：能拼出 = DIRECT；拼不出 = 升档。AI 自己分诊，只有形态未知且无法判断时才问用户一句。

### 形态探索（FULL/SCOPED 时执行）

形态探索是思考脚手架，不是真相源。完成即归档，唯一长期产物 = design tokens。

**探索手段**：DevTools CSS 注入（有 Chrome MCP 时）/ Penpot 画板（有 Penpot MCP 时）/ HTML 单文件（`_tmp/ui-mockup-*.html`，始终可用）。按可用工具自动选择，可组合。

**HARD-GATE**：FULL/SCOPED 档，用户未看过探索产出并拍板前，不写 plan、不动代码。DIRECT 档不做探索。

**探索五步**：察（扫描项目上下文→项目画像）→ 援（借鉴参考产品/§4 准则）→ 拟（2-3 套方向，含 tokens，过 §2+§4）→ 显（可视化呈现）→ 择（用户拍板→导出 tokens）

## §1 · Design Read（读懂再动）

> 知人者智。多数 AI 设计差，是因为跳过"读懂"直接套了个默认审美。

动手前先推断用户真正想要什么。读这些信号：

1. **界面类型** — 工具型 product / 仪表盘 / 数据密集工作面 / 表单流程 / 外围展示页
2. **氛围词** — "克制""Linear 风""Notion 风""极简""专业""高级感"
3. **参考信号** — 链接的 URL、贴的截图、点名的产品
4. **受众** — 谁在用、在什么场景用
5. **已有资产** — 现有 tokens、组件、配色。改造任务里这些是起点
6. **隐性约束** — a11y 要求、宿主环境。**覆盖**审美偏好

任何代码之前，一句话声明：**"我把这读作：<界面类型> 给 <受众>，<氛围> 语言，倾向 <设计系统或审美家族>。"**

歧义时只问**一个**澄清问题，绝不甩问题清单。能从上下文推断就不问。

## §2 · 三旋钮 + 动效命名（定调）

> 一生二，二生三。三个维度，定下整个界面的气质。

| 旋钮 | 1 端 | 10 端 |
|---|---|---|
| **VARIANCE** 版式变化度 | 完全对称、规整 | 艺术化、打破网格 |
| **MOTION** 动效强度 | 静止 | 电影级、物理弹性 |
| **DENSITY** 信息密度 | 画廊、空气感 | 驾驶舱、密集数据 |

### product UI 的基线

| 场景 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 数据密集工作面（列表/看板/triage） | 2-3 | 2-3 | **8-10** → 见 §5 |
| 表单 / 设置 / 配置流程 | 2-4 | 3-4 | 4-6 |
| 外围展示（空态/引导/欢迎页） | 4-6 | 4-5 | 3-4 |
| 营销落地页（如有） | 7-9 | 6-8 | 3-5 → 见 §A |

**旋钮按界面分区转档，不是全 app 一个值。** 基线只是起点，Design Read 里的明确信号覆盖基线。

### 动效命名系统

禁止匿名 `transition: all 0.3s`。每个过渡/动画用命名语义：

| 种子词 | 特征 | 典型用途 | 参考实现 |
|---|---|---|---|
| **Snap** | 即时，≤100ms | 按钮 `:active` 反馈、toggle 切换 | `duration-100 ease-out` |
| **Silk** | 流畅，150-200ms | hover 状态、面板展开 | `duration-150 ease-in-out` |
| **Spring** | 弹性，200-300ms | 模态弹入、卡片入场 | `duration-200 ease-[cubic-bezier(0.34,1.56,0.64,1)]` |
| **Float** | 缓慢，300-500ms | 页面切换、大区域过渡 | `duration-300 ease-out` |
| **Pulse** | 循环 | 加载指示、注意力引导 | `animate-pulse` 或自定义 keyframe |

**规则：只动 `transform` 和 `opacity`（GPU 合成层），禁止动 `width`/`height`/`margin`/`padding`。**

## §3 · 设计系统映射（别重造轮子）

> 朴散则为器。先选对器，再谈美。

### 原则

1. **一个项目一套系统** — 不在同一棵树里混用两个组件库/设计系统
2. **不重造官方 CSS** — 若项目已采用成熟设计系统，用它的 token 和组件，别手搓副本
3. **`cn()` 强制** — 所有 Tailwind class 组合必须通过 `cn()` 工具函数，禁止裸字符串拼接

### shadcn/ui 项目的目录规范

```
components/
├─ ui/           ← 基础组件（shadcn 原始 + 项目定制）
│   ├─ button.tsx    variant/size 定义在此，token 收口在此
│   ├─ input.tsx
│   └─ ...
├─ primitives/   ← 轻度组合（如 SearchInput = Input + Icon）
└─ blocks/       ← 业务组件（组合 ui/ + primitives/，不引入新样式值）
```

**blocks/ 不允许引入新的颜色/间距/圆角值**，只组合已有 ui/ 组件。新样式值必须先定义为 token，再在 ui/ 层引用。

### token 收口铁律

- 颜色/间距/圆角/阴影/字号 **只引用 CSS 变量或 Tailwind token**
- **禁硬编码** — `rounded-[8px]` 应为 `rounded-[var(--radius-control)]` 或对应 Tailwind class
- 出货前 lint 拦截裸值

### 组件规格层（约束性默认值）铁律

> 组件不只是样式复用，是约束的载体。约束靠调用方自觉 = 没有约束。

成熟组件库（antd/MUI）真正值钱的不是皮肤，是多年沉淀的**规格层**——把"不会出错的默认值"写死在组件里。自建组件库（headless 基座 + token）必须补齐这一层，否则"下一个装动态内容的弹窗必然溢出屏幕"：

1. **弹窗（Dialog/Modal）**：必须有默认高度上限（如 `max-h-[80vh]`）+ 超长内容滚动兜底；宽度走语义档位（`size="sm|md|lg|xl"`），禁止每个调用方手写 arbitrary 宽度
2. **弹层（Select/Dropdown/Popover/Tooltip）**：必须有默认 `max-height`（优先用定位引擎的 `--available-height`）+ `overflow-y-auto`；Tooltip 必须有默认 `max-width`
3. **长文本**：截断策略（truncate/line-clamp）是组件默认值，不是调用方补丁
4. **覆盖语义**：默认值可被 className 覆盖（tailwind-merge 保证后者胜出）——"默认约束 + 显式逃生舱"，不是"禁止覆盖"
5. **契约测试锁规格**：每条约束性默认值必须有 contract spec 断言（如 `toContain('max-h-')`），防止后续重构静默丢失

**审计口诀**：见 `overflow-y-auto` 找 `max-h`——有滚动无上限 = 滚动永不触发 = 假约束。

**参考蓝本**：对照 antd 5.x 组件总表做缺口审计（把 antd 当"规格捐赠者"，不当依赖，禁止因缺组件直接引入整套重库）；逐组件问三个问题——有档位吗？有约束性默认吗？约束有契约测试吗？审计结论落项目 `.claude/rules/component-health.md`「组件规格层」节。

## §4 · 通用判据（核心体检表）

> 反者道之动。AI 默认会滑向套路，这一节是反套路的体检表。

## §5 · 高密度档（DENSITY 8-10 专章）

> 万物并作，吾以观复。当 §2 把 DENSITY 拨到 8-10，本节接管。

**高密度的真谛：不是塞满，是精简后的紧凑。** 1 秒看懂整体 = 成功；要读文字/要滚动才能概览 = 失败。

### 信息三层架构

| 层 | 功能 | 视觉占比 | 交互 |
|---|---|---|---|
| 总览层 | 全局健康度 | 15-20% | 纯展示 |
| 列表层 | 每个个体状态 | 60-70% | 点击/hover |
| 操作层 | 需要时才出现 | 10-15% | 展开/收起 |

### 密度技法

- 每行自包含，关键指标靠右对齐
- 状态用颜色/图标不用文字 — 三色语义系统（充裕/注意/危险），面积越大越淡
- 缩写约定（D=日额 W=周额）、图标替代文字、hover 展开、对齐即结构、留白是信息
- 灰 = 无数据/不适用，别用灰表示"坏"

### 高密度反模式

| 病 | 治 |
|---|---|
| 卡片病 — 每条目大卡片 | 列表项一行即够 |
| 彩虹病 — 5+ 种颜色 | 三色系统，更多语义用形状 |
| 精确病 — 67.3% | 整数 + 颜色已够 |
| 标签病 — "日额度: 68%" | 约定 > 说明："D68%" |

## §L · 自适应布局（Adaptive Layout）

> 天下之至柔，驰骋天下之至坚。无有入无间。

静态设计稿不包含"窗口变化时什么拉伸、什么固定、什么折叠"。本章在设计与代码之间插入**布局行为规约**（Layout Behavior Spec）补全这个缺口。

### §L.1 · 三种布局策略

每个页面/面板的内容区域，必须声明属于以下三种策略之一。混用是常态——一个页面可以有 Stretch 的头部 + Cap 的正文。

#### Cap + Center（封顶居中）

内容有 max-width，水平居中，两侧对称留白。

**适用**：阅读型内容（报告/文档/历史时间线）、表单型内容（设置/偏好/对话框）。

**准则**：
- max-width 按内容密度选择：表单 640~720px，阅读 680~900px
- **必须 mx-auto 居中**——左对齐 + max-width 是最常见的错误，造成不对称空洞
- 留白是有意的——它是设计的一部分，不是浪费

**参考**：Linear Settings、GitHub Settings、Notion 页面正文

#### Stretch（流式拉伸）

内容跟随容器宽度变化，充分利用可用空间。

**适用**：仪表盘/概览（卡片可重排）、表格/数据列表、项目列表。

**准则**：
- 设置合理上限 max-width（1100~1400px），防止超宽屏下内容过于稀疏
- 超过上限后居中（mx-auto）
- 内部用 CSS Grid `auto-fill` / `auto-fit` 实现自动列数调整
- 卡片元素设 min-width（如 280~360px），防止过窄

**参考**：Linear Issues 列表、Figma 文件浏览、VS Code 设置

#### Multi-column（多栏结构）

页面有固定结构区域（侧栏/面板）+ 流式主内容。

**适用**：工作区（侧栏+内容+详情面板）、主从视图（列表+详情）。

**准则**：
- 结构区域用固定宽度 + shrink-0
- 主内容区 flex-1 填满剩余空间
- 当窗口缩小到阈值时，次要面板折叠或隐藏
- 主内容区内部可嵌套 Cap 或 Stretch 策略

**参考**：VS Code（侧栏+编辑器+面板）、Linear 工作区、Notion 侧栏+正文

### §L.2 · Layout Behavior Spec（布局行为规约）

静态设计稿的必要补充——描述每个结构区域在窗口尺寸变化时的行为。

#### 格式

每个有布局复杂度的页面，在项目 `.claude/rules/design-layout.md` 中声明：

```markdown
## <页面名>

| 区域 | 策略 | 默认尺寸 | 缩小行为 | 放大行为 |
|------|------|---------|---------|---------|
| 侧栏 | 固定 | 240px | 不变 | 不变 |
| 主内容 | Cap+Center | max 860px | min 600px | 居中，上限不变 |
| 右面板 | 固定 | 260px | <1100px 折叠 | 不变 |
```

#### 什么时候需要写

- **首次实现**有布局的页面（不是单组件）
- 设计原型是**固定尺寸**，没有标注自适应行为
- 发现**大屏空洞**或**小屏溢出**问题时

#### 不需要写的场景

- 设计稿本身已标注响应式行为
- 单组件/原子组件（由容器策略决定）
- 纯弹窗/对话框（固有 max-width + 居中）

### §L.3 · Layout Tokens

项目 design token 体系应包含布局类 token，分为三类：

| 类别 | 含义 | 命名建议 | 示例值域 |
|------|------|---------|---------|
| 结构区域尺寸 | 固定结构区域的宽度 | `layout-sidebar` / `layout-detail-panel` | 64~300px |
| 内容区域约束 | 各策略的 max-width | `layout-content-sm` / `layout-content-lg` / `layout-content-prose` | 620~1200px |
| 适配阈值 | 触发折叠/隐藏的窗口宽度 | `layout-collapse-at` | 1000~1200px |

token 值由项目定义，本章只规定分类。具体语法（CSS 变量 / Tailwind extend / JS 常量）随项目技术栈而定。

### §L.4 · 三视口验证

取代单视口截图验证。每个页面至少在三个视口下通过视觉检查：

| 视口 | 尺寸 | 验证重点 |
|------|------|---------|
| **min** | 项目定义的最小窗口 | 无溢出、无截断、折叠态正确 |
| **default** | 设计稿的参考尺寸 | 像素对齐设计稿（现有 L3） |
| **max** | 常见大屏（如 1920×1080） | 无空洞、居中合理、拉伸自然 |

#### 与 fidelity.md 的集成

- L3 视觉验证扩展为三视口
- 设计原型基线仍在 default 视口建立
- min/max 视口只验证布局行为（无溢出/无空洞），不做像素对比

#### 常见问题检查清单

- [ ] max-width 区域是否有 mx-auto 居中？
- [ ] Stretch 区域在超宽屏下是否有合理上限？
- [ ] min 视口下内容是否完整可见？
- [ ] 可折叠面板在阈值附近是否平滑过渡？
- [ ] 表格/列表在窄屏下是否有水平滚动或截断处理？

### §L.5 · 实施步骤

首次为项目引入自适应布局时：

1. **盘点**：列出所有页面，标注当前 max-width 和居中状态
2. **分类**：每个页面/区域选择三种策略之一
3. **写 Spec**：在 `.claude/rules/design-layout.md` 中写 Layout Behavior Spec
4. **加 Tokens**：在 CSS 变量和 tailwind config 中新增 layout tokens
5. **改代码**：按 Spec 修改各页面的布局约束
6. **三视口验证**：min / default / max 截图确认

步骤 1-3 是谋，4-6 是造。谋清楚了再动手。

## §7 · 设计资产（双模式）

> 道生一（tokens），一生二（基础件），二生三（业务件），三生万物（页面）。

### 双模式范式

设计资产有两条路径，按场景选择：

```
Mode R · Reflect（维护态）：代码 = 真相 → gallery 渲染真组件 → 永不漂移
Mode C · Construct（构建态）：设计工具 = 草图 → 分层构建设计系统 → 指导代码实现
```

| 场景 | 模式 | 真相源 |
|---|---|---|
| 已有产品，日常迭代 | R | 代码 |
| 新产品从零设计 | C → R | 先设计后代码，稳定后转 R |
| 已有产品重新设计（redesign） | C + R | 截图→设计系统→代码对齐，双向校验 |

**不混淆两条路径。** C 模式产出设计系统后必须同步到代码（转 R）；R 模式下不维护代码之外的真相源。

### 三层真相源（R 模式 + C 模式共用）

| 层 | 真相 | 统一性保证 | 维护成本 |
|---|---|---|---|
| **① Design Tokens** | token 定义（色/字/间距/圆角/阴影） | 所有组件只引用 token，**禁硬编码** | O(1)：改一处全局生效 |
| **② 基础组件** | 项目 `ui/` 目录 / 设计工具 Library Components | variant 一次定制，只引用 token | 趋近 0 |
| **③ 业务组件** | 真实业务代码 / 设计工具复合组件 | 组合①②，不引入新样式 | 随业务走 |

---

### §7C · Construct 模式：设计系统构建流程（S1→S5）★

**铁律：先资产后页面。** tokens → 组件 → 页面，每层只引用上一层，不越级。五步流程：S1 Design Tokens → S2 图标库 → S3 原子组件 → S4 复合组件 → S5 页面组合。

→ 详见 `references/construct-mode.md`（完整 S1-S5 操作步骤与验收标准）

---

### §7R · Reflect 模式（维护态）

**组件画廊（gallery）**：直接引用项目真实组件，展示所有 variant/状态一屏看全。引用不复制（改组件 gallery 自动更新），开发态开关隔离，兼任 §0 分诊裁判。

**MCP 双向校验**（可选）：有设计工具 MCP 时，读设计稿 token → 对比代码 CSS 变量 → 报告偏差（默认代码为准）。无 MCP 跳过。

**lint 守护**：禁硬编码设计值，只引用 token，出货前 lint 自动拦截。

---

### §7L · 设计工具定位（氛围编程范式）★

代码 = 唯一真相源。设计工具 = 按需探针，不是合同。

**三个用设计工具的时机**：① 起步探索（形态未知→草图+tokens→归代码后归档）② 复杂推敲（配色/密度在代码中 prompt 低效→精确方案→实现后稿子使命结束）③ 沟通对齐（给不能跑代码的人看效果→按需维护不追代码）。其余场景（功能迭代/bug 修/组件复用/日常调优）直接改代码。

§7C 是"起步探索"的系统化版本。转 Reflect 后不维护设计工具↔代码同步。视觉 bug 走截图→代码循环，不经设计工具。

## §8 · 验收（taste checklist + 工具联动）

> 慎终如始。验证不靠像素比对，靠体检表 + 真实渲染 + 工具实测。

### 8.1 体检表验收

1. 过 §4 体检表 — 逐条肉眼过。高密度区另过 §5 反模式表
2. 过 §6 组件审计 — 硬编码扫描 + 一致性检查

### 8.2 工具联动验收（按可用工具自动选择）

| 工具 | 验收动作 |
|---|---|
| Chrome DevTools MCP | 截图 + `evaluate_script` 量测 computed style（padding/radius/font-size/色值）+ 暗色模式截图 |
| Penpot MCP | 实现截图 vs 设计方案，验方向不验像素 |
| 无 MCP | `pnpm dev` 真实渲染 + DevTools 手检关键值 + 暗色切换 |

### 8.3 a11y 红线（不可破）

- 正文 ≥ 12px
- 焦点环可见
- 对比度 WCAG AA（正文 4.5:1，大字 3:1）
- 所有图标按钮有 `aria-label`

红线不破。通过 = 收尾；不过 = 改代码或改 token。

**验收对象是代码的真实渲染，不是稿子。不做 mockup-vs-代码的像素 diff。**

## 截图规格（自 dao.md 下沉，2026-07-07）

> dao.md 只留一行铁律：浏览器 MCP 截图必须落 `<项目根>/_tmp/qa/<context>/`。本节是规格细则。

- **`<context>` 命名**：默认 `<branch>--<topic>` 双段标识（branch = `git branch --show-current` 的 kebab-case，`/` → `-`；topic = loop 话题 / sync / 任务描述 slug）。特例：全量 fidelity 审计固定 `fidelity`、纯调试固定 `debug`。示例：`feat-workspace-rewrite--sync`、`main--async-state`
- **文件命名**：`<type>-<description>.png`，type 从 `audit|compare|verify|debug|export` 五选一
- **目录自动创建**：截图前若目录不存在则先建
- **`<项目根>` = 被操作的目标项目**，不是会话 cwd；跨项目场景截图归目标项目的 `_tmp/`
- 项目 `.gitignore` 必须含 `**/_tmp/`；生命周期（何时清理/何类入库）可由项目级 rule（如 screenshot-lifecycle.md）细化

## 反原则

- **简则简** — DIRECT 档别强行走流程，改个间距就是改个间距
- **代码即真相** — 设计工具是探针不是合同，不维护设计稿与代码的同步
- **token 先行** — 任何设计值走 token，裸值是 lint 错误
- **gallery 引用不复制** — 它渲染真组件，绝不 copy 代码进去
- **不为流程而流程** — 形态已知就别探索，tokens 够用就别重定调
- **判据是准则不是清单** — 守准则，清单按项目替换
- **工具是加速器不是必需品** — 没有 MCP 也能走完全流程，有 MCP 则更高效
- **改 token 必审计组件** — 这是血泪教训，不是可选步骤
- **不忘布局行为** — 翻译固定尺寸设计稿时必须同步产出 Layout Behavior Spec（§L.2）

法不违德，德不违道，道法自然。
