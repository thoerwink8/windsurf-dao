# 设计品味 · Design Taste（总闸）

> 少则得，多则惑。读而后行，最小变更。

本 skill 是所有 UI/设计任务的**全流程执行引擎**——从分诊到探索、从判据到审计、从实施到验收，一站覆盖。

**适用范围**：product UI（桌面/Web 应用、工具、仪表盘、多步骤流程、数据密集界面）为主。营销落地页专属规则见 §A 附录，默认不启用。

## §0-pre · 组件系统健康扫描（Component Health Scan）★ 无条件首步

> 不知常妄作凶。动手前先看清全貌——用户无法感知项目的组件把控情况，AI 必须主动发现。

**每次 skill 被触发时无条件执行本步骤**，不管后续分诊结果是 FULL/SCOPED/DIRECT。扫描结果作为分诊和实施的上下文注入后续所有步骤。

### 扫描三步法（用 Grep/Glob，30 秒内完成）

**一、组件盘点**
- `Glob` 扫描 `components/ui/` 目录，列出所有基础组件
- 快速统计：总组件数、有 variant 系统的组件数、有 contract 测试的组件数

**二、重复模式检测**（用户感知不到但影响维护性）
- Grep 五类高频重复：focus ring(`focus-visible:ring`)、hover overlay(`hover:bg-foreground/[`)、transition 串(`transition-[`)、inset shadow(`shadow-[inset`)、Surface variant map
- 产出：**重复模式清单**（哪些模式在 N 个文件里各自定义了一遍）
- **3 次护栏**：同一模式 3+ 组件才标记"需提取"。提取走组件常量或 CVA variant，**不用 `@apply`**

**三、健康度结论**（一段话，注入后续流程）
- 格式：`「组件健康度：<等级>。<N> 个基础组件，<M> 处重复模式。<建议>」`
- 等级判定：
  - **健康** — 重复模式 ≤ 2 处，无 Surface variant 重复
  - **需整理** — 重复模式 3-5 处，或 Surface variant 有 ≥ 50% 重叠
  - **各自为战** — 重复模式 > 5 处，多个组件独立维护相同的样式常量

### 扫描结论的消费方式

| 健康度 | 对后续流程的影响 |
|---|---|
| **健康** | 正常进入 §0 分诊，无额外步骤 |
| **需整理** | 在 §0 分诊后、实施前，先花一步提取公用常量（如 `styles.ts`），再做功能改动 |
| **各自为战** | 强烈建议先做一轮组件合并（抽公用常量 + 合并 Surface variants），再做任何样式改动。跳过合并 = 新改动继续各自为战 |

**扫描静默完成**——用户不需要知道有这道门。健康时一笔带过（"组件系统状态良好"一句话融入回答）；有问题时主动报告并建议先整理。

## §0 · 分诊门 + 形态探索（Triage Gate）★ 入口

> 治之于未乱。动手前先问：这次引入了多少未知？

**核心判据：流程的重量由「未知量」决定，不由「改动大小」决定。**

### 三档分诊

```
这次任务引入了多少未知？
│
├─ 重定整个产品的形态或风格（项目启动 / 换肤 / 大重构）
│   → 【FULL】  形态探索 → 风格定调（产 tokens）→ §1-§8 全流程
│
├─ 加一块「形态未知」的东西（新交互范式 / 信息架构不清）
│   → 【SCOPED】 tokens 不动 → 局部探索 → 实现 → 补进 gallery
│
└─ 在「已知形态」里做事（改样式 / 调间距 / 复用现成组件 / 标准 CRUD）
    → 【DIRECT】 跳过探索 → 查 gallery 找现成 → 写代码 → 过 §8 验收
```

**默认 DIRECT，升档要有明确信号。** gallery 兼任分诊裁判：有现成组件能拼 = 已知 = DIRECT；拼不出 = 未知 = 升档。

AI 自己分诊，默认 DIRECT。只有真碰到形态未知且无法自行判断时，才问用户**一句**："这个功能你心里有大概的样子吗，还是需要我先探索一下方向？"——大部分时候用户不会察觉有这道门。

### 形态探索（FULL/SCOPED 时执行）

> 大象无形，转其形而显之。让无形的设计语言显形。

形态探索是**思考脚手架**，不是真相源。完成即归档，唯一长期产物 = design tokens。

**三种探索手段**（按可用工具自动选择，可组合）：

| 手段 | 适用 | 产出 | 条件 |
|---|---|---|---|
| **DevTools CSS 注入** | 在真产品上即时看效果 | 实时视觉验证 | 有 Chrome DevTools MCP |
| **Penpot 画板** | 多方案并排比较、团队沟通 | 可视化方案板 | 有 Penpot MCP |
| **HTML 单文件** | 离线快速、无工具依赖 | `_tmp/ui-mockup-*.html` | 始终可用 |

**HARD-GATE**：FULL/SCOPED 档，用户未看过探索产出并拍板前，不写实施 plan、不动样式代码。
**反向 HARD-GATE**：DIRECT 档不做探索——形态已知还探 = 浪费。

探索五步（察 → 援 → 拟 → 显 → 择）：

1. **察**（项目上下文）：扫描产品定位、技术栈、现有视觉、关键场景，产出**项目画像**
2. **援**（借鉴已验证的视觉哲学）：从参考产品/用户提供的方向/§4 准则出发
3. **拟**（设计方向）：合成 2-3 套显著不同的方向，每套含结构化 tokens，全过 §2 三旋钮 + §4 判据
4. **显**（生成可视）：用上表中可用的手段呈现给用户
5. **择**（用户选定）：用户拍板后导出 tokens，进入实施流程

## §1 · Design Read（读懂再动）

> 知人者智。多数 AI 设计差，是因为跳过"读懂"直接套了个默认审美。

动手前先推断用户真正想要什么。读这些信号：

1. **界面类型** — 工具型 product / 仪表盘 / 数据密集工作面 / 表单流程 / 外围展示页
2. **氛围词** — "克制""Linear 风""Notion 风""极简""专业""高级感"
3. **参考信号** — 链接的 URL、贴的截图、点名的产品
4. **受众** — 谁在用、在什么场景用
5. **已有资产** — 现有 tokens、组件、配色。改造任务里这些是起点
6. **隐性约束** — a11y 要求、宿主环境。**覆盖**审美偏好

任何代码之前，一句话声明：**"我把这读作：<界面类型> 给 <受众>，<氛围> 语言，倾向 <设计系统或审美家族>。"**

歧义时只问**一个**澄清问题，绝不甩问题清单。能从上下文推断就不问。

## §2 · 三旋钮 + 动效命名（定调）

> 一生二，二生三。三个维度，定下整个界面的气质。

| 旋钮 | 1 端 | 10 端 |
|---|---|---|
| **VARIANCE** 版式变化度 | 完全对称、规整 | 艺术化、打破网格 |
| **MOTION** 动效强度 | 静止 | 电影级、物理弹性 |
| **DENSITY** 信息密度 | 画廊、空气感 | 驾驶舱、密集数据 |

### product UI 的基线

| 场景 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 数据密集工作面（列表/看板/triage） | 2-3 | 2-3 | **8-10** → 见 §5 |
| 表单 / 设置 / 配置流程 | 2-4 | 3-4 | 4-6 |
| 外围展示（空态/引导/欢迎页） | 4-6 | 4-5 | 3-4 |
| 营销落地页（如有） | 7-9 | 6-8 | 3-5 → 见 §A |

**旋钮按界面分区转档，不是全 app 一个值。** 基线只是起点，Design Read 里的明确信号覆盖基线。

### 动效命名系统

禁止匿名 `transition: all 0.3s`。每个过渡/动画用命名语义：

| 种子词 | 特征 | 典型用途 | 参考实现 |
|---|---|---|---|
| **Snap** | 即时，≤100ms | 按钮 `:active` 反馈、toggle 切换 | `duration-100 ease-out` |
| **Silk** | 流畅，150-200ms | hover 状态、面板展开 | `duration-150 ease-in-out` |
| **Spring** | 弹性，200-300ms | 模态弹入、卡片入场 | `duration-200 ease-[cubic-bezier(0.34,1.56,0.64,1)]` |
| **Float** | 缓慢，300-500ms | 页面切换、大区域过渡 | `duration-300 ease-out` |
| **Pulse** | 循环 | 加载指示、注意力引导 | `animate-pulse` 或自定义 keyframe |

**规则：只动 `transform` 和 `opacity`（GPU 合成层），禁止动 `width`/`height`/`margin`/`padding`。**

## §3 · 设计系统映射（别重造轮子）

> 朴散则为器。先选对器，再谈美。

### 原则

1. **一个项目一套系统** — 不在同一棵树里混用两个组件库/设计系统
2. **不重造官方 CSS** — 若项目已采用成熟设计系统，用它的 token 和组件，别手搓副本
3. **`cn()` 强制** — 所有 Tailwind class 组合必须通过 `cn()` 工具函数，禁止裸字符串拼接

### shadcn/ui 项目的目录规范

```
components/
├─ ui/           ← 基础组件（shadcn 原始 + 项目定制）
│   ├─ button.tsx    variant/size 定义在此，token 收口在此
│   ├─ input.tsx
│   └─ ...
├─ primitives/   ← 轻度组合（如 SearchInput = Input + Icon）
└─ blocks/       ← 业务组件（组合 ui/ + primitives/，不引入新样式值）
```

**blocks/ 不允许引入新的颜色/间距/圆角值**，只组合已有 ui/ 组件。新样式值必须先定义为 token，再在 ui/ 层引用。

### token 收口铁律

- 颜色/间距/圆角/阴影/字号 **只引用 CSS 变量或 Tailwind token**
- **禁硬编码** — `rounded-[8px]` 应为 `rounded-[var(--radius-control)]` 或对应 Tailwind class
- 出货前 lint 拦截裸值

## §4 · 通用判据（核心体检表）

> 反者道之动。AI 默认会滑向套路，这一节是反套路的体检表。

覆盖 9 个维度：颜色纪律（LILA RULE + 单主色 + 灰阶梯 + 语义色）、字体（同族强调 + 层级对比）、形状/阴影（半径锁 + 克制）、交互状态（四态强制 + 全周期反馈 + a11y）、组件摆放（按钮位置语义 + 间距一致性）、Icon 纪律（一库制 + 尺寸阶梯 + 容器控制）、表单（label 上方 + 禁 placeholder 当 label）、文案自审（出货前强制）、主题锁。

→ 详见 `references/design-criteria.md`（完整 4.1-4.9 详细规则与清单）

## §5 · 高密度档（DENSITY 8-10 专章）

> 万物并作，吾以观复。当 §2 把 DENSITY 拨到 8-10，本节接管。

**高密度的真谛：不是塞满，是精简后的紧凑。** 1 秒看懂整体 = 成功；要读文字/要滚动才能概览 = 失败。

### 信息三层架构

| 层 | 功能 | 视觉占比 | 交互 |
|---|---|---|---|
| 总览层 | 全局健康度 | 15-20% | 纯展示 |
| 列表层 | 每个个体状态 | 60-70% | 点击/hover |
| 操作层 | 需要时才出现 | 10-15% | 展开/收起 |

### 密度技法

- 每行自包含，关键指标靠右对齐
- 状态用颜色/图标不用文字 — 三色语义系统（充裕/注意/危险），面积越大越淡
- 缩写约定（D=日额 W=周额）、图标替代文字、hover 展开、对齐即结构、留白是信息
- 灰 = 无数据/不适用，别用灰表示"坏"

### 高密度反模式

| 病 | 治 |
|---|---|
| 卡片病 — 每条目大卡片 | 列表项一行即够 |
| 彩虹病 — 5+ 种颜色 | 三色系统，更多语义用形状 |
| 精确病 — 67.3% | 整数 + 颜色已够 |
| 标签病 — "日额度: 68%" | 约定 > 说明："D68%" |

## §7 · 设计资产（双模式）

> 道生一（tokens），一生二（基础件），二生三（业务件），三生万物（页面）。

### 双模式范式

设计资产有两条路径，按场景选择：

```
Mode R · Reflect（维护态）：代码 = 真相 → gallery 渲染真组件 → 永不漂移
Mode C · Construct（构建态）：设计工具 = 草图 → 分层构建设计系统 → 指导代码实现
```

| 场景 | 模式 | 真相源 |
|---|---|---|
| 已有产品，日常迭代 | R | 代码 |
| 新产品从零设计 | C → R | 先设计后代码，稳定后转 R |
| 已有产品重新设计（redesign） | C + R | 截图→设计系统→代码对齐，双向校验 |

**不混淆两条路径。** C 模式产出设计系统后必须同步到代码（转 R）；R 模式下不维护代码之外的真相源。

### 三层真相源（R 模式 + C 模式共用）

| 层 | 真相 | 统一性保证 | 维护成本 |
|---|---|---|---|
| **① Design Tokens** | token 定义（色/字/间距/圆角/阴影） | 所有组件只引用 token，**禁硬编码** | O(1)：改一处全局生效 |
| **② 基础组件** | 项目 `ui/` 目录 / 设计工具 Library Components | variant 一次定制，只引用 token | 趋近 0 |
| **③ 业务组件** | 真实业务代码 / 设计工具复合组件 | 组合①②，不引入新样式 | 随业务走 |

---

### §7C · Construct 模式：设计系统构建流程（S1→S5）★

**铁律：先资产后页面。** tokens → 组件 → 页面，每层只引用上一层，不越级。五步流程：S1 Design Tokens → S2 图标库 → S3 原子组件 → S4 复合组件 → S5 页面组合。

→ 详见 `references/construct-mode.md`（完整 S1-S5 操作步骤与验收标准）

### §7R · Reflect 模式（维护态）

#### 组件画廊（gallery）

一个展示页，**直接引用项目真实组件**，把所有 variant、所有状态摆出来一屏看全。

- gallery 引用真组件，绝不复制代码进去；改组件 gallery 自动更新
- 用开发态开关隔离，生产构建排除
- 兼任 §0 分诊裁判：能拼出 = DIRECT；拼不出 = 升档

#### MCP 双向校验（条件式）

如果有设计工具 MCP 可用（Penpot/Figma），可选执行以下校验：

1. AI 读设计稿中定义的 token 值
2. 对比代码中 CSS 变量的实际值
3. 报告偏差清单（哪些值不一致）
4. 决定以哪边为准（默认代码为准，因为 reflect 范式）

这不是强制步骤——没有 MCP 时跳过，有时作为辅助检查。

#### lint 守护统一性

**禁止硬编码颜色/间距/圆角等设计值，只准引用 token。** 用项目 lint 体系机器化，出货前自动拦截。

### §7L · 设计工具定位（氛围编程范式）★

> 上善若水。水善利万物而不争。设计工具是水——按需流入，不抢主位。

**核心洞察**：在 AI 编程中，代码本身就是设计的交付物。维护设计稿与代码的 1:1 同步 = 两份同义真相源互相追赶，纯冗余。

```
旧模式（冗余）：  设计稿 ←→ 代码  双向追赶
新模式（精准）：  代码 = 唯一真相源
                  设计工具 = 按需探针（三个时机才用）
```

#### 三个用设计工具的时机

| 时机 | 场景 | 产出 | 完成后 |
|---|---|---|---|
| **起步探索** | 新产品/新页面/新交互范式，形态未知 | 2-3 个方向的草图 + tokens | tokens 归代码，草图归档不维护 |
| **复杂推敲** | 配色、间距节奏、信息密度等视觉问题，在代码中反复 prompt 低效 | 精确的视觉方案 | 代码实现后，设计稿使命结束 |
| **沟通对齐** | 多人协作，需要给不能跑代码的人看效果 | 可分享的视觉参考 | 按需维护，不追代码 |

#### 不用设计工具的场景（直接改代码）

- 功能迭代（加按钮、改文案、调间距）
- Bug 修复（视觉问题直接走 `dao-design-qa` 的截图→代码循环）
- 已有组件的复用组合（token 体系已保证一致性）
- 日常调优（用 DevTools 截图 + 代码微调即可）

#### 设计稿的生命周期

设计稿是**探针**，不是**合同**：
- **创建时**：帮你在起步阶段快速定调方向
- **定调后**：tokens 提取到代码，稿子归档
- **此后**：代码迭代不回写设计稿；设计稿不追代码
- **再次启用**：仅当遇到上述三个时机之一

**与 Construct 模式的关系**：新产品从零设计时，§7C 的 S1-S5 构建流程仍然有效——那是"起步探索"的系统化版本。但构建完成转入 Reflect 后，不再维护设计工具中的资产与代码的同步。

**与 dao-design-qa 的关系**：视觉 bug 修复直接走截图→代码循环（无设计工具步），除非问题复杂到需要在设计工具中推敲（上述"复杂推敲"时机）。

## §8 · 验收（taste checklist + 工具联动）

> 慎终如始。验证不靠像素比对，靠体检表 + 真实渲染 + 工具实测。

### 8.1 体检表验收

1. 过 §4 体检表 — 逐条肉眼过。高密度区另过 §5 反模式表
2. 过 §6 组件审计 — 硬编码扫描 + 一致性检查

### 8.2 工具联动验收（按可用工具自动选择）

| 工具 | 验收动作 |
|---|---|
| Chrome DevTools MCP | 截图 + `evaluate_script` 量测 computed style（padding/radius/font-size/色值）+ 暗色模式截图 |
| Penpot MCP | 实现截图 vs 设计方案，验方向不验像素 |
| 无 MCP | `pnpm dev` 真实渲染 + DevTools 手检关键值 + 暗色切换 |

### 8.3 a11y 红线（不可破）

- 正文 ≥ 12px
- 焦点环可见
- 对比度 WCAG AA（正文 4.5:1，大字 3:1）
- 所有图标按钮有 `aria-label`

红线不破。通过 = 收尾；不过 = 改代码或改 token。

**验收对象是代码的真实渲染，不是稿子。不做 mockup-vs-代码的像素 diff。**

## 反原则

- **简则简** — DIRECT 档别强行走流程，改个间距就是改个间距
- **代码即真相** — 设计工具是探针不是合同，不维护设计稿与代码的同步
- **token 先行** — 任何设计值走 token，裸值是 lint 错误
- **gallery 引用不复制** — 它渲染真组件，绝不 copy 代码进去
- **不为流程而流程** — 形态已知就别探索，tokens 够用就别重定调
- **判据是准则不是清单** — 守准则，清单按项目替换
- **工具是加速器不是必需品** — 没有 MCP 也能走完全流程，有 MCP 则更高效
- **改 token 必审计组件** — 这是血泪教训，不是可选步骤

法不违德，德不违道，道法自然。
