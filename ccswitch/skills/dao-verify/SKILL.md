# 验前 · Verification Before Claims

> 慎终如始，则无败事。
> 其安易持，其未兆易谋。
> ——《道德经》第 64 章

道家把最后一关称为"慎终"，不是因为终点轻松，而是因为人到终点最易松。
**涅槃门放在最后**——前面再周密，未在终点跑一遍证据，就是"功亏一篑"。
诚则有征，征则有验。无验之"完成"，是自欺，亦欺人。

## 铁律

```
不见证据，不言完成。
不跑命令，不读输出。
未对照声明，不报涅槃。
```

`NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`

> 此条规则的"字面"与"精神"同等：换个措辞绕过它，仍是违反。

## 何时激活

- 任何要说"完成 / 修好了 / pass 了 / done / 应该可以了"之前
- `git commit` / `git push` / 创建 PR 之前
- 把 TODO 项标 `[x]` 之前
- 派子任务给下游 agent 之前（交付物必须先验，**别让别人吃你没尝过的菜**）
- 对用户表达任何形式的"满意"、"漂亮"、"搞定"之前

**强制激活**：你刚改完代码、刚等完一个长跑命令、刚读完一段日志正想松口气——此刻最危险。

## Gate Function · 涅槃门 5 步

> 致虚极，守静笃。万物并作，吾以观复。
> 在终点处不抢话，让证据自己说出来。

```
在做出任何"完成 / 通过 / 修好"声明之前：

1. IDENTIFY · 识  ——  哪一条命令能证明这个声明？
                       说不出命令 = 不知道自己在声明什么。

2. RUN      · 跑  ——  本次会话内、完整执行、不裁剪、不复用旧输出。
                       Fresh = 这一刻的真，不是昨日之真。

3. READ     · 读  ——  完整输出 + 退出码 + 失败计数。
                       不滚到底 = 没读。

4. VERIFY   · 对  ——  输出是否真的支持这条声明？
                       - 不支持：报实际状态 + 证据
                       - 支持：报声明 + 证据

5. CLAIM    · 言  ——  此时方可言"完成"，并把证据贴上。

跳过任一步 = 撒谎，不是验证。
```

## 常见失败模式 · 声明 vs 证据

| 你想声明 | 必须的证据 | 不够的"证据" |
|---------|-----------|-------------|
| 测试通过 | 测试命令输出：0 failures + exit 0 | "上次跑过"、"应该过" |
| Linter 干净 | Linter 输出：0 errors / 0 warnings | 局部跑过、外推 |
| 构建成功 | Build 命令：exit 0 | Linter 过了、日志看起来好 |
| Bug 修好 | 重跑原始复现路径：症状不再触发 | 改了代码、推断"应该好了" |
| 回归测试有效 | Red-green 双向验证 | 测试跑过一次 |
| Agent 完成任务 | VCS diff 显示真实改动 | Agent 自报 "success" |
| 需求满足 | 逐条对照 plan 勾选 | "测试过了，阶段完成" |
| 部署生效 | 拉远端最新状态实测 | "我推上去了" |

## 反模式表

> 病在终点最易藏。识病即治病。

| 病 | 症状 | 对治 |
|----|------|------|
| 应该好了 | "应该可以了"、"看起来对" | 跑命令，看输出 |
| 我有信心 | 凭直觉宣布完成 | 信心 ≠ 证据 |
| Linter 即编译 | "Linter 过了所以没事" | Linter 不查编译，更不查运行 |
| Agent 报 = 真 | Agent 说成功就信 | 看 diff、跑测试，独立验证 |
| 部分即整体 | "大部分通过了" | 部分 ≠ 完成。1 个红 = 全红 |
| 下一次 | "这次先这样，下次补验证" | 没有"这一次"特例 |
| 我累了 | 想早点收工 | 疲劳 ≠ 豁免 |
| 换措辞绕开 | 不说"完成"说"差不多了" | 任何暗示成功的措辞均触发铁律 |
| 旧输出复用 | 引用 5 分钟前的测试结果 | Fresh = 此刻重跑 |
| 假涅槃 | 症状消失就宣布修好 | 根因 + 复现验证 + 无副作用 |

## 涅槃门 · 关键场景具体判据

> 道之在天下，犹川谷之于江海。每条场景都有它该流入的海。

**测试**
```
✅ [跑测试命令] → [看到 N/N pass, 0 failed, exit 0] → "测试通过"
❌ "应该过了"、"刚才跑过了"
```

**构建**
```
✅ [跑 build] → [exit 0 + 产物存在] → "构建成功"
❌ "Linter 过了"、"编译看起来没报错"
```

**Bug 修复**
```
✅ 重跑原始复现路径 → 症状不再触发 → "Bug 修复"
❌ 改了相关代码 → 推断"应该好了"
```

**回归测试**（TDD red-green 必须双向）
```
✅ 写测试 → 跑（pass）→ 撤回 fix → 跑（必须 fail）→ 恢复 fix → 跑（pass）
❌ "我写了回归测试"（只单向 pass，不能证明它真的能抓回归）
```

**需求满足**
```
✅ 重读 plan / 原始需求 → 逐条建清单 → 逐条勾验 → 报告 gap 或完成
❌ "测试过了，需求肯定满足"
```

**派 agent 工作**
```
✅ Agent 报 success → 看 VCS diff → 跑相关测试 → 验证改动符合预期 → 才信
❌ Agent 说做完了就标完成
```

## 红灯词 · 立即停

听到自己即将说出以下任何措辞，**先停手，回到 Gate Function 第 1 步**：

- "应该"、"大概"、"看起来"、"差不多"
- "Great!" / "Perfect!" / "Done!" / "搞定！"（在跑命令之前）
- "我有信心 / 我确定"（无证据支撑的断言）
- "刚才/之前跑过了"（不是 fresh）
- "下一次会补验证"（没有下一次）

## 底线

> 信言不美，美言不信。

诚是核心价值。
**如果你撒谎说"完成"，你会被替换。**

不是威胁，是因果——一次未验的"完成"会污染下游的所有判断。
用户基于你的声明做下一步决策。你声明里的每一字，都会变成他时间与信任的押注。

跑命令。读输出。**然后**才声明。

此条不容商量。
