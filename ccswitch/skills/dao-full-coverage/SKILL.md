# 全面体检术 · Full Coverage Lens

> 知不知，上；不知知，病。
> 夫唯病病，是以不病。圣人不病，以其病病，是以不病。——《道德经》第 71 章

**核心**：不是没病才不病，是**清楚自己有病**才不病。主动找盲点 = 道家"病病"。

## 与现有体检概念的边界

| 概念 | 文件 | 对象 | 触发 |
|---|---|---|---|
| `/health-check` 快速体检 | `dao-evolve.md` workflow | **dao 体系自身**（rules/skills/workflows） | 行为异常时 |
| 编辑时质量门 | `quality.md` rule | **当前编辑文件** | glob 自动触发 |
| 死磕 bug | `dao-debug` skill | **已知 bug** | 被动·有 bug 才查 |
| **业务全面体检** | **本 skill** | **整个业务项目** | **主动·定期/重大变更后/发布前** |

dao-evolve 审查 dao 自己；本 skill 审查业务项目。两者正交，不冲突。

## 何时激活

**必激活**：
- 重大变更后（≥3 文件 / 核心模块 / 不可逆操作）
- 准备发布/上线前
- 接手新项目（前任交接 + 自己上手前）
- 用户报告"系统怪怪的但说不清楚"
- 周期性（每周/每月，按项目活跃度）

**不必激活**：
- 小修小改（typo / 文案微调 / 单文件 < 10 行）
- 主动开发流程中（避免被打断；记下来排队修）

## 8 维度体检清单

逐项过，不全扫——按**当前项目特征**挑相关维度。

### 1. 代码 · 内在质量

```
□ Lint 全绿（eslint / pylint / shellcheck）
□ TypeCheck 全绿（tsc --noEmit / mypy）
□ 死代码（grep + ts-prune / vulture）
□ 重复代码（jscpd / radon）
□ 复杂度（圈复杂度 > 10 的函数）
□ 命名一致性（用同一概念是否用同一词）
```
### 2. 测试 · 验证健康

```
□ 单测覆盖率（核心模块 > 80%）
□ 边界测试（空、null、极大、极小、并发）
□ 假阳性测试（测试自身是否真的检验了东西）
□ E2E 路径全覆盖（参 dao-user-simulation）
```

### 3. 文档 · 知识沉淀

```
□ README 描述当前状态（不是半年前）
□ API doc 与实现一致
□ 注释陈旧度（> 3 个月未更新且代码已变 → 标 stale）
□ AGENT_GUIDE.md / docs/ 与代码一致
□ DEPLOY 记录是否真实（参 e163 教训：声称"已部署"但 GHA 失败）
```

### 4. 依赖 · 供应链健康

```
□ 漏洞扫描（npm audit / pip check）
□ 过期依赖（major 版本落后）
□ lockfile 健康（npm ci --dry-run）—— 参 e163 教训
□ peer dep 范围冲突（双版本陷阱）—— 参 e163 教训
□ 单一版本（同一包不应有多个版本并存）
```

### 5. 配置 · 边界与安全

```
□ env 文件不含敏感信息（grep -i "password|secret|token|key")
□ 默认值合理（默认开/关、默认地址不指向生产）
□ Feature flag 状态（哪些 on/off，预期吗）
□ 跨环境一致（dev/staging/prod 的差异是否文档化）
```

### 6. 部署 · 上线机制

```
□ CI/CD 通道：build → test → deploy 全绿
□ 环境变量：CI 环境的 env 与本地一致
□ 回滚机制：能回到上一稳定版吗
□ 部署日志：DEPLOY.md / 部署系统记录是否真实
□ 健康检查端点：/health 返回正确状态
```

### 7. 性能 · 用户感知

```
□ 启动时间（冷启 / 热启）
□ 内存占用（idle / 高峰）
□ 慢查询（> 100ms 的查询）
□ 前端：首屏 LCP、INP、CLS（参 chrome-devtools MCP performance_start_trace）
□ 后端：p95/p99 延迟
```

### 8. 安全 · 攻防边界

```
□ 认证：所有需登录的端点都校验 token
□ 授权：用户只能访问自己有权的资源
□ 输入校验：所有 user input 都过 validate（SQL 注入/XSS/路径穿越）
□ 加密：敏感数据存储和传输都加密（HTTPS/TLS）
□ 密钥管理：密钥不在代码里，用环境变量或 secret manager
```
## 报告产出格式（统一，便于对比）

```markdown
# 项目 X · 全面体检报告 · 2026-XX-XX

## 概览
- 体检维度：[8 个全过 / 选了 5 个]
- 严重度分布：高 X / 中 Y / 低 Z
- 推荐优先修：N 项

## 详情

| 维度 | 项 | 严重度 | 当前状态 | 建议 |
|---|---|---|---|---|
| 依赖 | esbuild 双版本 | 高 | 顶层 0.24 + 嵌套 0.28，extraneous 标记 | 升级 esbuild ^0.28（参 e163 教训）|
| 测试 | E2E 覆盖率 | 中 | 仅 1 个端到端测试 | 用 dao-user-simulation 走 5 条主路径 |
| ... | ... | ... | ... | ... |

## 行动建议
- 🔴 立即修：[高严重度项]
- 🟡 排队修：[中严重度项 → 加入 TODO.md] 
- 🟢 监控：[低严重度项]
```

## 触发节律（不是每次都全 8 维度）

| 触发 | 维度选 | 深度 |
|---|---|---|
| 重大变更后 | 改动相关 3-4 维度 | 中 |
| 发布前 | 全 8 维度 | 深 |
| 接手新项目 | 全 8 维度 | 深 |
| 周期性 | 全 8 维度 | 浅（自动化为主） |
| 用户反馈"怪怪的" | 看症状选 2-3 维度 | 深 |

## 反模式

| 病 | 症状 | 对治 |
|---|---|---|
| 看见就修 | 体检中发现问题立即跳出修 | 主任务被打断；除非高严重度，否则**记 TODO 排队** |
| 全维度全深度 | 每次都 8 维度都深扫 | 浪费；按当前任务挑 |
| 盲扫无结论 | 跑了一堆工具但不出报告 | 必须出统一格式报告 |
| 不分严重度 | 把 typo 和 SQL 注入混在一起 | 必须打严重度标 |
| 一次性 | 体检后不沉淀，下次重做 | 体检结果归位 `docs/evolution/evolution-entries.csv` |

## 与其他 dao-* 协作

- `dao-evolve`（互补·正交）— 那个审 dao 体系，本 skill 审业务
- `dao-debug` — 体检发现的"高严重度问题"派给 dao-debug 死磕
- `dao-user-simulation` — 第 2 维度（测试）和第 7 维度（性能）部分由 simulation 实测得出
- `dao-empathy` — 第 7 维度（性能·用户感知）的"用户感知"部分由 empathy 视角判定
- `dao-finish` — `/dao-finish` 涅槃门必检 8 维度的关键 3-4 项

## 反原则

- **不为体检而体检**——发现的问题必须有人修；否则只是制造焦虑
- **不让体检成阻塞**——主任务进行中发现的问题，记下排队，不立即跳出修
- **体检报告不堆积**——每次报告必有"行动建议"段，否则不算完成

法不违德，德不违道，道法自然。
