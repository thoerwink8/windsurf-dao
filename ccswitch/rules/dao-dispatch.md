## 派单令必带首行（canonical 模板 · 原样复制，不要改写、不要判断该不该带）

写派单 prompt 时，**开头两行固定是这两句**（把尖括号换成真路径）：

```
开工第一步：Read `<dao 仓根>/ccswitch/rules/dao-officer-clauses.md`（跨项目通用判据）+ 本仓 `<项目条款库路径>`（本仓特有条款），两份都通读「通用节」+ 你所属官种那一节，逐条遵守。有冲突以盘上文件为准，不以本 prompt 的转述为准。
开工第二步：全套验证入口去 `<目标仓根>/CLAUDE.md` 自己查——**本令刻意不给验证命令**。那份文件没写、或它列的清单与盘上对不上时，以盘上为准，并把差异写进交付（别只在自己这一路悄悄改对）。
```

**为什么是两份**（2026-08-02 拆分）：官侧条款分**通用半边**（与技术栈无关的判据，住
`ccswitch/rules/dao-officer-clauses.md` —— 本文件是**帅侧**，那份是**官侧**，两份平级）
与**项目特有半边**（那个仓的验证入口 / 账本文件 / 进程名 / 专有脚本 / 专有标签，
住项目的 `docs/rules/dispatch-clauses.md`）。**只给一份路径就是让官漏读一半。**
项目侧还没有那份文件时（新项目 / 休眠仓），首行只写通用那份，并在派单令里说明
「本仓尚无项目特有条款库」—— 别因为缺一份就整句不写。

**为什么这两句要固定写、不许现场判断该不该带**（实测数据，不是设计偏好）：同属通用节、同一文件、
同样措辞强度的条款，携带率分裂成 **100% vs 9%** —— 跟着模板走的那条 68/68 全带，而要求帅
**每次重新判断该带哪几条**的两条只有 23.5% 与 8.8%。**区分变量不是文字 vs 机器闸，
是「形态」vs「判断」**。⚠️ **这组数字是第一步那句的，不是第二步的**——第二步 2026-08-04 才加，
它自己的携带率**未测**，写在这里的理由是「同一个机制」而不是「同一份证据」。
第一步那句同时解掉投递延迟：always-on 快照按 compaction 刷新
（实测约 12 小时），帅从自己快照里粘贴条款粘的是旧版；让官**自己 Read 盘上文件**，
读到的永远是最新版。

**为什么第二步是「不给命令」而不是「给对的命令」**（2026-08-04 加，判据全文见下面
`[#派-字段来源]`，本段只说这两行为什么长这样）：验证入口是**内容决定**的字段——只有盘上那份
文件知道它是什么，帅写下的任何值都只能来自记忆。**把这一格从派单令里删掉，比把它填对更彻底**：
填对是一次性的，删掉是结构性的。**第二步给的是路径不是命令**，正因为 `<目标仓根>/CLAUDE.md`
这个路径**不看仓也说得出**（结构决定），而 `scripts/run-tests.mjs` 说不出（内容决定）。

⚠️ **两格照直写，别把这两行读成已经万无一失**：
㈠**它不指定节名**。入库时实测两个仓的落点根本不同名——一个在 `## 五、验证`，
另一个在 `## 常用命令` 底下的「自检与测试」段。**写死节名会让它在第二个仓上静默落空**，
所以第二步只给文件、不给节。代价是官要自己在那份文件里找，找不到就按末句报差异。
㈡**那份文件本身会过期**。入库当天实测：dao 自己的 `CLAUDE.md` 确实写着正确的验证入口，
**同一段里的 PowerShell 测试清单却少了一半**（列 2 套、盘上 4 套）。⇒ 第二步末句
「以盘上为准 + 把差异写进交付」是**必填不是客套**；**帅收到差异后该改的是那份 `CLAUDE.md`，
不是下一个派单令的措辞**——改措辞等于让下一个官再撞一次。

**仍需手工携带的唯一场景**：某条款是本轮刚写入盘上、而任务**强依赖**它 ⇒ 除首行外再把该条原文
粘进 prompt（双保险）。其余情况不要手工摘条 —— 摘条本身就是那个 9% 的病灶。

**⚠️ 这条首行目前是唯一真的在投递官侧条款的通道**：`ccswitch/hooks/dao-subagent-clauses.js`
那条自动注入通道虽已存在，但 `ccswitch/clause-index.json` 的源清单里**还没有**官侧档
（源清单住 `ccswitch/lib/clause-parser.mjs`）⇒ 它今天渲染不出官种节，只能给指针。
**别把「有个 hook 在管」读成「不写首行也没事」。**

**合 · 分级验证**：将的产出必验，深度按**错误代价 × 反转难度**分级——
①**实现官全验**（复跑构建测试 + acceptance 逐条 + 真机验证，全过才合并）；
②**侦察兵 · 低风险抽验**（亲核 1-2 条最承重论断）；
③**侦察兵 · 高风险对抗验**（论断带出处 + 抽验承重 top 2-3，或双侦察独立调研只对分歧深挖）
——调研错误不炸 CI、反转成本高于代码 bug，该验得更狠。
**验证可委派，终审不可让渡**：定标准 / 读结论 / 按合并三下必须帅手。
**核验官输入完整性**：承重字段（发现清单 / 入池候选 / 出处）禁编排层静默截断，
截断即制造「无从核验」型误裁（出处：叙事 N1）。

**验证资源独占时，「每条都合规地挂了账」会掩盖「整批的覆盖率在跌」**：当某类验证依赖一个
**同时刻只能有一个人用**的资源（真机 / 设备 / 生产账号 / 独占端口），批内各路会各自合规地走
「降级挂账」——**单看每个 PR 都无可指摘，合起来看这一批几乎没被验过**。缺的不是纪律，
是**聚合视角**：合规性是逐条判的，覆盖率只有横着看才存在。⇒ 派批前先问「这一批里有几路要抢
同一个资源」，抢的路数 > 1 就**明确指定谁真的用它**、其余在派单令里写明「本路不验、由某某代验
或整批欠账」；窗末**按批**报一次真实覆盖率（不是按条报合规率）。
入库时基线：某窗 6 个 PR 的真机三态填写合规率 6/6，而实际走过真机的只有 1 路
⇒ 逐条读账本看不出任何异常。

**热重载型验证从专用 worktree 起，不从主仓树**（用户点名事故后固化 2026-08-01）：当验证方式是
「从工作树跑一个 watch 编译的进程」（`tauri dev` / `vite` / `webpack --watch` / 任何 HMR），
**那个工作树的任何写入都会触发重编译或重载、打断验证**——而主仓树是共享的。
**「冻结 main 推送」是纪律型约束，同窗被违反 ≥3 次**（谁违反的、后果如何见
`docs/evolution/dao-clause-rationales.md` §帅-5）。**正解不是更努力地冻结，是让验证进程从一个
专用 worktree 起**（如 `<repo>-wt-rm`）：主仓树怎么改都不进它的 watch 面，连 freeze 都不需要，
也不依赖每个官完美隔离（他们会滑，见基线）。判据一句话：**问「我的验证进程 watch 的是哪棵树？
那棵树此刻只有它一个人写吗？」——答案是主仓＝错，是专用 worktree＝对。**
