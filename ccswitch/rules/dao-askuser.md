## 一、选项构成

- 至少 1 个**深入/推进**：基于当前上下文预测用户最可能的下一步
- 至少 1 个**收尾/切换**：提交 / 验证 / 换话题 / 先这样
- 可选 1-2 个**横向探索**：相关但用户可能没想到的方向

涉及 🔒 必止门控时，选项必须指向门控本身（如"展示 Loop 计划"而非"开新 Loop"）。

## 二、选项质量要求

- **🔴 说人话（用户 2026-07-27 亲令，优先级高于其余各条）**：问题与选项里**禁止出现只有体系内部才懂的词**。
  自检判据一句话：**这个词，用户自己说过吗？** 没说过就必须翻译成他的话，或者干脆不提这个机制。
  - **禁用示例**（都是真实违例，同日实测用户回「看不懂」）：判断类候选 / 升格 / 收割 / 触发点 / 形态化 /
    观察区 / 观察线 / 槽位档 / 机检档 / 条款元字段 / 归位 / 载体 / 分流……**这些是 AI 之间的黑话，不是共同语言**
  - **翻译方向不是换个词，是换个说法**：不要把「升格」改成「提升等级」（还是黑话），
    要改成「**我发现一条好经验想写成规矩，要不要每次都问你**」——**说这件事对他意味着什么，不说这个机制叫什么**
  - **推荐项的理由也要是人话**，且尽量给他能验证的实据：
    「我以前自作主张删过两个工具，一个当天就被你发现叫我装回去」远胜「历史上退役审查准确率偏低」
  - **一个可自查的替身测试**：把问题念给一个**没参与过这个项目**的人听，他能不能判断自己该选哪个？
    不能就是没说人话
  - **为什么这条排在最前**：AskUserQuestion 是**全仓唯一验证有效的决策通道**（14/14 留档意图源于对话，
    GitHub 与文档侧零正面证据）。**唯一的通道上说黑话，等于把唯一的通道也堵了。**
- **🔴 拍板呈现用 STAR（用户 2026-08-07 亲令，射程=把事摆给用户拍板的那一段铺垫+选项）**：每件待拍的事四格讲齐——
  **发生了什么**（背景一句）→ **要你定什么**（这一板拍的具体是哪格）→ **我做了什么**（已查的实况、已备的方案与实据）→
  **选下去各得什么**（每条路的后果与代价，写进对应选项的描述里）。多件同批拍板时**每件独立走一遍四格**，
  禁止把几件事的背景混在一段里连讲、让用户自己拆。
  - 这是 `dao-workitem.md`「人读的载体（issue/PR/评论）用 STAR」那条的延伸：那边 2026-08-01 就固化了，
    但射程没盖到拍板呈现——**看 issue 的和拍板的是同一个人**，没理由一边 STAR 一边不。
    入库时基线 1/1：帅一次摆四件拍板未按 STAR，当场被用户叫停。
  - 与「说人话」的关系：STAR 是**结构**，说人话是**语言**——四格里每格照样要过「这个词用户说过吗」那关。
- **预测优先**：选项要比用户自己想到的更快、更具体。「继续」「下一步」这种空泛选项禁止出现
- **贴合上下文**：刚完成代码修改 → "跑测试验证" / "提交" / "看看还有没有相关文件要改"；刚回答了文件位置 → "帮我看看内容" / "帮我改" / "搜索引用处"
- **与归位提醒互补**：若本次回答触发了「产出归位提醒」，其中一个选项应为"执行归位同步"，将归位建议转为一键操作

## 三、选项溢出策略

AskUserQuestion 硬限 **2-4 个选项**（工具 schema `maxItems: 4`）。可选路径 > 4 条时：
- **槽位给高频**：4 个选项放当前上下文最可能的操作
- **提问文本暴露低频**：在问题文本中列出未占槽位的功能关键词，如 `（也可输入：od-sync / 审计 / token）`
- **Other 兜底**：用户选 Other 输入关键词 → 走意图识别路由（如 skill 的 §P.1）

Skill spec 编写动态选项列表时，**写完必须数一遍**，超 4 即砍。

## 投递现状（照直写，此刻它是纯文字兜底）

🔴 **本文件此刻没有任何机器投递，「必经动作」那四个字目前只有 dao.md 续力节的存根在兜。**
同批的另外两份细则档（`dao-powershell.md` / `dao-guard-writing.md`）各有一个作用域档
（`ccswitch/rules/scoped/dao-scope-*.md`）在 Read 到匹配文件时把它们送到眼前，
**本文件没有**——原因是作用域档的判据是「做这类事之前，我必然会 Read 某一类文件吗」，
而**写选项这件事不 Read 任何特定文件**，给它编一个路径锚点等于造一个永不触发的档
（dao.md 知识归位节明写这条禁令，那里点名的四个反例之一就是这一类）。

**已知的唯一候选投递通道是 `PreToolUse[AskUserQuestion]` 的 `additionalContext`**
（advisory，不拦截）。2026-08-02 文档核查结论：

- 官方文档记载 `PreToolUse` 的 `hookSpecificOutput` **支持 `additionalContext`**
  （表内释义「Context injected into Claude's window for the next model call」），
  且它与 `permissionDecision` 是并列字段 ⇒ **不下裁决只注入上下文是文档支持的形态**。
- `PreToolUse` 的 matcher 按 `tool_name` 做**不锚定的正则 test**、大小写敏感；
  文档称「All tool names are supported as matcher values」。
- **但 `AskUserQuestion` 这个名字在整份 hooks 文档里出现 0 次**，`Task` 只作为
  `TaskCreate` / `TaskCreated` / `TaskCompleted` 这几个**另外的事件**出现。
  ⇒ 上面那句「所有工具名都支持」是**总括陈述，不是这两个工具名的点名担保**。
- **本机零实测**：live `~/.claude/settings.json` 的 `PreToolUse` 只注册了
  `dao-hard-gates.js`，matcher 是
  `Bash|PowerShell|Edit|Write|MultiEdit|NotebookEdit|mcp__windows.*|mcp__chrome-devtools__take_screenshot|mcp__playwright__browser_take_screenshot`
  ——**覆盖不到 `AskUserQuestion` 也覆盖不到 `Task`**；且全仓 hook 里**没有任何一处**用过
  `PreToolUse` 的 `additionalContext`（实扫零命中），所以连「这条注入路径本机通不通」都没有
  过往证据。改 matcher 的写入面是 cc-switch DB 的 `providers.settings_config`，**属用户动作**。

⇒ **结论按文档为准，session 级实测待注册**。在真的实测出「注入到达」之前，
别把「有了这份档」读成「写选项前有人会提醒我」——那两件事之间隔着一次注册和一次实弹。
