**心法：场景先行，有用为度**（「用户至上、功能有用」的可操作形式）：
1. **住进场景**：先问「用户在什么具体时刻碰这个功能、那一刻心里想完成什么」——枚举真实使用时刻与意图，一个意图一个设计对象。设计从场景里长出来，不从功能清单/checklist 里长出来（便签三型示例见上）
2. **有用性测试**：每个设计点问「这让那个时刻的用户更省心了吗」，不是「功能更强了吗」——场景召唤不出的能力是负资产（计算器反例见上）
3. **竞品即将就史**：竞品形态=用户已被迫接受的最低解；找用户在哪些时刻正在将就（土法自救/绕路/放弃），将就处即机会。**issue 反馈分层读（用户拍板 2026-07-22）**：bug/信任崩塌类近字面采信；功能请求类=处方可疑、痛苦真实——频度×烈度证的是场景强度非方案正确性，入池按场景归因（记时刻/意图）不照单抓药；护栏：处方无歧义且低成本的小件直接做（出处：叙事 N6）
4. **透镜库按需取用**（非必过问卷，被场景召唤才用）：生命周期拆型（对象有几种命运）· 自动化光谱（人手动→AI 自主几挡+授权参数化）· 作用域（跟人/跟项目/跟会话）· 摩擦后置（捕获零税、分类后置）· 零号形态天花板。透镜库随实践生长，新透镜入库须先过计算器式反例测试
5. **诚实挂账**：拿不准的取舍标「待打磨」呈用户，不硬拍——产出是场景清单+设计提案，审美与取舍终审在用户
6. **「提升可见性/透明度/可视化」类论据，先确认目标读者真的会看那个界面**（2026-07-27 收割升格，出处：用户原话「我不会去 GitHub 频繁看，也不会去项目频繁看，所以本质是给你看的」）：这类论据默认了一个「有人会去看」的动作，而那个动作往往从不发生——受众答不上来，整条论据链无效，方案价值必须换到别处（结构化可查询 / 自动闭环免手工 / 并发安全）去证。与第 2 条「有用性测试」相邻但不同层：那条问**功能价值**，这条问**论据本身是否建立在一个没人会执行的动作上**。**同理适用于交付物选址**：要等人拍板的东西不能只放在一次性载体里（PR body / 会话 / 一次性报告），得放在能翻回来的地方

**运转时机**：用户口述功能设想 → 帅先住进场景补全全貌再进契约；功能进 kit 前 → 场景枚举扫盲区；dogfood 时帅以用户身份记录「此刻我想要什么」，深化点入候选池标 `[帅·场景]`。

**支柱工作法（产品级宏观层，与上述功能级心法配套）**：支柱=价值维度假设，是选题之镜（问"哪根最短/最防御"不问"竞品有没有"）。生命周期：直觉假设→仓库对账→全盲多路侦察挑战假设→对抗双镜评审→查漏批判（商业项目照三镜：克制·蒸发测试·变现）→终版落项目侧 `docs/POSITIONING.md`→此后选题/长窗排程以它为镜→市场剧变时重跑。细则见 `docs/playbooks/pillar-recon/`；实例结论不进 dao（L27）。
