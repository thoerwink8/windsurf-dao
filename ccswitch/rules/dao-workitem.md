**工作项三态归位（用户点名固化 2026-08-01，条件化生效）**：知识归位管「知道的事」，本条管「要做的事」——同一个道理推广到工作项。**一句话判据：说得出「关闭条件 + owner」→ issue；是聚合视图 → 看板；是流水/叙事/跨切 → 文件。** 三个家各归各的，别让一件事有两个真相源（双份必漂移）：

- **issue 区 = 分配中心**：有独立生命周期的单元（缺陷/任务/欠账 + 蓄水池「待拍板/需用户」）。低置信候选挂 `候选` 标签同池，**升级=relabel 不是 re-create**（酝酿→行动一个动作）。
  - **人读的载体（issue/PR/评论）用 STAR + 说人话 + 折叠证据（用户点名固化 2026-08-01；2026-08-02 用户点名去条件化）**：**本条不随下方「条件化」开关走——任何仓的 issue/PR/评论无条件生效**，因为看 issue 的永远是人，与那个仓接没接中枢基建无关（首证：windsurf-dao 未声明中枢，同日 7 个 issue 正文全行话裸奔，用户当场点名）。这些是**人**读的、不是 AI 交接密文。①**STAR 结构**：`为什么改→改了什么→怎么验的`（关单：`原来什么问题→怎么解的→验证结果`），人扫顶部就懂。②**说人话领先**：体系黑话（mutation/canary/各种档位名）人话在前、术语首现括注一次——不删精度，是把人话加在精度之上。③**技术证据进 `<details>` 折叠段**：精度数字一个字不删、折叠起来，**人读顶部、AI 读全部、零丢失**。判据：**没参与项目的人扫一眼顶部知不知道发生了什么。** 落地：PR 用 `.github/pull_request_template.md`（分层内建），issue 模板同理；这是「说人话」原则在**人读载体**上的延伸，不是新原则。
- **看板（GitHub Project 等）= 观测中心**：所有单的聚合全景，标签驱动自动归列——**别用「更多常驻 issue」凑观测中心，那是看板的活**。用户专属 inbox（待拍板/需用户）用 pinned issue，全景用看板，两者不冲突。
  - **「一眼对齐」hub（pin 有上限时的正解）**：GitHub pin 每仓上限 3 个，用户想 pin 的「重要内容」往往 >3。**别去挤那 3 个槽，做一个总览 hub 单占第 3 个 pin**——它聚合看板链接 + 各 inbox（待拍板/需用户/候选）+ 在途入口，给用户**单一对齐入口**（另两个 pin 留给最高频的两个可回复 inbox）。判据：用户说「X 也要 pin」时，先问「X 是不是已经能进 hub 的某一行」——酝酿层（候选）就是原 TODO 总览，进 hub 一行即可，不占独立 pin。hub 由帅每批收官刷新「现况」数。
- **仓内文件 = 叙事层**：流水账（PROGRESS 型）/发布物（CHANGELOG）/策略（POSITIONING）/流程 doc——没有 per-item 生命周期，硬塞 issue 反而散掉。**判据自检**：一个「问题树看板」型文件（WORKBOARD 型）在 issue 中枢+看板建成后多半**冗余**，退役归档、活账交 issue，是为道日损。

## 建单三件套 · 起单时必过的三格（2026-08-09 立 · 用户拍板，issue 可读性改造批）

**一句话判据：建 issue 时类型标签、标题、关联三格都要过，正文散文引用只作补充不作唯一记录。** [#归-建单可读]

- **①类型标签七选一必贴**：`bug` / `feature` / `test` / `docs` / `chore` / `refactor` / `perf`，恰选其一（判据：守卫/测试补强⇒`test`，hook/脚本缺陷⇒`bug`，新机制⇒`feature`，文档改真⇒`docs`，配置/基建/维护类⇒`chore`，不改外部行为的内部结构调整⇒`refactor`，性能⇒`perf`）。与已有的「类型」维（`缺陷`/`任务`/`欠账`/`候选`/`待拍板`/`需用户`，见上「label 体系」节）不是同一根轴——那一维答「这单归哪种流程」，这一维答「这单改的是什么性质的东西」，两维正交、同单可以都贴。
  ⚠ **射程标注（2026-08-09 PR #225 复核补）**：本条 7 标签维度当前只在 windsurf-dao 落地；dao canonical 模板（`ccswitch/templates/labels.json`，被 `ccswitch/scripts/dao-issue-bootstrap.ps1` 消费）未同步——新项目 bootstrap 尚不满足本条，下沉与命名属判断档待拍。
- **②标题人话式**：内部术语进正文不进标题，写完自检一句——**没参与项目的人读标题能知道这是干什么的吗**（参照 `#193`「多机/多 AI 并行处理 GitHub 的认领机制——标工作状态防两台机器撞同一张单」这类写法：用后果/风险描述代替内部机制代号，而不是删掉精度——精度留在正文，标题只担一件事：让人一眼知道这是干什么的）。
- **③关联用结构化字段**：跟进单挂 Sub-issues 父子（`gh issue edit <子单> --parent <父单>`，需 gh CLI 2.94+）；前置条件用 blocked_by（`gh issue edit <n> --add-blocked-by <N>`）。**⚠️ 2026-08-09 实测坑，调研报告未覆盖的一格**：blocked_by 的目标只能是 issue，不能是 PR。**证据分两层，2026-08-09 PR #225 复核订正**：`gh issue edit <n> --add-blocked-by <PR号>` 这条命令本身在 **gh CLI 客户端层**就被挡下，报的是 GraphQL 解析错误（`Could not resolve to an Issue with the number of <N>`），请求根本没送到 REST；**422**（`Validation failed: Target issue may only be an issue`）只有**直调 REST** `POST /repos/.../issues/<n>/dependencies/blocked_by` 才看得到（对 #218、#225 两个 PR 目标各验一次，两次都是它）。**结论不变**：blocked_by 拒绝 PR 这件事成立，只是「跑哪条命令看见哪层错误」此前记错了。「前置：PR #NNN 先合并」这类跟 PR 挂钩的前置条件，目前仍只能留在正文散文里，等那个 PR 合并/关闭后说明自然作废——结构化字段管不到这一格，别把「Dependencies 端点可用」读成「对 PR 也能用」，调研报告只验了端点存在、没验目标类型。正文散文引用只作补充，不作唯一记录。

出处与基线数字见台账 `ccswitch/clause-ledger.json`（2026-08-09 调研 `_tmp/issue-readability-research-20260809.md` 实测 40 张最近 issue：标题 75% 依赖内部黑话、除『缺陷』准类型标签（11 张）外无类型细分、六格 0%、关联结构化字段使用率 0%；用户 2026-08-09 拍板「A+B 叠加」）。

> 落在**查表那一步**（组合键），把跨宿主的认领挡在它上游。直接把别的宿主的认领对象喂给
> 它，它照旧答 `$true`（8e-2 钉住了这个现状）。**这仍是未经独立对抗复核的新实现。**

### 一、为什么一层装不下（先说清哪条路走不通，省下重新发明一遍）

| 只用这一样 | 它答得了 | 它答不了 |
|---|---|---|
| `assignee` | 「有人领了」，且 GitHub 所有列表视图天然显示 | **哪台机**。两台机跑的是**同一个 GitHub 账号** ⇒ `--assignee @me` 两边都命中；而 assignee 只能填有仓库权限的用户（[官方文档](https://docs.github.com/en/rest/issues/assignees)，上限 10 个），一个人就一个账号，机器数与可填的身份数对不上 |
| 一个标签（`在途`） | 「有人领了」，一条 `gh issue list` 就能把被领的单从队列里摘掉 | 谁 / 何时 / **过期没有**。标签只有「有」和「没有」两态，装不出第三态「标着，但那台机已经死了」 |
| 只发一条评论 | 谁 / 哪台机 / 何时（时间还是 GitHub 自己盖的） | 「列表级一眼避开」。评论要逐单点开才看得见，领活循环扫二十张单不可能每张都点 |

⇒ **两层组合，各干各擅长的，且不新建任何标签**（为道日损）：

| 层 | 载体 | 装什么 | 谁读 |
|---|---|---|---|
| **信号位** | **既有 `在途` 标签**（语义不变） | 「这单有人在干」 | 领活循环，一条命令筛掉 |
| **详情层** | 一条固定格式评论 | 机器 / 宿主 / 自报租期；**时间由 GitHub 盖** | 判过期、判撞车 |

### 二、认领怎么标（谁 / 哪台机 / 何时）

**一个动作两件事**：发一条认领评论 + 给单加 `在途`。**机器面这一行不要求是评论的第一行**
（2026-08-09 issue #198 订正，对抗 FAIL-1）：dao「人读载体人话领先」是无条件条款，评论可以
先写一两句人话说明在干什么，机器面**独立成行**、纯 ASCII，出现在正文里任意一行都算数——试点
评论本来就是这么写的（人话在前，`dao-claim:` 落在第 3 行），此前文字要求「首行」与这个实况
自相矛盾，现在改判据去对齐实况，不是反过来要求人话让位：

```
dao-claim: <机器名> / <宿主> / <自报租期>h
```

**「独立成行」是唯一的硬要求**：这一行前后可以有任意人话/表格/详情，但这一行本身（去掉可选的
首尾反引号后）必须整行只有这一个机器面，不能与别的文字挤在同一行——§六 命令③④ 的回读只认
**独立成行、字段合法**的机器面，混进散文或表格单元格的引用一律不命中，这正是 FAIL-2 那个
幽灵认领洞的堵法（详见下条字符集判据 + §六 解析实现）。

- **机器标识用 hostname，不用手填的别名**（`$env:COMPUTERNAME` / `hostname`）。判据是**这个值能不能被填错**：
  hostname 是宿主给的、结构决定的、**两台机默认就不同**（克隆的虚拟机与改过名的机器是例外，
  见本节末弱处 ㈣ —— **别把它读成「不可能相同」**）；别名要有一份配置、要在每台机上各填一次，
  而它填错时的失败形态恰好是**两台机自称同名**——那正是这套机制唯一防不住的形态（互相把对方的
  租约当自己的，接管判据全线失效）。**公开仓要脱敏时，正解是换成 hostname 的稳定哈希前几位，
  不是换成手填别名**——哈希仍然是结构决定的。
- 🔴 **机器名 / 宿主字段的合法字符集是 ASCII 字母数字加连字符/下划线**（`^[A-Za-z0-9][A-Za-z0-9_-]*$`，
  2026-08-09 issue #198 补，对抗 FAIL-2）：真实 hostname 天然落在这个字符集里，协议文档里凡是
  占位符示例都写成 `<机器名>` 这种带尖括号的形态——**这个字符集恰好把尖括号占位符、反引号、
  中文都挡在外面**。§六 的回读命令拿它做第一道判据：一行只要不满足「独立成行 + 字段合法」，
  就不是一条真认领，不管它长得多像（含裸标记，如只写了 `` `dao-claim:` `` 不带任何字段——
  #193 评论 1 的 `<details>` 里就潜伏一个这种裸标记，字段校验直接判它不算数，不依赖「Match
  只取第一条」这种实现细节侥幸躲过去）。
- **第二格是宿主**（`cc` / `codex`）：同一台机上两个 AI 宿主并行是真实形态（dao 本身就是双栈）。
- 🔴 **同机同宿主同时开多个并发会话时，第三格会话短 id 从「可选」升级为必填**（2026-08-09
  issue #198 补，对抗 FAIL-6）：格式变成 `<机器名> / <宿主> / <会话短id> / <自报租期>h`（会话
  id 插在宿主与租期之间；机器按字段数 3/4 自动区分要不要读它，见 §六 解析实现）。**只有单会话
  时才可以省略**（3 字段 `<机器名>/<宿主>/<N>h`）。判据是**能不能靠「机器+宿主」两格分清谁是
  谁**：单会话时两格已经唯一确定一次认领；一旦同机同宿主开了第二个并发会话，两格就退化成
  「共享同一个认领」——这正是本协议要治的原病（两路白干）在**同一台机器内部**重演（弱处 ㈩）。
  会话短 id 不强求全局唯一，只要求**同一时刻、同机同宿主内互不相同**（终端序号 / worktree
  名后几位 / 会话 pid 末三位，自报即可，不需要额外基础设施）。**它防不住「忘记填」**：漏填时
  退化为旧的二字段行为，这不是新洞，是把旧洞的边界画清楚，不是补上。
- **时间不自己写**：租期起算点是 **GitHub 给这条评论盖的 `createdAt`**。两台机的本地时钟不共享，
  GitHub 的时钟共享；自报时间戳会被时钟漂移和「照抄上一条模板」毁掉。**这一格没有让步空间。**
- **为什么机器面必须是 ASCII**：实跑发现 PowerShell 5.1 把传给 `gh` 的 jq 表达式里的**双引号静默吃掉**
  （`index("在途")` 到了 jq 那边成了 `index(在途)` ⇒ `failed to parse jq expression`），
  机器面标记因此不能依赖引号里的中文。emoji 与中文只做人读装饰，机器只认 `dao-claim:` 这一行。
- **assignee 用不用随意，但别把它当机器判据**：它是给人在 GitHub 网页上扫一眼用的，
  「哪台机」这一格它结构上答不了（见上表）。
- 🔴 **认领的单位是「机器 + 宿主」，不是单个 agent**——这一格不说清会读反：dao 的派单模型里
  帅与它派出去的官**跑在同一台机上**，所以他们共享**同一个**认领，官交付时**不摘 `在途`**
  （摘它发生在**帅销账**那一刻，与既有三节点留痕的第三节同一时刻、同一个人）。
  官那一侧的「交付结论」评论按第三节的判据**算续租**，不算释放。

### 三、过期怎么判（这一节是成败关键）

🔴 **没有租期的认领，只是把撞车病换成锁死病，而锁死病更隐蔽**：撞车会在 PR 冲突那一刻**响**，
锁死是一张单静静地**永远没人领**。本体系已有同型判据——接力单纪律明写「**不装实况快照**……
漂移的快照比没有快照更坏：**它看起来是可信的**」（`ccswitch/commands/dao-resume.md`）。
一个不会过期的 `在途` 标签就是那种快照：它看起来是「有人在干」，实际可能是三天前一个死掉的会话
留下的。⇒ **认领标注必须自带一个「它自己会失效」的机制，否则它是一个永远为真的断言。**

**租期取值 = 自报 + 协议上限，不是二选一**：

- **写死一个统一时长**必然二选一地错：一张五分钟的小单和一张跨窗的大单用同一个数——对小单太松
  （撞车窗口白开几小时），对大单太紧（正常干活被判过期抢单）。
- **纯自报**是给 AI 自己定及格线（`dao-legislation.md` 的两条否决项之一）：报 24h 谁都不会拒绝，
  于是退化成没有租约。
- ⇒ 认领方按活的大小自报 `N`，**`N` 有一个协议上限**。超上限的活，正确形态是**拆单**或**在租期内续租**，
  不是报一个更大的 `N`。
  **上限初值 8 小时、自报缺省 4 小时**，~~两个数都是 AI 自定、待用户拍板（阈值取值属判断档）~~
  **用户 2026-08-09 issue #70 追认为基线**（判据论证与数值本身一个字节未动，再动需新理由）。
- 🔴 **续租判据机器化（2026-08-09 issue #198 收紧，对抗 FAIL-4）**：判据是「本单**由当前持有人
  发出、最后一条格式合法的 `dao-claim:` 行**（格式见 §二、解析实现见 §六）」的 `createdAt`——
  ~~原判据「本单最后一条 dao 留痕评论」，且既有的三节点留痕（派单/交付/关单）与心跳对账评论
  只要落在这张单上就算续租~~ 这句在实现里等价于「最后一条评论，不管是谁发的、写了什么都算」
  （对抗实测：#193 上取到的是帅一句与认领无关的「收将挂账」评论），任何人的闲聊、机器人评论、
  甚至**别台机的 `dao-yield:`**，都会把一个已经死掉的租约续上——这正是本节开篇要治的锁死病，
  在实现层原样复现。**收紧后的代价**：三节点留痕/心跳对账这类纯散文评论，不再单独计入续租；
  真正持续在干活、只是没有重发认领的官，由下面「接管流程 step1」的**盘上真实活动检查**独立
  兜底（那一层查的是 commit/PR，本来就不依赖评论内容），不会被误判为可接管——续租判据变严不
  等于把这条防线撤了。临近租期上限时，持有人只需重发一条内容不变的 `dao-claim:` 即可续租，
  `createdAt` 由 GitHub 重新盖。

**过期 ≠ 可抢。** 过期只解锁「接管流程」，三步，缺一步就是抢单：

1. **先查盘上有没有活动**（那台机在租期内推过东西吗）：有活动 ⇒ 它没死、只是忘了续租 ⇒
   **不接管**，留一条「续租提醒」评论就走。
2. 零活动 ⇒ 留一条**接管评论**，独立成行的机器面格式（2026-08-09 issue #198 补，此前只有
   自然语言示例、没有可机器解析的格式，随本批一并补齐）：
   ```
   dao-takeover: <新机器名>/<新宿主> · 原认领 <旧机器名>/<旧宿主> 静默 <h>h（超自报 <N>h）· 盘上零活动
   ```
   `·` 前是机器可读字段（新持有人），`·` 后是人读详情（自由文本，写清楚接管的是谁、为什么）。
   **旧的认领评论一个字不动**——历史只增不改（dao.md `[#言-只读载体]`：不能被改的载体只能
   记录过去）；`dao-takeover:` 这一行**同时**让被接管那台旧机的所有旧 `dao-claim:` 退出 §四
   「当前有效认领」的比较，不需要旧机自己发 `dao-yield:`（见 §四）。
3. 接管评论落地之后才发自己的 `dao-claim:`。**`在途` 标签不摘也不加**——它本来就在，接管是换人
   不是换状态。

**谁可以摘 `在途`**：只有两种——①当前认领的那台机（销账/释放时，见第二节末「认领的单位」）
②走完上面三步的接管方。**第三方「顺手帮忙摘一下」是禁止的**：那恰好抹掉了唯一的撞车证据。

**拿不准就当它还被持有**（fail-safe 方向，代价不对称）：`gh` 跑不成、拿不到 `createdAt`、
认领评论格式看不懂 ⇒ **一律判「仍被持有」**。误判「可接管」的代价是两路白干加撞 PR；
误判「仍被持有」的代价只是这一轮少领一张单，而队列里还有别的单。**代价不对称，就往便宜那侧倒。**

### 四、两路同时认领谁让（冲突怎么解）

**先到者胜，判据是 GitHub 评论的 `createdAt`**（服务端时钟，两边共用），不是本地时间、不是谁手快。

- **认领之后必须回读一次**：`gh issue comment` 是 append——**两条认领都会成功、都不报错**，
  撞车在写侧**完全静默**，只有读侧看得见（同型：assignee 的加派也是 additive，两个人都会在上面）。
- 🔴 **回读发现有另一台机的「当前有效认领」`createdAt` 早于自己 ⇒ 自己让位**（2026-08-09
  issue #198 订正「当前有效认领」这个概念，对抗 FAIL-5）——~~原判据是「正文里任意一条
  `dao-claim:`」~~，这句在实现里会让**合法接管**的接管方一回读就误判自己该让位：第三节
  step2 要求接管时旧的认领评论一个字不动，于是单上同时存在两条 `dao-claim:`，而**死机那条
  更早**；`dao-yield:` 撤回之后，被撤回的那条 `dao-claim:` 若还被当「任意一条」计入，也会
  造成两台机相继让位的活锁。⇒ 判据改成只认**当前有效认领**，逐机器判定：
  🔴 **2026-08-09 issue #250 订正：下面三步里的「机」一律读作「机器 + 宿主」这个组合**
  （§二 已写明认领单位就是这两格）。原文写「某台机」「同一台机」，实现照字面只按机器名分组，
  于是同机的 cc 与 codex 被当成同一个主体——四种危险答案见本文件开篇五轮修法段。
  下面的字面**刻意不逐字改写**：它是 issue #215 那一批的原始表述，也是这条订正的出处，
  逐字改写会把"实现曾照着它跑偏"这条因果一起抹掉。读的时候按本行的口径读。
  1. 某台机最近一次发出的 `dao-claim:` 或 `dao-takeover:`，如果它之后**没有**再出现
     **同一台机**自己发的 `dao-yield:`/`dao-release:`，就是它当前的「有效认领」。
  2. 出现了 ⇒ 该机视为已放弃/释放，它名下所有认领（含被它接管掉的那条旧认领）**一并作废**，
     不再参与任何比较——`dao-takeover:` 除了是新持有人自己的一次有效认领事件，还会**同时**
     让被接管的旧机认领失效，不需要旧机自己发 `dao-yield:`；这正是堵住「合法接管后接管方对着
     自己刚接管掉的死机让位」的关键。
  3. 一台机自己发的 `dao-yield:` 会让它此前发的 `dao-claim:` **立即**退出比较——不需要等
     "对方下一次读到"，`dao-yield:` 生效的那一刻，回读就不该再把那条被撤回的 `dao-claim:`
     算作有效。
  ~~解析实现见 §六（`Get-EffectiveClaim`），FAIL-2 已验收样本与本定义共用同一套字段校验。~~
  🔴 **2026-08-09 issue #211 二轮对抗复核证伪（issue #215 追）**：上面这句不成立。
  **`Get-EffectiveClaim` 不是这个算法的实现**——它对全体标记只返回**全局最近一条**未撤销的
  `dao-claim:`/`dao-takeover:`，不区分「这是哪台机的」，做不到"每台机各自算出自己的有效认领、
  再互相比较"这一步（步骤 1）；它也**没有任何指名匹配**——判断一条旧认领是不是"被
  `dao-takeover:` 指名排除"（步骤 2），靠的完全是"它是不是全局最后一条"这个副作用，不是真的
  去查它有没有被点名接管过。两处后果都用改完的文档里逐字节提取出的函数原样跑合成序列坐实
  （`tests/dao-workitem-claim-protocol.tests.ps1` 场景 5 G3/G4 锁定当前的真实返回值）：
  两台机各自持有未撤销认领时（A 先认领、B 后认领），函数只报出较晚那一条（B）——A、B 各自
  拿这个值去跟自己比较时，**谁都判不出"该我让位"**，两边都留着各干各的，正是本节开篇要防的
  撞车原病；被接管的死机若在接管完成之后又发一条新的 `dao-claim:`，函数会把这条"醒过来的
  死机"重新判成当前有效认领（应为新持有人）。上面步骤 1-3 描述的仍是**设计意图**，不是
  "已实现"的陈述——**FAIL-2 的字段校验部分是真的共用**（那部分是"独立成行 + 字段合法"这道

  没有对应代码。真正的算法修法（`Get-EffectiveClaim` 需要按 host 分组、为每台持有未撤销认领
  的机器各自算出一条有效认领、并真正记住哪些 host 被 takeover 指名接管过）归 issue #215，
  合并前只做这一处文字改真，不在合并压力下抢修。

  为每台持有未撤销认领的机器各自算出一条有效认领（返回 Hashtable，不再是单值）；`Get-DaoMarks`
  新增从 `dao-takeover:` 人读详情里抓「原认领 <旧机器名>/<旧宿主>」，被指名的旧机在
  `Get-EffectiveClaim` 里整台除名（含它此后再发的任何 claim——简化处理，不支持"旧机重新走一遍
  认领流程合法复活"这个未定义的边界）。解析实现见 §六；回归网场景 5（原 G3/G4 缺陷锚点）已
  翻转为正例断言，新增三方场景与单条-claim 边界（G9）。**这是新实现，尚未经过独立对抗复核**
  ——判据类改动铁律是先过对抗验证官再合并，复核结论落地前请把这段读成「已提交修法方案」而不是
  「已验证修好」（dao「撤宣称不抢修」的另一半：这次不是撤宣称，是真的在做，但"做了"与"验过"
  仍是两件事）。
  找到「别台机的当前有效认领」且它早于自己时，发一条 `dao-yield:` 撤回自己的认领
  （独立成行：`dao-yield: <机器名>/<宿主>`），**不摘 `在途`**（那是先到者的），换下一张单。
- **同一秒的平局**要有一个不依赖时钟的确定性规则，否则两边同时让位（活锁）或同时不让（撞车）：
  **比机器名的字典序，小者胜**（这条规则现在只在「双方都是合法字符集的当前有效认领」范围内
  比较，占位符 `<` 之类的幽灵已经在字段校验那一关被排除，不会再进到这一步的比较）。

### 五、与既有 `在途` / `接力` 怎么共存不混淆

- **`在途` 语义一个字不改**（它已有的定义就是「已派 agent 在干，交付后摘掉」）。本节只给它补两样
  它此前没有的：**详情层**（谁/哪台机/何时）与**过期判据**。
- **别新建 `认领中` / `机器A` / `机器B` 之类标签**：`labels.json` 的状态维已经写明「只保留 `在途`
  一个——其余状态归看板列，**别用标签复刻看板**（双份必漂移）」。同一个理由在这里更强：
  每台机一个标签会随机器增减而漂移，而**机器名住在评论里是自描述的**，加一台机零改动。
- **`接力` 标签不参与认领**：它是每仓恰一个的常设单、没有关闭条件，认领它没有对象。
  反过来它要多装一格：**上一窗收在哪台机上**——让 `/dao-resume` 一眼看出接的是不是自己这台机的活。
- **`/dao-resume` 第 1 步筛出的 `在途` 单要逐单看机器名**：别人机器的单**只报不接**（那一步的读法
  已在 `ccswitch/commands/dao-resume.md` 同步）。

### 六、实操（PowerShell 5.1 实跑过，含三个实测坑）

```powershell
# ① 领活队列：把被认领的单摘掉（用 GitHub 搜索语法，不经 jq）
gh issue list --state open --search "label:任务 -label:在途" --json number,title --limit 50

# ② 认领 = 评论 + 标签（正文先落文件再 --body-file，禁经 PowerShell 字符串）
gh issue comment <n> --body-file _tmp/claim-<n>.md      # 独立一行 `dao-claim: <机器>/<宿主>/<N>h`
gh issue edit <n> --add-label 在途

# ②.5 合法机器标记行解析（③④ 共用，2026-08-09 issue #198 新增，堵 FAIL-2/4/5 三处洞；
#     2026-08-09 issue #215 批追加 CRLF 归一化 + takeover 旧机字段解析 + session/hours 透传）
#     只认"独立成行、字段合法"的 dao-claim:/dao-yield:/dao-takeover:/dao-release:，
#     裸标记（无字段）、混进散文/表格、占位符 <> 一律不命中——机器判据，不靠"写的人小心"。
function Get-DaoMarks {
    param([string]$Body)
    $Body = $Body -replace "`r", ''   # CRLF 归一化（issue #215）：收尾锚点 `[ \t]*$` 认的是
                                       # LF 语义，`\r` 留在行尾会让整行连"独立成行"这一关都过不去；
                                       # 真实输入 gh api 是 LF 故未爆，Windows 侧任何带 \r\n 的输入源
                                       # 会静默漏识别——split/正则匹配前先把 \r 扫平，不留到下游。
                                       # ⚠️ 这一步是**删除**不是**转换**：纯 CR（无 `\n` 伴随，老 Mac
                                       # 风格分行）的输入不在射程内，见下方 435 行订正（PR #240 对抗复核实测）
    $out = @()
    foreach ($m in [regex]::Matches($Body, '(?m)^`?dao-(?<kind>claim|yield|takeover|release):(?<rest>[^\r\n`]*)`?[ \t]*$')) {
        $rest = $m.Groups['rest'].Value.Trim()
        if (-not $rest) { continue }                        # 裸标记（如 `dao-claim:` 不带字段）⇒ 不算；
                                                              # 下面的字段数校验对空 rest 同样会拒（split
                                                              # 空串恒得 1 段），这行是提早退出、不是唯一
                                                              # 防线——归因订正见 F7（issue #215）
        $head = $rest; $tail = ''; $dot = $rest.IndexOf([char]0x00B7)    # · 之后是人读详情
        if ($dot -ge 0) { $head = $rest.Substring(0, $dot).Trim(); $tail = $rest.Substring($dot + 1) }
        $f = @($head -split '/' | ForEach-Object { $_.Trim() })
        if ($f.Count -lt 2 -or $f[0] -notmatch '^[A-Za-z0-9][A-Za-z0-9_-]{0,62}$' -or $f[1] -notmatch '^[A-Za-z0-9_-]{1,20}$') { continue }
        $kind = $m.Groups['kind'].Value; $ok = $false; $session = $null; $hours = $null; $oldHost = $null; $oldRuntime = $null
        switch ($kind) {
            'claim' {
                if ($f.Count -eq 3 -and $f[2] -match '^[1-9][0-9]?h$') { $ok = $true; $hours = $f[2] }
                elseif ($f.Count -eq 4 -and $f[2] -match '^[A-Za-z0-9_-]{1,16}$' -and $f[3] -match '^[1-9][0-9]?h$') { $ok = $true; $session = $f[2]; $hours = $f[3] }
            }
            'takeover' {
                if ($f.Count -eq 2) {
                    $ok = $true
                    # F2 修法（issue #215）：从人读详情里抓"原认领 <旧机器名>/<旧宿主>"——§三 step2
                    # 的固定模板，是唯一能拿到"谁被排除"的地方（机器面本身只有新持有人两格）。抓不到
                    # 就留 $null，Get-EffectiveClaim 对 $null 不做排除——宁可漏排除也不误排除，与 §三
                    # "拿不准就当它还被持有"同一个 fail-safe 方向。这段依赖的是人读自由文本的具体措辞，
                    # 与 F5（`·` 分隔符本身非 ASCII）同一族脆弱性，未在本批范围内加固。
                    $om = [regex]::Match($tail, '原认领[ \t]+(?<h>[A-Za-z0-9][A-Za-z0-9_-]{0,62})/(?<r>[A-Za-z0-9_-]{1,20})')
                    if ($om.Success) { $oldHost = $om.Groups['h'].Value; $oldRuntime = $om.Groups['r'].Value }
                }
            }
            default { if ($f.Count -eq 2) { $ok = $true } }  # yield/release 只要求 机器/宿主
        }
        if ($ok) { $out += [pscustomobject]@{ kind = $kind; host = $f[0]; runtime = $f[1]; session = $session; hours = $hours; oldHost = $oldHost; oldRuntime = $oldRuntime } }
    }
    return $out
}

# ③ 回读核撞车：逐机器各自算出"当前有效认领"，不是正文里任意一条 dao-claim:
#    （FAIL-2/5 修法定义见 §四；F1/F2 算法修法与局限见 §四 结尾订正，issue #215）
$c = (gh issue view <n> --json comments | ConvertFrom-Json).comments
$marks = @()
foreach ($cm in $c) {
    foreach ($mk in (Get-DaoMarks -Body $cm.body)) {
        $marks += [pscustomobject]@{ createdAt = $cm.createdAt; kind = $mk.kind; host = $mk.host; runtime = $mk.runtime; session = $mk.session; hours = $mk.hours; oldHost = $mk.oldHost; oldRuntime = $mk.oldRuntime }
    }
}
$marks = @($marks | Sort-Object createdAt)
@($marks | ForEach-Object { "{0}  dao-{1}: {2}/{3}" -f $_.createdAt, $_.kind, $_.host, $_.runtime })   # 人眼复核用，全量列出

function Get-EffectiveClaim {
    <#
      "当前有效认领"算法见 §四——F1/F2 修法（issue #215）+ 分组粒度修法（issue #250）：
      按「机器 + 宿主」分组逐桶判定（§二 写明认领单位就是这两格），被 dao-takeover: 指名
      接管过的那个旧桶除名（含它此后再发的任何 claim，简化处理：不支持"旧桶重新走一遍认领
      流程合法复活"，那条边界未做设计评审，照直写不是已经想清楚）。返回 Hashtable：
      key=`<机器名>/<宿主>`，value=该桶当前有效认领（$Marks 里的原始元素）。"谁该让位"是
      调用方拿这份逐桶结果自己做的比较（用法见下），本函数只答"每个桶各自有没有、是哪一条"。
      🔴 **分组键含 runtime 是 issue #250 的修法**，只按 host 分的旧版实测四种危险答案：同机
      另一个宿主的 dao-yield: 会把自己的 claim 一起杀掉、两个宿主各认领一次会挤进同一个桶由
      后发的覆盖先发的、接管指名 BOXA/codex 时 BOXA/cc 连坐除名、以及 §六 命令③ 用 $MyHost
      单键查出同机另一个宿主的认领并当成自己的（跨宿主冒领续命）。`/` 直接做分隔符是安全的：
      §二 的字符集把 `/` 挡在机器名与宿主两格之外，拼出来的 key 反解唯一。
      除名要 oldHost 与 oldRuntime **两格都在**才生效——缺一格不除名，宁可漏排除不误排除，
      与 §三"拿不准就当它还被持有"同一个 fail-safe 方向。
    #>
    param($Marks)
    $excluded = @{}
    foreach ($mk in $Marks) {
        if ($mk.kind -eq 'takeover' -and $mk.oldHost -and $mk.oldRuntime) { $excluded[('{0}/{1}' -f $mk.oldHost, $mk.oldRuntime)] = $true }
    }
    $eff = @{}
    foreach ($k in @($Marks | ForEach-Object { '{0}/{1}' -f $_.host, $_.runtime } | Select-Object -Unique)) {
        if ($excluded.ContainsKey($k)) { continue }
        $own = @($Marks | Where-Object { ('{0}/{1}' -f $_.host, $_.runtime) -eq $k })
        for ($i = $own.Count - 1; $i -ge 0; $i--) {
            if ($own[$i].kind -notin @('claim', 'takeover')) { continue }
            $laterRevoke = @($own | Select-Object -Skip ($i + 1) | Where-Object { $_.kind -in @('yield', 'release') })
            if ($laterRevoke.Count -eq 0) { $eff[$k] = $own[$i]; break }
        }
    }
    return $eff
}

function Test-IsMySessionClaim {
    <#
      issue #215-F3 完整版：$my 是 Get-EffectiveClaim 返回值里某个「机器/宿主」桶的当前有效
      认领，本函数判断它是不是"我这个会话"发的，还是同机同宿主另一个并发会话发的——这是
      dao-resume.md「先比对会话 id 是否一致再判是不是自己的单」缺的那个实现路径。
      §二「认领的单位是「机器 + 宿主」」那一条：认领单位不是单个会话，所以本函数**不改变**
      Get-EffectiveClaim 的分组/碰撞判定本身（那是跨桶比较，看谁的 createdAt 更早）——分组键
      已由 issue #250 扩成 `<机器名>/<宿主>`，本函数没参与那次改动，也不再往 session 拆细。
      本函数答的是另一件事："这条已经确认属于我这台机+宿主的有效认领，到底是
      不是我自己这个会话留下的"，只有 /dao-resume 这类"是不是我自己前任"的场景需要问这件事。
      返回 $true = 判定为"是我自己的"（含 $my/$MySession 任一没有会话 id 的旧行为：没有数据
      可比时不拦，向后兼容单会话场景——这正是本节末㈩弱处照直写的那半"忘记填仍退回旧行为"）。
      返回 $false = 两边都填了会话 id 且不一致 ⇒ 判定为"同机同宿主的另一个并发会话"，或 $my
      本身是 $null（没有有效认领，谈不上是不是我的）。
    #>
    param($my, $MySession)
    if (-not $my) { return $false }
    if (-not $my.session -or -not $MySession) { return $true }   # 任一没填 ⇒ 无数据可比，按旧行为放行
    return ($my.session -eq $MySession)
}

$eff = Get-EffectiveClaim -Marks $marks    # Hashtable：key=<机器名>/<宿主>，value=该桶当前有效认领
$MyHost = '<机器名>'                        # 本机 hostname（同 §二 判据），跑之前自己填
$MyRuntime = '<宿主>'                       # 本会话的 AI 宿主（cc / codex，同 §二 认领单位第二格）
$MySession = '<会话短id>'                   # 本会话自报的短 id（同 §二 格式），单会话场景留空
$MyKey = '{0}/{1}' -f $MyHost, $MyRuntime   # issue #250：查自己那个桶要连宿主一起查。只用
                                            # $MyHost 单键查，查到的可能是同机另一个宿主的认领，
                                            # 而下游会把它当成自己的（B3 跨宿主冒领）
$my = $eff[$MyKey]
$others = @($eff.Keys | Where-Object { $_ -ne $MyKey } | ForEach-Object { $eff[$_] } | Sort-Object createdAt)
if ($my -and $others.Count -gt 0 -and $others[0].createdAt -lt $my.createdAt) {
    # 别的「机器+宿主」有一条比自己更早的有效认领 ⇒ 自己让位（§四 判据），发 dao-yield: 撤回
    # 「别的」含**同机另一个宿主**：同机 cc 与 codex 各干一遍同一张单，正是本协议要防的原病
}

# ⑦ /dao-resume 用：这条 host 的有效认领是不是"我这个会话"发的，而不是同机同宿主的另一个
#    并发会话（issue #215-F3 完整版，dao-resume.md「先比对会话 id」的实现路径——见 Test-IsMySessionClaim 头注）
if ($my -and -not (Test-IsMySessionClaim -my $my -MySession $MySession)) {
    # 会话 id 都有值且不一致 ⇒ 这是同机同宿主另一个并发会话的认领，不是我自己前任留下的——
    # 按 dao-resume.md 判据"只报不接"；不要走上面 ③ 的"该我让位"逻辑（那是跨机器碰撞判定，
    # 这里问的是"这条已确认属于我的有效认领，是不是我自己发的"，是两件不同的事）
}

# ④ 租约还剩多久：只认"当前持有人自己"最后一条 dao-claim:，不是最后一条评论（FAIL-4 修法）
#    F1 修好后"当前持有人"天然就是"自己"（$MyHost/$MyRuntime）——不再依赖一个全局 $effective.host
#    issue #250：这里的过滤同样要带 runtime。只按 host 过滤时，同机另一个宿主刚发的 claim 会被
#    当成自己的续租锚点，租期从别人那条算起——实测形态 A3 的后半（自己的租约凭空延长/错位）
$holderClaims = @($marks | Where-Object { $_.kind -eq 'claim' -and $_.host -eq $MyHost -and $_.runtime -eq $MyRuntime })
$last = ($holderClaims | Select-Object -Last 1).createdAt
[math]::Round(([datetimeoffset]::UtcNow - [datetimeoffset]::Parse($last)).TotalHours, 2)

# ⑤ 接管前的盘上活动探针（两条独立路，都不精确，见下）
$prs = gh pr list --state all --json number,body,updatedAt,headRefName --limit 100 | ConvertFrom-Json

git log --all --since="<N> hours ago" --format="%h %ci %s"

# ⑥ 释放 = 评论 + 摘标签（独立一行 `dao-release: <机器>/<宿主> · <原因>`）
gh issue comment <n> --body-file _tmp/release-<n>.md
```

**三个实测坑，照直写**：

- 🔴 **jq 表达式里的双引号在 PowerShell 5.1 下会被静默吃掉**：`-q '… index("在途") …'` 到了
  `gh` 那边成了 `index(在途)`，报 `failed to parse jq expression`。三条出路——①改用 GitHub
  搜索语法（`--search "-label:在途"`，上面 ① 用的就是它）②把双引号转义成 `\"`
  ③`ConvertFrom-Json` 后在 PowerShell 侧过滤（上面 ③ 用的是它）。**机器面标记全用 ASCII
  就是为了绕开这一格。**
- ⚠️ **⑤ 那个活动探针是近似，两个方向都有反例**：`gh pr list --search "<n> in:body"`
  会命中正文里任何含这串数字的 PR（实测：查 `193` 命中了一个 body 里写着 `-25,193` 字节数的
  旧 PR），故上面改成 PS 侧按 `#<n>` 边界匹配；反方向也漏——**官还没推任何东西时，
  它活着也测不出来**。⇒ 探针零命中**不构成「那台机死了」的证据**，它只是接管的必要条件之一。
- 🔴 **`Get-DaoMarks` 的判别力已用真实语料验过，验收样本记在这里，别再重新发明**（2026-08-09
  issue #198）：#193 评论 1（真实认领评论）里，`<details>` 折叠段引用了一句「首行那个
  `` `dao-claim:` ``」——裸标记、没有任何字段。字段校验要求 `host`/`runtime` 都非空且合法，
  这条裸引用直接被拒，`Get-DaoMarks` 对整条评论只返回 1 个命中（真认领本身），**不依赖
  "只取第一条"这种实现侥幸**——就算改成扫全部命中（`[regex]::Matches` 本来就是全量扫），
  裸标记也进不了结果集。占位符幽灵（`<机器名>`/`<宿主>`/`<N>h`）与止血复发的第三条幽灵
  （机器名是一个单引号 `'`）同样因为 `host` 字段的字符集校验被挡在外面——这三类是 PR #195
  对抗复核实测过的全部已知幽灵形态，逐条验证脚本见本 PR。
- 🔴 **`Get-DaoMarks` 对 CRLF 输入不健壮，已修（issue #215）**：收尾锚点 `[ \t]*$` 按 LF 语义写，
  行尾带 `\r` 时整行连"独立成行"都过不去，字段校验把真认领挡掉（合并链实拦发现：CRLF 检出的
  测试 fixture 命中 0 条）。真实输入 gh api 是 LF 所以线上未爆，但 Windows 侧任何带 `\r` 的
  输入源（本地编辑器粘贴、某些 git 配置下的 checkout）都会静默漏识别，且是**危险方向**——
  认领消失比认领误报更糟（fail-open，与 §三 fail-safe 原则相反）。修法是 split/正则匹配前
  在函数入口 `-replace "`r", ''` 扫平所有 `\r`。~~不只 `\r\n`，裸 `\r` 也一并处理~~
  **订正（PR #240 对抗复核实测证伪）**：`-replace "`r", ''` 是**删除**不是**转换**——碰到
  `\r\n` 时删掉 `\r` 剩下 `\n`，行分隔关系不变，这一种确实处理对了；但碰到**纯 `\r`
  分行**（老 Mac 风格，行与行之间没有 `\n`）时，删除 `\r` 会把原本几行的内容**接成一整行**，
  认领反而更找不到（实测：`"…\rdao-claim: LONECR/cc/4h\r…"` 命中 0 条）。**实况是**：这一步
  只真正处理 `\r\n`，纯 CR 分行的输入不在射程内。要真兑现"裸 `\r` 也处理"，需要写成
  `-replace "`r`n", "`n" -replace "`r", "`n"`（先收敛 CRLF，再把剩下的裸 `\r` 转成 `\n`
  而不是删掉）——本次只订正文字，未改代码，纯 CR 分行场景不在当前实现的覆盖范围内。
