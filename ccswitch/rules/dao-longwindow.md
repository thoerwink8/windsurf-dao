## 一 · 开窗节（只在开窗那一刻用，逐条走一遍）

- **长窗自主排程**（用户拍板 2026-07-17：无明确目的的长窗，帅自主判断现状定任务，直到满足时长）：
  ①**开窗仪式**：设心跳（见 §心跳对账节 · 甲「长窗防停摆四层」①）→ **cron 常驻心跳兜底**（`[dao-heartbeat]` cron，session-only、每次开窗重建，与限流探针 cron 重建同一动作——两者都是 session-only、会话一断就得重设；⚠️ **间隔取值是判断档（命中 `dao-legislation.md` 否决项①「几条/多久算够」），此处 15 分钟档由 AI 自定、待用户拍板**——试点数据出处 issue #194 评论：**同一条**评论记录两发唤醒相隔 ~45 分钟（不是「两条评论」），均签名通过、载荷完整，这只支撑"cron 这个形态可行"，**不支撑"15 分钟"这个取值本身**（45 分钟间隔答不出"每小时 4 轮"的算术宣称，那是推算不是实测）；与 ScheduleWakeup 并行期间 **n=2，armed 态查不到，干扰与否未测**）→ TaskCreate 台账 → 输出**开窗报告**（现状分析→拆解→时长预算）；**台账时刻以 ScheduleWakeup 返回的实时为唯一锚，禁凭批次进度推算**（出处：叙事 N2）。
  ②**选题判断框架**（不是搬 TODO 清单）：先判健康期还是病期（体检/CI 红着→先修敌；干净→建设）；建设期按价值排序——**越晚越贵优先**（发布基建/账实对齐/CHANGELOG/教训沉淀）＞**基建刚铺完趁热件**＞**已定夺纯执行件凑小件批**＞一般候选按价值密度（竞品痛点/dogfood 高频；有项目侧 `docs/POSITIONING.md` 则以支柱图为镜）。
  ②.5**外向汲取（常态四源 + 见底兜底）**（用户拍板 2026-07-22 立、2026-07-27 扩为常态）：**外部输入是常态不是偶发**——用户原话「不断汲取网上最佳实践和 e2e 发现卡点和竞品优秀的地方抄袭和竞品评论区 or 社媒用户真实痛点」。**四源**：①**业界最佳实践**（做技术/交互决策前先查业界怎么做，不闭门发明）②**e2e 卡点**（自己端到端跑一遍，记「卡在哪」而不只记通过/失败）③**竞品优秀处**（学形态与信息架构；**读源码不禁**——版权保护表达不保护思想，读源码失去的只是「我从没看过」这一抗辩；但 **AI 读完不会像人那样自然模糊**，故实现期强制隔离：读→写自然语言原理笔记→**基于笔记实现不对着源码写**→自查命名结构无雷同；派单时由帅读完写笔记给官，不让官边读边写。绝对红线：不复制代码片段/注释/独特命名/文件结构。细则与许可证分级见 playbook）④**竞品评论区与社媒真实痛点**（GitHub issues / HN / Reddit / 社媒 / 应用评论区）。**常态化靠挂在必经动作上**（按遵守率实证，无标记时刻的自由裁量必失效）：用户面功能批**派单契约门**须附「外部参照三问」——竞品同面形态 / 业界最佳实践 / 用户真实痛点，各一句话+出处，查了没有就显式注「无先例」，**不许留空**；**dogfood 收尾**须记卡点清单；**见底前**再兜底扫一遍未消费源。入池一律过分层读（bug 近字面采信 / 功能请求处方可疑痛苦真实）+ 场景归因。**⚠ 四源皆「有声的加法源」，须配两个反向源**（2026-07-27 帅补，用户认可）：**⑤减法自问**——四源只说该加什么，与「为道日损」相冲，功能越多越难打磨；每批须问「这批之后有什么该删/该合并/该默认关掉」；**⑥无声失败扫描**——无障碍/边界数据量/极端环境的受害者不发声直接走人，竞品也常同样忽略、照抄照不到；且 e2e 由熟练者跑，**跑不出新手会卡的地方**（结构性盲区，近似解：专看竞品新用户抱怨 + 刻意以「第一次见」走首启链路）。豁免：无同类竞品 / 病期救火窗 / 短窗（<4h）。细则见 `docs/playbooks/outward-loop.md`。
  ③**问题树而非时间表**（用户 2026-07-27 亲纠，推翻原「时长换算容量」公式）——三条判据：
  　㈠**禁止给方向/任务预分小时数**（伪精确，且到点就切换 ⇒ 挖到一半的问题被搁置、新冒出的问题无处可放）。正解：**列大方向 → 每个方向钻到底 → 子问题拆到能解决为止 → 过程中的新发现挂回同一棵树**；完成判据是「该方向的树清空了」，不是「到点了」。
  　㈡**承接物按项目形态两态取一，都不是可选项**——**GitHub-backed** 走 dao.md 知识归位节的「工作项三态归位」（issue 区=分配中心 + 看板=观测中心）；**非 GitHub / 本地仓**留**问题树面板型仓内文件**兜底（项目侧 `docs/ops/WORKBOARD.md` 型：方向 / 子问题 / 🆕过程新发现 / ⏸挂账含解冻条件）。**没有承接物，「不搁置」就是空话**。
  　㈢**别把开工时段塞到没有交接余量**（收官要做 dogfood/欠账/总账/回归）——这一条是防塞满不是排期。**⚠️ 错法标记（2026-07-30 用户订正）：原写「窗口末段留 ~25% 给收官」已证伪**，那是把收官切进了报出去的时长里；收官在派单窗**之后**独立进行（判据见 ④.5①），故此处不给收官切窗内比例，只要求留余量。
  　**收官段必跑一次好实践收割**（`dao-harvest` workflow，用法与三判据见 `ccswitch/workflows/README.md`）：坏经验有天然触发器（出事了/返工了/被骂了），**好经验没有**；收官是长窗里唯一必经的「停下来」时刻，**这是收割的唯一触发点**。落地形态是收官简报里的两个固定槽位（简报铁序见 ③.5），原样写这两行：`🌾 收割：已跑（候选 N 条 / 入库 M 条 / 落点 <文件>） | 未跑（<一句理由>）`；`♻️ 整编：已跑（建议 N 条 / 采纳 M 条） | 未跑（<一句理由>）`——两行各自两态恰选其一，**都没有第三态**；简报缺任一行视同收官未完成（`♻️ 整编` 槽位为用户 2026-08-09 #70 一揽子拍板 J4 件新增，与 `🌾 收割` 并列，对应 `dao-consolidate` workflow——收割的减法对偶，用法见同一份 `ccswitch/workflows/README.md`）。**通用形态**：机器报事实（上次收割/整编在哪、此后发生了什么），人判该不该做——别让机器替人判「该做一件需要判断的事了」，那会逼出为过闸而敷衍的执行。改判的代价与它依据的 719/719、68/68 形态学证据：出处 叙事 N11。
  ③.5**收官简报四条铁律** —— 正文见本文件 **§心跳对账节 · 乙**（射程是每一轮而非只在开窗那一刻，故编在心跳节；出处：叙事 N3）。
  ④**时长循环**：授权的是**时长**不是批次——每批收官后核对剩余时长：≥1 批容量回②再排；<1 批但≥30 分钟填充短活；接近零才真收窗（出处：叙事 N4）。禁止「计划完成=窗口完成」的单方面提前收窗。
  ④.5**截止是三段不是一刀**（2026-07-30 用户点名立：「8 点截止了，应该要把手头的任务全干完才截止」）：**「到点」管的是「不再开新的」，不管「已经在跑的」**——一个已派出去的官正在烧真机、烧编译、烧额度，到点掐掉它等于**把已付出的成本全额作废**，而它往往只差最后一步（同窗实证：某官被判失联后又活了、跑完 8.7 小时交回本窗最有价值的一组数据；若准点收窗即全丢）。⇒ 三段：
  **① 软截止 = 你报出去的那个结束时刻本身，不是它的 75%**（2026-07-30 用户订正，原文写「约 75%」已证伪）：用户原话「**12h 指的是派单到早上 9:16，然后收官到任务全结束**」⇒ **对外报的窗口时长量的是「能开工的时段」，不是「从开窗到收摊的总时长」**。报「21:16 → 次日 09:16 的 12h 窗」，意思就是 **09:16 之前都可以派新活**，09:16 那一刻**停止派新活**、此后只收在跑的；**收官段在 09:16 之后继续，直到任务真结束**——它不占用报出去的那 12 小时。**错法（本窗实犯）**：把 09:16 当成「全部结束」，于是倒推 06:16 起进收官 ⇒ **凭空吃掉 3 小时开工时间**，而用户从没同意过那个扣除。**判据一句话：报出去的那个数，是「开工到几点」，不是「几点关灯」。**
  到点这一刻必须做一次**显式盘点**并写进台账——每一路的**预期交付物**与**兜底方案**各一行（凭印象对账在本窗实测失败多次：心跳载荷写「零路在跑」而实际有一路，因为载荷是设心跳那一刻写的）。
  **② 收官段与「收在跑的官」并行，不排在它后面**——收官大部分是文档动作（收割/HANDOVER/账本/拍板），不抢编译与真机资源。**串行是上一窗收官段整段消失的直接原因之一**：在跑的官把时间吃光，收官就没了。
  **③ 硬截止：两边都收完才停。** 在跑的官若超时未交付 ⇒ 走 §心跳对账节 · 甲②的失联流程（**先查环境终态再判死，判死后盘它已产出的部分接手**——接手也算「干完」，本窗实测那位官已把最难的部分做完只差最后一步，帅用它写的探针跑完即得数据）。
  **⚠️ 唯一的硬边界是「不再开新的」，它不容协商**：否则「把手头干完」会退化成无限延窗——问题树永远清不完，而每收完一批都会冒出新发现（这是问题树工作法的正常性质，不是异常）。**判据一句话：到点之后，允许收尾，不允许开工。**
  ⑤**自主边界（永不进自主窗）** —— 正文见本文件 **§心跳对账节 · 丁**（硬边界，射程是整段工期而非只在开窗那一刻，故编在心跳节）。
  ⑥**双档模式**（用户拍板 2026-07-21）：**标准档**（「自主任务 X 小时」）帅调度/单官或少量并行/成本门正常；**高性能档**（「高性能自主任务 X 小时」）多路 fan-out 默认化——调研审计评审走 workflow 舰队+对抗验证、实现件尽量并行拆官、验证升双验证官、成本门免除。**档位识别按语义不按口癖**：出现「高性能/放开用量/额度用不完/多开子代理/上 workflow/全力/舰队」任一语义，或处于用户先前放量授权期内 → 高性能档；无信号 → 标准档；拿不准 → 开窗报告首行声明档位。
  ⑥.5**窗界维度：时长窗 vs 目标窗**（用户提议入体系 2026-07-31；与⑥的档位正交，业界对应 goal-driven autonomy vs timebox）：授权语含「X 小时」⇒ **时长窗**（④/④.5 原样生效）；含「直到完成 / 直到达成 / 改无可改 / 无限深推 / 你认为完成为止」类语义 ⇒ **目标窗**——边界不是时刻，是**目标闭包**。两者可叠加（「8 小时内尽量做完」＝时长封顶的目标窗，先到者为界）。**目标窗三则**：㈠**收窗判据**＝问题树清空，或剩余项**全部挂账且每笔带解冻条件**（「证明此路不可达+写明何时可达」也是达成，停在半路不是），或触及 ⑤ 自主边界/🔒 门控；**没有「到点」这回事**。㈡**迷宫求解**（用户原话「像解决迷宫一样」）：遇阻**先绕**（换手段，继承反者道之动「败二即换」）；绕不通**回退**（撤当前支线走另一支，撤销留痕）；全支不通**挂账**（解冻条件必填）——**停摆不是四个动作之一**，防停摆心跳原样生效。㈢**防无限延窗的对应物**：④.5「不再开新的」在目标窗读作**树外不开新方向**——过程中的新发现挂回树内才做，树外的记候选不追（否则目标闭包被新发现无限撑大，目标窗退化为永动窗）。[基线:2026-07-31 首窗即含完整实例——L0-L3 四层推进中 L2 撞 GitHub 授权墙，绕路判无意义→回退挂账 #410 带解冻条件→继续推其余层，「挂账也是达成」当场演示] [#窗-目标闭包]
  **会话形态定稿**：几周级任务的正确形态是短会话接力（窗 1-2 天）+ HANDOVER 交接，不是不死的长会话（compaction 有损不可消除，见叙事 N8）。开窗模板固定三件：上批清偿件为本窗复审强制靶 / 心跳固定问句「剩余时长 vs 批容量」/ HANDOVER 必读必写。**接力/恢复的会话不经过①开窗仪式**——cron 兜底是 session-only，上一个会话建的不会跟着接过来；若接力后要续用长窗自主排程，接力单读完后补跑一遍①（至少把 cron 重建那一步单独做一次），否则这一路兜底在新会话里从头到尾都不存在而不自知。

  🔴 **会话长度硬判据（P7，2026-08-01 由「偏好」升「判据」）**——升格理由不是又一次踩坑，是**外部实证**：`arxiv 2605.10039` 测遍各种干预后，**会话进程（session progress）是唯一显著的遵守率杠杆**（每多一个函数 -5.6 个百分点），而**规则文件的大小、位置、措辞强度均无显著影响**。⇒ 「会话短一点」这件事，其效力量级高于本文件里绝大多数条款；把它留在「偏好」层是错配。**同时这条自己也是那条规律的实例**：它想治的病（窗开太久 ⇒ 什么都开始滑）**恰恰会让读它的人先滑掉它** —— 所以它不能是一句提醒，必须是一个槽位。

  **落地形态 = 收官简报里的一个固定槽位**（槽位档，同 `🌾 收割` 那一行；本仓最强实测正例 `[cc]` 前缀 719/719、subagent 身份铁律 68/68 皆为槽位档）。窗末简报原样写这一行，**两态恰选其一，没有第三态**：

  ```
  🔄 会话接力：建议收窗交接（本窗已合 PR <n> 个 / 已开窗 <h> 小时，达阈值）  |  可续窗（<n> 个 / <h> 小时，未达阈值）
  ```

  ⚠️ **阈值取值是判断档，此处初值由 AI 自定、待用户拍板**（按 dao.md 反·归「谁来定这条规矩」，「几个算够」命中否决项①「给 AI 自己定及格线」）。**槽位形态本身是照做档**（写简报时那一行的位置就在眼前，零现场判断），故形态先行、数字待裁——两半分开落，不因数字未定就把整条挂起。 [n=0 @08-01 触发:完成流水线③] [自定@08-01] [基线:mousse-cli 2026-07-26..08-01 七窗实测每窗合并 PR 数 25/42/21/13/23/53/17，中位 23；取 25 回测 **3/7 窗**触发（07-26/07-27/07-31）——刻意不取中位数，取中位会让它每窗都响、随即被当背景噪音无视（同「生下来就吵的检查一定会被静音」）。**「触发之后接不接力」零实测**，本条只证明阈值不会常响，不证明它选得对] [#窗-接力阈值]

### 甲 · 长窗防停摆四层（出处：L25）

核心原则——**监督信号必须独立于作业信道**，只靠 task-notification 驱动、任何一路 subagent 沉默即饿死整窗。

①第一动作设 ScheduleWakeup 心跳（高性能档 900s、标准档 1200-1800s；盘点在途→悬挂介入→无事推进下批→用户接管且无欠账即 stop）+ **cron 常驻心跳兜底**（`[dao-heartbeat]` cron，session-only，见一·开窗节①）——两路都是"监督信号独立于作业信道"的实例：殿后心跳（见 §乙）若因限流/API 错/工具报错/用户打断而没调成，简报已发但零 armed——cron 兜底**设计目标**正是把这种窗口唤回；⚠ 该救回路径**零实测**（#194 试点两发均落在正常轮，「截断后被 cron 救回」尚无样本，与 LW-2 同族待观测），已实测的只有「cron 在正常轮照常入队」。
②等待超时降级交付+后台验证主动轮询到终态（armed 不算主动，出处：叙事 N5，条款详见项目侧 `docs/rules/dispatch-clauses.md` 通用节）。
③在途任务 TaskCreate 登记，心跳醒来先对账不凭印象。
④派单后逐路抽验 worktree 基点（`merge-base` = main tip，旧基点先 merge 再开工，出处：L24）。

### 乙 · 收官简报四条铁律（先行铁序 / 预记禁令 / 循环存续铁律 / ~~三明治规则~~ **殿后铁律**，出处：叙事 N3）

**2026-08-09 订正（对抗复核 PR #208）**：「殿后铁律」取代的是原「三明治规则」——旧规则要求 ScheduleWakeup 后**必须**另有工具调用（心跳被夹在中间），issue #194 实测证明宿主不允许这个形态（心跳一返回轮即终结）；新规则反过来，心跳是轮的**殿后**动作。名字变了是因为内容被反转了，不是措辞润色。

窗末简报必须**先于**心跳设置、作为独立完整消息发出，ScheduleWakeup prompt 只准写未来动作不准预记「已发」；~~以 ScheduleWakeup 收尾的轮视为该轮未发简报，每次唤醒先核查上轮是否真发、未发则先补~~ **2026-08-09 订正（对抗复核 PR #208 指出的自洽缺口）**：殿后铁律生效后**每一轮**都以 ScheduleWakeup 收尾，若仍把「以心跳收尾」本身当"未发简报"的判据，会把每一轮都判成未发——这半句原本防的是**「简报只被折进心跳 prompt 里、没有作为独立消息真正发出」**，不是"轮子以心跳结尾"这件事本身。改为：**心跳一返回，本轮已无法回头补证"刚才那条简报是否真的作为独立消息发出去了"，所以每次唤醒仍须核查上一轮的简报是否真发（含"只写进了心跳 prompt 里"或干脆漏发这两种未发形态），未发则先补**；简报"已发"只准下一轮回看核实后记账；~~纯文本收尾的简报轮须在同轮更早的工具段先设好后继心跳（否则零在途+零待触发=循环饿死）~~ **同批订正**：这句假设"心跳可以设在轮中段、之后还能再写一段纯文本收尾"——与殿后铁律证伪的是**同一个前提**（心跳一返回轮就终结，不可能先设心跳、后面再跟一段纯文本）。改为：**一轮的收尾只有两种合法形态——殿后心跳，或显式 `{stop:true}`/交还用户；不存在"纯文本收尾且未设心跳"这一态**，误入即零在途+零待触发=循环饿死（**这正是 cron 常驻心跳兜底存在的理由**：殿后心跳若因限流/API 错/工具报错/用户打断而没调成，简报已发但轮被截断、心跳未调，落地就是零 armed 唤醒=饿死；兜底见 §心跳对账节·甲①与一·开窗节①）；~~ScheduleWakeup **永不作轮内最后一个工具调用**，其后必须再跟至少一个工具调用~~ **2026-08-08 订正（issue #194，同窗两次实测坐实）**：宿主实况是 ScheduleWakeup 一返回轮即终结，「其后再跟一个调用」这半句结构性不可执行——改为 **ScheduleWakeup 是轮内刻意的最后动作：调它之前，本轮简报与全部实质动作必须已完成**，它一返回轮就没了。**这一条与档案层 `docs/evolution/incident-narratives-202607.md` N3「样本更新」段字面冲突，照直标为开放问题、本 PR 不选边**：N3 记着 2026-07-24 通宵窗执行"Wakeup 挪至轮中段+心跳 prompt 末尾携带铁序一句"后"段间十连零失误"（即心跳后确曾有过后续工具调用），而 issue #194 是 2026-08-08 同窗两次实测"心跳一返回轮即终结"。现有证据配比是**新证 2 例（当前宿主）vs 档案 10 连（疑似更早宿主版本）**，两种解释都成立（①宿主语义在这段时间变了 ②档案记录本身有误，未去核对 2026-07-24 那个窗的原始转录），按 `[#官抗-基线是活的]` 本 PR 只按当前宿主实测订正判据、不裁定这份出入的成因。心跳 prompt 末尾固定携带铁序自提醒一句（**2026-08-02 扩为两句**：铁序自提醒 + 「醒来第一动作 Read 本文件 §心跳对账节」，模板与它那段未验证见本文件 §📮 投递通道）。

### 丙 · 在途水位线（用户点名固化 2026-08-01，任何项目生效）

帅的默认态是**多路满载，单路在途是需要理由的例外——不是反过来**。心跳对账固定加一问「**在途几路 × 队列有活吗**」：队列非空且在途低于水位（高性能档 3-4 路、标准档 2 路）⇒ **当轮补派到水位**，补不满的写明理由（真机名额独占 / 文件相交须串行 / 池子实况不稳）。两个已实证的滑落形态，都不是「忘了派」而是「有理由地不派」——理由是错的：①**连环 API 死亡后只重派了死的那路，没恢复其余并发**——要恢复的是路数，不只是任务；②**环境约束被扩大解读**——「冻结 main 推送」被读成「少开工」，而冻结管的只是推送，worktree 开工止步 PR 不受限。判据一句话：**每个「不派」都要答得出「这一路为什么不能现在跑」，答不出就是水位缺口。**

🔴 **彻底解决三层（用户第 2 次点名「能彻底解决吗」后固化 2026-08-01；前一版是「提醒型」条款，实测仍反复滑落，正是「提醒类携带率低」的自证）**——反复滑落的根因是**帅单线程既派又合又裁，串行合并期无人补水位**，故治法是改动作次序+改水位定义+识别真瓶颈，不是加提醒：

㈠**补水位提到每轮最前（次序硬规）**：心跳/回合的**第一个工具段**就是水位检查+补派，**在任何 merge/裁决/抽验之前**。合并期是水位最易漏的时刻（帅忙于串行终审），所以补在前面、让在跑的官在你合并时继续跑。**判据：这一轮我先补水位了吗？没有就是又滑了一次。**
㈡**自适应水位（水位是上限不是配额）**：目标=`min(档位水位, 并行安全队列深度)`。队列被**串行独占资源**（真机/单设备/单账号）主导时，**少于水位是对的，硬凑=造 busywork**。把行动层拆「纯代码可并行 / 串行资源类（真机等）/ 待拍板 / 受阻」四堆看——只有第一堆能填并行水位，串行堆各自排单资源队列。
㈢**识别串行资源瓶颈，抬吞吐的钥匙是解并行约束不是加 agent**：当剩余队列被单一独占资源主导（如 21 单真机全过一个实例），**并行天花板不由 agent 数定、由那个资源的并发度定**。此时最高杠杆动作是**解那个资源的并行约束**（如 mousse #446 让同机起 2 个 dev 实例=真机吞吐翻倍），而不是多派读代码官空转。判据：**问「现在什么资源在串行化整条队列」，去解它，而不是问「怎么再凑一路」。** [基线:2026-08-01 同窗——清掉 40+ 并行代码单后，剩余 22 行动层里 21 是真机（一实例串行），此时 1-2 路是物理天花板非纪律问题；真钥匙是 #446 双实例] [#窗-串行瓶颈]
㈣**三态自适应水位（用户拍板 2026-08-09：「该限流的时候应该限流，但发现好像能正常运行的时候，应该要恢复正常状态」）**：这是给 ㈡「水位是上限不是配额」公式里那个 `档位水位` 常量装的**取值器**，不是第五条独立规则——**不推翻 ㈠**「补水位提到每轮最前」的次序、**不推翻 ㈡**「水位是上限」的公式本身（`min(档位水位, 并行安全队列深度)` 照旧成立，本条只改左手边那个数）、**也不与 ㈢ 冲突**（㈢ 答「有没有资源在串行化整条队列」，本条答「档位水位这个数此刻该取多少」，两问正交、可同时生效）。判据靠读 `ccswitch/hooks/dao-rate-limit-sentinel.js` 落盘的中断标记与 fired.log 死亡记录，**不新造判据源**；**窗口刻意与标记 JSON 里的 `deaths_24h` 字段不同**——那个字段答的是「过去 24 小时死了几次」这个更粗的问题（供事后复盘用），本条要的是「过去 30 分钟」这个更细的窗（供当轮补水位用），两者独立读取、不互相派生：
　　- **健康态**（最近 30 分钟内零限流死亡）⇒ 档位水位照旧，满载 6-8 路。
　　- **受创态**（最近 30 分钟内发生过一波死亡）⇒ 档位水位减半，且补派**错峰**（不同时起两路，隔开起，避免落进同一波限流窗口再死一次）。
　　- **限流态**（`rate-limit-interrupt.json` 标记文件仍在）⇒ 档位水位收到 1 路，只放一路去探路，其余在队列里排着，不批量重派。
　　- **恢复**：标记解除后，首批重派的官**存活满 10 分钟**起，此后每 15 分钟档位水位 +1 路，爬回满载——不是标记一解除就立刻拉满。

### 丁 · 自主边界（永不进自主窗）
