# 设计同步 · Design Sync

> 上善若水。水善利万物而不争。设计流向代码是顺流，代码回灌设计亦是顺流——方向由你所在的位置决定，水自然流向该去的地方。

**一句话定位**：漂移检测 + 人话翻译 + 一键同步。用户不写提示词、不指定文件名、不思考方向——但可以追加指令缩小范围或指定意图。

**流水线位置**：设计管线的**入口快捷层**。底层复用 `dao-design-open`（Design→Code）和 `dao-design-asset`（Code→Design），本 skill 是它们之上的薄编排。

---

## §0 · 调用形态与方向判断

> 道法自然。方向由宿主决定，不由用户决定。参数是可选的锚点，不是必填的表单。

### 0.1 三种调用形态

| 形态 | 示例 | AI 行为 |
|------|------|---------|
| **裸调** | `/dao-design-sync` | 全量漂移检测，列出所有不一致项 |
| **带范围** | `/dao-design-sync 查一下按钮那块` | 只检测用户提到的区域/组件/页面，其余跳过 |
| **带模式** | `/dao-design-sync 仔细同步` | 全量检测 + 完整模式执行（§4.3） |
| **组合** | `/dao-design-sync 仔细同步 Card 组件` | 只检测 Card + 完整模式 |

用户追加的自然语言是**锚点**——缩小检测范围、指定关注点、切换模式。AI 解析意图后落入对应流程，不要求固定格式。

### 0.2 图片输入处理

用户可能随调用传入截图（如 `/dao-design-sync [Image] 检查这块`）。**图片直接在会话上下文中可见，不要试图从文件系统读取。** 直接看图识别用户指向的 UI 区域/组件，然后缩小漂移检测范围到该区域。

处理流程：
1. **看图** — 识别截图中的 UI 区域（按钮、卡片、导航栏等）
2. **定位** — 根据识别结果匹配 `design/` 下的对应文件和代码组件
3. **聚焦** — 只对匹配到的文件执行漂移检测（§1），跳过无关文件

**禁止**：用 Read / Bash / Glob 试图从文件系统"读取"用户传入的截图——它不是文件，是会话内容。

### 0.3 方向判断（自动）

| 宿主 | 方向 | 含义 |
|------|------|------|
| Claude Code | Design→Code | 设计稿有更新，同步到代码 |
| Open Design | Code→Design | 代码有更新，同步到 HTML 原型 |

**判断方法**：AI 根据当前运行环境自动判断。用户不需要指定方向。

## §1 · 漂移检测

> 不知常妄作凶。先看清全貌，再决定动作。

### 1.1 检测方法

**裸调**时扫描 `design/` 下全部 HTML 页面（排除 gallery/archive/workspaces）。**带范围**时只扫描用户提到的组件/页面/区域对应的文件。

对每个目标页面，找到其对应的代码组件，比较双方 git 最后提交时间：

```
git log -1 --format="%ai" -- design/button.html
git log -1 --format="%ai" -- src/components/Button.tsx
```

- 设计端更新 > 代码端更新 → 标记为「设计领先」
- 代码端更新 > 设计端更新 → 标记为「代码领先」
- 两端时间相近（<1min）或无变化 → 标记为「已同步」

### 1.2 对应关系

按优先级查找映射：

1. `design/.map.json`（显式映射文件，如有）
2. 文件名约定（`design/workspace.html` → `src/pages/Workspace.tsx`）
3. HTML 内 `data-component` 属性
4. 现有 `design-open` 翻译历史（git log 中的关联提交）

首次无映射时，AI 扫描两侧文件结构自动推断，推断结果写入 `design/.map.json` 供后续使用。

### 1.3 输出格式

漂移列表按方向分组展示。**所有设计文件路径输出为可点击链接**（绝对路径），用户可直接在浏览器打开查看：

```
📋 漂移检测结果：

设计领先（design 更新，代码未跟进）：
  1. Button — design/button.html（2h 前更新）
  2. Card   — design/card.html（昨天更新）

代码领先（代码更新，design 未跟进）：
  3. Navbar — design/navbar.html（代码 3h 前改了布局）

已同步：
  ✓ Sidebar, Footer, LoginForm
```

## §2 · 变更描述（人话翻译）

> 信言不美，美言不信。描述变更说人话，不说代码。

对每个漂移项，读取 git diff 并翻译为**视觉语言**：

| 不要这样说 | 要这样说 |
|---|---|
| `border-radius 从 8px 改为 12px` | 按钮圆角变大了（8→12px） |
| `新增 box-shadow 属性` | 卡片加了投影，悬浮感更强 |
| `gap 从 16px 改为 24px` | 列表项间距拉大了 |
| `color 从 #3B82F6 改为 #2563EB` | 主色调加深了一档 |

**翻译原则**：
- 先说**视觉效果**，再附**具体值**（括号内）
- 结构性变更（新增/删除 DOM 节点）单独列出
- 纯文案变更标记为「内容更新」不展开

## §3 · 用户确认

> 太上不知有之。确认是最后的人类决策点，之后全自动。

### CC 端（Design→Code）

展示漂移列表 + 变更描述，问用户同步范围：

```
设计稿有 2 处更新：

1. Button — 圆角变大（8→12px），背景色加深
   📎 design/button.html

2. Card — 新增阴影层，间距从 16→24px
   📎 design/card.html

要同步哪些到代码？
  [全部同步]  [只同步 Button]  [先看看设计稿]
```

用户选「先看看设计稿」→ 直接在终端输出设计文件的绝对路径（可点击打开浏览器查看）。

### OD 端（Code→Design）

展示代码变更列表，默认全量同步：

```
代码端有 2 处更新：

1. Navbar — 布局从 flex 改为 grid，新增搜索栏
2. Button — 加了 loading 状态动画

要更新 HTML 原型吗？
  [全部更新]  [只更新 Navbar]  [先不管]
```

## §4 · 执行同步

> 为无为，事无事。同步本身不该是一件"事"。

### 4.1 模式选择

| 模式 | 触发词 | 流程 | 适用场景 |
|------|--------|------|---------|
| **快速**（默认） | "同步" / "好" / "全部" | §4.2 直接应用 | 日常小改动 |
| **完整** | "仔细同步" / "走完整流程" | §4.3 委托底层 skill | 大改动 / 新页面 / 需要 QA 验证 |

### 4.2 快速模式

**Design→Code（CC 端）**：

1. 读 design HTML 的 git diff
2. 按 `dao-design-open` §2.5 的结构提取方法，提取变更的 CSS 属性和 DOM 结构
3. 直接定位对应的 React 组件，应用视觉变更
4. 跑 typecheck 确认无破坏
5. 报告完成

**跳过**：QA 截图循环（§4.4）、auto-gate 三关（§4.5）、完整结构提取文档

**Code→Design（OD 端）**：

1. 读代码组件的 git diff
2. 定位对应的 `design/*.html`
3. 直接更新 HTML 中对应的 CSS 属性和 DOM 结构
4. 浏览器打开验证外观
5. 报告完成

**跳过**：workspace 草稿流程、升格流程、handoff 文档

### 4.3 完整模式

**Design→Code**：委托 `dao-design-open`，从 §2.5 结构提取开始，走完整翻译 + QA 循环 + auto-gate。传入已检测的漂移信息，跳过重复的前置扫描。

**Code→Design**：委托 `dao-design-asset` §A，走完整的扫描 → 翻译 → 生成 → 验证流程。通过 workspace 草稿区 + 升格机制。传入已检测的漂移信息。

## §A · 与其他 skill 的关系

| Skill | 关系 |
|---|---|
| `dao-design-open` | 完整模式的 Design→Code 执行者。sync 传入漂移上下文，跳过重复前置 |
| `dao-design-asset` | 完整模式的 Code→Design 执行者。sync 传入漂移上下文 |
| `dao-design-fidelity` | 完整模式走 auto-gate 时触发，快速模式跳过 |
| `dao-design-standards` | 翻译时的视觉判据来源 |

## §B · 反模式

1. **让用户写提示词描述变更** — git diff 就是 spec，不需要自然语言再翻译一遍
2. **让用户指定文件名** — 漂移检测自动发现，用户只确认范围
3. **让用户思考方向** — 宿主决定方向，用户不需要知道 Design→Code 还是 Code→Design
4. **快速模式做 QA 截图** — 快速模式的价值就是快。需要 QA 时用完整模式
5. **输出文件路径不可点击** — 所有 design/*.html 路径必须输出绝对路径，用户可直接点开浏览器查看
6. **描述变更用代码语言** — 说"圆角变大了"不说"border-radius changed"
