# 设计 QA · Design QA Loop

> 反者道之动。发现问题是第一步，修对地方是关键。

本 skill 处理 **UI 视觉问题的发现与修复**——不是设计原则判断（那是 `dao-design-taste`），而是"看到问题 → 在正确的地方修 → 同步到代码"的工作流。

**核心原则：设计工具先行，代码后补。** 直接改代码容易头痛医头，在设计工具中修能看到全局影响，再回填代码保证一致性。

---

## 触发条件

以下情况自动进入本流程（无需用户手动调用）：

1. 截图/查看运行中的应用时**发现视觉问题**（布局错位、颜色不对、对比度不足、文字截断、间距不一致等）
2. 用户反馈 UI 问题（"这个标签被截断了"、"颜色不对"、"这里间距太大"）
3. 用户发来截图并问"发现问题了吗"
4. 设计审查时发现代码渲染与设计稿有差距

**不触发**：纯功能 bug（逻辑错误、接口不通）、纯代码重构、与视觉无关的改动。

## 三步循环

```
┌─────────────────────────────────────────────┐
│  Step 1 · 找问题（Identify）                │
│  截图实际界面 → 逐项列出视觉问题            │
│  工具：Playwright / Chrome DevTools / 截图   │
├─────────────────────────────────────────────┤
│  Step 2 · 修设计（Fix in Design）           │
│  在设计工具中修复 → 截图验证修复效果         │
│  工具：Penpot MCP / Figma / HTML mockup     │
├─────────────────────────────────────────────┤
│  Step 3 · 回填代码（Backfill Code）         │
│  代码实现设计修复 → 测试 → 截图验证对齐      │
│  工具：Edit + 测试 + 类型检查 + 截图验证     │
└─────────────────────────────────────────────┘
         ↑                                    │
         └────── 还有差距？继续循环 ───────────┘
```

### Step 1 · 找问题

1. **截图当前界面**：用 Playwright 或 Chrome DevTools 截取实际渲染
2. **系统性审视**：逐区域检查以下维度
   - 布局：对齐、间距一致性、溢出/截断
   - 颜色：token 是否正确引用、对比度是否达标、亮暗模式一致性
   - 字体：字号层级、字重区分、行高呼吸感
   - 组件：状态标签是否可读、圆角是否统一、阴影层级是否正确
   - 交互态（三层模型）：
     - **状态层**：hover / focus / disabled / loading / empty / error 是否都有处理
     - **动效层**：micro（按钮反馈）/ transition（面板展开）/ feedback（操作成功/失败）是否自然
     - **导航层**：入口可达 / 循环无死角 / 面包屑一致 / 404 兜底
3. **产出问题清单**：每个问题标注位置 + 具体现象 + 严重程度

**退出判据**：一轮审视后找不到值得修的问题 → 流程结束。

### Step 2 · 修设计

**前提**：有设计工具 MCP 可用（Penpot / Figma）。无设计工具时跳过此步直接到 Step 3。

1. **定位设计稿中对应页面/组件**
2. **在设计工具中实施修复**：
   - 修改前先截图/记录当前状态
   - 实施修改（调间距、改颜色、修布局）
   - 修改后截图对比确认改进
3. **注意事项**：
   - 设计工具中的修改要用 Library Component / token，不要硬编码
   - 修复要考虑全局影响（改一个组件影响所有引用处）
   - 设计工具注意：确保在正确的页面/画板上操作再编辑

**无设计工具时**：直接在代码中修，但要先在注释或 commit message 中说明改了什么、为什么改。

### Step 3 · 回填代码

1. **对比**：Playwright 截图代码渲染 vs 设计稿，确认差距点
2. **实现**：在代码中实施修改
   - 优先改 token/CSS 变量（一处改全局生效）
   - 其次改组件层（ui/ 目录下的共享组件）
   - 最后才改业务层（具体页面/视图）
3. **验证三关**：
   - 跑项目测试套件：契约测试通过
   - 跑类型检查（如有）：类型安全
   - 截图对比：视觉对齐设计稿
4. **亮暗模式都要验**：改了亮色必查暗色

**退出判据**：代码渲染与设计稿无可见差距 → 循环结束。

## 与其他 skill 的关系

| skill | 职责 | 本 skill 如何配合 |
|---|---|---|
| `dao-design-taste` | 设计原则、token 体系、审美判断 | 修设计时参考其判据（§4 体检表） |
| `dao-verify` | 全面体检 | 修完后可选走 verify 做最终验收 |
| `dao-review` | 代码评审 | 回填代码后可走 review |

**边界清晰**：taste 管"什么是好设计"，QA 管"发现问题并修到位"。taste 是知识，QA 是流程。

---

## 工具优先级

按可用性自动降级：

| 步骤 | 首选 | 备选 | 最低 |
|---|---|---|---|
| 截图 | Playwright MCP | Chrome DevTools MCP | 手动截图 |
| 修设计 | Penpot MCP | Figma MCP | 跳过，直接改代码 |
| 改代码 | Edit + 项目测试套件 | Edit + 手动验证 | — |

---

## 反原则

- **不跳过设计直接改代码**（有设计工具时）——直接改代码是症状修复，设计工具修是根因修复
- **不一次修太多**——每轮 1-3 个问题，修完验证再下一轮
- **不做像素级 diff**——验方向和一致性，不数像素
- **不忽略暗色模式**——改亮必查暗
- **无问题就停**——不为流程而流程，没问题就是最好的结果
