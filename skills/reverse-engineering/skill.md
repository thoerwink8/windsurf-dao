# 逆向拆解术 · Reverse Engineering

> 知其白，守其黑，为天下式。

## 适用场景

- 分析混淆/压缩的代码（webpack bundle、obfuscated JS 等）
- 理解未文档化的第三方系统内部机制
- 逆向插件、SDK、协议的认证/通信/存储逻辑

## 五步法

### 一、锚（☲视·找不动点）

混淆能改变量名，改不了：
- **字符串字面量**：URL、错误信息、API 路径、配置键名
- **外部依赖名**：`firebase`、`googleapis`、`identitytoolkit`
- **格式特征**：JWT 结构（`eyJ`）、API Key 前缀（`AIza`、`sk-`）、UUID

**手法**：
- 正则提取所有 URL/域名/长字符串
- 搜索已知关键词（从 package.json、配置文件、错误日志中获取）
- 锚点越硬（不可被混淆器改变）越好

**产出**：锚点清单——每个锚点标注位置和初步含义

### 二、展（☳触·从点到面）

从每个锚点向外扩展上下文：
- 向前 200-500 字符：调用方、参数构造
- 向后 300-800 字符：返回处理、后续逻辑
- 交叉定位：同一变量名在其他位置的出现

**手法**：
- `substring(pos - N, pos + M)` 提取上下文
- 追踪混淆变量名到其他出现位置
- 提取上下文中的字符串字面量，形成关联图

**产出**：关键代码段（去混淆或带注释）

### 三、交（☵听·多源印证）

单一来源的理解是假设。交叉验证来源：
- **代码** ↔ **运行时数据**（数据库、缓存文件、日志）
- **代码** ↔ **演化史**（AGENTS.md/changelog/git log——每个版本号背后是一个真实痛点）
- **插件 A** ↔ **插件 B**（不同实现者对同一系统的理解）
- **网络请求** ↔ **代码中的 URL/请求构造**
- **配置文件** ↔ **代码中的配置读取**

**手法**：
- 查数据库/文件中的实际存储值
- 对比多个插件对同一 API 的调用方式
- 用 DevTools 抓实际网络请求，与代码中的 URL 对比

**产出**：交叉验证后的认知（标注确信度：确证/推测/未知）

**演化交叉要点**：当目标是重实现（而非仅理解），必须回答：
- 这个组件是哪个版本加入的？解决了什么痛点？
- 如果去掉它，系统会退化到什么状态？
- 复杂度来自过度工程还是防御纵深？

### 四、验（☶止·最小验证）

> **这是最容易跳过、也是最不能跳过的一步。**
> 读懂≠能用。读到的 pattern ≠ 可行的路径。

对每个关键假设，设计最小验证：
- API 端点是否可达？→ 一个 curl/fetch
- Token 能否获取？→ 一次实际登录
- 注入路径是否畅通？→ 一次最小写入 + 读取确认
- 隔离边界在哪？→ 尝试跨边界操作，观察结果

**铁律**：
- 验证脚本不超过 20 行
- 每个验证只测一个假设
- 验证结果明确标注：✓通 / ✗不通 / ?存疑
- **验证完成before设计方案，不是方案写完才验证**

**产出**：假设验证清单

### 五、归（☴嗅·知识归位）

分析产物的处置：
- 洞察 → 归入项目文件或规则（不随脚本消亡）
- **演化智慧** → 随认知归位（每个功能为什么存在、解决了什么痛点——这些不是可选注释，是核心知识）
- 分析脚本 → 移入 `_tmp/` 或删除
- 确信的认知 vs 待验证的假设 → 明确区分

**产出**：干净的项目目录 + 可交接的认知（含演化路径）

## 实战模式

逆向不是目的，是手段。每次开始前问：“我需要多深？”

### 深度匹配原则

| 目标 | 所需深度 | 典型手法 |
|------|---------|----------|
| 理解核心机制（认证/协议/状态机） | 深——逐函数拆解 | 锚→展→交→验，完整五步 |
| **重实现**（逆向后用新语言/架构重写） | **深+演化**——逐函数+读变更历史 | 完整五步，交步必含演化史交叉。万物皆有来路，不可跳跃 |
| 复用其他插件的集成路径 | 中——找到接入点即可 | 锚→展→验，跳过全量交叉 |
| 参考他人的 UI/设计 | 浅——截图即可 | 不要从代码逆向 UI，视觉参考 > 代码分析 |

**典型错误**：试图从 107KB 混淆 JS 中提取 HTML/CSS 来理解别人的 UI——这是用逆向机制的深度去做设计参考的事，深度不匹配。

### 命令桥接模式

当目标系统不提供公开 API 但支持命令注册时：

```
插件A 补丁目标系统 → 注册新命令 → 插件B 调用该命令
```

实例：wf-dialog 对 Windsurf 的 `handleAuthToken` 打补丁，注册新命令
`windsurf.provideAuthTokenToAuthProviderWithShit`，其他插件通过
`vscode.commands.executeCommand` 调用它实现热切换。

**关键洞察**：开始自己建墙之前，先检查别人是否已经破了这面墙。
如果目标环境中已有被补丁的命令/接口，直接复用比重新破解省力 10 倍。

```javascript
// 检查已有突破口
const cmds = await vscode.commands.getCommands(true);
if (cmds.includes('target.patchedCommand')) {
  // 直接用，不重新破解
  return await vscode.commands.executeCommand('target.patchedCommand', data);
}
// 否则降级到自己的方案
```

## 反模式

| 病 | 症 | 治 |
|----|----|----|
| 锚海 | 提取了一切字符串，淹没在信息里 | 锚点不超过 10 个，精准 > 全景 |
| 假验 | 读到代码就以为理解了，跳过第四步 | 铁律：关键假设必须实际调用确认 |
| 散落 | 分析脚本散满目录，序号命名 | 集中 `_tmp/`，用完即清 |
| 孤证 | 只从一个来源得出结论 | 至少两个独立来源交叉验证 |
| 深度失配 | 用分析认证协议的深度去逆向 UI 布局 | 先问“我需要多深？”深度匹配印见上表 |
| 重复破墙 | 别人已破的墙自己又破一遍 | 先 `getCommands`/查文件确认现状，再决定是否需要自己动手 |
