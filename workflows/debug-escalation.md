# 调试升级 · Debug Escalation

> 知不知，上；不知知，病。夫唯病病，是以不病。
> —— 知道自己不知道根因，是上等。以为知道就动手改，是病。

## 铁律

```
无根因，不修。
为之于未有，治之于未乱。
```

未完成第一层（听症），不得提出修复方案。
每一层都是在积累证据，不是在猜测。

## 触发条件

- Bug难以复现或定位
- 修了一次没好，或修出新问题
- 错误信息不明确，不知从哪里下手
- 多组件系统中不确定哪层出了问题

## 四层升级

逐层深入，每层都有明确的入口条件和产出。**低层能解决的不升高层。**

---

### 第一层 · 听症（☵坎 · 听 · 守中）

> 多言数穷，不如守中。

**不急于修，先让系统把话说完。**

1. **读完整错误信息**
   - 不跳过、不略读。错误信息中往往有答案
   - 读完整堆栈：文件名、行号、错误码
   - 读警告——它们常常是线索

2. **复现**
   - 找到可靠的复现步骤
   - 每次都能触发？偶发？条件是什么？
   - 不可复现 → 加日志后重试，不猜

3. **查近期变更**
   - git log / git diff：什么变了？
   - 新依赖？配置变更？环境差异？
   - 如果能 git bisect 定位到引入点 → 问题基本解决

**产出**：症状描述 + 复现步骤 + 近期变更列表
**判断**：根因已明 → 直接修。未明 → 升第二层。

---

### 第二层 · 探脉（☲离 · 视 · 照见）

> 善行无辙迹，善言无瑕谪。

**追踪数据流，找到断裂点。**

1. **加诊断日志**（不是修复，是观察）
   - 在每个组件边界加入/出日志
   - 记录：什么数据进来？什么数据出去？
   - 环境变量/配置是否正确传播？

2. **运行一次，收集证据**
   // turbo
   - 跑一遍带日志的版本
   - 不改任何逻辑，只加观察
   - 对比：期望值 vs 实际值，在哪一层开始偏离？

3. **隔离组件**
   - 用最小用例单独测试可疑组件
   - Mock上游输入，看本层是否正确
   - 缩小范围直到定位到具体模块/函数

**产出**：数据流断裂点 + 可疑组件定位
**判断**：定位到具体函数/行 → 修。仍模糊 → 升第三层。

---

### 第三层 · 辨根（☶艮 · 味 · 止而辨）

> 知人者智，自知者明。胜人者有力，自胜者强。

**停下来做模式分析，不再往前冲。**

1. **找对照组**
   - 同一代码库中有没有类似的、正常工作的代码？
   - 逐项对比：什么不同？哪怕是微小差异也不放过

2. **形成单一假说**
   - 明确陈述："我认为根因是X，因为Y"
   - 写下来。不是"可能是A或B或C"——是一个明确的假说

3. **最小验证**
   - 只改一个变量来验证假说
   - 不同时改多处（"多言数穷"）
   - 假说证实 → 修。假说证伪 → 形成新假说，重复
   - **计数**：已尝试几个假说？

**产出**：经验证的根因假说
**判断**：
- 假说证实 → 修
- 已试3个假说都失败 → 升第四层（**强制**，不再试第4个）

---

### 第四层 · 问道（☴巽 · 嗅 · 反者道之动）

> 反者道之动，弱者道之用。

**3次修复失败意味着这不是bug——是架构问题。退一步，在更高处重新理解。**

1. **质疑架构**
   - 这个模式/方案本身是否合理？
   - 是否在"因为已经写了所以坚持用"？（惯性≠正确）
   - 每次修复是否暴露了不同位置的新问题？（这是架构病的信号）

2. **质疑假设**
   - 需求理解对吗？
   - 前提条件还成立吗？（环境、依赖、版本）
   - 是否在用旧地图导航新地形？

3. **请用户介入**
   - 至此必须止，不再独自尝试
   - 向用户清晰呈现：
     - 已做了什么（三层调查的证据）
     - 排除了什么
     - 当前最佳假说
     - 建议的方向（重构/换方案/重新定义需求）
   - **原则**：贵以身为天下，若可寄天下——信任用户的判断

**产出**：完整调查报告 + 架构级建议
**判断**：用户决策后，可能回到任意层级，或转入 `/cycle` 做架构级重构

---

## 与 /cycle 的关系

```
debug-escalation 是 /cycle 的特化：

/cycle:     观 → 行 → 验 → 省 → 改升
                ↕
debug:  听症 → 探脉 → 辨根 → 问道
        (观大)  (观深)  (省)    (改升)

区别：debug中「行」被约束——无根因不修
共同：螺旋升维，知止不殆
```

如果第四层问道后需要架构级变更，切换到 `/cycle` 进入完整的转法轮流程。

## 反模式

| 病 | 道德经诊断 | 对治 |
|----|-----------|------|
| 一看就改 | 不知知，病 | 铁律：无根因不修 |
| 同时改多处 | 多言数穷 | 一次一个变量 |
| 改了3次还在猜 | 强梁者不得其死 | 强制升第四层 |
| 加了日志不看 | 视之不见名曰夷 | 每条日志都要分析 |
| 修好不验证 | 假涅槃 | 必须复现"不再出现" |
| 改着改着范围扩大 | 企者不立，跨者不行 | 回到听症，重新定位 |

## 执行格式

每层开始时声明：

```
## 🔍 第N层 · [听症/探脉/辨根/问道]
### 当前证据：[已知事实]
### 本层目标：[要回答什么问题]
```

升级时记录：

```
### 本层结论：[发现/排除了什么]
→ [根因已明，修复 / 升级至第N+1层，因为...]
```

修复后验证：

```
### 修复验证
- 原始bug：[是否不再出现]
- 回归测试：[是否引入新问题]
→ [涅槃 / 需进一步处理]
```
