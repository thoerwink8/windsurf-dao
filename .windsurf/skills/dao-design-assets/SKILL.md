# 设计资产 · 代码即真相

> 道生一(tokens),一生二(基础件),二生三(业务件),三生万物(页面)。

## 范式根基:reflect,不是 push

> 先读懂这一节,否则会把旧的双向同步坑原样搬来。

设计资产的真相**在代码里**,不在代码之外的任何稿子里(.pen / Figma / mockup 都不是真相源)。

```
✗ push 模型(已废弃):
   外部设计稿 = 真相 → 推动代码去逼近 → 永远有 gap 要追 → 加契约测试锁像素
   病:双向同步、维护成本 O(3)、改一个按钮要改三处

✓ reflect 模型(现行):
   代码 = 真相 → 展示窗(gallery)渲染真组件 → 永远无 gap
   统一性靠"约束输入"(只准用 token),不靠"事后比对"
```

**一句话**:不维护代码之外的设计真相源,不写像素契约。统一性从 token 约束 + lint 来,可见性从 gallery 来,二者都比"稿子比对"更彻底、维护趋近于零。

## 三层真相源(各司其职)

> 把"统一的组件库"这个目标拆三层,每层用对工具,维护成本从 O(3) 降到接近 O(1)。

| 层 | 谁是真相 | 怎么保证统一 | 维护成本 |
|---|---|---|---|
| **① Design Tokens** | 项目的 token 定义(色/字/间距/圆角/阴影) | 所有组件只准引用 token,**禁硬编码** | O(1):改一个 token 全局生效 |
| **② 基础组件** | 项目组件目录里的基础件 | variant 一次定制好,只引用 token | 趋近 0:定好不动 |
| **③ 业务组件** | 真实业务组件代码 | 组合①②,不引入新样式 | 随业务走 |

**统一性的保证方式**:不再靠"代码 vs 稿子像素比对"(事后纠偏),靠**约束输入**——只准用 token、只准用现成组件。从"事后纠偏"升级为"根本不会跑偏"。

## 组件画廊(gallery)· 可见的资产展示窗

> 取代设计稿当"展示窗"。它和稿子的本质区别 = reflect vs push。

**问题**:copy-in 式组件库(组件代码在自己仓库、无统一主题)自由度高=不统一的风险高。新页面开发前若看不见"项目已有哪些组件",就会重复造、各搞各的样式(心智负担)。

**解法不是设计稿,是组件画廊**:一个展示页,**直接引用项目的真实组件**,把所有 variant、所有状态(default/hover/loading/empty/error)摆出来一屏看全。

```
设计稿(.pen/Figma):代码之外的静态副本 → 要双向同步 → 会漂移 → 得写契约锁
组件画廊         :渲染的就是真组件 → 改组件画廊自动更新 → 永不漂移、零同步、无需契约
```

**gallery 的三重价值**:
1. **资产可见** — 打开即知项目有哪些组件、长什么样、怎么用,新页面"挑现成"不重复造
2. **状态齐全** — 每个组件的空/错/载/禁状态一屏摆全,不用点进真实流程才看到
3. **分诊裁判** — 兼任 `dao-design-taste` §0 的裁判:能在 gallery 拼出 = 形态已知 = DIRECT;拼不出 = 升档

**实现准则**(具体技术按项目栈,不在此写死):
- gallery 是项目内的一个开发态展示入口,**引用真实组件**(绝不复制粘贴组件代码进去)
- 用开发态开关隔离,生产构建排除,不进发布产物
- 新增组件/状态时同步补一条进 gallery(这是唯一的手动成本,远轻于契约测试)
- 形态档轻重:小项目一个展示页即可;组件多到管不过来时再考虑专业工具(如 Storybook 一类),但默认不上重工具(为道日损)

> gallery 是 reflect 真相源的"窗",不是另一个真相源。它渲染代码,不定义代码。

## lint 守护统一性(禁硬编码)

> 这一条替掉了旧体系里成百上千行像素契约测试的绝大部分作用。

统一性靠"约束输入"落地为一条机器可执行的规则:**禁止硬编码颜色/间距/圆角等设计值,只准引用 token。**

- 颜色、间距、圆角、阴影、字号等设计值,必须走 token,不写裸值(裸色值/裸 px)
- 用项目 lint 体系(或等价静态检查)把这条规则机器化,出货前自动拦截
- 这是"根本不会跑偏"的实现:跑偏在写代码时就被 lint 拦下,不必事后拿稿子比对

**与旧契约的对比**:旧的 1000+ 行像素契约是"事后量代码和稿子差几像素"(push、脆弱、维护重);一条 lint 规则是"写代码时就禁止裸值"(reflect、稳健、零维护)。后者更强、更轻。

## 屏幕状态覆盖(在 gallery 里展示)

> 大成若缺,其用不敝。只展示 happy path 的资产是残缺的。

每个组件/屏幕的关键交互状态都要可见。旧做法是在设计稿里并排摆状态帧;**新做法是在 gallery 里用真组件渲染各状态**——同样并排可见,但渲染的是真相。

状态覆盖清单(每个组件至少各出现一次):

| 状态 | 说明 |
|---|---|
| default | 正常使用 |
| loading | 加载中(骨架屏匹配最终形状) |
| empty | 无数据/首次(空态引导 + CTA) |
| error | 请求/验证失败(内联提示) |
| hover / active | 悬停 / 按压反馈 |
| disabled | 不可操作 |
| 多实例不同态 | 同类元素的选中/完成/进行中/归档等 |

- 不需穷举所有排列组合,每种状态出现一次即可
- 暗色通过主题切换看,不为每个状态单独做暗色版

## 工作流(按 dao-design-taste §0 分诊接入)

```
FULL/SCOPED 档:
  dao-ui-mockup 探索形态 → 导出 design tokens
    → ① 落 token 到项目 token 定义(收口)
    → ② 实现/调整基础件、业务件(只引用 token)
    → ③ 补进 gallery(新组件/状态)
    → ④ lint 验证无硬编码 + 基石 §6 验收

DIRECT 档:
  查 gallery 找现成 → 组合现成组件 → (必要时)只引用 token 微调
    → lint + 基石 §6 验收
  全程不碰 token 体系、不画原型
```


## 反原则

- **代码即真相** — 不维护代码之外的设计真相源(.pen/Figma/mockup 皆非真相)
- **不写像素契约** — 统一性靠 token 约束 + lint,不靠稿子比对
- **gallery 引用不复制** — 它渲染真组件,绝不 copy 组件代码进去
- **token 先行** — 任何设计值走 token,裸值是 lint 错误
- **不提前造** — 组件按需建,不预先囤不用的(YAGNI)

法不违德,德不违道,道法自然。
