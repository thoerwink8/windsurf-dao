# 志 · Goal Anchor

> 志者，心之所之。
> 知止可以不殆。
> ——《道德经》第 33、44 章

`dao-goal` 的职责不是设计方案，也不是拆任务，而是先回答一个更根本的问题：**这一次到底要到哪里才算到，以及该自动调用哪条 dao 路径推进？**

目标不清，后续的 `/dao-cycle` 会空转，`dao-plan` 会乱拆，`dao-verify` 会假完成。目标先定，万法归一。

## 铁律

```
不明确成功标准，不算目标已定。
不明确范围外，不算目标已定。
不把目标契约交给后续流程，不算目标已定。
用户表达“持续推进/不用中途决策”时，默认进入持续推进模式，不把 Goal Contract 当确认关卡。
目标清楚后，AI 必须自动选择合适的 dao-* 路由，不把“下一步用哪个流程”交给用户决定。
```

## 何时激活

- 用户显式调用 `/dao-goal`
- 用户说“目标是 X”“这轮我们要达成 X”“帮我锁一下目标”
- `/dao-cycle` 前，任务复杂且容易漂移
- 多轮对话后，原始目标开始模糊
- 验收前，需要回到最初成功标准

**不激活**：

- 纯事实问答
- 单步机械操作
- 已有明确 design，需要直接进 `dao-plan`
- 需要探索 2-3 个方案的开放需求，此时回 `dao-brainstorm`

## 输出：Goal Contract

`dao-goal` 的标准产出是一份会话内目标契约：

```markdown
## 🎯 Goal Contract

- 原始目标：<保留用户原话，不改写成 AI 口吻>
- 成功标准：
  - [ ] <可观察、可验证的完成条件>
- 本次范围：<这次会做什么>
- 范围外：<这次明确不做什么>
- 推进模式：<持续推进 / 关卡确认 / 等待用户决策>
- 用户决策策略：<默认不问 / 仅阻断时问 / 每阶段确认>
- 自动路由：<dao-debug / dao-brainstorm / dao-plan / dao-execute / dao-cycle / dao-verify / 直接执行>
- 当前不确定点：<无 / 一句话列出关键不确定>
- 下一步动作：<AI 将立即执行的动作，而不是给用户的选择题>
```

## 生成协议

1. **保留原话**：`原始目标` 必须尽量贴近用户说法，不替用户美化目标。
2. **成功标准可验**：每条成功标准必须能通过测试、构建、文件存在、行为观察或用户确认验证。
3. **范围先收窄**：先写本次范围，再写范围外，防止顺手扩张。
4. **推进模式显式化**：用户说“持续推进”“不用中途决策”“自动往最终方向靠”时，`推进模式` 写“持续推进”，`用户决策策略` 写“默认不问，仅阻断时问”。
5. **自动路由**：根据目标类型选择合适的 dao-*，并写入 `自动路由`。
6. **小缺失自补**：不影响方向的小缺失由 AI 推断，并标注“推断”。
7. **大缺失只问一次**：只有影响方向、权限、安全、不可逆操作的大缺失，才用 `ask_user_question` 问一个多选问题。
8. **不默认落文件**：Goal Contract 默认只存在于当前会话，不创建 state，不写 docs。

## 推进模式

| 模式 | 何时使用 | 行为 |
| ---- | ---- | ---- |
| 持续推进 | 用户明确说“持续推进”“不需要用户决策”“一直往最终方向靠” | 输出 Goal Contract 后直接进入下一步，不询问“是否准确” |
| 关卡确认 | 用户想要阶段性把关，或任务涉及 UI 方向/产品取舍 | 在关键阶段 ask 用户确认 |
| 等待用户决策 | 目标存在方向性分歧，AI 无法安全推断 | 先问一个多选问题，再继续 |

**默认规则**：目标足够清楚时，不把 Goal Contract 本身作为审批门。`dao-goal` 是锚点，不是刹车。

## 自动路由

`dao-goal` 不是只给建议，而是选择下一条路并继续推进。

| 目标形态 | 自动路由 | 行为 |
| ---- | ---- | ---- |
| 用户反馈 bug、异常、现象不符合预期 | `dao-debug` | 先复现/定位根因，再修复 |
| 目标仍是开放想法，需要方案取舍 | `dao-brainstorm` | 只在方向真不清时进入需求澄清 |
| 目标清楚但需要多步实施计划 | `dao-plan` | 生成可执行任务清单 |
| 已有 plan 或任务足够明确 | `dao-execute` / 直接执行 | 直接落地，不再询问 |
| 任务复杂、需要持续推进和多轮校准 | `/dao-cycle` | 围绕 Goal Contract 观行验省改升 |
| 需要验证是否完成 | `dao-verify` | 按成功标准拿 fresh evidence |
| 涉及测试策略或补测试 | `dao-test` | 按测试铁律推进 |
| 涉及部署上线 | `dao-deploy` | 按项目部署策略推进 |
| UI 视觉方向不清 | `dao-ui-mockup` | 只有视觉方向需要拍板时才进入 |

### 路由优先级

```text
bug/异常现象 → dao-debug
目标不清/方案互斥 → dao-brainstorm
复杂持续推进 → /dao-cycle
已有清晰方案但需拆任务 → dao-plan
已有清晰任务 → dao-execute / 直接执行
完成声明前 → dao-verify
```

**持续推进模式下**：选定路由后立即执行。不要问“要不要进 dao-cycle / dao-plan / dao-debug”，除非命中阻断条件。

## 与 /dao-cycle 的衔接

当用户在 Goal Contract 后调用 `/dao-cycle`，cycle 的「观」必须先读取并复述目标锚点：

```text
本轮目标锚点：<Goal Contract 摘要>
本轮只围绕成功标准推进；范围外事项不进入行相。
推进模式：<持续推进 / 关卡确认 / 等待用户决策>
```

在「省」阶段，必须逐项对照成功标准：

```text
成功标准 1：已满足 / 未满足 / 需用户确认
成功标准 2：已满足 / 未满足 / 需用户确认
范围外是否被误触：否 / 是（说明）
```

任一成功标准未满足，不得宣布涅槃。

若推进模式是“持续推进”，`/dao-cycle` 中途不得因为“Goal Contract 是否准确”而停下；只能在权限、安全、不可逆、方向歧义、外部凭证缺失等阻断条件下询问用户。

## 与其他 dao-* 的边界

| 机制 | 职责 |
| ---- | ---- |
| `dao-goal` | 锁目标：成功标准、范围、反目标 |
| `dao-brainstorm` | 挖需求：探索方案、形成 design |
| `dao-plan` | 拆任务：把已定方案拆成 2-5 分钟任务 |
| `dao-execute` | 执行：按 plan 或明确目标落地 |
| `dao-verify` | 验证：按成功标准拿 fresh evidence |
| `/dao-cycle` | 循环：围绕目标观行验省改升 |

## 决策路由

```text
用户说了一个目标
  ├─ 目标清楚 + 可直接执行 → dao-goal 生成契约 → 直接做 / 进 dao-cycle
  ├─ 目标清楚 + 用户要求持续推进 → dao-goal 生成契约 → 直接进入 /dao-cycle 或执行
  ├─ 目标清楚但任务复杂 → dao-goal 生成契约 → dao-plan 或 /dao-cycle
  ├─ 目标不清，需要探索方案 → dao-brainstorm
  └─ 只是事实问答 → 不启用 dao-goal
```

## 反模式

| 病 | 症状 | 治 |
| ---- | ---- | ---- |
| 目标改写 | 把用户原话改成 AI 自己的项目愿景 | 原始目标保留用户话术 |
| 成功标准虚 | “体验更好”“更稳定”但不可验证 | 改成可观察条件 |
| 无范围外 | 什么都可能顺手做 | 必写“不做什么” |
| 偷跑实施 | 目标还没定就改代码 | 先契约，再按推进模式行动 |
| 替代 brainstorm | 方案没想清就用 goal 硬定 | 回 `dao-brainstorm` |
| 目标文件泛滥 | 每次 goal 都写 docs | 轻量版默认不落文件 |
| 默认求确认 | 输出 Goal Contract 后问“是否准确” | 持续推进模式下直接进入下一步 |

## 涅槃门

`dao-goal` 完成前检查：

- [ ] 原始目标已保留
- [ ] 成功标准可验证
- [ ] 本次范围明确
- [ ] 范围外明确
- [ ] 推进模式明确
- [ ] 用户决策策略明确
- [ ] 自动路由明确
- [ ] 下一步路由明确
- [ ] 若存在方向性不确定，已向用户问一个问题

全通后，才把 Goal Contract 交给后续流程。
