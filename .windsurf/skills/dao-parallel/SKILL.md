# 并 · Parallel Lens

> 江海所以能为百谷王者,以其善下之,故能为百谷王。
> 上善若水,水善利万物而不争。
> ——《道德经》第 66、8 章

道家"江海善下"是聚合观:**主会话不抢上,反而能聚合多路并行的产出**。
水有"分流"和"汇合"两态。并行调度即是把任务分成多路水(独立 task),让它们各自向下流(派 subagent),最后汇集回主会话。

## 铁律

```
不独立的任务不并行(有依赖必串行)。
不真有 2+ 任务不并行(单任务别派多个)。
账号 rate limit 实测 ≤1 并发,实操按串行设计,并发是奢望。
分流必汇合,不允许"派出去就不管"。
```

## 何时激活

- dao-plan 输出含 2+ 个独立(无相互依赖)Task
- /dev §二·造·编 阶段有可并行子任务
- 大批量同质改动(改 50 个文件 / 写 100 个测试)
- 多个独立调研 / 探索性查找

**不激活**:
- 任务有相互依赖(必须串行)
- 单一任务(派多 agent 是浪费)
- 账号已撞 rate limit(派出去也是 rate limited)
- 任务太轻(主会话直接做更快)

## 适合并行的判据(满足全部)

```
□ 真有 2+ 个任务?(不是 1 个伪装成多个)
□ 任务彼此独立?(无共享状态、无顺序依赖)
□ 每个任务都能独立 spec(派活四要素齐)?
□ 任务规模值得 subagent 调度开销?(单 task 太小不值)
□ 当前 rate limit 窗口有预算?(最近 1h 派过几次)
```

任一 NO → 改回串行 dao-execute。

## 实测限制(Windsurf 个人账户)

⚠️ **2026-05-08 实测**(T29 教训):

```
5 个并发  → 全 rate limited
2 个并发  → 全 rate limited
1 个 + 时间间隔 → 通过
```

**结论**:
- 个人账户实际并发 ≈ **1**
- 1 小时滚动窗口,打满后 "try again in about an hour"
- "no credits used" — 节流不扣费,但配额耗尽 1h 内不能再派
- Pro 账户上限可能更高,**自行实测**

**实操策略**:
- 即使任务"可并行",也用**串行 + 节流**(每个 subagent 间隔几分钟)
- 真需要并行的场景是 batch worker(N 个相同模板任务批量交给同一 worker 顺序做),而不是 N 个 subagent 各做一个
- "并行"作为**逻辑模型**保留,实际调度退化成串行

## 调度模式

### 模式 1: 真并行(Pro 账户或未来支持时)

```
Task 1, 2, 3 独立无依赖
  ↓
主会话同时派 3 个 subagent (run_subagent is_background=true × 3)
  ↓
等所有完成 (subagent_completion_notification × 3)
  ↓
主会话汇合产出 → dao-review
```

### 模式 2: 串行节流(个人账户实操)⭐

```
Task 1, 2, 3 独立无依赖
  ↓
主会话派 Task 1 → 等完成
  ↓
间隔(数十秒到数分钟,看 rate limit 窗口)
  ↓
主会话派 Task 2 → 等完成
  ↓
间隔
  ↓
主会话派 Task 3 → 等完成
  ↓
汇合产出 → dao-review
```

### 模式 3: 单 worker 批量(推荐:替代真并行)

```
Task 1, 2, 3 都是同一类型(如改 N 个文件用同一 pattern)
  ↓
合并成一个大 spec,派**单个** worker-batch subagent 顺序做
  ↓
worker 内部串行做 N 个,产出汇总 → dao-review
```

> 模式 3 是**最实用**的——避免 rate limit,避免多 subagent 调度开销,且 worker 内部对同类任务有 context 复用优势。

## 派活四要素(并行时尤其重要)

并行场景下,**任务边界**特别关键(避免多 worker 撞同一文件):

| 要素 | 单 task | 并行场景必加 |
|------|---------|-------------|
| Objective | 可观测产物 | 含"我的产物在哪个范围,别人的不归我管" |
| Output Format | 文件路径 + 模板 | **每个 worker 改的文件互不重叠** |
| Tools/Sources | 工具 + 参考 | 共享只读资源 OK,共享写入资源 NO |
| Boundaries | 不该做什么 | 含"不动其他 worker 的范围" |

## 失败处理

并行有部分失败时:

```
3 个并行 worker:
  ├─ Worker A: DONE
  ├─ Worker B: FAILED → 回打,回 dao-plan / spec-writer
  └─ Worker C: BLOCKED → 派 dao-debug

主会话:不等失败的强行往下,汇合阶段必须全部清晰
```

**不允许**"2 个成功,1 个先放着" —— 必须全部 PASS 才能汇合。失败的修完后再加进汇合。

## 反模式表

| 病 | 症状 | 道德经诊断 | 对治 |
|----|------|-----------|------|
| 单任务多派 | 1 个任务派 3 个 subagent | 不知止 | 单任务不并行 |
| 强并发 | 不顾 rate limit 一次派 5 个 | 不察实 | 实测 ≤1 并发,串行节流 |
| 任务有依赖还并行 | Task 2 依赖 Task 1 还并发 | 不知次 | 严守依赖图 |
| 派完不管 | 派 subagent 后忘了等结果 | 不汇合 | 必接 completion 通知 |
| 文件互踩 | 多 worker 改同一文件 | 不善下 | 每 worker 边界互不重叠 |
| 派"假并行" | 任务其实有共享状态 | 不诚 | 共享状态必串行 |
| 不验失败 | 一个失败照常汇合 | 不诚 | 失败必修完才汇合 |

## 涅槃门(并行汇合前)

- [ ] 每个并行 worker 都已 DONE 并贴 verification 证据
- [ ] 没有"先放着"的 BLOCKED / FAILED
- [ ] 文件改动范围互不冲突
- [ ] 总验证(全部 worker 完成后跑一次)pass

## 与其他 dao-* 协作

```
dao-plan
   │ 含独立 Task 1, 2, 3
   ▼
dao-execute
   ├─ 串行模式 → 自己处理
   └─ 并行模式 → dao-parallel(你)
        │
        ├─ Pro 账户:真并行派 3 worker
        ├─ 个人账户:串行节流派 3 次
        └─ 推荐:合并 spec 派单个 batch worker
        │
        ▼
   汇合 → dao-review
```

## 反原则(保留 dao 风格)

- **善下不争**——主会话不抢做事,让 worker 各自完成,自己只调度和汇合
- **不为并行而并行**——单 worker 顺序做几个 task 通常比多 worker 并行靠谱
- **水流不逆流**——任务有依赖就别强并行
- **江海善容**——汇合时主会话要容纳各 worker 的产出风格差异,不要苛求完全统一
