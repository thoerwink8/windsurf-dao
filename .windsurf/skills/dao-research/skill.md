# 前置研究术 · Research Lens

> 不出户，知天下；不窥牖，见天道。其出弥远，其知弥少。
> 是以圣人不行而知，不见而明，不为而成。

## 适用场景

- **设计阶段**：分析"这件事应该怎么做"时
- **技术选型**：多个方案可选，需要知道业界最优解
- **未知领域**：进入不熟悉的技术领域
- **卡壳时**：当前方案走不通，需要换思路

**不适用**：纯本地逻辑修改、已有明确方案的执行、简单bug修复

## 铁律

```
先研究，再设计，后编码。
不闭门造车，不重复发明轮子。
```

## 三步法

### 一、问道（☲视·明确要研究什么）

在搜索前，先提炼核心问题。模糊的搜索 = 无效的研究。

**提炼方法**：
1. 用户想要什么**效果**？（不是"怎么做"，是"做成什么样"）
2. 这件事的**领域关键词**是什么？（框架名、模式名、技术名）
3. 谁可能已经**解决过**类似问题？（开源项目、官方文档、社区）

**产出**：1-3 个精准搜索问题

### 二、采集（☵听·多源采集最优实践）

用搜索工具采集信息，**多源交叉验证**。

**工具选择**：

| 需求 | 工具 | 理由 |
|------|------|------|
| 库/框架的最新API | `context7` | 精准、最新、结构化 |
| 通用技术方案 | `search_web` | 广度覆盖 |
| 具体实现细节 | `read_url_content` | 深读关键文章 |
| JS渲染的文档站 | `playwright` | SPA内容需渲染 |
| 真实代码实现 | `github:search_code` | 代码不说谎——看别人怎么做比听别人怎么说更可信 |
| 参考项目/库 | `github:search_repositories` | 找到同类项目，学习架构和模式 |
| 读取仓库文件 | `github:get_file_contents` | 深读参考项目的关键实现文件 |

**采集原则**：
- **广度优先**：先 search_web 扫一遍全局，找到 2-3 个高质量来源
- **代码验证**：文章说的不一定对，GitHub 上的真实代码是最好的交叉验证。用 `search_code` 搜关键函数/模式名，看实际项目怎么用
- **深度跟进**：对最相关的 1-2 个来源用 read_url_content 或 get_file_contents 深读
- **官方优先**：官方文档 > GitHub 实现 > 技术博客 > Stack Overflow > 随机文章
- **时效性**：注意发布日期，2年前的方案可能已过时。GitHub 搜索可加 `pushed:>2025-01-01` 限定活跃项目
- **止于够用**：找到可信方案就停，不无限搜索。最多3轮搜索

**产出**：2-3 个候选方案 + 各自的优劣

### 三、融合（☳触·结合项目上下文综合方案）

> 天下皆知美之为美，斯恶已。

网上的最优解不一定是**你的**最优解。必须结合当前项目约束。

**融合维度**：

1. **技术栈兼容**：方案与当前项目的语言/框架/依赖是否兼容？
2. **复杂度适配**：方案的复杂度是否匹配问题的规模？（不过度工程）
3. **演化方向**：方案是否与项目的长期方向一致？
4. **实施成本**：引入新依赖的代价 vs 收益

**产出**：综合方案 = 最优实践 × 项目约束

**输出格式**（可根据场景简化）：

```
## 研究结论

**问题**：[一句话]
**最优实践**：[网上找到的最佳方案]
**项目适配**：[结合当前项目调整后的方案]
**理由**：[为什么选这个]
**参考**：[关键来源链接]
```

## 与推理链的关系

```
推理链（dao-philosophy.md §推理链 · 每条请求前）：
  观(意) → 静(止) → 朴(真) → 器(用) → 反(转) → 中(度)
                                ↑
                       研究术在「器(用)」步激活
                                            
资源优先（更新后）：
  skills → 本地workspace → 已有实现 → 【研究术：网络最优实践】→ 写代码
                                              ↑
                                     不再是兜底，而是设计阶段的标准动作
```

**触发判据**：
- 任务含"怎么做/如何实现/什么方案"的设计性质 → 自动触发研究术
- 纯执行性任务（已知怎么做，只需写代码）→ 跳过
- 简单问题（一行代码能解决）→ 跳过

## 与其他 Skills 的协作

```
dao-research（阴·知）  ←→  dao-boundary-probe（阳·验）
    问道→采集→融合            识壁→探路→择水
         ↘ 合 ↙
      （知行合一·执行）
```

- **研究术**告诉你"业界怎么做"，**边界探测术**验证"在这个系统中能不能做"
- 研究产出方案 → 边界探测验证可行性 → 综合决策

## 反模式

| 病 | 症 | 治 |
|----|------|------|
| 闭门造车 | 不搜就写，重复发明轮子 | 设计阶段必须至少搜一次 |
| 搜索依赖 | 每行代码都要搜 | 只在设计阶段研究，执行阶段靠自己 |
| 照搬照抄 | 网上方案原样复制，不适配项目 | 必须经过融合步骤 |
| 纸上谈兵 | 只看文章不看代码，方案停留在理论 | search_code 看真实实现，代码 > 文章 |
| 过度研究 | 搜了10篇文章还在搜 | 最多3轮，够用即止 |
| 时效盲区 | 用了5年前的过时方案 | 检查发布日期，context7查最新文档 |
| 权威崇拜 | 因为大厂用所以我也用 | 回到项目约束，适合的才是好的 |
