# 测试 · Red-Green Lens

> 知其雄，守其雌，为天下溪。
> 曲则全，枉则直；洼则盈，敝则新。
> ——《道德经》第 28、22 章

道家把"先示弱"放在创造之前——**先承认这段代码不会工作(看到 RED)**，才能见证它学会工作(GREEN)。
不肯守雌而直接写代码 = 假以为知。假知必生 bug，bug 必有代价。

## 铁律

```
不见红灯，不写一行实现代码。
不见绿灯，不言"完成"。
不见 refactor 后仍绿，不算闭环。
```

`NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`

> 字面与精神同等：先写代码后补测试 = 违反，不论怎么称呼。

## 何时激活

- 任何要写**新功能**之前
- 任何**修 bug** 之前(先写复现 bug 的失败测试)
- 任何**重构**已有代码之前(测试是重构的安全网)
- `/cycle` 测试镜头展开时
- 行为变更前(改公开 API、改业务逻辑)

**例外**(可与用户协商):一次性原型脚本、生成代码、配置文件。

> "想跳过 TDD 就这一次" = 合理化。停。

## 红绿循环 · Red-Green-Refactor

### RED · 守雌(承认未知)

> 知其雄，守其雌。先示无能，方见所成。

写**一个**失败测试，描述你想要的行为。

- 一次只写一个测试(一行 `and` 都是分裂信号)
- 测试名清晰描述行为(不是实现)
- 用真实代码,Mock 仅在不可避免时用
- 测试展示**期望的 API**——这是设计行为

#### RED 验证(必须,不可跳)

```bash
<跑这个测试>
```

确认:
- 测试 **fail**(不是 error)
- 失败信息符合预期
- 失败是因为 **feature 未实现**(不是 typo)

**测试立即 pass?** → 你测了已有行为。改测试。
**测试 error?** → 修 typo,重跑,直到 fail correctly。

### GREEN · 示雄(最小满足)

> 曲则全。绕个弯，反而完整。

写**最简单**能让测试 pass 的代码。

- 不加测试外的功能(YAGNI)
- 不重构其他代码
- 不"顺手优化"

#### GREEN 验证(必须)

```bash
<跑测试>
```

确认:
- 测试 **pass**
- **其他测试也仍 pass**
- 输出洁净——无 warning、无 error 噪音

**测试还 fail?** 改代码,不改测试。
**别的测试坏了?** 立刻修。

### REFACTOR · 全形(清理)

> 洼则盈，敝则新。低洼处反而装满，敝旧处反而焕然。

只在绿之后动手:
- 去重复
- 改名让含义清晰
- 抽出 helper

**保持绿**。**不加新行为**。

### 重复 · 周行不殆

下一个失败测试,下一个 feature。

## AAA 模式

每个测试遵循 **Arrange → Act → Assert**:

```typescript
test('retries failed operations 3 times', async () => {
  // Arrange: 准备
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  // Act: 执行
  const result = await retryOperation(operation);

  // Assert: 验证
  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

测试名格式:`should_[预期行为]_when_[条件]`。

## 测试类型选择

| 类型 | 场景 | 常用框架 |
|------|------|---------|
| 单元测试 | 纯函数、工具库 | Jest / Vitest / pytest |
| 集成测试 | 模块间交互 | Vitest / Mocha |
| E2E 测试 | 用户流程 | Playwright / Cypress |
| 回归测试 | Bug 修复验证 | 同上 |

## 必须覆盖的场景

- ✅ **正常路径**(Happy Path)
- ✅ **边界条件**(空值、极值、零、最大长度)
- ✅ **错误路径**(无效输入、权限不足、网络失败)
- ✅ **并发场景**(如适用)

## 覆盖优先级

核心逻辑优先,边界情况次之。**不追求 100% 覆盖率**——覆盖关键路径 > 覆盖行数。

## 反模式表

| 病 | 症状 | 道德经诊断 | 对治 |
|----|------|-----------|------|
| 测后写 | 写完代码补测试 | 不知雌而强为雄 | 删代码,从 RED 起 |
| RED 即过 | 测试一写就 pass | 测了"已有"非"应有" | 重写测试,确实 fail |
| 多变量同改 | 一次加 3 测试一并跑 | 不知一不能成 | 一次一个,逐个验 |
| 跳 verify-RED | 不跑测试就直接写实现 | 不亲见,不可信 | 必须看 fail |
| 跳 GREEN | 测试还红就报"完成" | 假涅槃 | 见绿才说话 |
| 跳 REFACTOR | 过了就提交 | 不慎终 | 清理才闭环 |
| 测实现非行为 | 改实现测试就破 | 测了"如何"非"何为" | 测 what 不测 how |
| 全 Mock 化 | 测试不接触真代码 | 离实远矣 | 减 mock,用真值 |
| "太简单不用测" | 跳过简单函数 | 轻敌则慎 | 没有"太简单" |
| "已经手动测过" | 用手代替自动 | 多言数穷 | 手动是临时,自动是长久 |

## 涅槃门(每个红绿循环)

- [ ] RED 看到 fail(不是 error,且失败信息符合预期)
- [ ] GREEN 看到 pass
- [ ] **其他测试仍绿**(无副作用)
- [ ] REFACTOR 后仍绿
- [ ] 输出无 warning,无 error 噪音

全通 = 闭环。任一未通 = 继续,不报"完成"。

## 与 dao-verify 的关系

TDD 是 dao-verify 在测试领域的具体形式:

```
dao-verify(通用):  声明前必有 fresh 证据
   └─ dao-test(测试):  声明"功能可用"前必有 RED→GREEN 双向证据
```

红绿循环 = 涅槃门的可执行版本。

## 反原则(保留 dao 风格)

- **不为测试而测试**——不追求 100% 覆盖
- **不为覆盖而生造 case**——关键路径优先
- **"我已经手动测了" ≠ TDD**——手动是临时,自动是长久
- **测试是设计**——好测试反映清晰设计;难测说明设计有问题
