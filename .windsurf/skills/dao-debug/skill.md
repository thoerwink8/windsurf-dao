# 调试诊断 · Debug Lens

> 知不知，上；不知知，病。夫唯病病，是以不病。

## 铁律

```
无根因，不修。
为之于未有，治之于未乱。
```

未完成第一层（听症），不得提出修复方案。每一层都是在积累证据，不是在猜测。

## 四层深入（对应 cycle 的螺旋层次）

低层能解决的不升高层。

### 第一层 · 听症（初转·法相·表层）

**不急于修，先让系统把话说完。**

1. **读完整错误信息**——不跳过、不略读。完整堆栈、文件名、行号、错误码、警告
2. **复现**——找到可靠的复现步骤。不可复现 → 加日志后重试，不猜
3. **查近期变更**——git log / git diff。能 git bisect 定位引入点 → 问题基本解决

**产出**：症状描述 + 复现步骤 + 近期变更列表
**判断**：根因已明 → 直接修（cycle 涅槃）。未明 → 第二层。

### 第二层 · 探脉（初转深化·观的第二深度）

**追踪数据流，找到断裂点。**

1. **加诊断日志**（不是修复，是观察）——在每个组件边界加入/出日志
2. **运行一次，收集证据**——不改任何逻辑，只加观察。对比期望值 vs 实际值
3. **隔离组件**——用最小用例单独测试可疑组件，Mock 上游输入

**产出**：数据流断裂点 + 可疑组件定位
**判断**：定位到具体函数/行 → 修。仍模糊 → 第三层。

### 第三层 · 辨根（二转·法性·结构层）

**停下来做模式分析，不再往前冲。**

1. **找对照组**——同代码库中类似的、正常工作的代码，逐项对比差异
2. **形成单一假说**——"我认为根因是X，因为Y"。写下来，不是"可能是A或B或C"
3. **最小验证**——只改一个变量验证假说。已试 3 个假说都失败 → **强制**升第四层

**产出**：经验证的根因假说

### 第四层 · 问道（三转·法空·本质层）

**3 次修复失败 = 不是 bug，是架构问题。退一步重新理解。**

1. **质疑架构**——模式/方案本身是否合理？是否在"因为已经写了所以坚持用"？
2. **质疑假设**——需求理解对吗？前提条件还成立吗？
3. **请用户介入**——至此必须止。清晰呈现：已做什么、排除了什么、当前最佳假说、建议方向

## 反模式

| 病 | 对治 |
|----|------|
| 一看就改 | 铁律：无根因不修 |
| 同时改多处 | 一次一个变量 |
| 改了3次还在猜 | 强制升第四层 |
| 加了日志不看 | 每条日志都要分析 |
| 修好不验证 | 必须复现"不再出现" |
| 改着改着范围扩大 | 回到听症，重新定位 |
