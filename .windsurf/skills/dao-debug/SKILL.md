# 死磕到底 · Relentless Debugging

> 天下之至柔，驰骋天下之至坚。无有入无间。
> 水善利万物而不争，处众人之所恶，故几于道。

## 铁律

```
不达目的，不罢休。
不穷尽手段，不求助。
不确认根因，不动手。
```

AI 的系统性弱点是**过早放弃**——降级为建议、转嫁给用户、在同一层面反复尝试。
本 skill 的存在意义：**把放弃变成系统性不可能，直到物理限制为止。**

## 何时激活

- 任何技术问题：Bug、构建失败、行为异常、性能问题、集成失败
- **尤其是**：已试过修复但没好、问题看起来"简单"但就是不工作、时间压力下
- **强制激活**：同一问题第 2 次出现、上一次修复是症状修复非根因

## 永动机：三层螺旋

每层包含多种武器。低层能解决的不升高层。每种武器只在有证据支撑时使用，不盲目扫射。

**螺旋规则**：
- 第一层 → 第二层 → 第三层 = 一圈
- 每圈结束后，如果有新信息，回到第一层重新审视 = 新一圈
- **最多螺旋 3 圈**，才允许请用户介入
- 请用户介入时必须带**完整证据链**：已尝试什么、排除了什么、当前最佳假说

### 第一层 · 常规诊断（听·看·追）

> 不急于修，先让系统把话说完。

**目标**：收集一手证据，定位断裂点。

| # | 武器 | 操作 | 产出 |
|---|------|------|------|
| W1 | **读完整错误** | 完整堆栈、文件名、行号、错误码、警告——不跳过不略读 | 症状描述 |
| W2 | **稳定复现** | 找到可靠复现步骤。不可复现→加日志后重试，不猜 | 复现步骤 |
| W3 | **查近期变更** | git log / git diff。能 git bisect 定位引入点→问题基本解决 | 变更范围 |
| W4 | **数据流追踪** | 在每个组件边界加入/出日志。运行一次收集证据，不改逻辑 | 断裂点 |
| W5 | **对照组** | 找同代码库中能工作的相似代码，逐项 diff 差异 | 差异清单 |

**判定**：
- 定位到具体函数/行 → 形成假说 → 修 → 验证 → 涅槃
- 仍模糊 → 进入第二层

### 第二层 · 深度搜索（挖·查·拆）

> 穷则变，变则通。

**目标**：用更强力的手段缩小搜索空间、增加信息量。

| # | 武器 | 操作 | 适用场景 |
|---|------|------|----------|
| W6 | **二分法** | git bisect / 代码块注释法 / 条件排除——每次排除一半 | 不知道哪个变更/哪段代码引入问题 |
| W7 | **最小复现** | 剥离到最小可触发 case——新文件、最少依赖 | 问题被环境/上下文掩盖 |
| W8 | **隔离组件** | Mock 上下游，单独测试每层 | 多组件系统，不确定哪层出问题 |
| W9 | **查资料** | context7 文档 / web 搜索 / GitHub issues / 官方 changelog | 怀疑是框架/库/平台的行为，非自身代码 |
| W10 | **逆向工程** | 读源码/反编译/node_modules 内部实现 | 文档不完整或行为与文档不符 |
| W11 | **诊断工具** | devtools / profiler / logcat / network inspector / heap snapshot / adb | 运行时状态不可见 |

**假说纪律**：
- 每次形成**单一假说**："我认为根因是 X，因为 Y"——写下来
- 只改**一个变量**验证假说
- 假说失败 → 记录排除项 → **换武器**，不在同一武器上重复 3 次
- 所有武器都试过 → 进入第三层

### 第三层 · 升维（退·破·建）

> 反者道之动，弱者道之用。退一步，是为了在更高处前进。

**目标**：改变问题本身。当第二层的手段都用尽时，问题不在细节层面——是假设或方向有误。

| # | 武器 | 操作 | 本质 |
|---|------|------|------|
| W12 | **换方向** | 绕过而非穿透。用另一种实现方式达到同样目的 | 路径执着是最常见的陷阱 |
| W13 | **质疑前提** | 需求本身合理吗？约束是真的吗？"必须用 X"是谁说的？ | 假设审计（第一性原理三问） |
| W14 | **降级方案** | 不追求完美解，先让系统可用，再逐步改善 | 80%解 > 0%完美方案 |
| W15 | **重建** | 从零写最小版本，逐步加回功能，看哪一步炸 | 终极隔离手段 |

**升维后**：
- 有新洞见 → 回到第一层重新审视（新一圈螺旋）
- 仍无进展 → 检查螺旋计数

## 螺旋计数器

```
圈数 = 0

每次走完第三层:
  圈数 += 1
  if 圈数 < 3:
    带着新信息回到第一层（新一圈）
  elif 圈数 == 3:
    强制止——向用户呈现完整证据链
```

**3 圈 = 硬上限**。超过意味着问题超出当前上下文的可解范围，继续死磕是浪费。

**呈现格式**（请用户介入时）：

```
## 死磕报告

### 已尝试（按时间顺序）
1. [武器] [操作] → [结果/排除了什么]
2. ...

### 已排除
- X 不是根因，因为 [证据]
- Y 方向不可行，因为 [证据]

### 当前最佳假说
[假说描述] + [支撑证据] + [无法自主验证的原因]

### 建议方向
- 选项 A: ...
- 选项 B: ...
```

## 反模式

| 病 | 症状 | 对治 |
|----|------|------|
| 一看就改 | 没读完错误就开始修 | 铁律：不确认根因，不动手 |
| 同时改多处 | 一次改了 3 个文件"看看行不行" | 一次一个变量 |
| 同一武器反复用 | bisect 了 5 次还在 bisect | 换武器，不在同一武器上超过 3 次 |
| 加了日志不看 | 加了 console.log 但没分析输出 | 每条日志都要分析 |
| 修好不验证 | 改了就说"应该好了" | 必须复现"不再出现" |
| 降级为建议 | "你可以试试..."、"建议检查..." | 铁律：能做就做，不说"你可以" |
| 转嫁给用户 | "请手动检查/重启/安装..." | 先自己做。只有物理操作才请用户 |
| 假涅槃 | 症状消失就宣布修好 | 理解根因 + 验证 + 无副作用 |
| 在同层打转 | 第一层试了 10 次不升层 | 严格按层推进，武器用尽就升层 |
| 过早求助 | 第一圈没走完就请用户介入 | 螺旋计数器 < 3，继续死磕 |

## 验证标准（涅槃门）

修复后必须逐项确认：

1. **根因已理解** — 能用一句话解释为什么出问题
2. **修复是根因修复** — 不是症状补丁
3. **复现路径不再触发** — 用原始复现步骤验证
4. **无副作用** — 相关功能仍正常
5. **教训已提炼** — 新洞见写入 AGENT_GUIDE.md

全通 = 涅槃。任一未通 = 继续。

## 实战洞见 · 从战场提炼的模式

> 知者不言，言者不知。塞其兑，闭其门，终身不勤。

### P1 · 上游逆向破局

**模式**：当你一直在修某个下游机制（如重载、缓存失效、事件同步），但怎么修都不生效时——**停下来，逆向目标系统的真实输入需求**。

**病理**：
```
表层问题：inject 后 soft reload 失败 → Windsurf 不识别新 token
执着路径：找更多 soft reload 命令 → 全部不存在 → OTT(25s) 兜底
```

**破局**：
```
逆向 NATIVE_CMD：handleAuthToken(token) → registerUser({ firebaseIdToken: token })
发现：它需要 Firebase ID token，不是 OTT，也不需要 soft reload
发现：服务端 allocate() 已经返回 firebaseIdToken（Firebase REST API <1s）
结论：答案早已在自己的代码库中，只是没连接起来
```

**检测信号**：你在下游反复修补（修了 A 又试 B、换了 C 还是不行）→ 升维到 W10+W13。

**操作处方**：
1. 停止修补下游。问："目标系统到底需要什么输入？"
2. 用 W10（逆向）追踪目标系统的入口函数
3. 用 W13（质疑前提）检查："我认为需要 X"是实测确认的吗？
4. 用 W5（对照组）检查：这个输入在我的代码库中是否已经存在？

**核心**：**下游修不通时，逆向上游需求。你缺的东西可能已经在手里。**

### P2 · 冻结自愈遗漏

**模式**：系统 A 在条件变化后新增了降级路径，但系统 B 的冻结逻辑仍按旧条件判定"永久不可用"。

**病理**：
```
旧世界：Firebase 密码登录失败 → 账号永久不可用 → 冻结
新世界：Firebase 失败但 OAuth 可用 → 账号仍可用
遗漏：冻结逻辑未更新，18 个可用账号躺在冰柜里
```

**检测信号**：引入新能力（降级路径、替代认证）后，检查所有"永久失败"判定是否仍成立。

**操作处方**：每次新增降级路径时，grep 所有 `setFrozen`/`markFailed` 调用点，逐个审查冻结条件是否仍有效。

### P3 · HTTP 客户端等 socket.on('end') 而 server 走 keep-alive（T176/T181）

**模式**：自己实现 HTTP 客户端（用 `net.createConnection` 绕过库），等 `'end'` 事件才解析响应——但 server 走 `Connection: keep-alive` 不主动关 socket。

**病理**：
```
GET / HTTP/1.1\r\nConnection: close\r\n   ← 客户端请求头
HTTP/1.1 200 OK ... Connection: keep-alive  ← Express/nginx 默认无视 close
socket 一直开着 → on('end') 永不触发 → 8s 兜底 timeout → 报「连接超时」
```

**误诊倾向**：先怀疑 server 卡死、网络抖动、DNS。实际 server 完全正常（外网 curl 89ms 通），是客户端等错了事件。

**操作处方**：
1. 先用 `curl -I` 看响应头有没有 `Connection: keep-alive` + `Content-Length`
2. 自实现 HTTP 客户端必须靠 `Content-Length` 字节数到位即处理 + 主动 `socket.destroy()`
3. 保留 `on('end')` 作为 chunked / 无 CL 兜底，不作为主路径
4. 项目特定：nginx + Express 默认 keep-alive 是常态，记 AGENT.md「项目特定坑」段

**核心**：**HTTP 终止判定靠协议层（Content-Length / chunked），不靠传输层（socket close）。**

### P4 · CPU 100% ≠ event loop 阻塞（T177）

**模式**：监控工具（pm2、top）显示 Node 进程 CPU 100%，第一假设"server 卡死/雪崩"。实际 Node 单线程占满 1 核 = 100% 是**常态**，与 event loop 是否阻塞无关。

**病理**：
```
pm2 list:  cpu 100%  ← 瞬时采样,Node 单核 100% = 设计如此
↓ 第一假设
"server 卡死,event loop 被阻塞"
↓ 实际验证
ssh curl http://127.0.0.1:3800/health → 200 OK 5ms
event loop 完全健康,HTTP 处理正常
```

**真实占用算法**：
```bash
ps -p <PID> -o pid,etime,time,%cpu
# TIME / ELAPSED 比值才是累积平均 CPU 占用
# 例: ELAPSED 27min / TIME 14:39 ≈ 54%
```

多个 `@Interval` / `setInterval` 后台任务合理满载也会刷出 100% —— 不是 bug。

**操作处方**：
1. 看到 pm2 / top CPU 100% 先**不要**假设"卡死"
2. 用本地 `curl 127.0.0.1:<port>/<快接口>` 试探 event loop 是否真阻塞（应秒级返回）
3. 若秒级返回 → 性能问题不存在，CPU 100% 是常态
4. 若超时 → 确实 event loop 阻塞，再用 W11 诊断工具（CPU profile、async_hooks）

**核心**：**Node CPU 100% 是单核满载，不是 event loop 阻塞。诊断前用本地快接口试探。**
