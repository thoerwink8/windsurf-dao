# 解耦 · Decouple Lens

> 万物负阴而抱阳，冲气以为和。——第 42 章
> 模块之间，当阴阳各守其分，以接口为气，冲和则不病。

**核心**：代码耦合不是错——**不知道自己耦合在哪里**才是错。阴阳纠缠不分 = 气滞。本 skill 帮你找到气滞之处。

## 与现有 skill 的边界

| skill | 对象 | 视角 |
|---|---|---|
| `dao-refactor` | 单文件/单函数 | **怎么改**——Extract Method / DRY / Rename |
| `dao-full-coverage` | 整个项目 | **有没有病**——8 维度扫描 |
| `dao-optimize` | 性能瓶颈 | **快不快**——CPU / 内存 / IO |
| **`dao-decouple`** | **模块间关系** | **该不该分**——职责、状态、时序、信号的纠缠度 |

dao-refactor 是手术刀（改代码），dao-decouple 是 CT 扫描（诊断结构）。先扫描再手术。

## 何时激活

**被动触发**（AI 检测到以下信号时主动加载）：

- Bug 修复涉及 ≥3 个文件的跨模块改动
- 改一个函数的逻辑需要理解另外 ≥2 个文件的状态
- 同一个全局状态对象（如 `S.*`）被 ≥5 个文件直接读写
- 函数参数中传递了"上帝对象"（一个参数包含 ≥5 个无关字段）
- 错误处理链穿透 ≥3 层（error → detect → switch → retry → inject）
- 用户说"改不动"、"牵一发动全身"、"不知道该改哪里"

**主动触发**：

- 用户说"分析耦合"、"是否需要解耦"、"模块太大了"、"拆一下"
- `/dao-cycle` 省阶段审视清单第 3 项（有没有影响到其他模块）发现牵连过广

## 六维耦合扫描

### 1. 职责纠缠（Responsibility Tangling）

> 一个函数/文件承担了多少个不相关的职责？

```
扫描方式：
□ 文件 LOC > 500 行 → 高嫌疑
□ 函数 LOC > 80 行 → 高嫌疑
□ 函数名含 "and" / 多个动词 → 中嫌疑
□ 注释中出现 "Phase X" / "Step X" > 3 处 → 多阶段混杂在一个函数
□ 一个文件 export 的公共函数 > 10 个 → 职责过载
```

**实例**（无感切号 `switch-engine.ts`）：`doSwitch` 函数集成了认证、切号、状态恢复、续连调度、云模式降级——5 个独立职责。

### 2. 共享状态蔓延（Shared State Sprawl）

> 一个状态对象被多少个模块直接读写？

```
扫描方式：
□ grep 全局状态对象（如 S.xxx）的引用文件数
□ 可写引用 > 3 个文件 → 状态蔓延
□ 读引用 > 5 个文件 → 考虑 accessor 封装
□ 状态字段数 > 20 个 → 状态对象本身需要拆分
```

**判定**：写入同一状态的文件越多 → 竞争条件 & 因果推理链越长 → 越需要解耦。

### 3. 时序依赖（Temporal Coupling）

> 操作 A 必须在操作 B 之前完成，但这个约束没有被代码结构表达。

```
扫描方式：
□ 注释中出现 "must be called after" / "先调用 X 再调用 Y" → 隐式时序
□ await A(); await B(); 且 B 依赖 A 的副作用（非返回值）→ 隐式时序
□ 事件监听器的注册顺序影响行为 → 脆弱时序
```

**对治**：时序依赖应被封装为 pipeline / state machine，而非散落在调用方。

### 4. 信号蛛网（Signal Spaghetti）

> 事件/信号/回调跨模块传播，形成不可追踪的连锁反应。

```
扫描方式：
□ 一个事件被 ≥3 个不同模块监听 → 高扇出
□ 一个处理函数触发另一个事件再触发第三个 → 连锁反应
□ 错误信号触发切号，切号触发续连，续连触发注入 → 三跳以上
□ 无法画出清晰的信号流向图 → 蛛网
```

**实例**（无感切号）：S0 错误 → `handleSignal` → `onErrorDetected` → `doSwitch` → `_scheduleRetryAfterSwitch` → `dispatchContinue` — 5 跳。

### 5. 导入扇入/扇出（Import Fan-in/Fan-out）

> 一个模块依赖/被依赖的模块数量。

```
扫描方式：
□ 扇出 > 8（一个文件 import ≥8 个本项目模块）→ 该文件是 god module
□ 扇入 > 6（一个文件被 ≥6 个本项目模块 import）→ 该文件是瓶颈/基础设施
□ 双向导入（A import B 且 B import A）→ 循环依赖
```

**注意**：高扇入不一定是问题（utils 被广泛引用是正常的），但高扇入 + 高变更频率 = 风险。

### 6. 修改耦合（Change Coupling）

> 改一个文件时，实际上总是要同时改另一个文件。

```
扫描方式：
□ git log --follow --name-only 分析共变文件对
□ 最近 20 次 commit 中 A 和 B 共同出现 ≥5 次 → 强修改耦合
□ 共变但无直接 import → 隐性耦合（最危险）
```

**判定**：共变文件要么应该合并，要么应该通过接口解耦。

```markdown
## 解耦策略推荐

| 模式 | 适用 | 做法 |
|---|---|---|
| Extract Module | 职责纠缠 | 把独立职责提取为新文件 |
| State Accessor | 状态蔓延 | 读写统一经过 getter/setter |
| Pipeline | 时序依赖 | 显式步骤链取代隐式顺序 |
| Event Bus | 信号蛛网 | 中央事件总线取代直接调用 |
| Facade | 高扇入 | 暴露简化接口隐藏内部 |
| Interface | 双向依赖 | 抽象接口打破循环 |
```

## 执行流程

```
1. 确定扫描范围
   - 用户指定模块 → 扫该模块 + 直接依赖
   - 用户指定问题 → 从问题文件出发向外扩展 2 层
   - 无指定 → 按文件大小排序取 top 10 + 按变更频率取 top 10

2. 六维扫描
   - 逐维度跑检查项（grep / git log / import 分析）
   - 每维度给出严重度（🔴/🟡/🟢）
   - 记录具体证据（文件:行号 或 git commit hash）

3. 产出报告
   - 按上述格式输出
   - 🔴 项必须给出具体解耦方案（不是"建议拆分"这种废话）
   - 方案必须包含：目标文件路径 + 移动哪些函数 + 新接口定义

4. 联动
   - 用户确认后，派 dao-refactor 执行具体拆分
   - 大规模解耦（≥3 文件 / ≥100 LOC）建议走 /dao-superpowers
```

## 反模式

| 病 | 症状 | 对治 |
|---|---|---|
| 过度解耦 | 3 行函数也要拆文件 | 耦合有度——内聚高时不必拆 |
| 只诊不治 | 出了报告不给方案 | 🔴 项必须有可执行方案 |
| 形式解耦 | 拆了文件但全局状态照用 | 解耦 = 减少共享，不是减少文件 |
| 忽略内聚 | 相关逻辑分散到 5 个文件 | 高内聚 > 低耦合；先聚再拆 |
| 大爆炸重构 | 一次全拆 | 渐进式：一次解耦一个维度 |

## 与其他 dao-* 协作

- `dao-refactor`（下游·执行）— 本 skill 出诊断报告，dao-refactor 执行拆分手术
- `dao-debug`（上游·触发）— debug 发现"改不动"时触发本 skill
- `dao-full-coverage`（正交）— 那是 8 维度健康检查，本 skill 专注模块间关系
- `dao-observability`（互补）— 解耦后新模块边界需要追踪日志（加载 dao-observability）
- `dao-plan`（下游）— 大规模解耦需要 plan 文件指导
- `/dao-superpowers`（下游·流程）— 解耦方案涉及 ≥3 文件时建议走五步流程

## 快速命令参考

```powershell

rg "S\.\w+" --type ts -l | Sort-Object | Get-Unique

# 维度 5: 导入扇出统计
rg "^import .+ from '\./[^']+'" --type ts -c | Sort-Object { [int]($_ -split ':')[-1] } -Descending

# 维度 6: 修改耦合分析
git log --oneline -20 --name-only -- "src/*.ts" | Select-String "\.ts$"
```

## 省

- 报告是否覆盖了六个维度？（遗漏 = 盲点）
- 🔴 项的方案是否具体到文件路径 + 函数名？（模糊 = 废话）
- 解耦方案是否会降低内聚？（拆散 > 拆分 = 走火入魔）
- 有没有"不需要解耦"的结论？（不是所有耦合都是病——高内聚模块内部耦合是健康的）
