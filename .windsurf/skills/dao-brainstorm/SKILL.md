# 析 · Brainstorming Lens

> 不知常，妄作凶。
> 知人者智，自知者明。
> ——《道德经》第 16、33 章

「常」是事物本然的运转规律。在挖出用户的「常」(真实意图、约束、成功标准)之前就动手,等同妄作。
**苏格拉底式追问**正是认识「常」的方法——不是替对方想答案,而是问出对方自己都没说出口的真实需求。

## 铁律

```
不挖出真实意图,不进 plan 阶段。
不探索 2-3 个方案,不写 design。
不分块审批 design,不进实施。
```

**HARD-GATE**:design 文档未经用户审批前,**不**调用任何实施型 skill、不写代码、不脚手架、不动文件。这条铁律对**所有项目**都生效——哪怕用户说"这个很简单,直接做"。

## 反模式 · "这个太简单不用 design"

每个项目都过这个流程。一个 todo list / 一个工具函数 / 一个配置改动——**都过**。
"简单"项目正是"未经检验的假设"造成无用功最多的地方。
design 可以短(简单项目几句话即可),但**必须呈现并取得审批**。

> 简则简,但不可省。曲则全,枉则直。

## 何时激活

- 用户提出新功能 / 重构想法 / 模糊需求
- 用户说"我想做 X"(X 是开放性目标)
- 进入 dao-dev §一·谋·析 阶段
- 任何"看起来简单"但其实需要决策的事

**不激活**:
- 任务已经具体到细节(派 dao-plan)
- bug 修复(派 dao-debug)
- 紧急 hotfix(可临时跳过,但事后补 design)

## 9 步检查清单(按顺序完成)

```
1. 探索项目上下文     ── 读文件、文档、近期 commits
2. 评估范围            ── 多子系统? → 先拆,不要在一份 spec 里塞多事
3. 一次一个澄清问题   ── 多选优先,理解 purpose / constraints / 成功标准
4. 提 2-3 个方案对比   ── 含 trade-off + 你的推荐 + 理由
5. 分块呈现 design    ── 每块按复杂度配字数,逐块取得审批
6. 写 design 文档      ── 路径 docs/specs/YYYY-MM-DD-<topic>-design.md,commit
7. spec 自审           ── 占位符 / 内部一致 / 范围 / 歧义,逐项扫
8. 用户审 spec 文档    ── 等用户批,有改动重写
9. 进 dao-plan         ── 这是唯一的下一站
```

> "终点" = 调用 `dao-plan`。**不**直接调用任何实施型 skill。

## 提问纪律

- **一次一个问题**——不要一条消息塞 5 个问题
- **多选优先**——比开放问题好回答
- **聚焦**purpose / constraints / 成功标准
- **不引入用户没用过的术语**——用对方话术
- **不替用户做决定**——给选项,让用户选

## 提方案纪律

- **2-3 个**(含"什么都不做"的对照)
- **每个含 trade-off**(优缺点)
- **明确推荐 + 理由**(不要"看你"模糊化)
- **YAGNI**——不要把"将来可能用到"塞进当前方案

## design 文档格式

```markdown
# Design: <feature/topic name>

## 我理解你想做的事
<用用户话术,1 段总结>

## 真正要解决的问题
<挖出的深层意图,1 段>

## 备选方案
### 方案 A: <名称>
- 怎么做 / 优势 / 劣势
### 方案 B: <名称>
- 同上
### 方案 C: 不做
- 什么时候选这个

## 推荐方向
<选哪个 + 为什么>

## 接下来的开放问题
<还需用户决定的事项,列表>

## 不在本次范围
<明确说不做什么,避免 scope creep>
```

**关键约定**:文档**分块输出**,每块输出后等用户确认("这一段对吗?"),不一次甩 5 段。

## spec 自审 4 项

写完 design 后用新眼光过一遍:

| 检查 | 问什么 | 修法 |
|------|--------|------|
| 占位符扫描 | 有 TBD / TODO / 模糊需求? | 全部填实 |
| 内部一致 | 各段是否互相矛盾?架构与功能描述对得上? | 修矛盾 |
| 范围检查 | 是否聚焦到能做单一实施 plan? | 范围过大就拆子项目 |
| 歧义检查 | 是否有可两种解读的需求? | 选一个明确写 |

修完不必复审,直接进下一步。

## 用户 design 审批门(关键关卡)

spec 自审通过后,**必须**问用户:

> "design 已写到 `docs/specs/<path>`。请审一下,有要改的告诉我,确认后再进 plan。"

**等用户响应**。改了就重审,直到用户批。**不偷跑**。

## 反模式表

| 病 | 症状 | 道德经诊断 | 对治 |
|----|------|-----------|------|
| 不析就编 | 跳过 design 直接写代码 | 不知常妄作 | HARD-GATE,不议不动 |
| 一次问 5 个 | 一条消息塞多个问题 | 多言数穷 | 一次一个 |
| 用术语压人 | 用对方不懂的词追问 | 不知人 | 用对方话术 |
| 替用户决定 | 不给选项,直接推方案 | 不自知 | 提选项让选 |
| 跳过备选方案 | 第一个想到的就推 | 企者不立 | 至少 2-3 个对比 |
| 一甩到底 | design 一次性输出 5 段 | 不慎重 | 分块,逐块审 |
| "太简单不用 design" | 觉得显然就跳过 | 假以为知 | 简也写,可短 |
| 跑 spec 但不让用户审 | 自审完就动手 | 独断 | 用户审是关卡 |

## 涅槃门(进 dao-plan 前)

- [ ] 真实意图已挖出
- [ ] 至少 2-3 个备选方案 + 推荐
- [ ] design 文档已写并 commit
- [ ] spec 自审 4 项全过
- [ ] **用户已显式批准 design**

任一未通 = 不进 dao-plan。

## pencil 设计阶段(design 审批后、plan 前)

design spec 批准后,如果项目涉及 UI,在进 dao-plan 之前先做 pencil 设计:

```
design spec 审批通过
    ↓
pencil 设计(有 UI 时)
    ├── Token 层 → pen 变量(色板/字体/间距/圆角)
    ├── 业务组件 → reusable 组件(PoolColumn / RoundSection / ...)
    └── 页面设计稿 → 完整屏幕 × light/dark
    ↓
dao-plan(拆任务时引用 pencil 设计稿)
```

**何时做 pencil 设计**:design spec 含 UI 变更(新页面/新组件/视觉重设计)
**何时跳过**:纯后端/纯逻辑/配置变更/bug 修复

详见 `.windsurf/rules/design-assets.md`。

## 与其他 dao-* 协作

```
dao-brainstorm (你)
   │
   ├── 输出: design 文档(已审批)
   │
   ├── [有 UI] pencil 设计阶段
   │
   ▼
dao-plan
   │
   ├── 输出: 2-5 分钟粒度任务清单
   │
   ▼
dao-execute / 主会话直接做
```

**横切**:任何阶段有 bug → dao-debug;任何完成声明 → dao-verify。

## 反原则(保留 dao 风格)

- **简则简**——简单项目 design 可只一段,但仍要审
- **不为流程而流程**——用户已说清的部分不要重问
- **挖出 ≠ 暴露**——挖到的真实意图不必让用户重复确认显然部分
