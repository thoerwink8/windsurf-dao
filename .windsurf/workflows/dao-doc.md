# 文档 · Doc

> 信言不美，美言不信。善者不辩，辩者不善。
> 知者不博，博者不知。
> 圣人不积，既以为人，己愈有；既以与人，己愈多。

## 铁律

```
文档写给下一个人。
可能是用户，可能是队友，可能是三个月后的自己。
写完后问：如果我什么都不记得了，这份文档能让我重新上手吗？
```

## 触发条件

- 新项目需要 README
- API 变更需要更新文档
- 架构决策需要记录
- 用户显式调用 `/doc`
- `/dev` 管线的「书」阶段

## 两种模式

### 生（从无到有）
项目已有代码但无文档，或需要全新文档。

### 更（从旧到新）
代码变了，文档需要跟上。

## 流程 · 四步

### 一、读（☲离 · 视 · 照见全貌）

> 不出户，知天下；不窥牖，见天道。

先读懂，再动笔。不懂的东西写不出好文档。

**生模式：**
1. 读项目结构（目录、文件组织）
2. 读入口文件（package.json / main / index）
3. 读核心模块（关键逻辑、数据流）
4. 读已有文档（哪怕只有注释）
5. 运行项目（如果能跑的话），体验实际行为

**更模式：**
1. 读变更（git diff / 最近改了什么）
2. 读现有文档（哪些部分受影响）
3. 对比：文档描述 vs 代码现实

**产出**：项目理解 + 文档差距清单

### 二、定（☶艮 · 味 · 止而定型）

> 始制有名，名亦既有，夫亦将知止。

确定写什么、不写什么。文档最大的病是写太多。

1. **选择文档类型**

| 类型 | 目的 | 何时写 | 何时不写 |
|------|------|--------|----------|
| **README** | 项目门面：是什么、怎么用、怎么跑 | 任何项目都应有 | — |
| **API文档** | 接口契约：端点、参数、返回 | 有API供他人调用时 | 纯内部逻辑 |
| **架构说明** | 设计决策：为什么这样做 | 中大型项目、多人协作 | 小脚本 |
| **变更日志** | 演化记录：什么变了 | 版本发布、破坏性变更 | 内部开发阶段 |
| **使用指南** | 用户路径：一步步教 | 面向非技术用户 | 开发者工具 |

2. **确定范围**
   - 必写：用户/读者需要知道的
   - 不写：代码本身已经说清楚的
   - **原则**：知者不博——精准胜过全面

3. **确定语气**
   - README：简洁直接
   - 架构说明：技术严谨
   - 使用指南：友善引导
   - 一致性：同一文档不混用语气

### 三、写（☳震 · 触 · 一笔到底）

> 善行无辙迹，善言无瑕谪。

好文档像好代码——看完不觉得它在那里，但缺了就迷路。

**写作原则**（铁律，高于模板）：
- **信言不美**：每句话都有信息量，删掉所有"废话填充词"
- **善者不辩**：不解释显而易见的事，不为设计辩护
- **示例胜千言**：能用代码示例说清的，不用文字描述
- **命令可复制**：所有命令都可以直接 copy-paste 运行
- **路径要准确**：每个文件引用都是真实存在的

> 模板内化于 AI——README/API/架构说明的标准格式无需写出，按类型自然生成。

### 四、校（☵坎 · 听 · 回响验证）

> 名与身孰亲？

写完不校 = 没写。文档最怕的不是少，是错。

// turbo
1. **事实校验**
   - 所有命令：真的能跑吗？
   - 所有路径：真的存在吗？
   - 所有示例：真的是当前代码的输出吗？
   - 版本号/依赖：是最新的吗？

2. **完整性校验**
   - 新人看完能上手吗？
   - 关键步骤有遗漏吗？
   - 前置条件说清楚了吗？

3. **一致性校验**
   - 术语统一？
   - 格式统一？
   - 与代码中的命名一致？

**更模式额外步骤：**
   - 旧内容是否已更新/删除？
   - 变更是否反映在所有相关位置？

**产出**：校验通过的文档

## 与其他工作流的关系

```
/dev 管线 → 「三·成」阶段的「书」 → 调用 /doc
/doc 内部 → 复杂架构文档可触发 /cycle 迭代
/doc 独立 → 任何时候需要文档都可直接触发
```

## 损之又损 · 文档的减法

文档不是越多越好。每次写完后做减法：

1. **删重复**：两处说了同一件事 → 只留一处
2. **删显然**：代码命名已经说清楚的 → 不再赘述
3. **删过时**：描述的是旧行为 → 更新或删除
4. **删没人看的**：三个月没人查阅的文档 → 考虑归档

> 为道日损。损之又损，以至于无为。
> 最好的文档是不需要文档——代码本身就是文档。
> 次好的文档是最短的完备文档。

## 反模式

| 病 | 道德经诊断 | 对治 |
|----|-----------|------|
| 写成百科全书 | 博者不知 | 精准胜全面，够用即止 |
| 华丽但不准确 | 美言不信 | 信言不美，每句可验证 |
| 命令跑不通 | 假涅槃 | 校验阶段必须实跑 |
| 写了不更新 | 死而不亡者寿 | 更模式：代码变则文档变 |
| 重复造轮子 | 多言数穷 | 链接已有文档，不重写 |
| 解释显而易见的事 | 善者不辩 | 相信读者的智力 |

## 执行格式

启动时：

```
## 📝 /doc 启动
### 模式：[生/更]
### 类型：[README/API/架构/变更日志/使用指南]
### 范围：[涉及哪些模块/文件]
```

交付时：

```
## 📝 /doc 完成
### 生成/更新：[文件路径]
### 校验：[命令可跑 ✓ / 路径正确 ✓ / 示例准确 ✓]
### 损：[删除了什么冗余内容]
```
