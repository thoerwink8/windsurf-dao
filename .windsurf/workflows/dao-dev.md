# 开发管线 · Dev Pipeline

> 合抱之木，生于毫末；九层之台，起于累土；千里之行，始于足下。
> 图难于其易，为大于其细。天下难事，必作于易；天下大事，必作于细。

## 触发条件

- 用户给出需求（一句话或一段描述），期望完整交付
- 新项目从零开始，或现有项目的完整功能模块
- 用户显式调用 `/dev`

## 总览 · 道生万物

```
一句话需求
    ↓
┌─ 一 · 谋 ─┐   道生一：从混沌到清晰
│  析 → 设   │
└────┬───────┘
     ↓ 🔒 用户确认方向
┌─ 二 · 造 ─┐   一生二：从图纸到实体
│ 编→筑→部  │
└────┬───────┘
     ↓ 🔒 用户预览
┌─ 三 · 成 ─┐   二生三：从实体到交付
│ 试→验→书  │
└────┬───────┘
     ↓ 🔒 用户验收
  万物 · 涅槃
```

**三个关卡（🔒）是止（艮）的时刻**——确认后才继续，避免南辕北辙。

**静默模式**（深度工作模式激活时）：
> 大音希声。善行无辙迹。

关卡降级规则：
- 方向明确（需求具体+技术选型无争议）→ 🔒自动通过，不中断执行
- 方向有歧义（多种合理路径）→ 🔒仍止，ask_user_question
- 静默≠跳过思考。每个关卡仍内部评估，只是不输出中间文字
- 最终报告包含所有阶段产出的压缩总结

## 一 · 谋（道生一 · 从混沌到清晰）

> 为之于未有，治之于未乱。

谋定而后动。这一阶段不写代码，只让需求从一句话变成可执行的图纸。

### 1.1 析 · 需求分析（☲离 · 视 · 照见本质）

从一句话中提取完整信息。

1. **解构需求**
   - 用户要什么？（功能目标）
   - 给谁用？（用户画像）
   - 有什么约束？（技术栈、平台、性能、截止时间）

2. **知彼**（集成/逆向/对接外部系统时）
   - 目标系统的隔离边界在哪？（权限、作用域、沙箱）
   - 哪些路径看起来通但实际不通？（读代码≠验证可行，关键假设须实调确认）
   - 最小验证：在写任何代码前，用最短路径验证核心假设能跑通

3. **补全缺失**
   - 用户没说但必须决定的事项
   - 小缺失：AI自行决定，在设计中注明
   - 大缺失（影响方向）：ask_user_question，最多问一轮
   - **原则**：认知卸载——替用户想到他没想到的，不制造新的认知负担

4. **拆解范围**
   - MVP（最小可行）包含什么？
   - Nice-to-have 是什么？
   - 明确不做什么？（划边界）

**产出**：需求清单（功能列表 + 约束 + 范围边界）

### 1.2 设 · 架构设计（☶艮 · 味 · 止而品）

在动手前把方案想清楚。

1. **技术选型**
   - 框架、语言、工具链
   - 优先用户已有的技术栈
   - 无偏好时选主流+轻量方案

2. **结构设计**
   - 目录结构
   - 核心组件/模块划分
   - 数据流/状态管理
   - 关键接口定义

3. **实施计划**
   - 编码顺序：依赖 → 核心 → UI → 集成
   - 预估复杂度：哪些部分可能需要 /cycle
   - 风险点：哪些部分可能触发 /debug-escalation

**产出**：设计方案（技术栈 + 结构 + 计划）

### 🔒 关卡一：方向确认

向用户呈现：
```
## 📋 设计方案
### 需求理解：[一句话总结]
### 技术选型：[框架/工具]
### 核心结构：[组件列表]
### 实施计划：[步骤概要]
→ 确认后开始编码
```

用户确认 → 进入「二·造」
用户调整 → 修订后重新确认

## 二 · 造（一生二 · 从图纸到实体）

> 天下大事，必作于细。

按计划逐步构建。每个步骤都是一个完整的小交付。

### 2.1 编 · 编码实现（☳震 · 触 · 一触推到底）

按设计方案的顺序，逐模块实现。

1. **依赖先行**
   - 创建项目骨架（package.json / requirements.txt 等）
   - 安装依赖
   // turbo
   - 配置基础设施（linter、tsconfig 等）

2. **核心模块**
   - 按设计的组件顺序，逐个实现
   - 每个组件：接口 → 实现 → 基本验证
   - **原则**：一触推到底——开始一个组件就做完，不留半成品

3. **UI/交互层**（如适用）
   - 美观现代的界面（不是毛坯）
   - 响应式、无障碍
   - 最佳UX实践

4. **集成**
   - 连接各模块
   - 端到端基本流程能跑通

**如某模块复杂度高** → 对该模块启动 `/cycle`
**如编码中发现设计缺陷** → 记录，完成当前模块后评估是否需要回到「设」

### 2.2 筑 · 构建（☵坎 · 听 · 听回响）

让系统编译/构建，听它的反馈。

1. **构建配置**：涉及凭证管理、商业分发或用户明确表达时，加入代码混淆（`wg:obfuscate: true`）；其余场景保持简洁。

2. **构建**
   // turbo
   - 运行 build / compile
   - 如有错误 → 先读完所有错误再修（不一个一个改）

3. **构建失败** → 启动 `/debug-escalation` 第一层
   - 多数构建错误在听症层就能解决
   - 如升级到第二层以上，记录为风险点

### 2.3 部 · 部署/启动（☵坎 · 听 · 水就下）

让系统跑起来。

1. **本地启动**
   - 启动 dev server（非阻塞）
   - 等待就绪信号

2. **预览**
   - browser_preview 让用户看到实际效果
   - 或提供可访问的URL

**启动失败** → `/debug-escalation`

### 🔒 关卡二：用户预览

```
## 👁️ 预览就绪
### 已实现：[功能列表]
### 预览地址：[URL]
→ 请查看，反馈调整意见或确认进入测试
```

用户满意 → 进入「三·成」
用户要调整 → 回到「编」修改，再构建部署

## 三 · 成（二生三 · 从实体到交付）

> 慎终如始，则无败事。

最后阶段不是收尾，是让交付物从"能用"变成"可信赖"。

### 3.1 试 · 测试（☱兑 · 说 · 让系统开口）

1. **功能测试**
   - 对照需求清单，逐项验证
   - 正常路径 + 边界情况 + 异常输入

2. **自动化测试**（如适用）
   - 核心逻辑的单元测试
   - 关键流程的集成测试
   // turbo
   - 运行测试套件

3. **视觉/交互测试**（如有UI）
   - 不同视口 / 设备
   - 无障碍检查
   - 性能基本检查

**测试发现bug** → `/debug-escalation`

### 3.2 验 · 验证（☲离 · 视 · 回到本源）

回到最初的一句话需求，对照验证。

1. **需求对照**
   - 逐条检查：每个需求是否已实现？
   - 遗漏 → 补。偏离 → 修

2. **质量检查**
   - 代码简洁无冗余（为道日损）
   - 无硬编码/临时代码遗留
   - 错误处理完备

3. **涅槃判定**
   - [ ] 功能完备：需求清单全部✓
   - [ ] 构建通过：无错误无警告
   - [ ] 测试通过：自动化测试全绿
   - [ ] 体验自然：用户流程顺畅（无为而无不为）
   - [ ] 代码清净：无多余（为道日损）

### 3.3 书 · 文档（☴巽 · 风 · 传灯）

让成果可交接、可延续。

1. **README**
   - 项目描述（一句话）
   - 安装/运行步骤
   - 使用说明

2. **架构说明**（复杂项目）
   - 目录结构说明
   - 关键设计决策
   - 扩展指南

3. **交付总结**
   - 实现了什么
   - 技术栈
   - 已知限制 / 后续建议

**原则**：文档是给下一个人（可能是未来的自己）看的。
**反原则**：不写没人看的文档。README足够就只写README。

### 🔒 关卡三：用户验收

```
## ✅ 交付总结
### 需求：[原始一句话]
### 实现：[功能列表 + 技术栈]
### 文档：[README位置]
### 验证：[测试结果]
→ 请验收
```

## 工作流协作

```
/dev 管线中的每个阶段都可以调用其他工作流：

                    ┌──────────────┐
                    │   /dev 管线   │
                    └──┬───────────┘
                       │
         ┌─────────────┼─────────────┐
         ↓             ↓             ↓
    某模块需要      遇到bug       需要深度
    深度打磨        难以定位      架构重构
         ↓             ↓             ↓
     /cycle      /debug-escalation  /cycle
    转法轮迭代     调试升级       转法轮迭代
```

## 反模式

| 病 | 道德经诊断 | 对治 |
|----|-----------|------|
| 不析就编 | 不理解就行动 | 铁律：谋定而后动 |
| 盲建 | 知己不知彼 | 集成外部系统时，目标系统的约束（隔离、权限、边界）是析的一部分，不是编时才发现的 |
| 读当验 | 以观代行 | 读懂代码≠验证可行。关键假设必须实际调用确认，观与验不可替代 |
| 熵遗 | 为学日益之弊 | 分析脚本、临时查询等中间物用完即清，不留散落 |
| 过度设计 | 企者不立 | MVP先行，够用即止 |
| 毛坯交付 | 慎终如始 | UI/UX不是可选的 |
| 跳过测试 | 假涅槃 | 验是必经之路 |
| 文档堆砌 | 多言数穷 | 够用即止，不写废话 |
| 不等确认就继续 | 独断 | 三个关卡必须止 |

## 执行格式

管线启动时：

```
## 🚀 /dev 启动
### 需求：[用户原话]
### 预估复杂度：[低/中/高]
### 预估阶段：[哪些阶段需要重点关注]
```

每个阶段完成时：

```
### [阶段名] ✓
- 产出：[...]
- 耗时/复杂度：[...]
→ [进入下一阶段 / 等待用户确认]
```

管线结束时：

1. **AGENT_GUIDE.md**（若项目有此文件）：在演化记录区追加版本条目（变更/根因/教训）
2. **虚·归位**：按法层「虚·知识归位」机制清理 Memory（见 dao-fa-layer.md）

```
## 🏁 涅槃
### 从 [一句话需求] 到 [完整交付]
### 经历：[阶段回顾]
### 成果：[文件/URL/文档列表]
### 虚：[归位了什么 / Memory已清空]
```
