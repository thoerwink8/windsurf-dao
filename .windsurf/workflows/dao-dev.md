# 开发管线 · Dev Pipeline

> 合抱之木，生于毫末；九层之台，起于累土；千里之行，始于足下。
> 图难于其易，为大于其细。天下难事，必作于易；天下大事，必作于细。

## 触发条件

- 用户给出需求（一句话或一段描述），期望完整交付
- 新项目从零开始，或现有项目的完整功能模块
- 用户显式调用 `/dev`

## 总览 · 道生万物

```
一句话需求
    ↓
┌─ 一 · 谋 ─┐   道生一：从混沌到清晰
│  析 → 设   │
└────┬───────┘
     ↓ 🔒 用户确认方向
┌─ 二 · 造 ─┐   一生二：从图纸到实体
│ 编→筑→部  │
└────┬───────┘
     ↓ 🔒 用户预览
┌─ 三 · 成 ─┐   二生三：从实体到交付
│ 试→验→书  │
└────┬───────┘
     ↓ 🔒 用户验收
  万物 · 涅槃
```

**三个关卡（🔒）是止（艮）的时刻**——确认后才继续，避免南辕北辙。

**静默模式**（深度工作模式激活时）：

> 大音希声。善行无辙迹。

关卡降级规则：

- 方向明确（需求具体+技术选型无争议）→ 🔒自动通过，不中断执行
- 方向有歧义（多种合理路径）→ 🔒仍止，ask_user_question
- 静默≠跳过思考。每个关卡仍内部评估，只是不输出中间文字
- 最终报告包含所有阶段产出的压缩总结

## Subagent 调度（按需而动，不强制）

> 动善时。治大国若烹小鲜。
> 不该动则不动，该动一次即止。

主会话(dispatcher)在每个阶段**自评**是否派 subagent。**不是每阶段都必须派**——rate limit 实测 ≤1 并发,盲目派既浪费配额又增加调度开销。

### 判断准则(进入阶段前自评,满足 ≥3 项才派)

```
□ 任务足够模板化?(能写出清晰 spec 给 worker)
□ 任务需要不同模型档?(深推理/结构化文档/批量廉价)
□ 主会话 context 已臃肿?(派 subagent 节省主 context)
□ rate limit 窗口内还有预算?(最近 1h 派过几次)
□ 任务价值高到值 15× token 成本?(单次调用约烧 4-15× 主会话)
□ 任务可真并行或串行可接受延迟?(否则主会话直接做更快)
```

满足少于 3 项 → **主会话直接做**(更快,无 rate limit 风险)。

### 场景建议(参考,不强制)

当你决定派 subagent 时,参考这张映射选 profile:

| 典型场景 | 推荐 profile | 模型 |
|---------|-------------|------|
| 挖真实需求 / 探索性方向 | `brainstormer` | Sonnet Thinking |
| 写 PRD / 接口设计 / 方案对比 | `plan-writer` | GPT Low/High |
| 一次性架构决策 / 卡死攻坚 | `strategist` | Opus XHigh/Max |
| 把 plan 翻成 worker 可执行 spec | `spec-writer` | Sonnet Thinking |
| 普通两阶段 review | `reviewer` | Sonnet Thinking |
| 核心模块(支付/认证/安全)review | `reviewer-critical` | Opus High |
| bug / 意外行为根因分析 | `debugger` | Sonnet Thinking |
| 严格按 spec 批量执行 | `worker-batch` | SWE Fast (free) |

### 派活四要素(每次派 subagent 必含)

1. **Objective** — 可观测完成判据
2. **Output Format** — 文件路径 + 完整代码模板
3. **Tools / Sources** — 用什么工具、读哪些文件、跑哪些命令
4. **Task Boundaries** — 显式说"不该做什么"

缺一 → subagent 大概率出轨。详见 `.devin/agents/<name>/AGENT.md` 和 `.windsurf/skills/dao-pyramid/SKILL.md`。

### 阶段默认倾向(仅供参考,自评优先)

dao-dev 七阶段在**典型情况**下的倾向:

```
§1.1 析:  用户需求清晰 → 主会话直接做;模糊/探索性 → 派 brainstormer
§1.2 设:  架构常规 → 主会话 + plan-writer;一次性关键架构 → 派 strategist
§2.1 编:  单一小改 → 主会话直接写;批量同质 → spec-writer + worker-batch 流水
§2.2 筑:  主会话跑 build(环境敏感);build 失败 → 派 debugger
§2.3 部:  主会话直接做(部署需实时反应,subagent 不擅)
§3.1 试:  主会话跑测试;大量测试产物 → 派 reviewer Stage 1
§3.2 验:  主会话 + dao-verify 自审;核心模块 → 派 reviewer-critical
§3.3 书:  文档量小 → 主会话;完整 README/PR/commit → 派 plan-writer
```

**横切触发**(任意阶段):

```
遇 bug / test failure / 意外行为   →  派 debugger(走 dao-debug 三层螺旋)
debugger 失败 ≥3 次                →  升级 strategist(质疑架构)
关键模块改动(支付/认证/安全)       →  派 reviewer-critical
跨多文件强耦合重构                 →  dao-worktree 隔离 + worker 批量
```

### ⚠️ 实测限制(Windsurf 个人账户)

subagent 派发受 **1 小时滚动 rate limit**,**实际并发上限 ≈ 1**:

- 1 小时内总派发次数有上限(打满后返回 "try again in about an hour")
- "no credits used" —— 节流不扣费,但配额耗尽 1 小时内不能再派
- **多任务采用串行 + 节流**,不要假设可并发
- Pro 账户上限可能更高,自行测试

→ 这是上面"判断准则"第 4 项(rate limit 预算)权重较重的原因。

## 一 · 谋（道生一 · 从混沌到清晰）

> 为之于未有，治之于未乱。

谋定而后动。这一阶段不写代码，只让需求从一句话变成可执行的图纸。

### 1.1 析 · 需求分析（☲离 · 视 · 照见本质）

从一句话中提取完整信息。

1. **解构需求**
   - 用户要什么？（功能目标）
   - 给谁用？（用户画像）
   - 有什么约束？（技术栈、平台、性能、截止时间）

2. **知彼**（集成/逆向/对接外部系统时）
   - 目标系统的隔离边界在哪？（权限、作用域、沙箱）
   - 哪些路径看起来通但实际不通？（读代码≠验证可行，关键假设须实调确认）
   - 最小验证：在写任何代码前，用最短路径验证核心假设能跑通

3. **补全缺失**
   - 用户没说但必须决定的事项
   - 小缺失：AI自行决定，在设计中注明
   - 大缺失（影响方向）：ask_user_question，最多问一轮
   - **原则**：认知卸载——替用户想到他没想到的，不制造新的认知负担

4. **拆解范围**
   - MVP（最小可行）包含什么？
   - Nice-to-have 是什么？
   - 明确不做什么？（划边界）

**产出**：需求清单（功能列表 + 约束 + 范围边界）

### 1.2 设 · 架构设计（☶艮 · 味 · 止而品）

在动手前把方案想清楚。

1. **技术选型**
   - 框架、语言、工具链
   - 优先用户已有的技术栈
   - 无偏好时选主流+轻量方案

2. **结构设计**
   - 目录结构
   - 核心组件/模块划分
   - 数据流/状态管理
   - 关键接口定义

3. **实施计划**
   - 编码顺序：依赖 → 核心 → UI → 集成
   - 预估复杂度：哪些部分可能需要 /cycle
   - 风险点：哪些部分可能需要深度调试（debug 镜头）

**产出**：设计方案（技术栈 + 结构 + 计划）

### 🔒 关卡一：方向确认

向用户呈现：

```
## 📋 设计方案
### 需求理解：[一句话总结]
### 技术选型：[框架/工具]
### 核心结构：[组件列表]
### 实施计划：[步骤概要]
→ 确认后开始编码
```

用户确认 → 进入「二·造」
用户调整 → 修订后重新确认

## 二 · 造（一生二 · 从图纸到实体）

> 天下大事，必作于细。

按计划逐步构建。每个步骤都是一个完整的小交付。

### 2.1 编 · 编码实现（☳震 · 触 · 一触推到底）

按设计方案的顺序，逐模块实现。

1. **基础设施审计**（编码第一步，不写代码先扫描）
   - 读取架构文档（ARCHITECTURE.md / 设计方案），提取需要的基建清单
   - 扫描项目目录，逐项判定基建是否就绪：

   | 基建需求 | 检测方式 | 缺失时的动作 |
   |---------|---------|-------------|
   | Web 前端 | 前端目录 + 基础配置是否存在 | `/dao-frontend-init`（脚本自动判定全量/增量） |
   | 后端 | `server/` 下有语言入口文件 | 按架构创建后端骨架 |
   | 数据库 | migration 目录 + ORM/SQL 配置 | 创建 migration 框架 |
   | CI/CD | `.github/workflows/` | 按部署方案创建 |

   **原则**：已有的不动，缺失的补全。子管线自带探测逻辑，dao 只负责调度。

2. **依赖安装**
   - 基础设施审计中触发的子管线（如 `/dao-frontend-init`）会自行处理依赖
     // turbo
   - 其余依赖在此安装
   - 配置基础设施（linter、tsconfig 等）

3. **核心模块**
   - 按设计的组件顺序，逐个实现
   - 每个组件：接口 → 实现 → 基本验证
   - **原则**：一触推到底——开始一个组件就做完，不留半成品

4. **UI/交互层**（如适用）
   - `/dao-frontend-init` 已在基建审计阶段完成脚手架 + 设计系统。此处聚焦业务页面
   - 具体标准由 `ui-ux-pro-max` skill 的规范文件提供（dao 不重复）
   - 美观现代的界面（不是毛坯）
   - 响应式、无障碍
   - 最佳UX实践

5. **集成**
   - 连接各模块
   - 端到端基本流程能跑通

**如某模块复杂度高** → 对该模块启动 `/cycle`
**如编码中发现设计缺陷** → 记录，完成当前模块后评估是否需要回到「设」

### 2.2 筑 · 构建（☵坎 · 听 · 听回响）

让系统编译/构建，听它的反馈。

1. **构建配置**：涉及凭证管理、商业分发或用户明确表达时，加入代码混淆（`wg:obfuscate: true`）；其余场景保持简洁。

2. **构建**
   // turbo
   - 运行 build / compile
   - 如有错误 → 先读完所有错误再修（不一个一个改）

3. **构建失败** → cycle + debug 镜头（多数在听症层解决）

### 2.3 部 · 部署/启动（☵坎 · 听 · 水就下）

让系统跑起来。

1. **本地启动**
   - 启动 dev server（非阻塞）
   - 等待就绪信号

2. **预览**
   - browser_preview 让用户看到实际效果
   - 或提供可访问的URL

**启动失败** → cycle + debug 镜头

### 🔒 关卡二：用户预览

```
## 👁️ 预览就绪
### 已实现：[功能列表]
### 预览地址：[URL]
→ 请查看，反馈调整意见或确认进入测试
```

用户满意 → 进入「三·成」
用户要调整 → 回到「编」修改，再构建部署

## 三 · 成（二生三 · 从实体到交付）

> 慎终如始，则无败事。

最后阶段不是收尾，是让交付物从"能用"变成"可信赖"。

### 3.1 试 · 测试（☱兑 · 说 · 让系统开口）

1. **功能测试**
   - 对照需求清单，逐项验证
   - 正常路径 + 边界情况 + 异常输入

2. **自动化测试**（如适用）
   - 核心逻辑的单元测试
   - 关键流程的集成测试
     // turbo
   - 运行测试套件

3. **视觉/交互测试**（如有UI）
   - 不同视口 / 设备
   - 无障碍检查
   - 性能基本检查

**测试发现bug** → cycle + debug 镜头

### 3.2 验 · 验证（☲离 · 视 · 回到本源）

回到最初的一句话需求，对照验证。

1. **需求对照**
   - 逐条检查：每个需求是否已实现？
   - 遗漏 → 补。偏离 → 修

2. **质量检查**
   - 代码简洁无冗余（为道日损）
   - 无硬编码/临时代码遗留
   - 错误处理完备

3. **涅槃判定**
   - [ ] 功能完备：需求清单全部✓
   - [ ] 构建通过：无错误无警告
   - [ ] 测试通过：自动化测试全绿
   - [ ] 体验自然：用户流程顺畅（无为而无不为）
   - [ ] 代码清净：无多余（为道日损）

### 3.3 书 · 文档（☴巽 · 风 · 传灯）

让成果可交接、可延续。

1. **README**
   - 项目描述（一句话）
   - 安装/运行步骤
   - 使用说明

2. **架构说明**（复杂项目）
   - 目录结构说明
   - 关键设计决策
   - 扩展指南

3. **交付总结**
   - 实现了什么
   - 技术栈
   - 已知限制 / 后续建议

**原则**：文档是给下一个人（可能是未来的自己）看的。
**反原则**：不写没人看的文档。README足够就只写README。

### 🔒 关卡三：用户验收

```
## ✅ 交付总结
### 需求：[原始一句话]
### 实现：[功能列表 + 技术栈]
### 文档：[README位置]
### 验证：[测试结果]
→ 请验收
```

## 工作流协作

```
/dev 管线 ── 驱动 ──→ /cycle（引擎）
                         │
                   ┌─────┼─────┬─────┐
                   ↓     ↓     ↓     ↓
                 debug refactor test optimize
                 lens   lens   lens  lens
                (skill) (skill)(skill)(skill)

深度打磨 → /cycle 多转
遇到bug → /cycle + debug 镜头
测试覆盖 → /cycle + test 镜头
文档生成 → /doc
前端初始化 → /dao-frontend-init（自动触发）
```

镜头（lens）是 /cycle 的领域插件，按需自动加载，详见 dao-cycle.md 镜头机制。

## 反模式

| 病             | 道德经诊断   | 对治                                                                             |
| -------------- | ------------ | -------------------------------------------------------------------------------- |
| 不析就编       | 不理解就行动 | 铁律：谋定而后动                                                                 |
| 盲建           | 知己不知彼   | 集成外部系统时，目标系统的约束（隔离、权限、边界）是析的一部分，不是编时才发现的 |
| 读当验         | 以观代行     | 读懂代码≠验证可行。关键假设必须实际调用确认，观与验不可替代                      |
| 熵遗           | 为学日益之弊 | 分析脚本、临时查询等中间物用完即清，不留散落                                     |
| 过度设计       | 企者不立     | MVP先行，够用即止                                                                |
| 毛坯交付       | 慎终如始     | UI/UX不是可选的                                                                  |
| 跳过测试       | 假涅槃       | 验是必经之路                                                                     |
| 文档堆砌       | 多言数穷     | 够用即止，不写废话                                                               |
| 不等确认就继续 | 独断         | 三个关卡必须止                                                                   |

## 执行格式

管线启动时：

```
## 🚀 /dev 启动
### 需求：[用户原话]
### 预估复杂度：[低/中/高]
### 预估阶段：[哪些阶段需要重点关注]
```

每个阶段完成时：

```
### [阶段名] ✓
- 产出：[...]
- 耗时/复杂度：[...]
→ [进入下一阶段 / 等待用户确认]
```

管线结束时：

1. **演化记录**：加载 `dao-evolution` skill，先运行 `search.py ensure --data-dir <project>/data`，再写入 `data/` CSV（write_entry + write_lesson）。`AGENT_GUIDE.md` 仅保留项目概览/架构/指南与 CSV 指针，不再作为主演化账本
2. **虚·归位**：按「虚·知识归位」机制清理 Memory（见 `knowledge-routing.md`）

```
## 🏁 涅槃
### 从 [一句话需求] 到 [完整交付]
### 经历：[阶段回顾]
### 成果：[文件/URL/文档列表]
### 虚：[归位了什么 / Memory已清空]
```
