# 知识沉淀 · Distill

> 致虚极，守静笃。万物并作，吾以观复。

## 触发条件

- 用户显式调用 `/distill`
- 用户想综合本会话多轮任务的教训，统一写入文档

> **注**：单次任务的教训提炼已内置于 `/dao-cycle` 涅槃流程。`/distill` 用于**会话级全量扫描 + Git 考古**——处理本会话未捕获的洞察，同时从 Git 历史中挖掘跨会话的系统性规律。

## 为什么用 Git 考古

各 Cascade 会话彼此隔离，无法直接读取历史会话内容。但每个会话的**产出都沉淀在 Git 历史中**：

```
会话 → 代码变更 → git commit（完整可枚举）
```

Commit 信息 + diff 是历史会话的最可靠痕迹，尤其是：
- 重复出现的同类 fix → 系统性问题，值得写成教训
- 架构/重构 commit → 设计决策，值得写入决策记录
- 版本 bump + 特定修复 → 阶段性演化节点

## 流程

### 零、考古（☵坎·Git 历史扫描）

> 温故而知新。

**在扫描当前会话之前**，先挖掘 Git 历史：

1. **取近 20 条 commit**：
   ```
   git log -n 20 --oneline
   ```

2. **分类标注**——按 commit message 前缀识别：
   | 前缀 | 意义 | 处理 |
   |------|------|------|
   | `fix(...)` | 修复 bug | 重点关注，是踩坑教训的直接来源 |
   | `refactor(...)` | 重构 | 可能含架构决策 |
   | `feat(...)` | 新功能 | 可能含设计决策 |
   | `chore/ci/build` | 工程配置 | 可能含部署教训 |
   | 无前缀/杂项 | 跳过 | 通常不含可复用知识 |

3. **模式检测**——识别跨 commit 的规律：
   - 同一模块/文件被多次 fix → 系统性弱点，值得写教训
   - 同一类型 fix 重复出现 → 根因未解决，值得写反模式
   - 短时间内大量 chore/ci commit → 部署/配置领域有知识缺口

4. **选择性深挖**——对标记为「重点关注」的 commit，读 diff：
   ```
   git show <sha> --stat
   git show <sha> -- <具体文件>   （只读相关文件，不读全量）
   ```
   **控制深挖数量**：每次 distill 最多深挖 5 个 commit，优先选「重复模式」中的代表性 commit。

5. **与 AGENT_GUIDE.md 对照**：读 `§教训` 章节，看哪些 commit 揭示的问题**尚未被记录**——只有 gap 才进入写入步骤。

### 一、识（☲视·扫描当前会话）

回顾**本会话从头到尾的全部内容**，识别所有可复用的洞察：

- 踩坑经验：做了无效尝试、发现外部系统行为与预期不符、推翻假设
- 新模式/反模式：发现了更优做法，或确认了某种做法不可行
- 架构/设计决策及理由
- 工具/库/API 的正确用法（与文档/预期不一致的部分尤其重要）
- 命名/约定/风格的新共识

### 二、去重（☶艮·先查再写）

合并「零、考古」和「一、识」的洞察候选列表，统一去重：

- 哪些洞察已有记录 → 跳过
- 哪些是新的 → 进入写入步骤
- 哪些与已有内容冲突 → 替换旧内容并注明原因

### 三、写（☳触·直接写入）

不需要 `ask_user_question` 确认——用户触发 `/distill` 即是授权写入。

每条新洞察按类型路由到对应文件：

| 知识类型 | 归属 |
|---------|------|
| 教训（踩坑/假设被推翻/反模式） | `data/evolution-lessons.csv`（via `dao-evolution` skill） |
| 演化条目（变更记录） | `data/evolution-entries.csv`（via `dao-evolution` skill） |
| 架构/设计决策 | `AGENT_GUIDE.md §架构决策` |
| 开发操作指南 | `AGENT_GUIDE.md §开发指南` |
| 行为准则（怎么思考/工作） | 道德法术层规则文件 |
| 领域技能 | `skills/` |

**教训写入**：加载 `dao-evolution` skill，调用 `write_entry` + `write_lesson`。
Git 考古来源的教训，tags 中加 `git` 标记。
新教训推翻旧教训时，调用 `deprecate_lesson(old_id, new_id)`。

写入时遵循：
- 不重复已有内容（已在第二步去重——先用 `search.py lessons "关键词"` 搜索确认）
- 冲突时废弃旧教训并注明
- **来源标注**：Git 考古挖掘的教训 tags 加 `git`，与当前会话来源区分

### 四、虚（☴巽·清理残留）

> 万物归根，归根曰静。

检查当前会话中系统检索到的 Memory 列表：
- 与本次写入内容相关且已被文件完整覆盖的 → 直接删除
- 未完整覆盖的 → 补充写入后再删除

**原则：规则文件 > 项目文档 > Skills > Memory。Memory 一旦写入文件即应清理，不留残存。**

## 反模式

- **为沉淀而沉淀**：纯执行性任务（改变量名、修 typo）无需沉淀
- **重复写入**：写入前必须检查目标文件是否已有相同内容（第二步去重）
- **Memory 堆积**：写入文件后忘记清理对应的 Memory
- **过度细碎**：每个小发现都写入 → 合并同类，保持文件精炼
- **等待确认**：直接写入，不打断用户——触发 /distill 即是授权
- **考古失控**：深挖超过 5 个 commit，或读全量 diff → 只读相关文件，严控深挖数量
- **重复模式视而不见**：同一模块被多次 fix 却没有提炼为教训 → 这是考古的核心价值
