# 测试 · Test

> 名与身孰亲？身与货孰多？得与亡孰病？

## 触发条件

- 新功能需要测试覆盖
- Bug 修复需要回归测试
- 用户显式调用 `/test`
- `/dev` 管线的「试」阶段

## 流程

### 一、析（☲离 · 视 · 识别需求）

1. **测试类型**：单元 / 集成 / E2E / 回归
2. **测试框架**：根据项目技术栈选择
   - Android/JVM → JUnit / Espresso
   - Node.js → Jest / Vitest / Mocha
   - Python → pytest
   - Web → Playwright / Cypress
3. **覆盖范围**：核心逻辑优先，边界情况次之

### 二、写（☳震 · 触 · AAA模式）

每个测试遵循 **Arrange → Act → Assert**：

```
// Arrange: 准备测试数据和环境
// Act: 执行被测行为
// Assert: 验证结果
```

**必须覆盖的场景：**
- ✅ 正常路径（Happy Path）
- ✅ 边界条件（空值、极值、零、最大长度）
- ✅ 错误路径（无效输入、权限不足、网络失败）
- ✅ 并发场景（如适用）

**命名约定**：`should_[预期行为]_when_[条件]`

### 三、跑（☵坎 · 听 · 听回响）

// turbo
- 运行测试套件
- 收集结果：通过 / 失败 / 跳过
- 失败的测试 → 分析原因，不盲修

### 四、报（☶艮 · 味 · 总结）

```
## 🧪 测试报告
### 覆盖：[X/Y 场景]
### 通过：[N] | 失败：[N] | 跳过：[N]
### 失败分析：[原因及修复建议]
```
