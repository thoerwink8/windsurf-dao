# 优化 · Optimize

> 少则得，多则惑。

## 触发条件

- 代码运行缓慢、内存占用过高
- 用户反馈性能问题
- 用户显式调用 `/optimize`

## 流程

### 一、测（☲离 · 视 · 量化瓶颈）

**不猜，先量。** 没有数据的优化是妄作。

1. **建立基线**：当前性能指标（时间 / 内存 / CPU）
2. **定位瓶颈**：
   - 时间复杂度：O(n²) 循环？不必要的遍历？
   - I/O 阻塞：同步文件/网络操作？
   - 内存：大对象未释放？重复创建？
   - 热函数：哪个函数消耗最多时间？

**工具：**
| 平台 | 工具 |
|------|------|
| Android/JVM | Android Profiler, JMH |
| Node.js | `--prof`, clinic.js |
| Python | cProfile, py-spy |
| 前端 | Chrome DevTools Performance |

### 二、策（☶艮 · 味 · 选对策略）

| 瓶颈类型 | 策略 |
|---------|------|
| 算法 | 换更优算法/数据结构 |
| I/O | 异步化 / 批处理 / 缓存 |
| 内存 | 池化 / 懒加载 / 流式处理 |
| 热函数 | 内联 / 减少分配 / 预计算 |

**原则**：
- 先改算法，后改常数
- 80/20：优化消耗80%时间的20%代码
- 不优化不是瓶颈的地方（知止）

### 三、行（☳震 · 触 · 最小改动）

- 每次只改一个优化点
- 改前改后对比数据
- 不牺牲可读性换取微小性能提升

### 四、验（☵坎 · 听 · 数据说话）

- 对比基线：提升了多少？
- 回归测试：功能是否正常？
- 边界情况：大数据量 / 极端条件下表现如何？

```
## ⚡ 优化报告
### 瓶颈：[定位]
### 策略：[选择]
### 基线 → 优化后：[数据对比]
### 副作用：[有无]
```
