# 外向环 · 战术手册（Outward Loop Playbook）

> 不出户，知天下；不窥牖，见天道——这句常被单读作「闭门参悟即可」，反过来读同样成立：户不出、牖不窥，久而久之便是画地为牢。制度化地「偶尔出门看看」，是闭门造车与追热点两端之间的中道。
>
> 蓝本：2026-07-22 用户点名「不希望闭门造车」——帅在 8h 高性能窗宣告候选池见底转值守，桌面竞品 Coffee-CLI 却从未被实机体验过，候选池里全部 `[竞品]` 条目都来自 issue 文本挖掘（第一人称体验为零）。条文正文在 `ccswitch/rules/dao-dispatch.md` §七「开窗那一刻」第 ③ 条（外部输入是常态），本文件是它的操作细则——条文说过的不重复，条文没细说的在此展开。**⚠️ 2026-08-01 订正：本行原写「是本手册唯一 always-on 锚点」，dao.md 瘦身后已不成立**——长窗排程 ①-⑥.5 整段从 always-on 的 dao.md 迁进上面那个文件，改由「开窗第一动作 Read」承载，dao.md 帅节只剩一行存根。故本手册的锚点**不再每轮注入**，它挂在开窗仪式上。

## §1 触发时机（常态入口 + 兜底入口）

> **2026-07-27 用户扩条**：原设计四个触发点全是「触发式」（见底/派单/战略重跑），
> 用户点明外部输入应是**常态**——原话「**不断**汲取网上最佳实践和 e2e 发现卡点和竞品优秀的地方
> 抄袭和竞品评论区 or 社媒用户真实痛点」。故重排为「常态入口在前、兜底入口在后」。
> **常态化的实现方式不是「记得多看」（按遵守率实证，无标记时刻的自由裁量注定 9-24%），
> 而是挂在已有的必经动作上**——下列 A/B 两个常态入口都是必经动作，不需要额外记性。

### 常态入口（挂在必经动作上，每次自动发生）

- **A · 派单契约门 → 外部参照三问**（用户面功能批**每批必带**，dao.md ②.5 强制）：派单 prompt 须附三行，各一句话+出处——
  ① **竞品同面形态**：这个功能竞品怎么做的（或显式注「无先例」）
  ② **业界最佳实践**：这类问题业界的标准解法是什么（或注「未查」并说明为何不必查）
  ③ **用户真实痛点出处**：这个需求的痛苦证据在哪（issue / 社媒 / dogfood / 用户原话）
  **三行都不许留空**——「查了没有」与「没查」是两种不同的诚实，都可接受；留空不可接受。
  目的：防实现官闭门发明已有答案的形态，也防帅凭想象立项。
- **B · dogfood 收尾 → 卡点清单**（产品型项目每个中等 PR 收尾必做）：dogfood 不只记「通过/失败」，
  必须记**卡点**——「哪一步我犹豫了 / 找不到 / 要试两次 / 想放弃」。通过但别扭的地方才是打磨点，
  而「全部通过」的报告等于没做 dogfood。卡点入 TODO 标 `[dogfood·卡点]`。

### 兜底入口（防常态入口漏掉的）

- **C · 见底前自检**：宣告「候选池见底」的那一刻，扫一遍 §2 名录有无未消费项，有则消费一轮再见底——
  池空≠没事做，池空=该出门看看。
- **D · 战略级重跑**：支柱工作法「市场剧变重跑」（见 `docs/playbooks/pillar-recon/PLAYBOOK.md`）。
  产品定位级整体重估，外向环只是它调用的信号采集手法之一——重跑判北极星准不准，见底自检判有没有活干，
  量级不同不可互代。

## §2 外向信号源名录（成本升序，择用不全跑）

按「距上次消费时长 × 该源近期动静」择用，不要求每次触发全跑一遍：

| # | 信号源 | 触发条件 |
|---|---|---|
| ① | **e2e 卡点（dogfood 自用）** | **常态源**（2026-07-27 用户扩条，此前被标为「不属本名录」）——每个中等 PR 收尾必做，记**卡点**不只记通过/失败；「全部通过」的报告等于没做 dogfood |
| ② | 竞品 release/issue 增量扫 | release feed 有新版，或距上次扫描 ≥ 一个自然发布周期 |
| ③ | 竞品实机体验 | 桌面已装且从未体验过，或距上次体验超 N 窗（N 按竞品活跃度定，无硬编码） |
| ④ | 上游生态 changelog | 依赖库出大版本（major/breaking），非补丁级噪音 |
| ⑤ | 新竞品雷达 | 距上次雷达扫描满一季度，或用户在对话中提及未知同类产品 |
| ⑥ | **竞品评论区与社媒真实痛点**（GitHub issues / HN / Reddit / X / Discord / 应用商店评论） | **常态源**（2026-07-27 由被动改主动）：立项某功能前**必查该功能面的用户抱怨**；另按「距上次扫描 ≥ 一个发布周期」定期扫。原触发条件「竞品发新版后或出现争议话题」太被动，等于只在别人搞出动静时才看 |
| ⑦ | **业界最佳实践** | **常态源**（2026-07-27 新增，原名录完全缺此源）：做技术/交互决策前先查这类问题的标准解法（官方文档 / 权威工程博客 / 成熟开源项目的做法），不闭门发明。**判据**：能说出「业界通行解法是 X，我们选 Y 因为 Z」才算查过；查完发现无通行解法也是合格结论，注「无标准解法」 |
| ⑧ | 商业动向（定价页/融资页） | 距上次核查满一季度 |
| ⑨ | 邻接类目 & 竞品的竞品 | 距上次扫描满一季度 |

**★ 已发布产品用户反馈 = 最高权重外向源**，独立于上表编号，产品未发布时 N/A；一旦发布即置顶所有其他源之上——真实用户的声音比任何竞品挖掘都直接。**发布之日即全表权重重排**：①-⑨ 全部降为它的补充。

## §2.6 两个反向源（补上表的结构性盲区，2026-07-27）

> 上表 ①-⑨ 全是**有声的加法源**——它们只回答「该加什么/该修什么」，且只覆盖**会发声的用户**。
> 以下两源专补这两个盲区，它们不在上表里因为**没有外部触发条件，只能靠自问**。

### ⑤减法自问（对抗加法源的自我强化）

加法源天然自我强化：竞品有的想抄、用户喊的想做、最佳实践想跟——结果是功能越堆越多，而**功能越多越难打磨到位**，与「为道日损」直接相冲。

**每批收官必问一句**：这批之后，有什么**该删 / 该合并 / 该默认关掉 / 该藏进二级入口**？
- 判据不是「有没有人用」而是「**不用它的人是否在为它付代价**」——多一个选项就是多一次选择负担，多一个入口就是多一分找不到的概率
- 答「无」也可以，但要给理由（如「本批纯修复未新增面」），不许留空

### ⑥无声失败扫描（对抗「只听得见有声用户」）

会发 issue、上社媒的用户是**幸存者**——他们至少还在用。真正走掉的人不发声：

| 无声失败面 | 典型受害者 | 为何照抄竞品也照不到 |
|---|---|---|
| 无障碍 | 键盘流用户、屏幕阅读器、色盲、低视力 | 竞品大概率同样忽略 |
| 边界数据量 | 10 万条会话 / 单条 50MB 输出 / 千文件工作区 | 竞品用户群未必碰到该量级 |
| 极端环境 | 低分辨率、200% DPI、慢磁盘、离线、老 GPU | 开发者的机器都太好 |
| **首次使用** | **新手** | **我们和竞品的 e2e 都由熟练者跑** |

**首次使用是其中最隐蔽的**：e2e 卡点由天天用的人跑，**结构性地跑不出新手会卡的地方**——不是做得不够仔细能解决的。近似解两条：
1. **专看竞品的新用户抱怨**（"我不知道这个按钮干嘛的"类），新手困惑往往跨产品同构
2. **刻意以「第一次见」走一遍首启链路**：假装不知道任何快捷键与约定，只用界面上看得见的东西完成一件事

扫描产出入池标 `[无声]`，与 `[竞品]`/`[dogfood]` 并列。**未发布期这一源权重更高**——发布后有真实用户报错，发布前只有这一条能照到无声面。

各源「上次消费窗」记录位见 §4 登记表，开窗盘点靠登记表读数，不凭印象猜距上次多久。

## §2.5 入池研判总则（对全部外向信号源生效，用户拍板 2026-07-22）

不止实机体验——§2 全部信号源（issue 挖掘/社区讨论/用户反馈…）产出的发现入池前都过这层判读，防止「频度高=该做」的天真采信：

1. **分层读原则**：反馈按类型分层可信度。bug/崩溃/信任崩塌类——近字面采信，用户在报告真实故障，复述即可；功能请求类——「处方可疑、痛苦真实」，频度×烈度证明的是场景强度（这里确实有人受苦），不证明用户开的方子就是正确解法。
2. **场景归因强制**：任何 `[竞品]`/`[竞品·体验]` 条目入池，必须记「时刻/意图」（用户在什么时刻、想完成什么），不得照抄竞品 issue 里的功能名当需求直接转录；用户自己提出的具体方案另列一行标「用户开的方子」，仅供参考，不作设计输入。
3. **反面护栏**：处方明显、成本低、无歧义的小件——直接做，不必层层归因空转。判据 = 处方歧义度 × 成本，两者皆低时走完整归因流程是形式主义。
4. **实证**：Codex #9203 388 人齐呼复活 `/undo`，而 git 系 undo 恰救不了其主诉的 untracked 半边——用户集体开的处方，治不全用户自己的病（2026-07-22 mousse-cli rewind spike 实测）。

## §3 竞品实机体验走查（②.5 中权重最高的消费动作）

### 启动权与实测义务（2026-07-23 夜窗实证补）

- **实测义务**：外向自检盘点桌面状态必须实测（进程列表 + 注册表卸载表两探针，分钟级成本），不凭印象或上窗台账下结论——2026-07-23 夜窗帅未探测即写下「Coffee 需用户重开 → 用户件不自主」，被用户点破；补探后 30 秒即定位安装位与版本，还顺带暴露了装机版落后最新 release 一个版本的观察时效信息。未验而断，正是外向环要治的病在自检环节的复发。
- **启动权**：启动已装竞品属自主动作（可逆、无破坏），不是用户件——真正的用户件边界在**凭据/登录态、安装/更新流程**（出现即停）。「app 没在跑」不构成跳过实机体验的理由；07-22 误触自更新事故的教训是「不碰更新入口」，不是「不碰启动」。

### 源码接触纪律（2026-07-27 用户挑战后重写，原「洁净室红线：禁止读源码」已作废）

> **原条文错在哪**（用户点破 + 帅自查）：①它**一律禁读源码**，而读源码是理解机制最高效的路径，禁掉是狭隘的
> ②它自称服务于「clean-room 血统」，但**我们本来就不是严格 clean room**——严格 clean room 是完全隔离
> （一组人读原作写规格、另一组人从未接触原作只照规格实现），而我们看界面、读 issue、学信息架构、抄交互形态，
> 这些全是接触。**条文假装我们在做 clean room，其实我们做的是「独立实现 + 避免表达复制」**，
> 规矩该按后者定。

**法律事实**：版权保护**表达**不保护**思想**——算法、思路、架构模式本身不受版权保护。
AGPL 的传染性针对「把它的代码放进你的项目」，不针对「你看过它」。
**读源码不违法**；读源码失去的是「我从没看过」这一抗辩（举证问题，非合法性问题）。

**⚠ AI 特有风险（本纪律存在的真正理由）**：人读完源码，细节会随时间模糊，剩下思路——
**模糊本身就是天然的表达过滤器**。AI 不会模糊：源码进上下文即逐字保留，生成时极易
**无意识复用其结构/命名/错误处理顺序**，此时已从「思想」滑入「表达」而自己未必察觉。
故不是禁读，而是**加一个隔离步骤**。

**分场景**
- **理解期**（搞清某机制怎么回事）→ **读**，这是最高效路径，不必绕路
- **实现期**（正在写同一功能）→ **最危险，不该边看边写**

**隔离纪律（四步，实现期强制）**
1. 读前明确「我要理解什么」，不漫游
2. 读完**写成自然语言原理笔记**——不含代码片段、不含其命名
3. **基于笔记实现，不对着源码写**
4. 实现后自查：命名 / 结构 / 注释顺序有无雷同

**派单时的连带责任（尤其重要）**：实现官若需理解竞品做法，**由帅读完写笔记、把笔记给官**——
让官直接读源码等于跳过隔离步骤（它读完转手就写代码，第 3 步物理上不存在）。

**按许可证分级**
| 许可证 | 处置 |
|---|---|
| MIT / Apache / BSD | 基本无顾虑，甚至可直接使用并注明出处 |
| AGPL / GPL | 走上述隔离纪律；**产物必须是独立表达** |
| **无许可证** | **最危险**——默认全版权保留，比 AGPL 更严，此时才接近「不如不看」 |

**保留的绝对红线（无论读不读都成立）**：不复制代码片段、不复制注释、不复制独特命名、不移植文件结构。

### 非破坏红线（体验伦理）

若走查对象是用户正在使用的实例：只读导航，**不删数据、不发指令、不改设置、不关窗口**。走查是「看」不是「碰」——留不下痕迹才算过关。

### 走查清单模板

1. **将就点/亮点双向清单**：逐场景记录「用户在这里明显在将就（土法自救/绕路/放弃）」与「这里做得比预期好」，各自独立成行，不要只记吐槽不记优点。
2. **场景归因**：每条将就点/亮点补一句「用户在什么时刻、想完成什么」——脱离场景的观察是噪音，见 dao.md 品·产品之思「住进场景」。
3. **三列对照**：走查收尾汇总成表——**它有我无** / **我有它无** / **同有形态异**（同一功能两边都做了，但形态不同，各自的取舍是什么）。三列对照比单向清单更能定位差异化机会。

### 入池规范

入池前先过 §2.5 判读（分层读+场景归因+反面护栏），再标 **`[竞品·体验]`**（`[竞品]` 的子标，区别于 issue 文本挖掘）。`[竞品·体验]` 在选题排序中权重高于普通 `[竞品]`——这正是这个子标存在的理由：第一人称体验能发现用户说不出口的将就点，issue 挖掘挖的是用户已经会抱怨的部分。若采而不加权，单开一个标签毫无意义。

## §4 体验环境登记

登记写进**产品项目**既有 intel 文档（如 `docs/research/` 下的竞品专题文档），**不新建专用文件**——环境信息是竞品研究的附属数据，不是独立门类。

登记字段：

- `app`：竞品名称
- `版本`：当前观测到的版本号
- `装机位置`：本机路径/桌面快捷方式/浏览器书签等
- `授权边界`：能碰到什么程度（只读导航 / 可测试账号 / 沙箱实例）
- `上次体验窗`：日期 + 窗口标识，供 §2 择用判断距上次多久

**更优解方向（待落地增强，非现行要求）**：开窗 scaffold 阶段自动探测已装竞品版本并自刷新登记表，防止人工维护漂移——OD 面板曾因人工维护滞后一周才被发现，是同类漂移的前车之鉴。现阶段仍手工登记，此增强留待有余力时补。

## §5 反例豁免清单（2026-07-27 修：豁免是**分源的**，不再一刀切）

> **原条文的漏洞（本次自查发现）**：原文写「以下情形**整个外向环**不适用」，
> 但 §2 新增的 ⑦业界最佳实践与 §2.6 的 ⑤减法自问、⑥无声失败扫描**根本不依赖竞品存在**——
> 一刀切豁免会把这三源一起豁免掉，而它们恰恰是内部工具类项目最需要的。故改为分源豁免。

| 情形 | 豁免哪些源 | 仍然生效的源 |
|---|---|---|
| **无同类竞品项目**（内部工具、基建、一次性分析） | ②③⑤⑥⑧⑨（全部竞品类） | **①e2e 卡点 · ⑦业界最佳实践 · ⑤减法自问 · ⑥无声失败扫描 · ④上游生态**——没有竞品不等于没有业界标准解法，也不等于不会堆功能、不会有无声失败 |
| **病期救火窗**（体检/CI 红着） | 全部外向源 | 无——先修敌，不分心看外面 |
| **短窗（< 4h）** | ②③⑤⑥⑧⑨（重型采集） | **①e2e 卡点 · ⑤减法自问**——这两个挂在必经动作上（dogfood 收尾 / 每批收官），零额外成本，短窗也不豁免 |

**分源豁免的判据**：一个源是否豁免，看它**有没有外部依赖**——
依赖「存在竞品」的可豁免；依赖「存在业界」「存在用户」「存在功能面」的不可豁免（这三样永远存在）。
