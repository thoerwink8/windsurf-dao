# 机制巡检：dao-sync 两次把飞书新码快进进来，活进程从开机起没换过，总控群还在跑旧码

## 结论

`server-sync.sh` 自己写着 2026-09-04 实咬：「合了 ≠ 生效」，所以快进到飞书文件就 `systemctl try-restart feishu-triage`。本轮现场：脚本在、sudoers 白名单在、reflog 里至少两次 BOT_PATHS 命中的 `merge origin/master: Fast-forward` 都发生过，`feishu-triage.service` 的 PID 仍是 09-12 06:29 开机那一个，`NRestarts=0`。磁盘上的 `feishu-triage-core.mjs` / `plain-words.mjs` 是今天 04:24 的 #919（报帅单代号换人话），进程在启动时 `loadCore()` 一次、顶层 `import` 一次，吃不到。重启失败被 `|| echo` 吞成单元 success。闸 0 处问「活进程启动时间是不是比它加载的文件旧」。

### 2. dao-sync 自己快进过两次命中 BOT_PATHS 的提交

`scripts/server-sync.sh:2-9,56-60`：

```
# 2026-09-04 实咬：总控群对话的 PR 合了，飞书机器人进程还跑着旧码——「合并了」≠「生效了」。
BOT_PATHS='^(scripts/feishu-triage\.mjs|scripts/lib/feishu-triage-core\.mjs|scripts/lib/plain-words\.mjs|host/skills/feishu-triage/)'
…
if g diff --name-only "$before" "$after" | grep -qE "$BOT_PATHS"; then
  sudo -n /usr/bin/systemctl try-restart feishu-triage || echo "机器人重启没成（单元缺失或没权限），代码已更新、进程还跑旧码"
  echo "飞书机器人代码有变，已请求重启让它吃到新码"
fi
```

### 3. sudoers 白名单在，失败被吞，闸不问进程新旧

`sudo -n -l` 本轮原文含：

```
(root) NOPASSWD: /usr/bin/systemctl try-restart feishu-triage
```

与仓内 `host/machine/sudoers.d/dao-sync` 逐字相同。`dao-sync.service` 正文写了「NoNewPrivileges 会连 sudo 一起挡掉，所以这里不能开」；本轮 `systemctl show`：`NoNewPrivileges=no`，`User=orca`，`ProtectHome=read-only`。单元最近一次 06:31:00 `ExecMainStatus=0`。

`|| echo` 之后脚本继续 `relink`、exit 0。`SuccessExitStatus` 未设，但退出码就是 0，`--failed` 里没有它。

本轮 `grep`（`ExecMainStartTimestamp|try-restart feishu|BOT_PATHS`）在这些文件里是 0 行：

- `scripts/dao-check.mjs`
- `scripts/server-check.mjs`
- `scripts/lib/commander-inventory.mjs`

没验证：那两次 journal 里「已请求重启」/「机器人重启没成」原文（orca 读不了 journal，已报 `2026-09-08-orca读不了journal-探针连红闸没查成.md`）。没验证：`sudo -n /usr/bin/systemctl try-restart feishu-triage` 此刻会不会真换 PID——本会话不许启停服务，没跑。按 PID / NRestarts / 两次命中的 ff-merge，重启没有发生过。

## 建议的最小改造

删掉「我这一轮刚快进到 BOT_PATHS → 请求一次 try-restart → 失败只 echo」这一层。问的应是**正在跑的 PID 是不是比它加载的那几份文件新**；旧了就 restart，restart 之后 PID 没变 / sudo 非零 = 单元非零，进 `--failed`。不要把「已经请求过」当成「已经吃到新码」。
