# 机制巡检：用量导出/采集 TimeoutStartSec=90，活任务跑不完就被 SIGTERM，采集账从 23:29 起没再写完过

## 结论

`dao-execution-usage-export` 和 `dao-execution-usage` 都是 `Type=oneshot`、`TimeoutStartSec=90`。timer 每 5 分钟响。本轮现场：root 导出 00:38:11 起、00:39:41 被杀掉，`Result=timeout` `ExecMainStatus=15`（SIGTERM），刚好 90 秒。采集器上一次也是同一形态（23:28:23–23:29:54，status=15），之后再没跑完；`collection.json` 停在 23:29，`complete:false`，`committed:0`。昨天中午同一份导出 8 秒就 success。90 秒墙钟现在比活短，设计里「exit 2 = 采集不完整、要人看得见」走不到，变成 SIGTERM。`--failed` 里采集器常在；failed-units 闸把「配对 timer 响过」收成 flaky 绿（09-12 已报），land 推送前那一格仍绿。

## 证据

本轮 2026-09-16 00:28–00:44 CST，身份 `uid=999(orca)`，未用 sudo。`HEAD=8aa15def`，与 `origin/master` 相同。未改 `docs/observations/` 以外的文件。未用 sudo，journal 原文没验证。

### 1. 导出和采集都是 90 秒墙钟；本轮导出被杀

仓内与 `/etc` 同文：

```
host/machine/systemd/dao-execution-usage-export.service:22  TimeoutStartSec=90
host/machine/systemd/dao-execution-usage.service:25         TimeoutStartSec=90
```

活单元 `TimeoutStartUSec=1min 30s`。timer `OnCalendar=*:3/5`（`dao-execution-usage.timer:5`）。采集器 `Requires=` 导出（采集器单元 :3）。

本轮 `systemctl show`：

```
dao-execution-usage-export.service
  ExecMainStartTimestamp=Wed 2026-09-16 00:38:11 CST
  ExecMainExitTimestamp=Wed 2026-09-16 00:39:41 CST
  Result=timeout
  ExecMainStatus=15

dao-execution-usage.service
  ExecMainStartTimestamp=Tue 2026-09-15 23:28:23 CST
  ExecMainExitTimestamp=Tue 2026-09-15 23:29:54 CST
  Result=timeout
  ExecMainStatus=15
  ActiveState=failed
```

00:38→00:39:41 = 90 秒。23:28:23→23:29:54 = 91 秒。status=15 是 SIGTERM，不是单元注释写的 exit 2（`dao-execution-usage.service:28`「Exit 2 is an explicit collection gap」）。

00:43:10 导出又进入 `activating`（timer 下一拍），本轮 00:44 仍未退出——同一只 90 秒钟还在走。

`/home/orca/.dao/execution/usage/collection.json` mtime `2026-09-15 23:29:15`，原文：

```
{"complete":false,"committed":0,"duplicates":46175,"sources":1443,
 "gaps":["source_scan_pending","inbox_export_incomplete"],
 "imported":0,"collectedAt":"2026-09-15T15:29:15.689Z"}
```

到本轮 00:44 已 75 分钟没再写完。root inbox manifest mtime `2026-09-15 23:28:23`：`rows:40244` `complete:false` `published:0` `exportedAt=2026-09-15T15:28:23.773Z`。

对照昨天中午那份观察（`2026-09-15-用量root副本冻在旧归属.md`）当时导出是 **success / 8 秒**（12:23:14–12:23:22，`ExecMainStatus=0`）。同一份 09-11 的 `/usr/local` 副本，墙钟没变，活变长了，90 秒盖不住。

`tests/` 全文 0 处锁用量单元的 `TimeoutStartSec`。巡逻单元的测试反倒写着「默认 90 秒会把正常的一轮掐死」（`tests/patrol.test.js:273-274`），用量这两只没盖到。

### 2. 闸看见失败也不红

本轮 `systemctl --failed --no-pager --plain`：

```
dao-execution-usage.service          loaded failed failed start …
systemd-networkd-wait-online.service loaded failed failed …
```

导出超时后会短暂进 `--failed`，下一拍 timer 再拉起来就变成 `activating`，列表里不一定还留着。采集器从 23:29 起一直 failed。

`scripts/lib/failed-units-check.mjs:68-74` 原文把这只采集器设计成「每 5 分钟必然重进 `--failed`」，配对 timer 响过 → `flaky` → **green**。`scripts/dao-check.mjs:2166` 取数带 `--plain`；`:2206-2213` unknown 才 SKIP，green 走 `green(r.detail)`。land 推之前跑 dao-check（`scripts/land.mjs:93-104`），这一格不挡。09-12 已经报过「响过就不红」；本条对象是 **90 秒墙钟把活杀掉**，不是那一格的 SKIP/绿。

没验证：root 导出 90 秒里卡在扫哪一段（orca 读不了 journal，也读不了 `/proc/<root pid>/stack`）。按 `TimeoutStartSec` 与两次恰好 90 秒的 `timeout`/`status=15`，是墙钟杀的，不是脚本自己的 exit 2。

## 建议的最小改造

删掉用量导出/采集上「90 秒必须退」这一层。oneshot 的超时要盖住 inbox 这个量级（本轮 4 万行），或者让脚本自己在不完整时 exit 2——SIGTERM 和「采集不完整」不是同一个出口，failed-units 按设计只认识后者。不要再把「timer NEXT 还在」当成这条腿在干活。
