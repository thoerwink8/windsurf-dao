# 在役审官 28 个，实际一个都没在跑：复审票在队列里躺了 5 轮

2026-09-11 02:20 实测。现象是**机器空转**：负载 1.5、零执行进程、9 张已消歧单不派工、
7 张 PR 卡在「当前 head 零判定」。

先排除的两个嫌疑（都不是）：

- **不是准入闸**：`admission` 报 `slots:35, why:"CPU 占用 39% < 85%，内存余量 7901MB"`；
- **不是缺标签**：#1161/#1153/#1155/#1160/#1127/#1118 的署名 issue 上
  `model/` `reviewer/` `type/` 都齐。

真凶在复审队列。`_flow/queue/review-pending/` 里 4 张票躺着，
`review-pending-drain` 每轮报：

```json
{"scanned":0,"drained":0,"held":4,"why":"在役 4 个已达上限 3，这一轮拉 0 张（票留在队列，不丢）"}
```

## 根因一：读的字段名在真实名单里不存在

`countLiveReviewers` 只看 `s.runState`，而执行运行时给的会话名单里**没有这个字段**：

```
会话名单真字段：sessionKey, backend, agent, model, …, state, phase, cleanupVerified, …
                          ↑ 没有 runState
```

`runState` 恒 `undefined` → `phase` 恒空串 → 永远命不中终态 → **每一条登记记录都被算成在役审官**。
实测 29 条登记数出 **28 个在役**。上限 3 永久吃满。

仓里别处早就兜底了，只有这一处漏：

```
commander-core.mjs:1339   s.state || s.runState || s.driverState
execution-runtime.mjs:386 hit.runState || hit.phase
```

## 根因二：终态清单是手打副本，漏了最常见的几个

`REVIEWER_DONE_PHASES` 手打 8 个词，漏了 `stopped` / `incomplete` / `gone` / `rejected`。
修完根因一之后数出来 19 条残留，其中 **12 条是 stopped、2 条是 incomplete**，
一条都没被算成终态。（这是同一晚第 4 处手打状态副本，已并入 `execution-states.mjs` 正典。）

## 为什么测试全绿却生产恒错

原有 5 条用例**全部只喂 `runState`**——夹具用的字段名和代码读的字段名错在同一处，
所以夹具和生产用的是同一个幻觉。加了一组用**真实字段名**（`state` / `phase`）喂的用例才照出来。

这条比 bug 本身更值得记：**夹具的字段名要从真实数据源抄，不能从被测代码抄。**

## 中间态不能直接当终态放行

`stopping` 是「收尾走了一半」，可能真在收。改法按 lease-gc 同一套纪律：
**过 15 分钟宽限**才不占位；时间读不到一律占位（fail-closed）。

## 实证

```
修前：在役 28（复核时 19），drained 0，held 4
修后：在役 0，drain 真拉起来 —— PR #1127 起了审官会话 codex:a3b8f0f8，phase=streaming
```

剩下 3 张票**卡在正当业务拦截上，不是死锁**：

- `#1091` `mergeable=CONFLICTING` → 先让工人 rebase，别派审官白审；
- `#1114` 「审官位只许同厂换顺位，不许无凭据换厂到 kimi-k3」；
- `#1155` `mergeable=UNKNOWN`（GitHub 还在算）——等服务端算出结果即可。
