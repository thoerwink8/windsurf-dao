# 拍板值没落到路由表、收尾并发写死在代码里：一个能力层建好了，收尾那条路一次都没走

2026-09-14 用户问「盘面只有队列满员只有 3，是不是也不太合适」，顺带指出「这些重要信息没存成
文档，是不是制度缺失」。查证结果：**不是文档缺失，是三道真相源各说各话，且没有一处会报警。**

## 一、实测：三个「3」，三套依据，两套已过期

| 常量 | 落点 | 依据 | 今天还成立吗 |
|---|---|---|---|
| `FINISH_SLOTS_MAX = 3` | `scripts/lib/commander-core.mjs` | 注释原文是**人体工学**（「一轮开太多会把决定表拉长、不好定位」），不是任何资源 | 从来没成立过——它压根不是容量数 |
| `DEFAULT_REVIEWER_CAP = 3` | `scripts/lib/dispatch/review-pending.mjs` | 2026-09-07 实测「gptpool 单腿同时活得下来约 3 个」 | **不成立**：gptpool / pqapi / windsurf 的执行档今天全是 `enabled:false`，在役审官只剩 `xai-native` 与 `mirasim-relay`，一条都不过网关 |
| `CONSERVATIVE_CAP = 3` | `scripts/lib/channel-concurrency.mjs` | 待填腿的保守值，依据 issue #1145 正文「某些上游渠道（如 Codex）实测容量只有 3-4」 | 是保守值，本身设计如此；但它与上面两个 3 **同值不同源**，混在一起看不出谁在卡 |

三处都取 3，是巧合。盘面上「拉 3 张」到底是哪一道在卡，当时无人能答。

## 二、真正的病：一个能力层建好了，收尾那条路没接进去

`#1145` 的渠道并发三件套（`scripts/lib/channel-concurrency.mjs`）**已经在读路由表**、按渠道计在途、
带熔断与原子占槽。它接进了 `collectCandidates` 的**派新活**那条路。

**叫审官 / 返工 / 解冲突 / 收口泵这条收尾路，一次都没调它。** 收尾走的全是上面那两个手打常量。

同一份实测快照里两句话并存：
- `admission.why = "CPU 占用 42% < 85%，内存余量 5950MB，还能收 28 张"`
- `channelInFlight.counts = {}`（一个在途树都归不到渠道 ⇒ 渠道闸对在途实际是 inert）

也就是说，**上游账面余量 28、渠道闸空转、而收尾被一个写死的 3 卡着**。

判例：memory `fix-landed-at-one-call-site-only`（「带解释注释的修法最容易漏接，因为注释让人确信已经处理好了」）。
`#1145` 的注释写得很足，足到没人回去补另一半。

## 三、这个 3 卡掉了多少：20 小时快照回放

拿 `~/.dao/commander/situation-*.json` 最近 60 轮（约 20 小时）跑新旧两份 `decide` 对比：

- **16 轮**多派了收尾动作，累计 **+27 个**
- 峰值那轮：旧 3，新 6
- 更早一轮 13 小时 / 40 轮的对照（3 vs 99）测得：14 轮被卡、少派 28 个、峰值那轮想要 10 只给 3

## 四、制度缺失在哪

1. **拍板 → 路由表这一段没有闸**。2026-09-08 拍板档案
   （`docs/decisions/2026-09-08-channel-concurrency-two-planes.md`）白纸黑字写了 windsurf=6、dspool 共享、
   pqapi=2、mirasim=5、grok 不限，**6 天过去路由表腿节里 windsurf / dspool / sub 三条还是 `null`**。
   `dao-check` 的 `checkLegCaps` 只把待填腿「显式列出来」，**故意不红**——人看不见的东西不会填。
   察觉不到的违反没配会报警的闸，正撞全局约定「察觉不到的规则（预算、配额类）不等出错，立规矩时就配自动检查」。
2. **收尾名额用尽完全静默**。`reportAdmission` 只在 `admissionUnscanned` 或 `dispatchSlots===0` 时说话；
   收尾名额被领光时零输出。于是「这一轮想派 10 个只派了 3 个」与「本来就只有 3 个要派」
   在盘面上一模一样——**限流不可观测，等于没人会去调它**。它就这么卡了 13 小时。
3. **结论落在档案里，没落到机器读的那份表里**。用户记忆里的「12 并发」不是并发额度，是
   `2026-09-08-channel-concurrency-two-planes.md:42` 记的**第三道天花板**：
   「网关机 CPU：总并发长流 ~12-14 条即触发 90% CPU 保护整机 503」。
   结论在档，但它是**上限塌点**，不是**可用额度**；两处混读就会得出「可以跑 12 个」。
   防这种混读的机制也是同一个：让公式里每个数都只有一个机器可读的落点。

## 五、处置（2026-09-14）

- 收尾名额上限从手打 `FINISH_SLOTS_MAX = 3` 改成 `finishSlotCap(cores)`（按核数，保底 2）。
- 审官上限从手打 `DEFAULT_REVIEWER_CAP = 3` 改成 `resolveReviewerCap({ cores, reviewerIds, channelOf })`：
  机器那层按核数、上游那层按**本轮票实际会用的审官**（及同厂有效 fallback）所落渠道取严。
  有限渠道上限始终是最终上界；保底只在没有任何有限渠道约束时生效。
- 收尾名额用尽当场报一条（含少派了几个、本机几核、上限几）；这条通知不依赖 `prReviews`。
- 路由表三条待填腿按 2026-09-08 拍板值填上。
- `dao-check` 对账 `docs/decisions/2026-09-08-channel-caps.json`（拍板快照的机器可读落点）：
  档案里某渠道已有数，腿节该渠道仍是 null ⇒ 判红。只写「待填理由」不能放过。
