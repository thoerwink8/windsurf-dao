# 记录的时间戳冻住了，判活靠它 → 正在跑的会话 45 分钟后会被当成死的

**定性先说清楚：这是潜伏风险，不是正在丢数据。** 本轮实测没有观察到任何误删
（文末「实测：本轮没有真删错」有数）。写下来是因为判据本身不可靠，
而它可靠与否取决于「恰好没跑到」。

2026-09-11 02:05 实测（#1150，会话 `grok:9a7f6534`）：

```
服务端 record.json   runState   = running        ← 说在跑
                     updatedAt  = 17:32:55Z     ← 起会话后 ~1 秒冻住，此后再不动
会话视图 session-read phase      = streaming      ← 服务端也说正在流
                     toolCalls  = 255 条
实际进程             该树 18 个进程正在跑整套测试
（provider-probe.test.js 63% CPU / redact.test.js 24%）
树内文件             NEW-MACHINE.md / AGENTS.md mtime 01:44（起会话之后仍在改）
```

## 判活走的是哪条路（已逐行核实）

`board-gc.mjs:95` 把 `record.json` 喂给 `sessionFromMirasimSession`，
`runState='running'` **既不在** `DRIVER_TERMINAL_STATES`（completed/done/
finished/failed/error/cancelled）**也不是** `incomplete`，所以：

- `unscanned = false`（没落进「没查成」那条）
- 于是判活只剩**时间判据**：`(now - updatedAt) > 45 分钟 → silent`

而 `updatedAt` 是冻的，所以到期必然翻转。实测推演（同一条会话记录）：

```
距会话启动   判活结果   算「活着」(免清)
    31 分钟    active     是        ← 现在在这里
    44 分钟    active     是
    45 分钟    silent     否 ← 从此可回收
   120 分钟    silent     否
```

`board-gc.mjs:370-375` 明写「silent / unscanned / done 都不算活着」，
所以越过 45 分钟那一刻，这张卡就**从「有活会话」那一档掉出来**。
#1150 起于 01:32:55，也就是约 **02:18** 越线。

## 但这一张卡暂时死不了（已核，别把它当成正在发生的删除）

`planBoardGc` 里「会话还活着」只是**第一道**免死牌（`board-gc.mjs:390-395`），
后面还有一道：`board-gc.mjs:398-407` 判「这张卡的 PR 还开着就留」。

实测 #1150 的这两张牌：

```
PR #1153（headRefName=dao-1150）  state=OPEN
issue #1150                       state=OPEN
```

所以它掉出「活会话」那一档之后，会被 PR 还开着那条接住，**不会**被清。

**那么这条还值不值得管？值得**，理由有三：

1. 接住它的是**另一条**判据，不是原意。原意是「有活在跑就别动」，
   现在变成「碰巧它的 PR 还开着」。PR 一合、或 issue 一关，
   这两道牌同时失效，而下一次 board-gc 读到的仍是那个冻住的时间戳——
   那时它已经被判 silent，会**直接可回收**，中间没有「它其实在跑」的提示。
2. 同形状的卡不一定都有开着的 PR。本轮「要人判」名单里躺着 12 张，
   其中 `ISSUE-#792`（issue 已关闭、无 PR、整树没活进程、12 个 tracked 改动）
   就是这类形态——它已经被判「整树没有活着的进程」，
   如果那个判断本身是拿冻住的时间戳做的，就会把一个真在跑的树读成死的。
3. `board-gc` 是**每小时**跑一次（`OnCalendar=*:07:00`）。时间戳冻住之后，
   任何一次运行都可能落在「已越线」的窗口里——
   判据的可靠性不该依赖「恰好没跑到」。

## 根因：`updatedAt` 记的是「服务端最后一次写记录」，不是「执行体最后一次有动静」

上游 run 断流（`stream disconnected before completion`）之后，本地执行体继续干，
但记录不再回写。于是「记录的新鲜度」与「活干的进度」从此脱钩——
一个冻住的旧值被当成「它安静了 45 分钟」。

## 判据该改哪

仓里已经有更可靠的信号，只是没被这条判据用上：

- **进程**：`processCheck(workdir)` / `scanSessionProcs` 已经在 `startSession`
  里用来挡「worktree already has an execution process」——同一个信号该给判活用；
- **树内产出**：`liveness.mjs` 的 `progressSignature` / `gitDirty` 已经在算
  「这棵树有没有在动」，`assessLiveness` 也已经返回 `hasOutput`，
  但 `board-gc` 只取了 `state === 'active'` 那一个字段。

判据顺序建议：**记录说终态但该树有活进程 → 按在跑处理**（fail-open 到「别动它」）。
反过来（记录说在跑、进程没了）才该算安静。时间判据只作为最后兜底。

## 实测：本轮没有真删错

2026-09-11 02:07 那轮 board-gc 的「要人判」名单 12 张卡，逐张独立数该树的真实进程：

```
ISSUE-#1003 / #1017 / #1056 / #1125 / #792 / #948
ISSUE-#965 / #966 / #967 / #982 / #999 / #1116
→ 真实进程数全部为 0
```

也就是说 `board-gc` 判「整树没有活着的进程」在这 12 张上**判对了**，
本轮没有误删。这条观察记的是**判据的可靠性**，不是一次已发生的故障——
别拿它当「刚才删错了东西」去查。
