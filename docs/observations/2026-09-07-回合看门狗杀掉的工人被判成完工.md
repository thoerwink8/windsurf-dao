# 被 30 分钟回合看门狗杀掉的工人，编排判成「完工」

## 结论

`pi` 有一道**每回合 30 分钟**的看门狗。它掐掉一个还在干活的工人时，会话快照并不变成失败态——

```
phase:      done
error:      "pi turn stalled past 30 minutes"
incomplete: （不设）
```

而 `scripts/lib/mirasim-runtime.mjs:332 judgeCompletion` 判终态时：

- `done` ∈ `DONE_PHASES`（第 45 行）⇒ 走完工分支；
- 只检查 `view.incomplete === true`（第 357 行）判「半截收尾」；
- **`view.error` 在 `phase` 为 done 时从头到尾没人读**。

所以被掐死的工人和真正干完的工人，在编排眼里长得**一模一样**。后续交叉核（账本里有没有起针后的成功调用行）也拦不住——工人被掐前已经打了七八十个工具调用，账本行有的是。

结果：`status: done` → 编排收工 → 没人重派 → 单子原地不动，而盘面显示「已完工」。

## 实测

2026-09-07 一天之内至少三次，全部落在同一形状上：

| 单 | 派工时刻 | 被掐时刻 | 产出 |
|---|---|---|---|
| #1116 | 11:11 | 11:41（30 分整） | 脚手架提交 + 空 draft PR #1118 |
| #1116（重派） | 11:54 | 12:24（30 分整） | 无（79 个工具调用全是 read/bash） |
| #1117 | 11:54 | 12:24（30 分整） | 无（71 个工具调用全是 read/bash） |

三次的会话 `error` 字段都是 `pi turn stalled past 30 minutes`，`phase` 都是 `done`。两棵工作树里**没有一个文件被写过**——`git status` 干净，最新文件 mtime 就是建树时刻。

第一次（11:41）快照带上了 `incomplete`，被判 failed，对账循环试图重派但因「会话名单读不到（没查成）」放弃；后两次连 `incomplete` 都没有，直接判完工。**同一个死因，两种判决**，说明现在靠的是 `incomplete` 这个不稳定的旁证，不是死因本身。

## 为什么工人 30 分钟还在读

派工时机器负载 **7.7–12.3（6 核）**，长期两倍超售。每个 read/bash 都被拖慢，工人还没读完仓就到点了。负载本身由编排自己造出来：23 张开放 PR、一堆审官会话、外加按 issue 逐条 `gh` 调用的看板扫描（每次一个 node 进程）。

所以这条有两层，判据层可以单独修，负载层不行：

- **判据层**：`phase=done` 且 `error` 非空时不许判完工。这是确定性的量，一行判据的事。
- **负载层**：工人跑得慢是因为机器被编排自己吃满。掐死的阈值（30 分钟）是 `pi` 的，改不动；能改的是同时在跑多少东西。

## 为什么危险

这是**幽灵进度**：盘面、账本、`gh pr list` 三处都显示这张单有人在做、甚至已经做完，只有进工作树 `git status` 才看得出一个字都没写。帅位盯盘时看到的是「工人开工了」，不会去开树。本仓反复禁止「把没查成当成查过没事」——这条更进一步，是**把被杀当成干完**。

同族判例：`probe-checks-env-not-startup`（探针验的不是开工）、`dispatch-accepted-vs-worker-started`（受理不等于开工）。这条是第三段：**开工了不等于还活着，报完工不等于干完**。

## 落点

- `scripts/lib/mirasim-runtime.mjs:332` `judgeCompletion`（第 350–362 行的终态分支）
- `scripts/lib/mirasim-runtime.mjs:45` `DONE_PHASES` / `FAILED_PHASES`
- 负载层：`scripts/commander.mjs` 的准入闸（现按内存余量判，没看负载）
