# 盘面在跳，但它在单向冻结

`commander-act.timer` 每 20 分钟准时跑、从没漏过一轮，而 17 张 open PR 里 13 张挂着「卡死」标——**只增不减**。一轮实际产出 2 条动作，两条都是空转。

「还在跳」和「还在推进」是两件事。定时器健康、journal 有输出、没有报错，这三样全绿，盘面照样可以完全冻住。

## 三条独立的冻结路径（都实测到了）

### ① 派成功的返工，工人死了以后永不重派

`pushRework` 开头 `if (prev.ok === true) return;`。判据是「派出去过吗」，要问的是「现在还有没有人在做」。工人静默退出后两边永久分叉：`head` 要工人推才变、账上 `ok:true` 要下一次派工才重写，而下一次派工正被这一句挡着。

实证 `rework:1154@f1d553cb…`：`at 2026-09-14T05:37`、`ok:true`，14 小时后会话名单 342 条里零活会话、head 一字未动、PR 仍 CONFLICTING，指挥官零动作。#1091 / #1216 同形状。

唯一逃生口是判据版本（epoch）换代把账本键整批作废——**靠改代码来解冻卡住的 PR，不是机制**。

修在 #1271：`judgeReworkOrphan`，会话面确知没人 + 超 180 分钟 + head 没动，三条齐了才解冻，之后落回原有的 tries/宽限/上限路。

### ② 会话登记说「结束了」，进程还活着，树永远拆不掉

`dao-review-pr-1232` 被两个 `codex app-server` 占住：会话登记 `gone`/`done`、PR 05:18 已合、**6.5 小时 0 秒 CPU**、目录 6.5 小时无写入。而 `reap-tree` 只信 `/proc` 扫描，于是连失败 **18 轮**，每轮在 journal 里写一行一模一样的失败。

判活看进程、收工看登记，两者对不上时进程赢 —— 没有任何一侧会去核对另一侧。手工 kill 掉后当轮即 `已拆`。

（同形状判例：memory `deleted-card-process-outlived-it`。）

### ③ 闸确定性拒绝，照烧复审预算，然后按**无关的理由**认输

drain 被闸当场拒时，一个审官都没起来，却照记一次 try：

```
16:28 rereview 第 1 次 → drain → reviewer-attach 失败
17:31 rereview 第 2 次 → drain → reviewer-attach 失败
18:32 rereview 第 3 次 → drain → reviewer-attach 失败
19:31 mark-exhausted「叫了 3 次审官，当前 head 判定仍是 0——停手交人」
```

写在 PR 上的认输理由是「叫了 3 次审官没判定」，**真因是闸拒**，两者毫无关系。看 PR 的人得不到任何可行动信息。

实测到的两种闸拒，都是确定性的、重试一万次也一样：

- `mergeable=CONFLICTING` ⇒「先让工人 rebase master，别派审官白审」
- 票上写的审官 `kimi-k3` 已于 2026-09-12 退役，不在审官顺位表里

## 共同形状

三条都是同一句话：**判据钉在「写下时的快照」上，而现实后来变了，没有任何一处负责把两者对上。**

- ① 账上「派成功了」是派出那一刻的事实，工人后来死了没人改这条账
- ② 会话登记是收工那一刻的事实，进程没跟着死没人核
- ③ 票上的审官是写票那一刻的顺位表，表后来改了没人回头看票

（同族判例：memory `snapshot-field-used-as-live-key-freezes-the-chain`、`hand-typed-constant-will-be-wrong`。）

## 处置（2026-09-17 帅位）

- **① → #1271**（原已开）。
- **③ → #1331**，不另开单。#1331 是同日独立撞出来的第二现场：`mirasim` 回环 ws 断连 3 小时，`start` / `session-stop` 轮轮失败，每轮照扣重试账，3 次后打认输标、理由写「叫了 3 次审官没判定」。与本条 ③ 的闸拒是**同一句话**——重试账把「压根没真正尝试成功过」的失败，当成「尝试了但对方没给结果」来记。两者只是失败来源不同（③ 是确定性闸拒，#1331 是基础设施故障），修法同一处：失败分型，不占业务重试名额。证据已回填进 #1331。
- **② 仍未开单**：会话登记说结束、进程还活着、`reap-tree` 只信 `/proc` 于是连失败 18 轮。2026-09-17 撞到它的**镜像形态**——登记停在 `stopping`、cleanupOwner 进程已死、租约已被 GC 收走，于是 `dao-review-pr-1282` 树被锁 10 小时、复审起不来（当天 `session-stop` 补一针即解）。两个方向共一句话：**登记与进程谁也不核对谁**。未开单的原因是它横跨 mirasim 会话面与本仓 reap 两侧，边界要先判；判例 memory 已有 `deleted-card-process-outlived-it`。

## 监视面：不缺探测，缺可行动的出路

`progress-watch` 干得很好——它每轮都在报「盘面停滞 5 轮（21 个对象没动）」，还逐条写明 head、合不合得上、有没有判定，并按 6 小时墙钟节流重推帅位（`DEFAULT_REALERT_MS`）。

**它连报了 5 轮，一次都没错。**问题不在探测，在于探测出来以后自动化侧没有任何动作可做——报警正确、无人可应。所以往监视面加东西（更多探针、更细的分类）解决不了这一类；要加的是被报出来那件事的**处置路径**。

### ④ 工人是 GPT 的 PR，审官位无解（帅位自己开的单全中）

刚开的 #1271 第一轮 drain 就报：

```
reviewer-attach 失败：审官位只许同厂换顺位（当前 gpt-5.6-luna／gpt），
不许换厂到 grok-4.6／grok——换厂只在上一位死于满载/看门狗时成立：没交换厂凭证
```

两条都是用户拍过板的规矩，在这一格正面相撞：

| 规矩 | 要求 |
|---|---|
| 审查换厂商（`refuseIfSameVendor`） | 工人是 GPT ⇒ 审官**不许**是 GPT |
| 审官位（`assertReviewerSeat`） | 审官**必须**是当前顺位或其同厂备选，而当前顺位是 `gpt-5.6-luna` |

于是**工人家族 = GPT 的 PR 拿不到任何合法审官**。帅位自己开的单全中：`pr-open` 拒收 `claude-opus-5`（不在 registry），只能挑 `codex-relay-gpt-5.6-luna`，一挑就进这个死格。#1265 #1266 #1270 #1271 四张全在这里，零判定。

普通派工不撞是因为工人多是 `grok-4.6`（非 GPT），审官落到 GPT 座位上天然跨厂成立。

这是**规则层的碰撞**，不是代码 bug——改任一侧都属「改规则」，留给人拍。已有 OPEN 单 #1214「合并路自锁」管这个起因。

## 还没修

- **③ 闸确定性拒绝照烧预算**：应当像 `pushRework` 那样先过 `judgeRetry`，terminal 的当场交人并**带上闸的原文**，而不是攒够 3 次报一个无关理由。
- **#1114 的票钉着已退役的 `kimi-k3`**：读票侧的自愈只换同厂备选（跨厂要满载/看门狗死因凭证，`assertReviewerSeat`），顺位里没有同厂的就不换、照旧失败——设计如此，但这条路没有出口，每轮白试。跨厂换人属「改规则」，留给人拍。
- **打标/摘标读的不是同一本账**：`mark-exhausted` 打标不写推送账本，而 `planExhaustedLabelClear` 第 ① 条拿推送账本里最新那条的 head 跟当前 head 比 —— 于是刚打上的标下一轮被误摘、再下一轮重打。自限于两轮（看门狗随后会在当前 head 补一条推送记录），不是死循环，但每张 PR 白烧两轮 + 一对 GitHub 评论。09-14 当天在 #1111 #1209 #1225 #1226 #1253 #1258 #885 上各转了一圈。
