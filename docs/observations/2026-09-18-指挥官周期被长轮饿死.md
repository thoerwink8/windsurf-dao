# 指挥官周期：长轮饿死下一轮，`NEXT` 显示 `-` 像定时器死了

## 病

`commander-act.timer` 的触发条件全是墙钟：

```
OnCalendar=*:11/20
OnUnitActiveSec=20min
```

而一轮实测约 **20 分钟**（2026-09-18 04:00:21 起，04:20 还在跑）。`Type=oneshot` 的服务还 active 时
定时器触发**直接跳过、不排队**，于是每轮吃掉下一个档期，实际节奏退化到 40 分钟以上。

看起来的样子最骗人：`systemctl list-timers` 里 `NEXT` 是 `-`、`Trigger: n/a`，
跟「定时器挂了」一模一样，而实际是上一轮没跑完。

`TimeoutStartUSec=infinity`（oneshot 默认）让这件事没有底：**一轮真卡住就永远占着单元，定时器再也不触发**。

## 代价（实咬）

PR #1377 的复审票 03:53 就写进 `_flow/queue/review-pending/`，等到 **04:20** 才被 drain——
27 分钟里没人动它。无人值守时这等于整条审查链停摆。

一轮里的时间都花在哪：串行的 `node scripts/dao.mjs session-stop --session grok:… --worktree …`，
每个约 10 秒、一个接一个。这正是 **#1350**（stop-session 对已删的树每轮重试，判据在 judgeRetry 里）
在烧时间——那条单是根因，本条只处理「周期被饿死」这一层。

## 垫片（已上，2026-09-18 04:25 CST）

两个 systemd drop-in，不改原单元、删掉目录即可回滚：

- `/etc/systemd/system/commander-act.timer.d/10-no-starve.conf` → `OnUnitInactiveSec=3min`
  「上一轮**跑完**之后 3 分钟再跑」。systemd 取所有触发条件里最早的那个，墙钟档期照旧有效，
  只是再也不会被长轮饿死。
- `/etc/systemd/system/commander-act.service.d/10-anti-hang.conf` → `TimeoutStartSec=45min`
  防挂底线，不是调度器。实测一轮约 20 分钟，留一倍余量；真被它砍到说明那一轮不正常，
  该去查而不是调大这个数。

验：`systemctl show commander-act.timer -p TimersMonotonic` 出现 `OnUnitInactiveUSec=3min`，
`commander-act.service` 的 `TimeoutStartUSec=45min`。

## 待办（垫片退役条件）

1. **`commander-act.service` / `.timer` 根本不在仓里**——`host/machine/systemd/` 下没有这两个文件，
   单元只存在于机器上。这本身是漂移：重装机器就没了，改动也没有评审面。
   要把两个单元（含本 drop-in 的内容）收进 `host/machine/systemd/` 并配装机脚本。
2. 根因仍归 **#1350**：session-stop 对已消失的树不该每轮重试。那条修好后一轮耗时会大幅下降，
   本垫片的 `OnUnitInactiveSec` 仍有价值（保证不饿死），`TimeoutStartSec` 也仍该留着。
