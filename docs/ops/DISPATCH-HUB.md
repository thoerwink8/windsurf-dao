# issue 派单中枢 · 流程总览（单一真相源）

> issue 区是任务的**登记处与账本**，会话只是执行通道——**会话崩了任务不丢**。
> 纪律条款在 `CLAUDE.md`（always-on 精简版）；本文是全景手册，**改流程先改 canonical 模板再同步这里**。

## 一、全景：一件事的一生

```
想法/发现 ──┬─ 低置信（AI 推测/走查疑点/外部情报）→ 打 `候选` 标签，不进行动层
            └─ 准入（用户点名 / AI 确信有证据 / 缺陷坐实）→ gh issue create + 打标 ← 行动层入口
                    │
                    ▼
       队列（领活循环：自主窗选题与每次心跳对账都扫 P0→P1）
                    │ 帅派单：三节点之一「⚔️ 已派」评论 + `在途` 标
                    ▼
       官干活（worktree 隔离 → PR → 止步 gh pr create）
                    │ 官交付：三节点之二「交付结论」评论
                    ▼
       帅终审（独立复验 + 一键验证真退出码 + merge）
                    │ 帅销账：三节点之三「关单结论」评论 + 摘 `在途`
                    ▼
                 CLOSED（每单关闭都有证据链）
```

**三节点留痕是硬要求**：派单 / 交付 / 关单各留一条评论。少了任何一节，这张单在事后就只剩标题——
而「这件事当时为什么这么定」恰恰是最贵的部分。

## 二、label 体系 = 派单标准（四维正交）

**canonical 定义在 `ccswitch/templates/labels.json`，本文不重抄**——
抄一份就是双份真相源，改一处忘一处是必然而不是意外。这里只放一眼可读的速查与本项目的收窄。

| 维 | 基数 | 标签 |
|---|---|---|
| **类型**（建单必打） | 恰选 1 | `缺陷` `任务` `欠账` `候选` `待拍板` `需用户` |
| **改动性质**（建单必打，2026-08-09 立） | 恰选 1 | `bug` `feature` `test` `docs` `chore` `refactor` `perf` |
| **优先级** | 缺陷/任务恰选 1；欠账与蓄水池不打 | `P0` > `P1` > `P2` |
| **派单约束**（决定「怎么派」） | 可多个 | `结构受阻` `守卫类` `真机` |
| **状态** | 0-1 | `在途` |

🔴 **「类型」与「改动性质」是两根正交轴，别混**：「类型」答「这单归哪种流程」（缺陷/任务/欠账/…）；
「改动性质」答「这单改的是什么性质的东西」（bug/feature/test/…），程序员英文命名、恰选其一，同单可以两维都贴。
判据、写作规范（建 issue 三件套：类型标签必贴 + 标题人话式 + 关联用结构化字段）与基线数字的正文在
`ccswitch/rules/dao-dispatch.md` §一「开单三件套」，本文件只留这一行速查指针，
不复述细则——canonical 定义未来若下沉进 `labels.json`，同样只改那一处。

**帅读标签 → 派单动作速查**（完整判据与派单含义见 labels.json 的 `dispatch` 字段）：

- `缺陷`/`任务` + `P0`/`P1` + 无 `在途` → 领活优先派，按类型选官种（多机/多 AI 并行时：`在途` 但租约过期**且**盘上零活动 ⇒ 走接管流程再领，不直接抢；见 `ccswitch/scripts/dao-claim.ps1`）
- 任意 + `守卫类` → 实现官止步 PR，**必接对抗验证官**才合
- 任意 + `真机` → 排实例队列串行，PR 证据不许走「随后补」
- 任意 + `结构受阻` → **先出解锁设计**，不派实现官
- `候选`/`待拍板`/`需用户` → 不派，进各自蓄水池；`候选` 升级走 **relabel 不是 re-create**

**用户只需要记三个标签**：`待拍板`（要他决策）+ `需用户`（要他动手）+ `候选`（酝酿层，他扫一眼有没有该提优先级的）。

### 二.5 本项目的判据（空着等于该标签没生效）

| 标签 | 本项目判据（一眼可判） |
|---|---|
| `真机` | **本仓当前无适用面，标签建了但留作扩展**。windsurf-dao 是规则/脚本/hook 仓，没有 GUI、没有打包版、没有真实输入设备——「测试全绿但真机是坏的」这一类缺陷在这里不存在。**它的近亲在本仓叫「live 生效面」**（hook 要在 cc-switch 下发后的 live 配置里真的注册上才算数），那一类目前靠 `--selfcheck` 与 settings-drift 自检覆盖，不走这个标签。哪天本仓长出 GUI 或真机依赖面，在这一格写死判据再启用。 |
| `守卫类` | 改动落在以**拦截 / 守卫 / 扫描 / 判定**为职责的文件：`ccswitch/hooks/**`（尤其 `dao-hard-gates.js` 这类 PreToolUse 拦截器）· `ccswitch/scripts/check-*` · `ccswitch/scripts/verify-*` · 任何 lint / scanner / drift 检测入口（`check-alwayson-budget.mjs` / `check-archive-pointers.mjs` / `settings-drift.js`）· `scripts/dao-check.mjs` 与 `scripts/dao-exit-gate.mjs`。**路径可机械判定**，不靠语义判断。 |
| `结构受阻` | 卡在「不先做一个设计决定就没法动手」的位置。本仓已出现的三种形态：①**写入面归属未定**——要改的东西在 cc-switch DB 的 `providers.settings_config` 里，AI 侧被权限闸拦（#64 是实例，那张单同时是 `需用户`）②**跨仓归属未解**——某份语料/指针该住在哪个仓没定（#48 clause-index 的跨仓语料）③**上游没给 API**——GitHub Projects v2 的自动入板 workflow 无 API，只能人在网页点（见 §六.5 末尾）。 |

> 为什么这几格必须由项目填：概念是通用的（存在「测试全绿但真机是坏的」这类缺陷、存在以拦截判定为职责的代码），
> 但**哪些改动算、哪些路径算**只有项目答得出。照抄别的项目会得到一个在自己项目里一眼判不了的判据，
> 而一眼判不了的判据等于没有——谁都能说服自己这次不适用。

## 三、常设单（永不关闭，置顶）

GitHub 每仓**置顶上限 3 个**。三个槽的分配是：两个最高频的可回复 inbox + 一个总览 hub。

| 单 | 是什么 | 置顶 |
|---|---|---|
| #70 📌 待拍板总览 | AI 攒决策，用户在评论区回一条即算拍板 | ✅ |
| #71 📌 需用户总览 | 只有用户能做的事集中入口，含耗时估计 | ✅ |
| #72 📌 总览 hub | 一眼对齐入口：看板链接 + 各 inbox + 在途 | ✅ |
| #69 📌 候选总览 | 酝酿层全景 + AI 的按住理由与 promote 条件 | ❌（从 hub 进） |

**为什么候选总览不占 pin**：用户说「X 也要置顶」时先问「X 是不是已经能进 hub 的某一行」——
能进就进 hub，别去挤那三个槽。hub 由帅每批收官刷新一次「现况」列。

**蓄水池纪律**：`待拍板` / `需用户` / `候选` 三类**永不进清零目标**、不催、攒批。
任何「issue 清零」类目标一律读作「**除蓄水池外**清零」。

## 四、批次机制（父单 + sub-issues）

多子任务的活开**父单**写目标+验收，子单逐一挂上去，父单进度条即清偿进度，子单全关父单收官。

```
gh api repos/thoerwink8/windsurf-dao/issues/<父单编号>/sub_issues -f sub_issue_id=<子单的 database id>
```

🔴 **`sub_issue_id` 要的是 database id，不是 issue 编号**——传编号会挂错单或报错，
而挂错的那一刻没有任何提示。取法：`gh issue view <n> --json id -q .id` 拿到的是 node id（GraphQL 用），
database id 走 `gh api repos/thoerwink8/windsurf-dao/issues/<n> -q .id`。两个 id 长得完全不同，别混。

舰队批处理同型：一批开一个批次父单，处理对象挂子单，批完关父单。

## 五、全量核账的五向分流（triage verdict）

批量核账（如「把所有 open issue 过一遍」）时每单判一向。**判 `ghost` 门槛最高**——
要证明「确实不存在了」，拿不准一律降级 `keep`（判错方向的代价不对称：误判 keep 只是多留一张单，
误判 ghost 是把一个真问题关掉且从此没人再看见它）。

| verdict | 含义 | 后续动作 |
|---|---|---|
| `ghost` | 已修 / 已过时 / 不再成立 | 帅复核证据链 → 关单留结论 |
| `fixable` | 仍成立可修 | 进实现批（批次父单组织，并行拆官） |
| `blocked` | 结构受阻 | 记解锁依赖，解锁件排优先 |
| `keep` | 成立但不属以上 | 留队列按 P 序 |

**官只读不写**：判定与关单草稿交回，`close`/`comment` 动作归帅（**终审不可让渡**）。

## 六、既有约束的裁剪（领活时逐条过）

- **独占资源类**（真机 / 单设备 / 单账号）：同时刻只准一路，排队合批清。**本仓当前没有这类资源**，见 §二.5。
- **账本类**（教训 CSV / 条款库 / 版本快照）：冻结归帅收账，不并行——多路并行时账本是唯一共享写入面，抢改必冲突
- **判据/护栏类改动**：对抗验证前置到 merge 之前，不先合后审（本仓这类占比高，见 §二.5 `守卫类`）
- 派单契约门、军衔通报、验证分级：见 `ccswitch/dao.md` 帅节 + `ccswitch/rules/dao-dispatch.md`（本文不重复）
- **跨仓引用面**：windsurf-dao 与 mousse-cli 双向引用密集（dao.md / skills / stacks / 条款库互指）。
  改文件名、条款标题、节标题、脚本路径时，**Grep 面必须含另一个仓**；跨仓改动进不了同一个 PR，
  正确形态是同批开一个跨仓 issue，不是「顺手记一下」。
- **always-on 配额**：`ccswitch/dao.md` 每轮注入给所有 agent。往里加字之前先问「这是不是每轮都要用」——
  只在某个时刻用得上的，归 `ccswitch/rules/` 存根 + 现场 Read，或归作用域档。
- **配置生效面**：hook / 权限类改动的真实下发源是 cc-switch DB 的 `providers.settings_config`，
  **改 git 快照层与 `common_config_*` 镜像层不生效**（#49 实测证伪）。判据见 dao.md Shell 节「改配置先认源与投影」。

## 六.5 三态归位——什么进 issue，什么留文件，什么进看板

**判据一句话**：说得出「关闭条件 + owner」→ issue；是聚合视图 → 看板；是流水/叙事/跨切 → 文件。
（dao 通用条款「工作项三态归位」的项目落地，细则正文在 `ccswitch/rules/dao-dispatch.md` §一。）

| 载体 | 装什么 | 本项目现状 |
|---|---|---|
| **issue 区（分配中心）** | 有生命周期的单元 + `候选` 酝酿层 + 蓄水池 | 13 个标签已建（基础集 11 + 扩展 `守卫类`/`真机`）。**存量单多数无类型标**——中枢 2026-08-02 才上线，此前的单靠回溯补标 |
| **看板（观测中心）** | 全部单的聚合全景，标签驱动归列 | [windsurf-dao 观测中心](https://github.com/users/thoerwink8/projects/1)，六列：候选/待办/在途/待验/蓄水池/完成 |
| **仓内文件（叙事层）** | 无 per-item 生命周期的密集内容 | `docs/evolution/`（教训账本 CSV + 事故叙事 `incident-narratives-202607.md` + 条款论证史 `dao-clause-rationales.md`）· `docs/specs/`（批次 spec 与收官记录）· `TODO.md`（酝酿层残余）· `AGENT_GUIDE.md`（细则与出处） |

🔴 **本仓没有 `PROGRESS.md`**（canonical 模板默认它存在）。流水叙事分散在 `docs/evolution/` 与 `docs/specs/` 两处，
这是实况不是缺项——本仓的「一件事的经过」历来按**教训**和**批次**组织，不按时间线。要总账时读这两个目录，
别去找一个不存在的文件。

**判据自检**：一个「问题树看板」型文件（`WORKBOARD.md` 型）在 issue 中枢+看板建成后多半**冗余**——
退役归档、活账交 issue，是为道日损。留着它就是双份漂移。本仓的 `TODO.md` 待过这一道：
它现在同时装着酝酿层候选与历史勾选，候选那半应迁 `候选` 标签的 issue（**未做，见未尽处**）。

🔴 **一次性人工动作**（Projects v2 自动化 gh CLI 建不了）：看板的「新 issue 自动入板」workflow
要在网页点一次（约 2 分钟）。步骤见 issue #71（原 `docs/USER-ACTIONS.md` 已删并入该单）。在那之前，新建 issue 由帅手动
`gh project item-add` 灌入。

## 七、用户视角（只需要知道这四件）

1. **有想法**：对帅说一句话即可，帅代建单打标（或自己开 issue 随手写，帅补标）
2. **有空了**：打开置顶的 #70（待拍板）/ #71（需用户），评论区回复即生效
3. **想看全景**：打开 [windsurf-dao 观测中心](https://github.com/users/thoerwink8/projects/1)，六列一眼看完哪些待办/在途/待验/待你拍
4. **想看细账**：`docs/evolution/`（教训与事故叙事）+ `docs/specs/`（批次收官）；任何 issue 点开都有三节点留痕

## 未尽处

- **三节点留痕在存量单上基本为零**——中枢 2026-08-02 才上线，此前的单（#44 及更早一路到 #68）没有这个习惯。
  别以为每张老单都有证据链；老单的「当时为什么这么定」多半只能回 PR body 或 `docs/specs/` 找。
- **「用户在总览单评论、帅心跳扫到」这条通道，在首次真实往返之前都只是设计**，不是已验证的能力。
- **`真机` 标签建了但零适用面**（§二.5）。留着它有一个已知代价：看板与速查表上会一直有一格空转，
  而空转的格子容易被后来的人读成「这里应该有单，只是还没建」。哪天确认本仓永远长不出真机面，
  正确动作是删标签而不是继续留着。
- **`TODO.md` 的候选层未迁 issue**（§六.5 末）。迁移属「改用户可见面」，按 dao 分档判据归判断档，
  不由 AI 自定——挂在这里等用户一句话。
- **看板归列目前是手动的**：`auto:true` 只表示「这一列的归属可由标签机械判定」，不表示 GitHub 会自动放进去。
  自动入板 workflow 没点之前，新单不进板，看板会静静地过期。这是 issue #71 里 USER-ACTIONS 并档的第 1 条（原 `docs/USER-ACTIONS.md` 已删）。
