# issue 派单中枢 · 流程总览（单一真相源）

> issue 区是任务的**登记处与账本**，会话只是执行通道——**会话崩了任务不丢**。
> 纪律条款在 `CLAUDE.md`（always-on 精简版）；本文是全景手册，**改流程先改 canonical 模板再同步这里**。

## 一、全景：一件事的一生

```
想法/发现 ──┬─ 低置信（AI 推测/走查疑点/外部情报）→ 打 `候选` 标签，不进行动层
            └─ 准入（用户点名 / AI 确信有证据 / 缺陷坐实）→ gh issue create + 打标 ← 行动层入口
                    │
                    ▼
       队列（领活：调度靠用户会话点名；要排序就用看板列顺序，拖到列顶即最高——优先级 label 已删，见 §二）
                    │ 帅派单：三节点之一「⚔️ 已派」评论（多机/多 AI 并行认领走 `ccswitch/scripts/dao-claim.ps1` 评论租约）
                    ▼
       官干活（worktree 隔离 → PR → 止步 gh pr create）
                    │ 官交付：三节点之二「交付结论」评论
                    ▼
       帅终审（独立复验 + 一键验证真退出码 + merge）
                    │ 帅销账：三节点之三「关单结论」评论
                    ▼
                 CLOSED（每单关闭都有证据链）
```

**三节点留痕是硬要求**：派单 / 交付 / 关单各留一条评论。少了任何一节，这张单在事后就只剩标题——
而「这件事当时为什么这么定」恰恰是最贵的部分。

## 二、label 体系（8 个，issue #360 拍板终表）

**立标签的门槛**：答得出「谁在什么时刻会筛它」+ 配得出自动化钩子。答不出的一律不立——
从来没人筛的标签不是中性的，它在看板上占一格空位，后来的人会读成「这里应该有单，只是还没建」。
机器可读定义（名称/颜色/描述）的真相源在 `ccswitch/templates/labels.json`；判据与派单动作只住本表。

**配色法则**：同一根轴同一色系，轴内明度 = 催促度。收件箱轴统一紫族（**紫色 = 等用户**，零例外），旗标轴暖色。

| label | 轴 | 颜色 | 任务面筛选式 | 消费方 × 消费时刻 | 自动化钩子 |
|---|---|---|---|---|---|
| **缺陷** | 类型 | `d73a4a` 红 | `is:open label:缺陷` | **总帅**，派单那一刻——走「先复现再修」路径，不直接改 | 每日扫未派单的开放缺陷 → 提请进派单队列 |
| **任务** | 类型 | `0075ca` 蓝 | `is:open label:任务` | **总帅**，派单那一刻——默认路径，按「要不要先查清楚」分侦察官/实现官 | 每周：open 且 >30 天无评论 → 提请降 `候选` 或关单 |
| **欠账** | 类型 | `fbca04` 黄 | `is:open label:欠账` | **总帅**，收账批开工那一刻——关闭条件是「那一面验了」不是「代码改了」 | 每周：正文引用的 PR 已合并 → 提请解冻收账 |
| **待拍板** | 收件箱 | `8250df` 深紫 | `is:open label:待拍板` | **用户**有空扫一眼那一刻；**总帅**开窗第一动作也扫 | 每日刷新 #70 汇总表；>7 天未拍的置顶标红 |
| **需用户** | 收件箱 | `a371f7` 中紫 | `is:open label:需用户` | **用户本人**，只有他能做的事（凭据/登录态/目验） | 每日刷新 #71 汇总表；按耗时升序排 |
| **候选** | 收件箱 | `d4c5f9` 浅紫 | `is:open label:候选` | **总帅**闲时/收工扫描；**用户**扫「有没有该提优先级的」 | 每周刷新 #69 汇总表；>60 天无人动 → 提请关单 |
| **接力** | 指针 | `c5def5` 浅蓝 | `label:接力`（全仓恰一张） | **AI**，`/dao-resume` 启动那一刻——靠它找到接力单 | 每日：`count != 1` 即告警（0=接力断了，≥2=会读错） |
| **守卫类** | 旗标 | `b45f06` 深橙 | `is:open label:守卫类` | **总帅**，派单那一刻——强制加派对抗验证官才准合（dao.md `[#帅-对抗前置]`） | 每日：守卫类单关联的 open PR 无对抗记录 → 告警 |

**实况注记（2026-08-13）**：GitHub 上当前是 **9 个 label**——终表 8 个之外 `test` 暂留。这不是本表写错：
拍板 1-A 要求 `test` 存量「先出映射清单呈人扫、不许直接刷」，31 张清单已出（29→`欠账` 2→`任务`，
`_tmp/2026-08-13-label-migration-test30.md`），人扫单是 **#372**。解冻条件：#372 人扫通过后按清单刷 31 张并删 `test`，实况即归 8。

**钩子现况**：拍板 2-A 首批 3 条 automations 已建成 enabled 且各真跑过一轮
（收件箱汇总刷新 09:00 / 接力唯一性校验 09:05 / 守卫类无对抗告警 09:10）；其余 6 条挂跟进单 **#373**，跑两周看噪音再扩。

**`真机` 标签本仓已删、跨项目模板留**（拍板 1-D）：windsurf-dao 是规则/脚本/hook 仓，没有 GUI、没有打包版、
没有真实输入设备，「测试全绿但真机是坏的」这类缺陷在这里不存在——标签留着只会空转误导。
`ccswitch/templates/labels.json` extensions 段那份原样保留给有 GUI 的项目；本仓哪天长出真机面，再建是 10 秒的事。

### 二.3 帅读标签 → 派单动作速查

- `缺陷`/`任务` 无认领 → 领活派，按类型选官种；排序看板列顺序（多机并行时先过 `dao-claim.ps1` 租约，不直接抢）
- `欠账` → 不单派，攒收账批清
- 任意 + `守卫类` → 实现官止步 PR，**必接对抗验证官**才合
- `候选`/`待拍板`/`需用户` → 不派，进各自蓄水池；`候选` 升级走 **relabel 不是 re-create**
- `接力` → `/dao-resume` 专用，谁都别打第二张

**用户只需要记三个紫的**：`待拍板`（要他决策）+ `需用户`（要他动手）+ `候选`（酝酿层，扫一眼有没有该提的）。

## 三、常设单（置顶 = 等你回话，零例外）

**判据**（#360 拍板 6-A/6-B）：能在上面**回一句话就让事情动起来** ⇒ 常设 issue（交互面）；
只是想看全景、不需要回话 ⇒ 看板（观测面），不开单。常设单数量与收件箱 label 一一对应（条款正文在 `ccswitch/rules/dao-dispatch.md` §一）。

三个置顶槽全部给交互面：

| 单 | 是什么 | 置顶 |
|---|---|---|
| #70 📌 待拍板总览 | AI 攒决策，用户在评论区回一条即算拍板 | ✅ |
| #71 📌 需用户总览 | 只有用户能做的事集中入口，含耗时估计 | ✅ |
| #69 📌 候选总览 | 酝酿层全景 + AI 的按住理由与 promote 条件 | ✅ |

**#72 总览 hub 已撤**（拍板 6-A）：它是纯观测面，观测归看板；看板链接挪到**仓库 About 栏**（首页右上一眼可见）。
从此**置顶数字有变化 = 有事等你回话**，不用点进去分辨哪张是全景哪张是收件箱。

三张单的内容都是从 label 筛出来的清单，**不手维护**（手维护的清单必过期），由 automations 每日刷新（§二钩子现况的 3 条之一）。

**蓄水池纪律**：`待拍板` / `需用户` / `候选` 三类**永不进清零目标**、不催、攒批。
任何「issue 清零」类目标一律读作「**除蓄水池外**清零」。

## 四、issue 标题三闸

**三道闸，全部一眼可判、可机检**（#360 拍板 3-A）：

| 闸 | 规则 | 为什么 |
|---|---|---|
| **长度闸** | 标题 **≤30 字符**（中英文都按 1 字符算，含标点） | 本仓标题常带技术标识符（`dao-rule-echo` 一个就占 13 字符），30 是给标识符留的余量，不是放宽 |
| **结构闸** | 主干必须是**动词 + 对象**（「补 X」「删 X」「查 X 为什么 Y」），不许是名词短语 | 名词短语标题读完不知道要做什么，得点开正文才知道 |
| **标点闸** | **禁 `——`、禁 `（…）`/`(…)` 后缀、`：`至多一个**（冒号后仍计入 30 字符） | 实测本仓全部超长标题都是这三个标点后面挂第二子句造成的。禁标点比数字数更治本 |

**第四条**：**同日同型的批次单，标题必须自带可分辨项**。本仓实证：4 张标题一模一样的
`云审红：ci-sweep 2026-08-12`，任务面上完全不可分辨，想找某一张只能逐个点开。修法：加 PR 号或红项名，
如 `云审红 ci-sweep · PR#352 hook 路径`。

**只对新单生效，存量 173 张不回头改**（拍板 3-B）：改旧标题会让评论/PR body/`docs/specs/` 里引用旧标题的
地方全部对不上，而已关闭的单靠搜索也找得到——回头改是为整齐而整齐，别做这个无用功。

## 五、issue 描述分三档

**判档一句话**：这单关掉半年后，有人问「当时为什么这么定」，答案是不是只能在这张单里找到？是 ⇒ L，否 ⇒ 短的。

**判档规则**（拍板 4-A）：**AI 自判，默认 M 档**。带 `待拍板` 标签的自动 L 档；标题含「批」「迁移」「云审红」等
重复型的走 S 档；**其余一律 M 档**。写 L 档要在正文第一行注明理由——默认必须是短的，长描述要主动申请。

### S 档 · 一句话（机械活、可逆、有先例）

```markdown
做什么：<一句话>
关单条件：<一句话，可机检最好>
```

### M 档 · 三行式（默认档，绝大多数单）

```markdown
**为什么**：<一句话，说人话>
**做什么**：<一句话>
**特有验收**：<一句话——只写这单特有的，全仓缺省项不写>
```

### L 档 · STAR 全结构 + 证据折叠（只有三类单配：①要用户拍板的 ②改用户可见面或不可逆的 ③设计/立法类）

```markdown
## 说人话（没参与的人扫这段就够）
<3-5 行>

## 为什么（S/T：现状与要解的问题）
## 做什么（A：方案与取舍）
## 怎么验（R：验收条件）

<details><summary>技术证据</summary>
<数字一个不删，只是收起来>
</details>
```

### 五.3 全仓缺省段清单（一律不写，不写即默认生效）

本仓每张单都适用、因而写了等于噪音的（拍板 4-B 定此清单归本仓，dao 内核只留「全仓缺省项不进单」一条通用原则）：

- 验收跑 `node scripts/dao-check.mjs` exit 0
- commit subject 带 `[cc]` / `[codex]` / `[pi]` 前缀
- 走分支 → PR → 合并（PR-first），不直推 master
- worktree 隔离开工
- 三节点留痕（派单/交付/关单各一条评论）
- 说人话三条（STAR / 人话领先 / 证据折叠）

**只写这单特有的**。举例：「本单必须在 PS 5.1 上也跑通」是特有的，该写；「跑 dao-check」不是，别写。

### 五.4 进度不进正文（硬规矩）

执行心跳归 **Orca 板列 + 树备注**（§六），issue 只记**生死**——开单（为什么/做什么）与关单（怎么解的/验证结果）。
中间过程要留痕就发评论，**不要回头编辑正文**：正文被反复编辑之后，「当初是怎么定的」就永远查不回来了。

## 六、Orca 树备注规范

板列只答四态（todo/in-progress/in-review/completed），答不出「in-progress 里的具体哪一步」——树备注补这一格。

**格式**（≤40 字符，Orca 卡片一行显示得下）：

```
<编排形态> · <当前棒次> · <等什么>
```

| 格 | 取值 |
|---|---|
| 编排形态 | `轻装单兵` / `树帅制` / `多树并行`（三档来自 `dao-dispatch.md` §二） |
| 当前棒次 | **固定五值枚举**：`派单中` / `实现官在写` / `对抗官在跑` / `待终审` / `等用户`（拍板 5-B：加新值走拍板，不许自由发挥） |
| 等什么 | 一句话；无阻塞写 `无阻` |

举例：`树帅制 · 对抗官在跑 · 等 mutation 红集归因`、`轻装单兵 · 实现官在写 · 无阻`、`多树并行 · 待终审 · 等 #360 拍板`。

**issue 号不写进备注**：`--issue` 是 Orca 的结构化字段（建树/`worktree set` 都能带，可按 `issue:<n>` 查询），
备注里再写一遍就是第二份真相源——两份必漂移，且漂移时没人会发现。

### 六.2 写入时刻表（谁在什么时刻写）

| 时刻 | 动作 | 谁做 |
|---|---|---|
| 建树 | `orca worktree create --issue <n> --comment "<形态> · 派单中 · 无阻"` | 派单的帅。**必带**——拍板 5-A：包建树入口做硬闸强制 `--comment`（直接敲 `orca` 仍可绕，闸管正路） |
| 换棒（官交回/转手） | `orca worktree set --worktree <sel> --comment "..."` | 协调者顺手 |
| 打回返工 | 同上，`等什么` 格写打回原因 | 协调者 |
| 收活（进终审） | `orca worktree set --worktree <sel> --workspace-status in-review --comment "... · 待终审 · 无阻"` | 协调者 |

**与板列的分工**：`--workspace-status` 管四态大格，`--comment` 管这一格里的具体位置。
**两者必须同一条命令里一起改**——只改状态不改备注，备注就开始撒谎。

## 七、批次机制（父单 + sub-issues）

多子任务的活开**父单**写目标+验收，子单逐一挂上去，父单进度条即清偿进度，子单全关父单收官。

```
gh api repos/thoerwink8/windsurf-dao/issues/<父单编号>/sub_issues -f sub_issue_id=<子单的 database id>
```

🔴 **`sub_issue_id` 要的是 database id，不是 issue 编号**——传编号会挂错单或报错，
而挂错的那一刻没有任何提示。取法：`gh issue view <n> --json id -q .id` 拿到的是 node id（GraphQL 用），
database id 走 `gh api repos/thoerwink8/windsurf-dao/issues/<n> -q .id`。两个 id 长得完全不同，别混。

舰队批处理同型：一批开一个批次父单，处理对象挂子单，批完关父单。

## 八、全量核账的五向分流（triage verdict）

批量核账（如「把所有 open issue 过一遍」）时每单判一向。**判 `ghost` 门槛最高**——
要证明「确实不存在了」，拿不准一律降级 `keep`（判错方向的代价不对称：误判 keep 只是多留一张单，
误判 ghost 是把一个真问题关掉且从此没人再看见它）。

| verdict | 含义 | 后续动作 |
|---|---|---|
| `ghost` | 已修 / 已过时 / 不再成立 | 帅复核证据链 → 关单留结论 |
| `fixable` | 仍成立可修 | 进实现批（批次父单组织，并行拆官） |
| `blocked` | 结构受阻 | 记解锁依赖，解锁件排优先 |
| `keep` | 成立但不属以上 | 留队列 |

**官只读不写**：判定与关单草稿交回，`close`/`comment` 动作归帅（**终审不可让渡**）。

## 九、既有约束的裁剪（领活时逐条过）

- **独占资源类**（真机 / 单设备 / 单账号）：同时刻只准一路，排队合批清。**本仓当前没有这类资源**（`真机` label 已删，拍板 1-D，见 §二）。
- **账本类**（教训 CSV / 版本快照）：冻结归帅收账，不并行——多路并行时账本是唯一共享写入面，抢改必冲突
- **判据/护栏类改动**：对抗验证前置到 merge 之前，不先合后审（本仓这类占比高，见 §二.5 `守卫类`）
- 派单契约门、军衔通报、验证分级：见 `ccswitch/dao.md` 帅节 + `ccswitch/rules/dao-dispatch.md`（本文不重复）
- **跨仓引用面**：windsurf-dao 与 mousse-cli 双向引用密集（dao.md / skills / stacks 互指）。
  改文件名、条款标题、节标题、脚本路径时，**Grep 面必须含另一个仓**；跨仓改动进不了同一个 PR，
  正确形态是同批开一个跨仓 issue，不是「顺手记一下」。
- **always-on 配额**：`ccswitch/dao.md` 每轮注入给所有 agent。往里加字之前先问「这是不是每轮都要用」——
  只在某个时刻用得上的，归 `ccswitch/rules/` 存根 + 现场 Read，或归作用域档。
- **配置生效面**：hook / 权限类改动的真实下发源是 cc-switch DB 的 `providers.settings_config`，
  **改 git 快照层与 `common_config_*` 镜像层不生效**（#49 实测证伪）。判据见 dao.md Shell 节「改配置先认源与投影」。

## 十、三态归位——什么进 issue，什么留文件，什么进看板

**判据一句话**：说得出「关闭条件 + owner」→ issue；是聚合视图 → 看板；是流水/叙事/跨切 → 文件。
（dao 通用条款「工作项三态归位」的项目落地，细则正文在 `ccswitch/rules/dao-dispatch.md` §一。）

| 载体 | 装什么 | 本项目现状 |
|---|---|---|
| **issue 区（分配中心）** | 有生命周期的单元 + `候选` 酝酿层 + 蓄水池 | label 终表 8 个（§二，#360 拍板；实况暂 9，`test` 待 #372 人扫）。确定性迁移 37 张已刷并回验；`test` 组 31 张待人扫后刷 |
| **看板（观测中心）** | 全部单的聚合全景，标签驱动归列 | [windsurf-dao 观测中心](https://github.com/users/thoerwink8/projects/1)（入口在仓库 About 栏） |
| **仓内文件（叙事层）** | 无 per-item 生命周期的密集内容 | `docs/evolution/`（教训账本 CSV + 事故叙事 + 条款论证史）· `docs/specs/`（批次 spec 与收官记录）· `TODO.md`（酝酿层残余）· `AGENT_GUIDE.md`（细则与出处） |

🔴 **本仓没有 `PROGRESS.md`**（canonical 模板默认它存在）。流水叙事分散在 `docs/evolution/` 与 `docs/specs/` 两处，
这是实况不是缺项——本仓的「一件事的经过」历来按**教训**和**批次**组织，不按时间线。要总账时读这两个目录，
别去找一个不存在的文件。

**判据自检**：一个「问题树看板」型文件在 issue 中枢+看板建成后多半**冗余**——退役归档、活账交 issue。
本仓的 `TODO.md` 待过这一道：候选那半应迁 `候选` 标签的 issue（**未做，见未尽处**）。

🔴 **一次性人工动作**（Projects v2 自动化 gh CLI 建不了）：看板的「新 issue 自动入板」workflow
要在网页点一次（约 2 分钟）。步骤见 issue #71。在那之前，新建 issue 由帅手动 `gh project item-add` 灌入。
