# 2026-08-31 方向：编排与工位树只在 Linux 服务器，Windows 本机不编排

> 方向记录，不是施工单。服务器还没买，**没机器之前不改运行时代码**。
> 后人要对齐「本机为什么还有一堆 worktree / 要不要把派工搬服务器」，先读本文，再读 8-24。

## 谁提的，什么场景

用户 2026-08-31（mirasim 会话）：先问本仓为什么有很多 worktree、是不是只留 `origin/master` 把其余删掉；接着设想改造——

- 编排流程全部放在 Linux 服务器；
- 本地不再做编排，因此本地也不起工位 worktree；
- 只有 Linux 服务器上才有工人 / 审官 worktree。

服务器尚未购买。本文只把方向写死，方便买到机器或下一次改运行时的人对齐，不进入 issue 队列（说不出哪一批开工 ⇒ 不开单）。

## 决定（方向）

1. **唯一编排运行时是一台专用 Linux 服务器**（另买，不是现在那台反代机）。orca 无头、`dispatch`、工人/审官卡、看门狗该留的部分、automations，都只在那台上。
2. **Windows 本机不编排。** 不起工人/审官 orca 卡，不 `worktree create`，不跑本机自动派单 / 本机 `flow` / 本机保活钩。人看 GitHub，或远程连服务器上的 orca。
3. **本机可以留一份普通 `git clone`（master）**，给人手改、读文档。那不是工位树，跟派工无关。Mirasim / Cursor 自己的会话检出也是另一回事。
4. **本机不跑 `dispatch`。** 比 8-24「一条命令两处用」更干净：人要派单就上服务器敲，或打到服务器 runtime。避免再出现本机一份真相、服务器一份真相。
5. **现有反代机（156.224.28.95，1.9G）继续只做订阅转 API，不塞 orca。** 8-28 那次翻车就是一台小鸡两头扛。

## 改动大不大（预估，不是工期）

- **派工闭环本身不大。** `dao.mjs`、士兵/审官任务书、GitHub 当队列、ledger、bot 身份、点将台，原样搬；工位树只是换一台机器创建。
- **中等偏大的是删 Windows 编排层**（没宿主之后才删）：五层判活、`flow.mjs` 常驻、`windowsHide` / powershell 依赖、保活 hook、`dao-check` 里专为本机设的项。多数是删除，不是重写。
- **真正的门槛是机器规格**，不是仓库。1.9G 已经证伪。建议 Ubuntu 24.04、**16GB 内存起（32GB 更稳）**、4 核、100GB+ 盘、无需 GPU；6768 只走 Tailscale 或 SSH 隧道，不公网裸挂。装法与坑见 `NEW-MACHINE.md` §9d（Ubuntu 24.04 已真跑过）。

## 切法（有机器再做；没机器禁止提前拆本机）

1. 买对机器，按 §9d 起 `orca serve` + systemd + 账号。零代码。验收：`node scripts/server-check.mjs`。
2. 切断本机 orca 当运行时：派工只打服务器；Windows 停自动派单、停建卡。
3. 再删 Windows 编排层。层已经没宿主，删才安全。
4. 搬家前置仍按 8-24：**先补审官代码质量标准**（任务书里「审读规矩」是空指针）。全自动会把坏审查放大成一堆绿勾，这个比搬家急。
5. 影响体系的落地过夜再开工（8-24 S4）：服务器会一夜做完拍错的事。

## 明确不做什么

- 现在不删保活 / `flow` / 本机 hook——没有第二台 runtime，拆了就没闭环。
- 不开 GitHub issue、不把本文当本迭代施工单。
- 不把反代机再改回 orca 机。
- 不在 Windows 上保留「手动 `dispatch` 也能建卡」的第二入口。

## 体系类三问

1. **谁提的，什么场景？** 用户 2026-08-31，本机工位树多、觉得乱，想把编排搬走；服务器未买。
2. **删哪一层能让这个问题不存在？** 删「Windows 本机当编排运行时」整层。工位树是这一层的派生物，层去则本机不再长树——不是靠人记得删树。
3. **从零重做今天还会造它吗？** 会造「Linux 上的多模型派工运行时 + 命令库 + 自检 + 拍板档案」。不会造本机工位树、自研五层保活、本机/服务器两套派工入口。
