# 设计题

## 背景

一条全自动的软件协作流水线，参与者都是 AI：

- **工人**：接到任务后写代码，开一个 PR（合并请求）
- **审官**：另一个 AI（刻意选用不同厂商的模型，避免同源盲区），审查这个 PR
- 审官判红 → 工人按红项返工 → 审官再审 → 循环
- 只有审官判绿，PR 才能合并

调度器每 20 分钟跑一轮，负责派工、催返工、叫复审。全程无人值守。

## 实测数据

24 小时观察窗内：

- 17 张开放 PR 累计 **53 个审查轮次，0 次判绿**
- 单张 PR 最长跑到 **9 轮 / 19 次提交 / 12 天**
- 抽查多轮评审正文：红项都带 `文件:行号` 与实际命令输出，**是真缺陷**，不是吹毛求疵或风格洁癖
- 现象是：每轮工人修完上一轮的问题，审官又发现下一层问题
- 同一时间窗内，**243/351 会话小时（69%）花在「重新派发同一个任务」上**
- 调度器从没漏过一轮，日志正常无报错，但盘面可以完全冻住

补充事实：

- 工人和审官都是当代前沿大模型，能力不是瓶颈
- 审官有一份书面的审查标准，工人有一份书面的任务说明
- 任务本身是真实的工程活：修 bug、加检查、改基础设施脚本
- 每一轮返工和复审都要花掉真金白银的模型调用额度

## 用户诉求

这条流水线要能**在无人值守下持续产出**——活派下去能完成、能合并，不需要人每次介入。

现在它在空转：机器一直在跑，产出为零。用户要的是「事情办成」，不是「系统看起来很忙」。

## 你要回答的

1. **这条流水线为什么永不收敛？** 根因是什么？（不要停在「审官太严」这种表层描述，往下挖）
2. **你会怎么改？** 给出具体的机制设计——不是原则口号，是可以落地成代码或流程的东西。说明它为什么能收敛。
3. **你的方案在什么情况下会失效？** 给具体的失效条件。
4. **如果只能改一处，改哪里？** 只给一个答案。
