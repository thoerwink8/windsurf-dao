# 设计题作答

## 1. 这条流水线为什么永不收敛？根因是什么？

### 现象背后的结构

题面给的关键线索可以拼成一条因果链：

- 红项是**真缺陷**（有文件行号、有命令输出），说明审官不是在「挑刺」，而是在做**全量深度审计**。
- 工人每轮**只修上一轮点名的红项**，审官下一轮又发现**下一层**问题——这是典型的「打地鼠」模式，不是随机噪声。
- 69% 会话小时花在「重新派发同一个任务」上，说明调度器在**重复同一策略**，没有根据失败模式切换打法。
- PR 规模与轮次正相关（I：3161 行 / 9 轮；A/B/C：小改动但 24 小时内也 0 绿），说明问题不只在「PR 太大」，而是**收敛判据本身有问题**。

### 根因：缺少可终止的「完成定义」，审查被建模成无界搜索

表面说法「审官太严」只描述了症状。往下挖，根因是**系统把合并条件定义成「审官在当前轮次找不到任何新问题」**——这在工程上等价于对一个开放代码库做**无界缺陷搜索**，理论上不保证终止。

具体机制如下：

**（1）审查范围是「全 PR 扫描」，返工范围是「上轮红项清单」——二者不对称**

每一轮复审，审官默认职责是重新审查**整个 PR**（所有文件、所有路径、所有边界情况）。工人收到的输入却只有**上一轮列出的几条红项**。工人按清单做**局部最小修补**；修补本身又改动代码、引入新上下文，审官用**不同的检查角度**（安全、并发、错误处理、测试覆盖……）自然能在相邻层发现新缺陷。

这不是「工人能力差」，而是**搜索空间随轮次单调扩大**：每修一处，审官的有效探测面就多一块。在真实工程任务里（修 bug、加检查、改基础设施脚本），缺陷本来就有**层次性**——单元逻辑对了，集成边界才暴露；边界对了，运维路径才暴露。流水线没有任何机制说「这一层算完成，下一层另开任务」。

**（2）没有「阻塞 / 非阻塞」分级，所有发现都等价于判红**

审官的书面标准若未强制区分 severity，则模型倾向于**保守**：任何一个真实 bug 都足以判红。真实 bug 的供给在复杂 PR 里**近似无限**——永远存在更深一层的 edge case。人类团队能合并，是因为有**「够好可 ship」** 的社会契约；当前流水线把这个契约缺省了，换成**「零已知缺陷」**，在无人值守下必然永不收敛。

**（3）任务卡与审查标准之间缺少可机器核验的「验收闭包」**

工人有任务说明、审官有审查标准，但合并门控是**纯 LLM 主观裁决**，没有一层**独立于审官的、单调递减的客观关卡**（测试套件全绿、lint 全绿、任务卡里的 acceptance criteria 逐条打勾）。结果是：即使客观指标已满足，审官仍可因「又发现一个新角度的问题」判红；工人无法知道「还要修几轮才算完」。

**（4）调度器只做「催返工」，不做「策略升级」**

20 分钟一轮的调度器在 PR 已卡 9 轮 / 12 天时，仍用**同一张任务卡、同一种派工方式**重新唤醒工人。69% 时间花在重派同一任务上，说明系统在**重复同一局部最优策略**（修红项 → 再审 → 再红项），没有触发 PR 拆分、范围冻结、验收模式切换、或 escalation。这不是调度 bug（日志正常），而是**状态机设计缺失**：缺少 `stuck` 状态及对应的结构性干预。

### 一句话根因

**合并条件被定义为「LLM 全量审查零发现」，而工人被约束为「逐条修补上轮红项」；再叠加无 severity 分级、无验收闭包、无 stuck 干预——系统在数学上是一个没有下界的最优化过程，不是一条能终止的工作流。**

能力不是瓶颈（题面已说明），**流程拓扑**才是：这不是模型问题，是**把开放式 code review 当成了 merge gate 且未设终止条件**的问题。

## 2. 你会怎么改？具体机制设计

下面是一套可落地为代码/配置的机制，目标是把「无界搜索」改成**有上界的有限状态机**。

### 2.1 三层门控：客观层 → 验收层 → 审查层（审查层权力被收窄）

```
派工 → 工人开 PR
         ↓
    [G1 客观门]  CI / lint / 单元测试 / 任务自带脚本 —— 全绿才进入审查
         ↓
    [G2 验收门]  任务卡 AC 清单逐条自动核验（见 2.2）
         ↓
    [G3 审查门]  审官仅审「AC 相关 diff + 上轮阻塞项 delta」（见 2.3）
         ↓
       合并
```

**实现要点：**

- G1 由现有 CI 管线执行，**不过 G1 不消耗审官额度**，调度器直接打回工人。
- G3 不再对全 PR 做开放式挑错；审官 prompt 硬约束：「你只能就下列清单项判 blocking；清单外发现必须写入 `follow_up` 字段，不得判红。」

这直接切断了「每轮发现新层问题 → 判红」的无限链。

### 2.2 任务卡强制带「可核验验收闭包」（Acceptance Closure）

派工时，调度器要求任务卡包含结构化 AC，例如：

```yaml
acceptance:
  - id: AC-1
    check: "pytest tests/test_foo.py -k test_edge_case_x"
    expect_exit: 0
  - id: AC-2
    check: "grep -q 'validate_input' src/foo.py"
    expect_exit: 0
  - id: AC-3
    check: "manual_review_rubric: error_messages_must_not_leak_internals"
    reviewer_only: true   # 仅 G3 审官按 rubric 打勾，不可自由发挥
```

调度器在派复审前**自动跑**非 `reviewer_only` 的 AC；任一失败 → 打回工人，**不叫审官**。

**为什么能收敛：** AC 条数是任务派发时固定的有限集合，每条的通过状态是单调的（过了不会回退，除非工人 force-push 改坏——那由 G1 抓）。合并条件变成「AC 全绿 + 零 blocking 审查项」，搜索空间有**有限上界**。

### 2.3 审查输出契约：blocking / non-blocking + 范围冻结

审官输出强制 JSON schema：

```json
{
  "blocking": [{"id":"B1","file":"...","line":42,"reason":"..."}],
  "non_blocking": [{"id":"N1","file":"...","suggestion":"..."}],
  "ac_checklist": {"AC-3": "pass"}
}
```

规则（写进审官标准，调度器强制执行）：

| 规则 | 内容 |
|------|------|
| R1 | **仅 `blocking` 非空时判红**；`non_blocking` 自动开 follow-up issue，不阻塞合并 |
| R2 | **Round-1 范围冻结**：第一轮审完后，调度器生成 `frozen_scope.json`（= 该轮全部 blocking 项）。Round 2+ 审官**只能**验证 frozen 项是否修复 + 本次 diff 是否引入新的 blocking（见 R3） |
| R3 | **新发现默认 non-blocking**，除非命中 `hard_blockers` 白名单（如：明文密钥、RCE、数据丢失）——白名单由人维护，约 10–20 条，不交给模型自由扩展 |
| R4 | Round 2+ 审官输入**不包含全 PR**，只包含：`frozen_scope` + `git diff <last_reviewed_sha>..HEAD` + AC rubric |

**为什么能收敛：** Round 1 把「必须修什么」定成有限集合；后续轮次审官**不被允许**无限追加 blocking（除 hard_blockers）。工人目标从「猜审官下一步想什么」变成「清空 frozen 清单」——清单长度单调递减。

### 2.4 派工侧：PR 尺寸硬顶 + 超线自动拆分

调度器在工人开 PR 后跑：

```python
if pr.changed_lines > 300 or pr.changed_files > 8:
    reject_merge(); spawn_task("split_pr", parent=pr)
```

拆分任务卡模板：`「将 PR #N 按 commit 或目录拆成 ≤200 行的子 PR，每子 PR 独立 AC」`。

题面数据里 I（3161 行 / 9 轮）是极端 case；硬顶避免单 PR 承载过多缺陷层。

### 2.5 调度器状态机：stuck 检测与策略升级

在现有 20 分钟轮询上增加 PR 级状态：

```
OPEN → IN_REVIEW → REWORK → ... 
                      ↓ (rounds≥3 且 blocking 数未减少)
                   STUCK_SPLIT   → 强制拆分 / 重写任务卡
                      ↓ (rounds≥5)
                   STUCK_REBASE  → 换工人模型 + 注入完整审查历史摘要
                      ↓ (rounds≥7)
                   STUCK_ESCALATE → 挂起自动流，打标「需人看」，停止烧额度
```

**关键：重派时必须变更策略**，禁止同策略第 N 次重派（直接解释 69% 空转）。

触发 `STUCK_*` 时，调度器**不得**用原任务卡 verbatim 重派；必须附带 `strategy_version++` 和结构化失败摘要。

### 2.6 工人侧：返工包必须是「类修复」而非「点修复」

工人返工输入从「红项列表」改为：

```
blocking_items[] 
+ required_for_each: { root_cause, fix_approach, test_added_or_updated }
+ regression_command: 工人必须新增或更新的测试命令
```

调度器在叫复审前**自动跑** `regression_command`；不过则不进入 G3。

这减少「修了 A 引入 B」的循环——工人被强制为**缺陷类**补测试，而不只是改一行。

### 收敛性论证（简述）

| 变量 | 上界 |
|------|------|
| AC 条数 | 派工时固定 |
| Round-1 blocking 条数 | 有限（审官一轮输出有限） |
| 后续新增 blocking | 仅 hard_blockers 白名单 |
| 复审轮次 | stuck 状态机强制 ≤7 自动挂起 |
| PR 规模 | 300 行硬顶 |

因此系统从「无界搜索」变为**有限状态空间上的单调递减过程**（blocking 清单在 R2 约束下只会缩短或触发 stuck 升级），故可收敛。

## 3. 你的方案在什么情况下会失效？

以下失效条件都是**具体可观测的**，不是抽象「模型变笨了」。

### 3.1 任务无法被写成可核验 AC（验收闭包为空或虚假通过）

**条件：** 任务本质是探索性重构、审美性 API 设计、或「让系统更好用」这类**无客观 oracle** 的活；派工者敷衍写 AC（`expect_exit: 0` 但脚本是 `true`），或 AC 只覆盖 happy path。

**表现：** G2 全绿但合并后仍有大缺陷；或工人 gaming AC（最小改动通过 grep 检查），审官被 R2/R3 束缚无法判 blocking。

**本质：** 方案把收敛性建立在「AC 可信」上；AC 不可信时，系统退化成**快速合并烂代码**，而非**慢速不合并**——是另一种失败，不是冻住，但同样达不到「事情办成」。

### 3.2 hard_blockers 白名单覆盖不足，真实高危缺陷只能进 non-blocking

**条件：** 新类漏洞（如某种 prompt injection 在内部工具链中的变体）不在白名单；审官按 R3 只能写 `non_blocking`；PR 合并后出事故。

**表现：** 收敛很快、合并很多，但**安全/正确性债务**转移到 follow-up issue 池且无人值守无人处理。

**触发场景：** 基础设施脚本、权限边界、多租户隔离——缺陷类型快速演化，静态白名单滞后。

### 3.3 Round-1 范围冻结把「大缺陷」锁在错误粒度

**条件：** 审官第一轮漏报关键 blocking（同源盲区、prompt 误导、或 PR diff 过大审官上下文截断）；该缺陷不在 `frozen_scope` 里；Round 2+ 审官按 R2 ** legally 不能** 将其升为 blocking。

**表现：** PR 快速判绿，缺陷潜伏；或工人/fix 在 frozen 项上空转，真正问题在合并后暴露。

**题面关联：** 题面说审官刻意异厂商——但**第一轮**仍可能漏；冻结机制把「第一轮完整性」变成单点故障。

### 3.4 PR 拆分破坏原子性

**条件：** 任务在逻辑上必须原子交付（跨文件重构、迁移脚本 + 代码同 PR）；300 行硬顶强制拆分。

**表现：** 子 PR 单独 CI 绿、单独 AC 绿，但**合并顺序错误**导致 main 中间态 broken；或拆分边界切在藕断丝连处，follow-up 子 PR 永远派不出去（依赖未合并）。

**观测信号：** main 分支在部分子 PR 合并后出现 CI 红，且多个 sibling PR 互卡。

### 3.5 stuck 升级仍无法收敛的「 genuinely hard」任务

**条件：** 任务需要外部 secret、人工审批、或依赖尚未存在的上游接口；已达 `STUCK_ESCALATE` 挂起。

**表现：** 不是方案逻辑失败，而是**问题被正确识别为不可无人值守**——盘面从「假 busy」变成「真 blocked」。若用户不接受「需人看」的挂起态，会感知为方案失效。

### 3.6 工人-审官合谋 gaming（在非异厂商子路径下）

**条件：** 若 stuck 升级后「换工人模型」但仍无 G1/G2 硬约束，或同一厂商临时替补；工人学会只改 frozen 项外观（改行号、改注释）通过 delta 审查。

**表现：** 轮次下降、合并上升，但红项复现于生产。

**缓解依赖：** G1 测试 + 工人必交 regression_command；若项目测试本身稀，此路仍通。

### 3.7 测试/CI 本身不可靠（G1 不可信）

**条件：** flaky test、CI 环境漂移、基础设施脚本在 CI 与生产不一致。

**表现：** G1 随机红/G1 假绿；系统在 REWORK 与 IN_REVIEW 间振荡，或 G1 假绿 + G3 被收窄后漏检。这与原题「审官发现真缺陷」不同，是**客观层撒谎**导致整体失效。

---

**小结：** 方案最大赌注是 **「AC 可信 + Round-1 完整 + hard_blockers 够用」**。三者任一系统性失败，收敛性仍在，但**语义正确性**或**安全**会失守。

## 4. 如果只能改一处，改哪里？

**只改一处：审查输出契约 + 调度器强制执行——「仅 blocking 判红，且 Round-1 之后不得新增 blocking（hard_blockers 白名单除外）。」**

### 为什么选这里

- 根因是「无界搜索 + 每轮全量扫描判红」；**范围冻结 + severity 分级** 直接截断无限链，无需先动派工、CI 或工人 prompt 就能见效。
- 题面 53 轮 0 绿、真缺陷逐层暴露——这是**审查门控建模错误**的直接症状；改判红逻辑是**最小手术面、最大杠杆点**。
- 69% 重派空转：只要 blocking 清单在 Round 2+ 不再膨胀，工人有**有限目标**，轮次自然有上界，调度器重派才会「有意义地接近完成」而非「第 N 次打地鼠」。

### 落地形态（一处 = 一个组件）

在**调度器解析审官输出、决定是否判红**的那个模块里，硬编码：

1. 解析 `blocking` / `non_blocking` schema；`non_blocking` 自动建 issue，**不触发 REWORK**。
2. 维护 `frozen_scope`（Round-1 blocking 集合）；Round 2+ 若 `blocking` 中出现不在 `frozen_scope` 且不在 `hard_blockers` 的项 → **丢弃并记审计日志**，不判红。
3. 判绿条件：`blocking == []`（在冻结语义下）。

其他改进（AC 闭包、PR 尺寸、stuck 状态机）都增强 robustness，但**单点改审查-调度接口**即可把系统从「永不收敛」改成「最多 N 轮必绿或必挂起」——N 由 Round-1 blocking 条数决定，有限。
