# 1. 这条流水线为什么永不收敛？

根因不是“审官太严”，而是这套协议没有定义一个**有限、稳定、可判定的完成状态**。

当前实际运行的是：

```text
工人修当前可见问题
→ 审官重新做一次开放式缺陷探索
→ 发现新的真实问题
→ 再把同一个任务派回去
```

这不是“修复直到满足验收条件”，而是“每轮都重新搜索整个系统”。因此有三个相互放大的结构性问题：

1. **审查目标不封闭。** 书面审查标准和任务说明并不等于可执行的验收契约。没有明确的范围、优先级、完成判据和“本轮之后不再扩大范围”的规则，审官每次都可以沿着新暴露的依赖继续往下挖。它发现的缺陷是真缺陷，但“是真缺陷”不代表它们属于当前 PR 的无限阻塞集合。

2. **进展不是单调的。** 没有稳定的 finding（问题）身份、状态和基线；也没有规定复审只能验证已知阻塞项及回归。工人改动代码会移动审查对象，审官于是又对整个新 diff 开放探索。即使每轮修掉了旧问题，阻塞集合也可能被新发现补回，系统没有“距离完成更近”的可证明指标。

3. **调度器把活跃当成进展。** 日志正常、轮次在增加、提交在增加，于是调度器继续重派同一个任务；它没有最大轮次、模型调用预算、租约/去重、停滞检测或隔离状态。于是一个本应结束为“已合并”或“明确阻塞”的任务，被错误地当成可无限重试的正常任务。243/351 会话小时花在重复派发，正是这个反馈回路的直接证据。

所以这是一个**无界的发现过程 + 无界的重试策略**造成的活锁（livelock）：每个局部动作都合理，系统整体却没有终点。PR 越大、依赖越深，暴露下一层问题的概率越高；I 已经达到 9 轮、19 次提交，说明轮次增加本身没有带来收敛保证。

# 2. 我会怎么改？

把“审官自由发挥、调度器不断重派”改成一个有边界的、可审计的状态机。下面是一套可以落成代码的协议。

## 2.1 先生成当前 PR 的验收契约

派工时先创建一份版本化的 `contract`，至少包含：

- 本 PR 的明确范围和不做什么；
- 可测试的验收条件（每条对应测试、检查命令或可观察输出）；
- 阻塞级别定义：例如 S0（安全/数据损坏/无法启动）、S1（违反验收条件），S2/S3 只记录为后续任务；
- 最大改动范围、最大审查轮次和模型调用预算。

`contract` 固定后，审官不是“检查整个仓库是否还有任何问题”，而是检查“这个 diff 是否满足这份契约，以及是否引入 S0 回归”。契约变更必须显式开新版本并重置预算，不能在同一 PR 中悄悄扩大。

## 2.2 让审查结果成为结构化、可追踪的集合

审官必须返回机器可读的结果，而不是只有一段自由文本。每个 finding 至少有：

```text
id/fingerprint, severity, file, line, reproducible command/output,
violated_contract_item, status(open|fixed|wont_fix|follow_up)
```

`fingerprint` 由归一化后的规则、位置和问题摘要生成；位置移动时由上下文匹配更新，而不是凭文字猜测。系统保存每轮的 `base_sha`、`head_sha` 和 finding 快照。

第一轮允许在契约范围内做一次完整审查，但必须一次性提交全部已知 S0/S1。工人拿到整批阻塞项后一次返工，避免“一轮只修一个、下一轮再开一个”的串行放大。

## 2.3 复审只做有限的验证

复审轮次（例如最多 2 轮，或由任务风险等级配置）只允许：

1. 验证上一轮的 S0/S1 是否确实修复；
2. 运行契约中列出的 CI/测试；
3. 检查修复是否造成 S0 回归。

新发现如果只是 S2/S3，关闭当前 PR 的阻塞并自动开 follow-up 任务；只有违反当前契约或属于 S0 的新问题才可继续阻塞。审官若要保留旧 finding，必须给出在新 `head_sha` 上的复现证据，不能因为措辞相似就重新计数。

## 2.4 调度器按状态和进展调度，而不是按“还没绿”调度

任务记录保存 `state`、`lease_owner`、`round`、`head_sha`、`contract_hash`、`open_blockers`、`budget_left`。状态可设为：

```text
ASSIGNED → IMPLEMENTING → REVIEWING
         → REWORKING → REVIEWING
         → GREEN → MERGED
         ↘ BLOCKED/QUARANTINED
```

调度器必须做到：

- 同一任务同一时刻只有一个有效租约，重复事件幂等；
- 只有检测到新提交、finding 状态变化或 CI 状态变化，才允许进入下一步；
- 轮次、时间和模型额度任一耗尽，立即转 `BLOCKED/QUARANTINED`，停止重派同一任务；
- 隔离时自动生成带上下文的 follow-up（通常按契约条目或模块拆小），而不是把原任务原样再投递；
- 只有“CI 全绿 + 无 S0/S1 + 审官明确 `GREEN`”才能合并，合并动作本身也要幂等。

## 2.5 为什么这会收敛

对一个固定契约，定义势函数：

```text
未关闭的 S0/S1 数量
+ 尚未通过的验收条目数
+ 剩余重试/预算消耗（反向计数）
```

每次合法返工都必须关闭或验证一个已知阻塞项；新问题不能无限扩大当前阻塞集合；预算又是有限的。因此系统只能到达 `GREEN/MERGED` 或 `BLOCKED/QUARANTINED` 两类终点，不会再出现“轮次一直增加但状态没有终点”的活锁。隔离路径还保留了真实缺陷，不靠让审官放水来换取假绿。

# 3. 方案在什么情况下会失效？

这里的“失效”分两类：错误合并（假绿），或无法合并但能及时停在隔离态（假红/阻塞）。具体条件包括：

1. **验收契约写错或漏写关键需求。** 例如契约只要求接口返回 200，却没有要求权限隔离；CI 和审官都能绿，但产品语义已经错了。这是规范/产品输入错误，不是复审轮次能补救的。

2. **测试和检查命令不是可靠的判定器。** 测试覆盖不到真实路径、断言过弱、测试被错误地跳过，或测试本身 flaky；则“CI 全绿”不能推出实现正确。若同一 flaky 检查在预算内反复波动，系统会按设计进入 `QUARANTINED`，但仍不会自动解决根因。

3. **工人与审官存在共同盲区。** 两者虽然是不同模型，但如果共享同一错误假设、同一检索资料或同一坏的静态规则，可能一起漏掉缺陷。不同厂商只能降低相关性，不能提供正确性证明。

4. **缺陷跨越当前 PR 的边界。** 例如数据库 schema、部署配置和另一服务必须同时变更；当前契约只覆盖其中一块。把跨边界问题降为 follow-up 可能导致当前 PR 在局部看似可合并，或后续任务无法独立落地。此类任务必须在契约阶段标为跨 PR 原子变更，不能硬拆。

5. **环境或外部依赖不可复现。** 生产凭据、真实流量、第三方服务时序、硬件差异等不在 CI 可见范围内；审官无法给出稳定复现证据时，不能把“未复现”当成“没有问题”，应阻塞并隔离，等待补充模拟器或新的验收条件。

6. **需求在执行中改变，或工人超出范围改动。** 若 `contract_hash` 变化、改动文件/行数超过预算、基础分支漂移，旧的 finding 和测试结论都可能失效；必须新建契约版本或新 PR，不能沿用旧轮次继续审。

7. **状态机实现本身有错。** 例如租约过期后重复派发、事件丢失、finding 指纹碰撞、合并回调非幂等。机制会退化成原来的重复循环，所以状态转移、去重和合并动作需要持久化、幂等，并配套审计日志和告警。

8. **预算/轮次上限低于完成该任务所需的最小工作量。** 复杂迁移可能确实需要三轮以上；硬上限会把可完成任务过早隔离。这个代价是可接受的可见失败，但需要按历史数据调节预算，不能把隔离率误解为质量提升。

因此这套设计承诺的是：在契约、判定器和执行环境可信且任务可分割时，流程有限收敛；超出这些前提时，优先**可解释地停机并保留证据**，而不是产出未经验证的绿或继续烧额度。

# 4. 如果只能改一处，改哪里？

**只改调度器：给每个 PR 加上有硬上限的、带终态的重试状态机。**

最小实现是持久化 `round`、`budget`、`last_head_sha` 和 `open_blockers`，规定“没有新提交/新证据就不再派发”；达到轮次、时间或额度任一上限就转 `QUARANTINED`，停止原任务重试，并自动生成一个带当前证据的后续任务。只有 CI 通过、阻塞项为空且收到结构化 `GREEN` 才能进入合并态。

这一个改动不能凭空修复漏写的需求，但能立刻切断当前 69% 会话小时所形成的无界反馈回路：每张 PR 必然到达“合并”或“隔离”之一，盘面不会再因同一任务的无限重派而冻结；同时所有未解决的真实缺陷仍被保留下来，不会用强行放绿掩盖问题。
