# 模型校准闭环 v1

`scripts/calibrate.mjs` 从本仓 GitHub PR 的官方数据中生成模型战绩。它把每个真实任务当作一次校准样本：同一任务不重复运行，不另建 benchmark，也不建立数据库或埋点。脚本只读 GitHub 数据并把 Markdown 打到终端，不改文件、不发评论。

## 用法

在仓库根目录运行。需要已安装并登录 GitHub CLI，且当前目录能由 `gh repo view` 识别为目标仓库。

### 单单模式

```powershell
node scripts/calibrate.mjs --pr <N>
```

输出 PR `N` 的标题、状态、模型、任务类、返工轮数和审查红项数。若该 PR 同时带有 `model/*` 与 `type/*` 标签，输出还会附上该模型×任务类的最新累计战绩，并把尚未合并的本单临时计入累计值；这样主会话可在终审合并前直接把本单成绩和累计战绩呈现给用户。

没有完整标签的 PR 仍会输出本单成绩，但不会归入累计战绩。

### 全量模式

```powershell
node scripts/calibrate.mjs
```

输出所有模型×任务类组合的 Markdown 累计战绩表，包括样本数、平均返工轮数、平均红项和最近 3 单趋势。累计数据只取已合并 PR。

表中的最近 3 单按合并时间从旧到新排列，每项采用 `#PR号 返工/红项` 格式。

## v1 口径

脚本顶部注释与本文采用同一套定义：

- **样本**：同时带 `model/*` 和 `type/*` 标签的 PR。全量累计只使用已合并 PR；单单模式会把指定 PR 作为本单展示，并在标签完整时临时纳入该组合的累计战绩。
- **返工轮数**：PR 首次 ready 之后新增的 commit 数。若 PR 从未是 Draft，GitHub 不会产生 `ready_for_review` 事件，脚本以 PR 创建时间作为首次 ready 时间。
- **审查红项数**：从每条 review 正文**判定行**提取「判定：红 N 项」或「红 N 项」的最大 N，跨 review 取最大值（v2，issue #444）。#444 当时同账号不能 request-changes，审官以 COMMENT 提交、结构化线程数为 0——只数线程会把红项永远计成 0，已两次污染成绩单。#573 已废这条限制（审官是 `dao-reviewer[bot]`，走 approve / request-changes）；判定仍写正文首行，本口径继续认。跨 review 取最大 ⇒ 复核绿不清零首审红项；结构化 request-changes 的线程数仍兼容，取两者最大值。判定行指行首为「判定」「复核结论」（允许 `>`、`**` 前缀）的行——正文叙述里引用他单红数（如「比 #440 的红 4 项干净多了」）不计入，防引用性多计（对抗审 #449 红 1）。正则配真实语料回归（tests/calibrate.tests.js，语料为 gh api 拉取的 #446/#440 review body）。
- **无审读 vs 0 红**：0 条 review 的 PR 红项记 null，报告呈现「无审读」（单单模式还显示 review 条数）——「没人审过」与「审过零红」必须可区分，否则把没查成当查过没事（对抗审 #449 红 2，仓规硬条款）。累计平均只对审过的样本计红项；趋势里无审读记为「无审」。
- **平均值**：对应组合全部样本的算术平均值，保留一位小数。
- **最近 3 单趋势**：对应组合最近合并的最多 3 个样本，按时间从旧到新展示每单的“返工/红项”。
- **未标注**：已合并 PR 缺少 `model/*` 或 `type/*` 任一标签。它们只计入“未标注”提示，不混入战绩。

“无样本”和“成绩为 0”是两件事：没有样本的组合在样本数、平均值和趋势中都显示“无样本”；已有样本且没有返工或红项时显示数值 `0` 或平均值 `0.0`。

## 标签约定

每个校准样本需要各有一个模型标签和任务类标签：

- `model/<id>`：执行任务的模型，例如 `model/gpt-5.6-sol`。
- `type/<任务类>`：任务类型。v1 标准任务类为 `type/写码`、`type/判断`、`type/查证`、`type/审查`、`type/UI`。

脚本会读取仓库现有的 `model/*` 标签并展示其与各标准任务类的组合。若 PR 只有一类标签，仍视为未标注。一个 PR 应只使用一个 `model/*` 和一个 `type/*` 标签；v1 遇到同类多个标签时取 GitHub 返回的第一个，因此多标签会让归类含糊。

## 与 `docs/model-routing.toml` 的关系

校准结果是路由策略的证据，不是自动执行器。`docs/model-routing.toml` 描述当前模型路由定位；当累计数据显示某个模型×任务类组合的定位可能不合适时，由主会话整理调整建议，另开策略 PR 呈现给用户拍板。

数据只产生提案，不自动修改 `docs/model-routing.toml`，也不自动改变任何任务的模型选择。

## 已知局限

- commit 数只是返工轮数的近似。同一轮返工拆成多个 commit 会被多计，多个修改压成一个 commit 会被少计。
- review 正文红项数只是审查红项的近似。判定行格式约定「判定：红 N 项」（或加粗变体）之外的写法识别不到；同一问题拆成多条线程会被多计（结构化线程数兼容仍计入）；普通 PR 评论、口头反馈和外部审查不会被计入；0 条 review 记「无审读」而非 0 红。
- GitHub 只保留当前标签状态。PR 合并后补标签或改标签，会改变下一次全量报告的归类。
- 从未是 Draft 的 PR 没有 ready 事件，只能用创建时间近似首次 ready。
- v1 单个 PR 最多读取 100 个 commit。超过上限时脚本会明确失败，不输出不完整成绩。
- 样本来自本仓生产任务，任务难度、人员介入和交付范围不同；战绩用于持续校准定位，不应解释为跨仓库、跨时期的绝对模型排名。

## 不做

- **不自动改路由**：数据只形成策略提案，由用户拍板后再改。
- **不建定时任务**：先在每单终审时手动运行并养熟口径。
- **不给 PR 发评论**：脚本保持只读；主会话负责把结果呈现给用户。
- **不做 benchmark 对跑**：一个真实任务只由一个模型做一次，避免为测量而重复任务。

这些边界遵循 issue #425 的判例“手动养熟再自动化”，也遵循用户 2026-08-14 拍板的“一个任务只做一次”。
