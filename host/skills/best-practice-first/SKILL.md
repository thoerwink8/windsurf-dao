# best-practice-first：提方案之前先查业界怎么做

## 什么时候读

**任一「提方案」的时刻**——用户提的、或我自己提的：

- 用户说「我想做一个 X」「加个机制」「多个 skills」这类**方案/设计类**输入；
- 我自己准备**改协作方式、加规则、造长驻机制**（本仓 `CLAUDE.md` 的「体系类改动」三问也在这一步）。

**一句话**：**设计问题不许凭记忆答**。记忆里的「业界做法」可能已经过时；用户也不该每次打字提醒「你去查查最佳实践」。

## 怎么做（五步，顺序不可换）

1. **先查**（用 `docs-lookup` 的选路，不重复它）：搜索用 **`ddgs`**（本机 CLI，不要先试 WebSearch）；
   库/框架文档走 **context7**；GitHub 上的实现/讨论走 **`gh api` / `gh search`**；已知 URL 走 fetch MCP。
   **至少两条独立来源**，并记下**链接与日期**。
2. **摆对照**：一张表——「业界怎么做」vs「我们的约束」（把约束写清：本仓的规矩、机器形态、成本）。
   **业界做法与我们的约束冲突的地方，正是要拍板的地方。**
3. **给从零方案**：剥掉现状重推一遍（与 `grill-ai` 同精神）。**必须显式摆出「删掉整层」的选项**。
4. **摆代价表**：从零方案 / 现状方案 / 业界更重的方案，各写**代价与风险**，交用户拍板（`AskUserQuestion`）。
   **禁止替用户默认取舍**，也禁止「两个都做」。
5. **落库**：结论 + 依据（链接）+ 拍板结果写进对应 issue / PR。**只写指针与结论，不抄大段文档**（本仓「避免重复信息」）。

## 硬规矩

- **没有查证的设计回答，视为未完成**（可以答，但要标「未查证」并说明为什么这次不查——例如纯本仓内部事实）。
- **引用必须可点开**：给 URL 或 `文件:行`；不许写「业界普遍认为」这种无出处的句子。
- **不许拿记忆当来源**：本 skill 的起因就是这条——AI 凭印象答设计题，用户每次要自己补「去查最佳实践」。

## 闸（待实现，记在 #1460 的优先级视图里）

**T2 类改动**（机制/协议/安全，见 T34 风险分层）的 issue 或 PR 必须带标记段 `## 最佳实践`，
且**至少一条可点开的来源**；缺段或缺来源 → 红（并进 `repo-hygiene` 出口，与 T22/T31/T44 同族）。
**反例样本**（上线前必须构造）：一个 T2 改动不带该段 → 闸必须红。
