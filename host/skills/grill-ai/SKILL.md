# 从零拷问·兜底令

## 与 grill-me 分工

| | 拷问对象 | 典型开场 |
| --- | --- | --- |
| `grill-me` | **用户脑子里的方案**——该不该做、长什么样 | 「拷问我」「grill me」「帮我把这想法压一压」 |
| `grill-ai` | **AI 手上正在走的路径**——这条路是不是从一开始就走歪了 | 「不对劲」「从零拷问」「你这做法有问题」，或 AI 自查触发 |

一句话分界：**要动的是用户的想法 ⇒ grill-me；要动的是我自己的做法 ⇒ grill-ai。**
两个都像 ⇒ 先 grill-ai。自己的路没证明是对的之前，拷问用户的想法只是在替一条歪路找理由。

## 何时触发

**用户触发**：上表里的任一说法，或直接调用本 skill。

**AI 自触发（不等用户发现，这是硬闸）**——动手前先过这三问，任一命中即停：

1. **补丁层数**：这次改动的起因，是不是「我上一次改动带来的副作用、或它没覆盖到的情况」？
   - 是 ⇒ 这是补丁第 1 层，记下，先不算命中。再问一次：**上一次**改动的起因，是不是又是它前一次改动的副作用？
   - 也是 ⇒ 我正在动手的是**第 2 层**，本问命中。这就是「同一种办法连错两次」（反者道之动）。
   - 计数只认「同一目标、同一方向」，**不看时间跨度、不看改的是不是同一个文件、不看每层看起来多小**。补丁在局部看都小而顺手，正是这样骗过连错计数的。
   - **层号从下面的「补丁链记录」读，不靠回忆**——补丁链常跨会话形成，回忆一定漏。
2. **措辞报警**：我的方案里出现了「兼容一下现状」「先这样绕过」「加个开关避免冲突」「再加一层就能圆上」——出现即视同第 1 问命中。
3. **同处二修**：同一处问题我已经修过两次还没修好。

自触发时不许「顺手先修完再说」：**当场停手，本轮不落盘**，先把清单走完再决定要不要动手。

## 补丁链记录（跨会话的账）

层号必须落盘，否则换一轮上下文就归零。落点要选**跨 PR 找得回**的：补丁链按定义跨时间，PR 合了会归档、worktree 干完就删——把账记在「当前 PR 正文」，等下一层在新 PR 里动手时正好读不到，等于没记。

所以**锚在 git 历史**：commit 进了主干就永久可查，一条命令翻出整条链，跨 PR、跨会话、跨机器都成立。正文仍写在 issue / PR（人在那儿读），但找回链**不靠正文寻址**。

- **链名 slug**：目标的短名（kebab，如 `inbox-banner`）。判出第 1 层那一刻定，整条链共用。
- **锚（必做）**：从第 1 层起，每层的 **commit 标题**末尾带 `[chain:<slug>#<层号>]`。这是唯一不随 PR 归档消失的落点——**锚在 commit 消息里，不在 PR 正文里**（正文会随 PR 归档失联，这正是上一版的病灶）。
  锚串自带层号，这是与回抄互不依赖的双保险：**回抄告诉你「为什么」，锚告诉你「几层」，落闸只需要后者**——层 1 的正文哪怕被删光，检索到 `#1` 也知道本次动手是第 2 层。
  **前提（跨项目必看）**：锚要活下来，合并后的 commit 消息必须保得住它。GitHub squash 只在 `squash_merge_commit_message = COMMIT_MESSAGES` 时把分支各 commit 的完整消息写进 squash body（`git log --grep` 默认搜整条消息，所以查得到）；设成 `PR_BODY` / `BLANK`，或合并时手动清空 squash body，锚就进不了主干。那种仓库改用 merge / rebase 合并，或把锚**同时写进 PR 标题**。
- **正文记在哪**：有统领这件事的 issue ⇒ 写 issue 正文；没有 ⇒ 写当前 PR 正文。段名固定 `## 补丁链`。**建段时回抄全部历史层**，让最新一处永远是整条链的全量快照——读到任意一处最新记录就够，不用逐个 PR 翻。
- **记什么**（一层一行）：`层号 | 目标 | 方向 | 起因 | 所修副作用 | 落点`。
  - **层号**：从 0 起，本方案是 0，第一次打补丁是 1。
  - **目标**：这件事要达成的本质结果（整条链共用一个，中途换了目标就是另一条链）。
  - **方向**：这一层用的办法。同一目标下**换了根本办法**才算层号归零重开一条链，判准是可查的：**上一层的机制被整段删掉了才算换方向；它还留着、你只是在它旁边加东西，就仍是同一条链。**
  - **起因**：为什么现在要动手。
  - **所修副作用**：具体修的是上一层的哪个后果。**填不出来就不是补丁**，别记。
  - **落点**：本层记录写在哪个 PR / issue 号。
- **何时创建**：判出「本次起因 = 上一次改动的副作用」的那一刻建段，一次补两行——第 0 层（本方案）和第 1 层，并给本层 commit 打上锚。第 0 层单独存在时不记，普通改动不背这个负担。
- **何时更新**：此后每层**动手前先写行，再动手**；commit 时带上锚标记。写行时若填不出「所修副作用」，说明这是新问题，不加层。
- **何时读取**：动手前先查一次链，**不靠回忆、也不靠翻上一个 PR**：

  ```bash
  git log --all --grep="chain:<slug>" --oneline   # 知道 slug
  git log --all --grep="chain:" --oneline         # 不知道：列出全部链，按目标词认
  ```

  命中就顺着 commit 找到它的 PR / issue，读那儿的 `## 补丁链` 段（最新一条即全量）。
  **0 命中不等于没有链**——「查不到」和「没查成」输出一模一样（都是空 + exit 0），把没查成当没有链，闸就静默开门。所以 **0 命中时先自证「查得成」**，三条都过才可以判第 0 层：

  ```bash
  git rev-parse --is-shallow-repository   # 必须 false；true = 浅克隆，历史根本不全
  git log --all --oneline | wc -l         # 检索面有多少条；只有一两条、或明显少于这仓该有的历史 ⇒ 没查成
  gh api repos/{owner}/{repo} --jq .squash_merge_commit_message   # 必须 COMMIT_MESSAGES，否则锚进不了主干
  ```

  任一条不过 ⇒ 判**没查成**，按**有链**处理（fail-close）：回去老老实实过一遍上面第 1 问，并把这次「查不成」写进本层记录，不许当第 0 层放行。
  补充路径：`gh search issues --repo <owner/repo> --include-prs "补丁链 <目标词>"`（跨 issue 与 PR 全文搜，闭合的也搜得到）——有索引延迟，只作补充，不作主路径。
- **不进 git 的补丁链**（本机配置、面板按钮、`settings.json` 这类）没有 commit 可锚——**给它建 issue，段写 issue 正文**，这是它唯一能被找回的地方。本 skill 自己的起源就是这种链（Orca 快捷命令，落在 issue #483）。

### 边界判例

**算**（同一方向的第 2 层）——信箱台横幅治理，2026-08-15，链名 `inbox-banner`：

| 层 | 目标 | 方向 | 起因 | 所修副作用 | 落点 |
| --- | --- | --- | --- | --- | --- |
| 0 | 用户输入框不被 Orca 横幅抢走 | 把 coordinator 身份转给哑终端 | 消息到达即注入，ack 追不上 | —（本方案） | issue #464 |
| 1 | 同上 | 派工序加「run-use → 派工 → ensure 归还」 | 派工要 run-use | run-use 会夺走 coordinator | issue #464 |
| 2 | 同上 | 幂等脚本自动夺回归属 | 人会忘了归还 | 第 1 层靠人记的乒乓不可靠 | PR #466 |

目标一路没变；每层都把上一层的机制**留着**再加一层绕开它的后果（不是整段删掉），所以不算换方向；每层起因都是上一层的副作用 ⇒ 第 2 层落闸。注意层 2 落在另一个 PR 里——这正是「锚在 git 历史、不靠翻当前 PR 正文」的原因。

**不算**（看似同方向，其实是新问题）——PR #467 三轮返工，每轮红项各自独立，第三轮红 1 还标着「本轮新引入」：上一轮把事前拦截写成只比文件名、并删掉了覆盖另一半的那句话，这轮改对。

分界线一句话：**上一层按设计工作了、是它的设计带来新后果 ⇒ 加层；上一层没做到自己的设计、把它改对 ⇒ 返工，不加层。** 返工次数多不触发本 skill（那是实现质量问题），补丁层数才触发。

## 五条清单（逐条回答，不许跳）

1. **第一性原理**：剥掉全部现状与已有实现，这件事的本质需求是什么？从零推，最佳实践长什么样？
2. **补丁链检查**：现在的方案是不是在给现状做兼容、打补丁？画出补丁链——每一层在修谁的副作用。补丁已到第二层即触发「同一种办法连错两次就换路」，必须停手从零重推，不许在原方向打第三层。
3. **马斯克五步法按序过一遍且顺序不可换**：质疑需求 → 删除 → 简化 → 加速 → 自动化。
   五步法本体在 `grill-me` skill 的「五步法（存量决策）」节（仓内真相源 `host/skills/grill-me/SKILL.md`），照那节走，**这里不重复**。
   grill-ai 的加严：**删除**这一步必须显式摆出「删掉整层」的选项——不是「删掉某个参数」，是「这一层机制根本不要，回到没有它的世界」。摆不出来即视为这一步没过。
4. **摆差异与代价表**：把「从零方案」与「现状方案」的差异和代价摆出来，用 `AskUserQuestion` 交用户拍板，**禁止替用户默认取舍**。
5. **判制度**：这次偏差是制度缺失还是执行失守？
   - 执行失守（规矩本来就有，是我没识别）⇒ 写判例进 memory，不改协作约定。
   - 确属制度缺失 ⇒ 才提议改协作约定。

## 收尾

清单走完必须以 `AskUserQuestion` 结束，选项里至少包含：**删掉整层的从零方案**、**继续现状方向**。带上各自代价。
不许自己选完再通知用户，也不许「两个都做」——那是第三层补丁换了个名字。

参考判例：memory `patch-stacking-is-two-strikes`（信箱台横幅治理连打三层补丁，2026-08-15）。
