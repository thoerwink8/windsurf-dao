2026-08-15 PR #496（信箱台身份判据）：工人交卷时单测 104 全绿、dao-check 12 全绿、三处该改的都改了、PR 正文齐全——表面无懈可击。审官照任务书做了一个判别性实验：**把信箱台终端的标题改掉再跑 ensure**。结果 ensure 返回 reject/exit 1，证明身份根本没从标题上摘下来，只是把标题格式改漂亮了。本单的核心目标一点没达成。

同一天 PR #490 也一样：审官要求「证明第二次偏离时真的没执行 #491」，工人给的是人工整理的工具清单——判红；改成导出原始 tool_use 事件、并与源会话逐 ID 交叉印证后才判绿。

**Why:** 测试测的是「实现是否符合实现者对目标的理解」。理解偏了，测试会跟着偏，而且偏得越彻底，测试越绿。工人不是在作弊——它真心以为改好了。所以再多的绿灯也不能替代一个「如果目标没达成，这个实验必然失败」的设计。

**How to apply:** 派单时，任务书里点名至少一个判别性实验，写清「构造什么场景、期望什么结果、以及它在目标未达成时会怎么失败」。审官任务书里标为「不要跳过」。两个可复用的形状：①**破坏识别源**——如果声称身份/依据改成了 A，就把 B（旧依据）破坏掉，看还认不认得出 ②**要求反向证据**——证明「没做某事」要完整事件序列，人工摘录不算，且事件要能与独立来源交叉印证。另外要求工人自验判别力：故意改坏实现，对应断言必须变红（#496 工人自验时 97 passed/6 failed，改回 103 全绿，这才算测试有判别力）。相关：[[monitor-self-check-design]]（同源：检查器自己坏了和被检对象正常长得一样）。
