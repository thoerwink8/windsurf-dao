2026-08-15 一轮派工里，我给自己写的 Monitor 连续三次判据坏掉，全部是「看起来在工作、其实测不到该测的」：

1. **漏扫**：过滤写成 `/493-|审官-GPT/`，而 #490 工人的树路径是 `488-` 开头——派出去的活跑成什么样完全看不见，面板上却一切正常。
2. **静默盲区**：只在 `status != 'working'` 时报事件。结果「一直 working」的工位永远静默，卡死和正常干活分不出来。
3. **噪音误报**：比较键里带了 `preview`，而 TUI 刷新残影（`Wo•Running 2•Wor4`）每次都不同，于是每 90 秒都判定为「状态变化」，报了一堆零信息事件。

**Why:** 这三次都不是规则不知道——dispatch 手册明写「数字总在变，先剔掉再比静止」，CLAUDE.md 明写「输出必须能区分扫完 0 条和没扫到样本」。问题在于写检查器时只想着「怎么发现异常」，没想过「它自己什么情况下会假阳/假阴」。检查器的失效和被检对象的正常长得一模一样，所以不会有人来告诉你它坏了。

**How to apply:** 挂 Monitor 或写任何检查脚本之前，先回答三问：①覆盖面——要盯的对象是不是每一个都真的进了扫描范围（把清单列出来数一遍，别信正则看起来对）②失败可见性——被盯对象崩了/卡死了，这个检查器会不会输出东西？不会就是漏了失败路径 ③判据纯度——比较用的字段里有没有会自己变的噪音（时间戳、token 计数、TUI 残影）？有就剔掉再比。另外让检查器自报扫描到的样本数，少于预期就告警——这是区分「扫完没事」和「压根没扫到」的最便宜做法。相关：[[report-requires-fresh-state]]（同源：只看一层就下结论）。
