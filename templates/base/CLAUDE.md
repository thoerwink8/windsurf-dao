## 协作约定（改代码前必读）

### 说人话

- 所有对外文字（issue、PR、README、注释）写给**没参与项目的人**看：先讲发生了什么，再讲细节；术语第一次出现时用括号解释。
- 判断标准：**这个词用户自己说过吗？** 用户没说过、只有我们内部用的词，不要用。

### PR 即任务书

- 每个 PR 的 body 写三段：**目标**（为什么做）、**验收标准**（怎么算做完）、**进展**（做了/剩什么）。
- 验收标准尽量写成**可执行命令**或可勾选清单，不要写"功能正常"这种没法验证的话。
- 任务开工**先开 draft PR 再动手**：push 即留痕，别人随时能看你在干什么。
- 干完自查验收标准，全部通过后把 PR 从 draft 转 ready。

### 兜底

- 改坏了就 **revert**，不要在原 PR 里反复打补丁硬救。
- 本地必须有一条能一键跑的 check 命令，跑通才算完。本项目是：

```sh
{{填命令，例：npm run check}}
```

### 新增东西先过三问

加规则、加流程、加文件之前，先回答这三问（答不上来就别加）：

1. 谁提的、什么场景？
2. 删掉哪一层能让这个问题不存在？
3. 从零重做，还会造它吗？

## Windows / PowerShell 注意（非 Windows 项目删除本节）

- 判断原生程序（.exe）的成败看 `$LASTEXITCODE`；cmdlet 看 `$?` 或 try/catch，不要只看输出里有没有 "error" 字样。
- 中文环境的「所在位置 行:X」是错误定位信息，命令是否真的失败要看 `$?` 与退出码，不能只凭输出观感。
- `2>&1` 在本机 PowerShell 5.1 下与原生程序组合时曾制造过假错误，谨慎使用。
- 用 PowerShell 5.1 写文件时注意 BOM：管道重定向默认带 BOM，会坏 JSON。
